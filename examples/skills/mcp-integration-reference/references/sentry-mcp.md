# Справочник по серверу Sentry MCP

Справочный файл для сервера Sentry MCP. Прочтите это, прежде чем совершать какие-либо вызовы Sentry MCP. Он содержит синтаксис запроса, известные ошибки и рабочие примеры, которые уменьшают количество сбоев вызовов.

> Это справочный файл шаблона. Замените контент, специфичный для Sentry, эквивалентом для вашего сервера MCP.

---

## Доступные инструменты

### `mcp__sentry-mcp__list_issues`

**Purpose**: Получить список проблем из одного или нескольких проектов.

**Основные параметры**:
- `organization_slug` (обязательно): ваш URL-адрес организации Sentry, а не название организации. Получите его по URL-адресу Sentry: `sentry.io/organizations/<slug>/`.
- `project_slug` (необязательно): Охват одного проекта. Опустить выборку по всем проектам.
- `query` (необязательно): поисковый запрос часового. Поддерживает `is:unresolved`, `level:error`, `has:user`. По умолчанию: `is:unresolved`.
- `limit` (необязательно): возвращено максимальное количество проблем. По умолчанию: 25. Макс.: 100.

**Gotchas**:
- Обозначения организации и проекта написаны строчными буквами и разделены дефисом. Не используйте отображаемое имя.
- Без `query` вы получаете все статусы, включая `resolved`. Всегда добавляйте `is:unresolved`, если вы специально не хотите решить проблемы.
- Ограничение `limit` составляет 100 за вызов. Для больших организаций используйте `cursor` для нумерации страниц (см. ниже).

### `mcp__sentry-mcp__get_issue`

**Purpose**: получение полной информации об одной проблеме, включая последние события и трассировку стека.

**Основные параметры**:
- `issue_id` (обязательно): числовой идентификатор проблемы Sentry. Получите его от `list_issues`.
- `organization_slug` (обязательно): то же, что и выше.

**Gotchas**:
- Возвращает только самое последнее событие. Если вам нужно конкретное событие, используйте вместо него `get_event` с идентификатором события.
- По умолчанию кадры стека упорядочены от внешнего к самому внутреннему. Нижний кадр обычно является местом падения.

### `mcp__sentry-mcp__get_event`

**Purpose**: получение полной информации о конкретном событии в задаче.

**Основные параметры**:
- `event_id` (обязательно): полный 32-значный идентификатор события (формат UUID, без дефисов).
- `organization_slug` (обязательно): то же, что и выше.
- `issue_id` (обязательно): идентификатор родительской проблемы.

**Gotchas**:
- Идентификаторы событий не чувствительны к регистру, но API чувствителен к регистру. Используйте строчные буквы.
- События старше 90 дней могут быть недоступны в плане хранения по умолчанию.

### `mcp__sentry-mcp__search_events`

**Purpose**: поиск необработанных событий по задачам. Медленнее, чем `list_issues`, но поддерживает полнотекстовые запросы.

**Основные параметры**:
- `query` (обязательно): Полнотекстовый поиск. Поддерживает полевые фильтры: `message:`, `level:`, `user.id:`, `url:`, `transaction:`.
- `project_slug` (необязательно): Охват одного проекта. Требуется, если в организации много проектов (производительность).
- `start` / `end` (необязательно): временные метки ISO 8601. По умолчанию: последние 24 часа.
- `limit` (необязательно): По умолчанию: 10. Макс.: 100.

**Gotchas**:
- Полнотекстовый поиск не учитывает регистр, но фильтры полей обеспечивают точное совпадение. `level:ERROR` не работает; используйте `level:error`.
- Временные диапазоны должны соответствовать стандарту ISO 8601: `2026-04-10T00:00:00Z`. Относительные форматы, такие как `now-24h`, здесь не поддерживаются (используйте `list_issues` для относительных диапазонов).
- Без `project_slug` большие организации отключат `search_events`. При поиске событий всегда ограничивайте масштаб проекта.

## Синтаксис запроса

### Поисковый запрос Sentry (для параметра `query` в `list_issues` и `search_events`)

```
is:unresolved                          # Unresolved issues only
is:unresolved level:error              # Unresolved errors (not warnings)
is:unresolved has:user                 # Issues affecting identified users
is:unresolved times_seen:>100          # High-frequency issues
project:api-service is:unresolved      # Scope to one project
assigned:me is:unresolved              # Issues assigned to current user
!has:assignee is:unresolved            # Unassigned issues
```

### Пагинация

Для организаций с большим количеством проблем используйте нумерацию страниц на основе курсора:
1. Первый вызов: `list_issues(..., limit=100)` — ответ включает поле `cursor`.
2. Следующая страница: `list_issues(..., limit=100, cursor="<cursor from previous response>")`
3. Остановиться, когда в ответе нет поля `cursor` или количество проблем < предела.

## Известные закономерности и исключения

При анализе проблем эти шаблоны обычно представляют собой шум, и их следует исключать из отчетов, если это явно не запрошено:

| Шаблон | Причина исключения |
|---------|-------------------|
| Ошибки `404` на `/static/` или `/assets/` | Ожидаемое поведение: браузер запрашивает устаревшие URL-адреса ресурсов после развертывания. |
| `ChunkLoadError` в пакетах внешнего интерфейса | Обычно возникает из-за одного и того же времени развертывания, а не из-за ошибки кода. |
| `ResizeObserver loop limit exceeded` | Предупреждение на уровне браузера, недействительно |
| Ошибки конечной точки проверки работоспособности | Мониторинг инфраструктуры, а не взаимодействие с пользователем |

Если вы исключаете проблему, укажите это явно в разделе отчета «Вне области действия».

## Рабочие примеры

### Получите список самых неустраненных ошибок в производстве.

```
list_issues(
  organization_slug="your-org",
  query="is:unresolved level:error",
  limit=50
)
```

### Получить проблемы из конкретного проекта за последнюю неделю.

```
list_issues(
  organization_slug="your-org",
  project_slug="api-service",
  query="is:unresolved",
  limit=100
)
```

### Получите полную трассировку стека для конкретной проблемы

```
get_issue(
  organization_slug="your-org",
  issue_id="1234567"
)
```

## Адаптация этого файла

При разветвлении этого шаблона для другого MCP (Datadog, PagerDuty, Linear и т. д.):

1. Замените «Sentry» на имя вашего сервера MCP.
2. Замените названия инструментов (`mcp__sentry-mcp__*`) фактическими названиями инструментов вашего MCP.
3. Задокументируйте 2–3 наиболее частые ошибки параметров для каждого инструмента.
4. Добавьте синтаксис запроса, специфичный для вашего MCP (диалект SQL, синтаксис фильтра и т. д.).
5. Добавьте раздел «Известные закономерности и исключения» для шума в источнике данных.
6. Включите 3–5 рабочих примеров, охватывающих вариант использования 80 %.

Цель: после прочтения этого файла Claude не должен допустить ни синтаксических ошибок, ни повторных вызовов, вызванных неправильным форматом параметров.
