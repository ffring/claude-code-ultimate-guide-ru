# Контрольный список оценки качества шаблона проектирования

Систематические критерии оценки качества реализации шаблонов проектирования.

## Критерии оценки

Каждый критерий оценивается **0-10**, где:
- **9-10**: Образцовая реализация эталонного качества.
- **7-8**: Хорошо, возможны незначительные улучшения.
- **5-6**: Приемлемые, заметные проблемы, требующие решения.
- **3-4**: Проблема, необходим значительный рефакторинг.
- **0-2**: Неверно или с серьезными ошибками.

**Общий балл** = Среднее значение всех критериев

---

## 1. Правильность (0-10)

**Question**: Правильно ли реализация соответствует канонической структуре шаблона?

### Рекомендации по выставлению оценок

| Счет | Описание |
|-------|-------------|
| 9-10  | Идеальное соблюдение структуры шаблона, все роли присутствуют и правильно реализованы. |
| 7-8   | Незначительные отклонения, не ставящие под угрозу цель шаблона |
| 5-6   | Некоторые структурные проблемы, но рисунок узнаваем и функционален. |
| 3-4   | Серьезные структурные проблемы, схема реализована лишь частично. |
| 0-2   | Неправильная реализация, вообще не соответствует шаблону |

### Контрольный список

**Singleton**:
- [ ] Частный конструктор
- [ ] Статический метод getInstance()
- [ ] Поле частного статического экземпляра
- [ ] Потокобезопасность (если применимо)
- [ ] Возвращает один и тот же экземпляр каждый раз

**Observer**:
- [ ] Интерфейс темы с attach/detach/notify
- [ ] Интерфейс наблюдателя с методом обновления
- [ ] Субъект ведет список наблюдателей
- [ ] Обновление уведомлений о вызовах для всех наблюдателей
- [ ] Наблюдатели могут быть added/removed динамически.

**Strategy**:
- [ ] Алгоритм определения интерфейса стратегии
- [ ] Контекст содержит ссылку на стратегию
- [ ] Контекст делегирует стратегию
- [ ] Стратегии взаимозаменяемы
- [ ] Клиент может установить стратегию во время выполнения

**Фабричный метод**:
- [ ] Фабричный метод возвращает класс interface/abstract
- [ ] Подклассы переопределяют фабричный метод
- [ ] Клиентский код зависит от интерфейса, а не от конкретных классов
- [ ] Логика создания инкапсулирована

**Decorator**:
- [ ] Декоратор реализует тот же интерфейс, что и обернутый объект.
- [ ] Декоратор хранит ссылку на обернутый объект.
- [ ] Делегирование декоратора обернутому объекту
- [ ] Можно складывать несколько декораторов
- [ ] Поддерживает контракт интерфейса

### Типичные ошибки (вычеты)

- **-2**: отсутствует ключевой компонент (например, Singleton без частного конструктора).
- **-3**: неправильное делегирование (например, декоратор не вызывает обернутый объект)
- **-4**: нарушение инвариантов шаблона (например, синглтон, возвращающий разные экземпляры)

## 2. Тестируемость (0-10)

**Question**: Насколько легко писать модульные тесты для этой реализации?

### Рекомендации по выставлению оценок

| Счет | Описание |
|-------|-------------|
| 9-10  | Легко имитируемые, внедряемые зависимости, без глобального состояния. |
| 7-8   | Тестируется при незначительной настройке, существует некоторая связь |
| 5-6   | Требует значительной настройки тестирования, умеренной связи |
| 3-4   | Трудно тестировать, жесткая связь, глобальное состояние |
| 0-2   | Практически невозможно протестировать, статические зависимости, нет точек внедрения. |

### Контрольный список

- [ ] Зависимости внедряются (не создаются внутри)
- [ ] Используются интерфейсы (можно издеваться)
- [ ] Никаких жестко запрограммированных зависимостей
- [ ] Нет доступа к глобальному состоянию (или минимальный)
- [ ] Возможна изоляция тестов (тесты не влияют друг на друга)
- [ ] Нет статических методов, над которыми нельзя издеваться.
- [ ] Побочные эффекты сведены к минимуму или контролируемы.

### Красные флажки (вычеты)

- **-2**: использование `getInstance()` вместо внедрения зависимостей.
- **-2**: жестко закодированное создание конкретного класса.
- **-3**: доступ к глобальному состоянию (окно, глобальный, процесс.env в бизнес-логике)
- **-3**: Статические методы с побочными эффектами.
- **-4**: невозможно внедрить тестовые двойники.

### Примеры

**Плохая тестируемость (оценка: 2/10)**:
```typescript
class PaymentService {
  processPayment(amount: number) {
    // Hard to test: creates dependency internally
    const gateway = PaymentGateway.getInstance();
    // Hard to test: accesses global config
    const apiKey = process.env.PAYMENT_API_KEY;
    return gateway.charge(amount, apiKey);
  }
}
```

**Хорошая тестируемость (оценка: 9/10)**:
```typescript
class PaymentService {
  constructor(
    private gateway: IPaymentGateway,
    private config: Config
  ) {}

  processPayment(amount: number) {
    const apiKey = this.config.getPaymentApiKey();
    return this.gateway.charge(amount, apiKey);
  }
}

// Easy to test with mocks
const mockGateway = { charge: jest.fn() };
const mockConfig = { getPaymentApiKey: () => 'test-key' };
const service = new PaymentService(mockGateway, mockConfig);
```

## 3. Принцип единой ответственности (0-10)

**Question**: Есть ли у компонента одна, четко определенная ответственность?

### Рекомендации по выставлению оценок

| Счет | Описание |
|-------|-------------|
| 9-10  | Единая, целенаправленная ответственность; у класса есть одна причина измениться |
| 7-8   | В основном сосредоточены, незначительные второстепенные проблемы |
| 5-6   | Несколько связанных обязанностей |
| 3-4   | Несколько несвязанных обязанностей |
| 0-2   | Класс Бога со многими обязанностями |

### Контрольный список

- [ ] У Class/module есть одна ясная цель.
- [ ] Все методы относятся к основной ответственности
- [ ] Изменение одного требования не требует изменения этого класса.
- [ ] Название класса четко отражает его ответственность
- [ ] Нет «и» в имени или описании класса (например, «UserManagerAndLogger» — это плохо).

### Красные флажки (вычеты)

- **-2**: Класс решает две разные проблемы.
- **-3**: Класс решает более 3 проблем.
- **-4**: класс Бога (>20 методов,>300 строк)
- **-1**: Методы, не связанные с основной ответственностью.

### Примеры

**Плохая рекомендованная розничная цена (Оценка: 3/10)**:
```typescript
class UserService {
  createUser(data: UserData) { /* ... */ }
  validateEmail(email: string) { /* ... */ }
  sendWelcomeEmail(user: User) { /* ... */ }
  logUserActivity(activity: string) { /* ... */ }
  generateReport(userId: string) { /* ... */ }
  // Too many responsibilities: creation, validation, email, logging, reporting
}
```

**Хорошая рекомендованная розничная цена (Оценка: 9/10)**:
```typescript
class UserService {
  constructor(
    private validator: UserValidator,
    private emailService: EmailService,
    private logger: Logger
  ) {}

  createUser(data: UserData): User {
    // Focuses only on user creation orchestration
    this.validator.validate(data);
    const user = new User(data);
    this.emailService.sendWelcomeEmail(user);
    this.logger.logActivity('user_created', user.id);
    return user;
  }
}
```

## 4. Принцип Open/closed (0-10)

**Вопрос**: Можно ли расширить компонент без изменения его исходного кода?

### Рекомендации по выставлению оценок

| Счет | Описание |
|-------|-------------|
| 9-10  | Полностью расширяемый посредством наследования или композиции, никаких изменений не требуется. |
| 7-8   | В основном расширяемый, могут потребоваться незначительные изменения. |
| 5-6   | Некоторые точки расширения существуют, но ограничены. |
| 3-4   | Трудно расширить, требуется модификация в нескольких местах. |
| 0-2   | Закрыто для расширения, необходимо изменить исходный код |

### Контрольный список

- [ ] Использует интерфейсы или абстрактные классы
- [ ] Новое поведение можно добавить с помощью новых классов, а не модификаций.
- [ ] Шаблон конфигурации или стратегии для различного поведения
- [ ] Никаких операторов переключения типов (если добавление нового типа требует модификации)
- [ ] Инверсия зависимостей (зависит от абстракций)

### Красные флажки (вычеты)

- **-2**: тип включения (добавление нового типа требует модификации)
- **-3**: Нет интерфейсов (везде конкретные зависимости)
- **-3**: жестко запрограммированное поведение (нет точек расширения).
- **-4**: Изменение существующих методов — единственный способ добавить функции.

### Примеры

**Закрыто для продления (Оценка: 2/10)**:
```typescript
class PaymentProcessor {
  process(type: string, amount: number) {
    switch (type) {
      case 'credit': return this.processCreditCard(amount);
      case 'paypal': return this.processPaypal(amount);
      // Adding crypto payment requires modifying this class
    }
  }
}
```

**Открыт для расширения (Оценка: 9/10)**:
```typescript
interface PaymentStrategy {
  process(amount: number): Promise<Receipt>;
}

class PaymentProcessor {
  constructor(private strategies: Map<string, PaymentStrategy>) {}

  process(type: string, amount: number) {
    const strategy = this.strategies.get(type);
    if (!strategy) throw new Error(`Unknown payment type: ${type}`);
    return strategy.process(amount);
  }
}

// Add new payment method without modifying PaymentProcessor
class CryptoPaymentStrategy implements PaymentStrategy {
  process(amount: number) { /* ... */ }
}
```

## 5. Документация (0-10)

**Question**: Хорошо ли документирована реализация с четкими намерениями и использованием?

### Рекомендации по выставлению оценок

| Счет | Описание |
|-------|-------------|
| 9-10  | Полная документация: намерения, использование, примеры, крайние случаи. |
| 7-8   | Хорошая документация, охватывает основные случаи использования. |
| 5-6   | Базовая документация, минимальная, но присутствует |
| 3-4   | Скудная документация, неясные намерения |
| 0-2   | Отсутствие документации или вводящая в заблуждение документация |

### Контрольный список

- [ ] Class/interface имеет комментарий JSDoc/TSDoc, объясняющий цель.
- [ ] Намерение шаблона документировано («Это синглтон, потому что...»)
- [ ] Публичные методы имеют документацию.
- [ ] Сложная логика имеет встроенные комментарии.
- [ ] Примеры использования приведены (в README или комментариях).
- [ ] Инварианты и ограничения документированы.
- [ ] Именование самодокументируется (четкие, описательные имена).

### Красные флажки (вычеты)

- **-2**: нет документации на уровне класса.
- **-2**: общедоступные методы API недокументированы.
- **-3**: загадочное именование (x, foo, temp, data)
- **-1**: Сложная логика без объяснений.

### Примеры

**Плохая документация (Оценка: 2/10)**:
```typescript
class S {
  private static i: S;
  private constructor() {}
  static get() {
    if (!S.i) S.i = new S();
    return S.i;
  }
  do(x: any) { /* ... */ }
}
```

**Хорошая документация (Оценка: 9/10)**:
```typescript
/**
 * Configuration service implemented as a Singleton to ensure
 * all components share the same configuration state.
 *
 * Use `ConfigService.getInstance()` to access the singleton instance.
 *
 * @example
 * const config = ConfigService.getInstance();
 * const apiUrl = config.get('API_URL');
 */
class ConfigService {
  private static instance: ConfigService;

  /**
   * Private constructor prevents direct instantiation.
   * Use `getInstance()` instead.
   */
  private constructor() {
    // Load configuration from environment
  }

  /**
   * Returns the singleton instance of ConfigService.
   * Creates the instance on first call (lazy initialization).
   *
   * @returns The singleton ConfigService instance
   */
  public static getInstance(): ConfigService {
    if (!ConfigService.instance) {
      ConfigService.instance = new ConfigService();
    }
    return ConfigService.instance;
  }

  /**
   * Retrieves a configuration value by key.
   *
   * @param key - Configuration key
   * @returns Configuration value or undefined if not found
   */
  public get(key: string): string | undefined {
    return process.env[key];
  }
}
```

## Оценка конкретного шаблона

### Специально для синглтона

**Дополнительный контрольный список**:
- [ ] Ленивая инициализация (если применимо)
- [ ] Учитывается потокобезопасность (менее критично в JS)
- [ ] Создание подклассов предотвращается или контролируется
- [ ] Нет публичного конструктора
- [ ] Механизм сброса тестов (или упомянутая альтернатива DI)

**Deductions**:
- **-3**: открытый конструктор (не соответствует цели)
- **-2**: несколько методов getInstance(), возвращающих разные экземпляры.
- **-2**: изоляция тестов не учитывается.

### Для наблюдателя

**Дополнительный контрольный список**:
- [ ] Наблюдатели могут отказаться от подписки
- [ ] Нет утечек памяти (наблюдатели правильно удалены)
- [ ] Порядок уведомлений является детерминированным (если это имеет значение)
- [ ] Наблюдатели не зависят от порядка уведомления
- [ ] Субъект не знает конкретных типов наблюдателей.

**Deductions**:
- **-3**: нет механизма отказа от подписки (риск утечки памяти).
- **-2**: Тема зависит от конкретных типов наблюдателей.
- **-2**: порядок уведомлений имеет значение, но не гарантируется.

### Конкретно для стратегии

**Дополнительный контрольный список**:
- [ ] Стратегии реализуют общий интерфейс
- [ ] Контекст не зависит от конкретных стратегий
- [ ] Стратегии взаимозаменяемы
- [ ] Стратегия может быть установлена ​​во время выполнения
- [ ] Стратегии не разделяют состояние (если это явно не предусмотрено)

**Deductions**:
- **-3**: Контекст зависит от конкретных стратегий.
- **-2**: Стратегии не являются полностью взаимозаменяемыми.
- **-2**: невозможно изменить стратегию во время выполнения.

## Формула общей оценки

```
Overall Score = (
  Correctness × 0.30 +
  Testability × 0.25 +
  Single Responsibility × 0.20 +
  Open/Closed × 0.15 +
  Documentation × 0.10
) / 5
```

**Weighted**, потому что правильность важнее всего, за ней следует тестируемость.

## Пример отчета об оценке

### Узор: Синглтон
**Файл**: `src/services/config-singleton.ts`
**Lines**: 5-34

#### Результаты

| Критерий | Счет | Обоснование |
|-----------|-------|-----------|
| Корректность | 8/10 | Правильно реализует синглтон, второстепенное: нет потокобезопасности (не критично в JS) |
| Тестируемость | 4/10 | Трудно издеваться, нет механизма сброса, глобальное состояние делает тесты взаимозависимыми |
| Единая ответственность | 9/10 | Ориентирован исключительно на управление конфигурацией. |
| Open/Closed | 7/10 | Можно добавлять новые ключи конфигурации, но источники конфигурации жестко запрограммированы. |
| Документация | 6/10 | Имеет JSDoc, но отсутствует обоснование выбора синглтона. |

**Общая оценка**: **6.8/10** (приемлемо)

#### Выявленные проблемы

1. **High Priority**: добавьте метод `resetInstance()` для изоляции тестов.
   - Текущее: тесты должны выполняться в определенном порядке.
   - Исправлено: добавление `public static resetInstance()`, защищенного проверкой среды.

2. **Средний приоритет**: обоснование одноэлементности документа
   - Сейчас: Непонятно, зачем необходимо глобальное состояние
   - Исправление: добавьте JSDoc, объясняющий выбор (например, «Singleton обеспечивает согласованную конфигурацию для всех служб»).

3. **Low Priority**: рассмотрите альтернативу внедрения зависимостей.
   - Текущее: сложно проверить, тесная связь.
   - Рекомендация: оцените использование контейнера DI или контекста React.

#### Рекомендации

```typescript
// Add test-friendly reset
public static resetInstance(): void {
  if (process.env.NODE_ENV === 'test') {
    ConfigService.instance = null!;
  }
}

// Better yet: refactor to DI
class ConfigService {
  constructor(private envVars: EnvVars) {}
}

// Inject in DI container or provider
const config = new ConfigService(process.env);
```

## Использование в навыках

Когда навык работы с шаблонами проектирования запускается в режиме **Evaluation Mode**, он:

1. Определяет, какой шаблон реализован
2. Применяет соответствующие элементы контрольного списка
3. Баллы по каждому критерию (0–10)
4. Рассчитывает взвешенный общий балл
5. Формирует подробный отчет с:
   - Таблица результатов
   - Обнаруженные проблемы (в порядке приоритета)
   - Конкретные рекомендации с примерами кода
   - Альтернативы стека, если применимо
