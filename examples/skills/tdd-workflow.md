# TDD навыки рабочего процесса

## Цикл TDD

```
RED → GREEN → REFACTOR
 ↑__________________|
```

### 1. КРАСНЫЙ: Напишите неудачный тест.
- Напишите наименьший тест, который не пройден
- Тест должен завершиться неудачей по правильной причине
- Убедитесь, что тест действительно выполняется

### 2. ЗЕЛЕНЫЙ: добиться успеха
- Напишите минимальный код, чтобы пройти тест
- Пока не оптимизируйте
- Ничего страшного, если код некрасивый

### 3. РЕФАКТОР: Очистка
- Улучшить структуру кода
- Удалить дублирование
- Следите за тем, чтобы тесты проходили успешно

## Лучшие практики TDD

### Соглашение об именовании тестов
```
should_[expected behavior]_when_[condition]
```

Examples:
- `should_return_empty_array_when_no_items`
- `should_throw_error_when_invalid_input`
- `should_calculate_total_when_items_present`

### Структура теста (AAA)
```typescript
it('should calculate discount when coupon applied', () => {
  // Arrange - Set up test data
  const cart = new Cart();
  cart.addItem({ price: 100 });
  const coupon = new Coupon('10OFF', 10);

  // Act - Execute the behavior
  cart.applyCoupon(coupon);

  // Assert - Verify the result
  expect(cart.total).toBe(90);
});
```

### Тестовая изоляция
- Каждый тест должен быть независимым
- Нет общего состояния между тестами
- Используйте `beforeEach` для общей настройки.
- Очистка в `afterEach`

## Пример рабочего процесса TDD

### Особенность: Добавить товар в корзину

**Шаг 1: RED**
```typescript
describe('Cart', () => {
  it('should add item to cart', () => {
    const cart = new Cart();
    cart.addItem({ id: 1, name: 'Book', price: 29.99 });
    expect(cart.items).toHaveLength(1);
  });
});
```
Запустить тест → FAILS (корзина не существует)

**Шаг 2: ЗЕЛЕНЫЙ**
```typescript
class Cart {
  items = [];

  addItem(item) {
    this.items.push(item);
  }
}
```
Запустить тест → ПРОЙДЕНО

**Шаг 3: РЕФАКТОР**
```typescript
class Cart {
  private _items: CartItem[] = [];

  get items(): ReadonlyArray<CartItem> {
    return this._items;
  }

  addItem(item: CartItem): void {
    this._items.push(item);
  }
}
```
Запустить тест → Все еще ПРОХОДИТ

### Следующая итерация: подсчитать итоговую сумму
Повторите цикл для каждого нового поведения.

## Когда использовать TDD

### Хорошо для TDD
- Бизнес-логика
- Сложные алгоритмы
- Конечные точки API
- Государственное управление
- Вспомогательные функции

### Менее подходит
- Макет пользовательского интерфейса (лучше визуальное тестирование)
- Миграция базы данных
- Внешние интеграции (используйте интеграционные тесты)
- Код Exploratory/prototype

## Распространенные ошибки TDD

1. **Написание слишком большого количества тестов** — Начните с наименьшего неудачного теста
2. **Написание слишком большого количества кода** — Достаточно только для прохождения
3. **Пропуск рефакторинга** — Накапливается технический долг
4. **Тестирование реализации** — Тестирование поведения, а не внутренних компонентов
5. **Игнорирование неудачных тестов** - Исправьте или удалите, никогда не пропускайте

## <a name="test-doubles"></a>Тестовые двойки

| Тип | Цель | Пример |
|------|---------|---------|
| Заглушка | Возвращать фиксированные данные | `jest.fn().mockReturnValue(42)` |
| Насмехаться | Проверка взаимодействия | `expect(mock).toHaveBeenCalled()` |
| Шпион | Отслеживать звонки | `jest.spyOn(obj, 'method')` |
| Фальшивый | Упрощенная реализация | База данных в памяти |
