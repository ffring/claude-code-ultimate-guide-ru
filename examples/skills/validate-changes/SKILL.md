# Проверка изменений перед фиксацией

Оценивайте поэтапные изменения git с помощью агента оценщика вывода, чтобы выявить проблемы перед фиксацией.

## Процесс

### Шаг 1. Проверьте поэтапные изменения

Запустите `git diff --cached --stat`, чтобы увидеть, что происходит. Если ничего не подготовлено, сообщите об этом пользователю и выйдите.

### Шаг 2. Получите полный дифференциал

Запустите `git diff --cached`, чтобы получить полный список всех поэтапных изменений.

### Шаг 3. Вызовите оценщика

Используйте инструмент «Задачи», чтобы запустить агент `output-evaluator` с разницей:

```
Evaluate these staged changes for correctness, completeness, and safety.
Return a JSON verdict with scores and issues.

Changes:
[paste the git diff here]
```

### Шаг 4. Анализируйте и действуйте согласно вердикту

По результатам оценки:

**Если УТВЕРЖДЕНО:**
- Сообщите пользователю, что изменения прошли оценку
- Показать сводку и баллы
- Спросите, хотят ли они продолжить фиксацию

**Если NEEDS_REVIEW:**
- Показать все найденные проблемы (сгруппированные по серьезности)
- Показать предложение оценщика
- Спросите пользователя, как действовать:
  - Устраните проблемы и повторите оценку
  - В любом случае принять на себя обязательства (признать риски)
  - Прервать

**Если ОТКЛОНИТЬ:**
- Четко заявите, что изменения были отклонены.
- Показать критические проблемы, вызвавшие отказ
- В любом случае НЕ предлагайте брать на себя обязательства
- Предложите конкретные исправления

### Шаг 5: Подтвердите (если одобрено)

Если пользователь подтвердит, создайте фиксацию, используя стандартный процесс фиксации.

## Примеры использования

```
/validate-changes
```

Output:
```
Evaluating 3 staged files...

VERDICT: NEEDS_REVIEW

Scores:
  Correctness:  8/10
  Completeness: 6/10
  Safety:       9/10

Issues Found:
  [MEDIUM] src/api/handler.ts:45
    Missing error handling for network failures

  [LOW] src/utils/format.ts:12
    Consider adding input validation

Suggestion: Add try-catch around the fetch call in handler.ts

How would you like to proceed?
  1. Fix issues and re-evaluate
  2. Commit anyway (1 medium issue)
  3. Abort
```

## Осведомленность о затратах

Эта команда вызывает оценку LLM, в которой используются токены API:
- **Типичная стоимость**: 0,01–0,05 доллара США за оценку (с использованием Haiku).
- **Большие различия**: может стоить дороже из-за увеличения использования токенов.

## <a name="when-to-use"></a>Когда использовать

- После значительных изменений кода перед фиксацией
- При работе с незнакомыми частями кодовой базы
- Для изменений, влияющих на код, чувствительный к безопасности.
- Прежде чем отправлять в общие ветки

## Когда пропустить

- Тривиальные изменения (опечатки, форматирование)
- Изменения только в документации
- Когда вы уже тщательно просмотрели вручную
- При быстрой итерации ветки функций

## Интеграция с git-хуками

Для автоматической оценки каждого коммита см. хук `pre-commit-evaluator.sh`.
Эта команда является альтернативой ручному использованию, если вы хотите контролировать время выполнения оценки.
