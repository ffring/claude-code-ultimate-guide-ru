# /plan-pipeline:start: 5-этапное планирование

Проанализируйте запрос и разработайте полный план реализации, разбитый на структурированные этапы. Код не пишется. Каждое важное решение фиксируется. Запустите `/clear` после этой команды перед запуском `/plan-pipeline:validate`.

---

## Этап 1: PRD и анализ конструкции

### Шаг 1.1: Анализ PRD

*Пропустить, если PRD не существует (рефакторинг, изменение инфраструктуры, исправление ошибок).*

Прочтите все файлы PRD и `docs/INFORMATION_ARCHITECTURE.md`, если они есть. Сканируйте базу кода, чтобы понять текущий статус реализации.

Поверхностные находки в 3 ведрах:

**Отсутствующие требования**: критерии приемки отсутствуют или являются неполными.
**Неоднозначные требования**: элементы с несколькими допустимыми интерпретациями
**Проблемы соблюдения требований**: безопасность, конфиденциальность данных, последствия контракта API

По каждому выводу: представьте варианты с конкретными pros/cons. Обсудить с пользователем. Прежде чем двигаться дальше, записывайте каждое решение в файле плана в разделе `## Decisions`. Не проходите мимо неразрешенных двусмысленностей.

### Шаг 1.2: Анализ проекта

*Пропустить, если в области действия нет изменений пользовательского интерфейса.*

Прочтите: `DESIGN_SYSTEM.md`, существующие ADR UX, правила CLAUDE.md UX.

Произвести спецификации для:
- **Инвентаризация экранов**: экраны new/modified, размещение маршрутов, аудит повторного использования компонентов
- **Каталог состояний**: пустое, загружаемое, заполненное, ошибочное и частичное состояния для каждого интерактивного элемента.
- **Спецификации взаимодействия**: потоки пользователей (счастливый путь + альтернативы), поведение focus/keyboard
- **Спецификации анимации**: сопоставьте каждое взаимодействие с существующими ключевыми кадрами или укажите новые, включая резервные варианты `prefers-reduced-motion`
- **Отзывчивое поведение**: точки останова, решения о расхождениях web/mobile
- **Accessibility**: выбор шаблона WAI-ARIA, живые регионы, видимость ошибок

Создавайте рекомендации по дизайну для важных UX-решений (выбор шаблона взаимодействия, новое соглашение о анимации, расхождение платформ). Запишите незначительные варианты макета непосредственно в файл плана.

## Этап 2: Технический анализ

Создайте 1-2 агента. Исследуйте агентов для целевого исследования кодовой базы. Запустите их в фоновом режиме с помощью инструмента «Задачи».

Пока агенты работают, проверьте:
- Существующие ADR в `docs/adr/`: если 3+ ADR подтверждают решение → автоматическое разрешение без запроса
- PATTERNS.md: применять подтвержденные шаблоны напрямую

Когда агенты вернутся: презентуйте архитектурные решения по 2-3 варианта каждое, конкретный pros/cons и рекомендацию. Запрашивайте мнение пользователя по каждому нерешенному решению.

По каждому значимому решению:
1. Создайте `docs/adr/ADR-XXXX.md`, используя стандартный формат Найгарда (Контекст/Решение/Статус/Последствия)
2. Обновите `docs/adr/PATTERNS.md` новым наблюдением.

## Этап 3: Оценка объема

Примените триггерные правила, чтобы определить, какие исследовательские агенты необходимы. Предоставьте предложенной команде обоснование каждого включения.

**Пул исследовательских агентов:**

| Агент | Курок | Модель |
|-------|---------|-------|
| `code-explorer` | Всегда | Sonnet |
| `arch-researcher` | Изменения затрагивают более 2 архитектурных слоев. | Sonnet |
| `database-analyst` | Любое изменение схемы БД | Sonnet |
| `security-analyst` | Авторизация, платежи, PII, RBAC, ограничение скорости | Opus |
| `test-analyzer` | Нетривиальная функция (не просто исправление ошибок) | Sonnet |
| `cross-platform-specialist` | Требуется равенство Интернет и мобильная связь | Sonnet |
| `native-app-specialist` | Задачи касаются пакета пользовательского интерфейса mobile/native. | Sonnet |
| `design-system-researcher` | Изменения в области пользовательского интерфейса | Sonnet |
| `dependency-researcher` | Добавляются новые пакеты | Sonnet |
| `devops-specialist` | Docker, переменные окружения, изменения CI/CD | Sonnet |
| `integration-researcher` | Новые сервисы, библиотеки, конфиг OTEL | Opus |
| `planning-coordinator` | Всегда, если выбрано 2+ агента | Opus |

**Уровневые метки** (описательные, а не предписывающие):
- Уровень 0 (0 агентов): Соло (встроенное исследование, без появления)
- Уровень 1 (1–3 агента): Сосредоточенный
- Уровень 2 (4–6 агентов): Стандартный
- Уровень 3 (7–9 агентов): Комплексный
- Уровень 4 (10+ агентов): Полный спектр

Скажите пользователю: «Я рекомендую команду **[Tier N — Label]**: [список агентов с однострочным обоснованием для каждого]. Хотите добавить или удалить каких-либо агентов?»

Дождитесь одобрения перед этапом 4.

## Этап 4: Исследование и создание плана

**Tier 0**: Проведение встроенных исследований. Напишите план напрямую, без нерестовых агентов.

**Tier 1+**: параллельно создавать утвержденных агентов с помощью инструмента Task (run_in_background: true). Для каждого агента укажите:
- Его конкретный объем исследований
- Соответствующий files/areas для расследования.
- Вопросы, на которые он должен ответить

Контролируйте агенты, читая их выходные файлы напрямую (TaskOutput был удален в версии 2.1.278; вместо этого используйте `Read` в пути вывода, указанном агентом). Отчет о ходе выполнения: «Агенты 3/6 завершены...»

Когда все агенты вернутся: если был создан `planning-coordinator`, отправьте ему все отчеты агентов и попросите его синтезировать окончательный план. В противном случае синтезируйте напрямую.

Структура файла **Plan** (`docs/plans/plan-{name}.md`):

```markdown
# Plan: {feature-name}
Created: {date} | Branch: {branch-name} | Tier: {N}

## Summary
One paragraph: what this implements and why.

## Decisions
Decisions recorded during Phase 1 (PRD analysis).

## Architecture
ADRs created, patterns applied, architectural choices made.

## Tasks
Ordered task list with layers (1 = foundation, 2 = depends on 1, etc.)

### Layer 1
- [ ] Task A: description, files affected, acceptance criteria
- [ ] Task B: description, files affected, acceptance criteria

### Layer 2
- [ ] Task C (depends on A): description, files affected, acceptance criteria

## Test Plan
How each task will be verified. TDD tasks marked explicitly.

## Integration Verification
Smoke test commands to run post-execution (if backend/services in scope).

## Out of Scope
What this plan explicitly does not address.
```

Фиксация: файл плана + файлы ADR + манифесты отчетов агента.

## Этап 5. Завершение работы над метриками

Записывайте временные метки, продолжительность фаз, количество агентов и смету затрат в `docs/plans/metrics/{name}.json`. Совершить.

## Auto-transition

Если Фаза 1 не привела к неразрешенным неопределенностям, а Фаза 2 не привела к неразрешенным решениям: автоматически запустите `/plan-pipeline:validate` без запроса.

Если возникло какое-либо человеческое обсуждение: спросите: «Готовы проверить этот план?» прежде чем продолжить.

---

## Использование

```
/plan-pipeline:start
```

При появлении запроса укажите описание функции или укажите файл PRD. Остальное команда обрабатывает в интерактивном режиме.

## <a name="when-to-use"></a>Когда использовать

Используйте для любой нетривиальной функции: чего-либо, затрагивающего более двух файлов, включающего архитектурные решения или где ошибку планирования будет дорого исправить.

Для простых изменений (опечатки, тривиальные рефакторинги): вместо этого используйте режим `/plan`.

## Положение трубопровода

```
/plan-pipeline:ceo-review    → product direction locked
/plan-pipeline:eng-review    → architecture locked
/plan-pipeline:start         → produce implementation plan   ← you are here
/plan-pipeline:validate      → validate before execution
/plan-pipeline:execute       → execute to merged PR
```
