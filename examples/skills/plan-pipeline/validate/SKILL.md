# /plan-pipeline:validate: двухуровневая проверка.

Независимая проверка плана, составленного `/plan-pipeline:start`. Код не пишется. Запустите `/clear` после этой команды перед запуском `/plan-pipeline:execute`.

Валидация отличается от планирования по замыслу: валидаторы, которые не писали план, не привязаны к его предположениям.

---

## Предварительное условие

Зафиксированный файл плана должен существовать по адресу `docs/plans/plan-{name}.md`. Если существует несколько планов, перечислите их и спросите пользователя, какой из них нужно проверить.

---

## Уровень 1: Структурная проверка

Запускайте немедленно, агенты не требуются. Проверьте плановый документ на наличие:

**Формат и полнота**
- [ ] Присутствуют все необходимые разделы (Сводка, Решения, Архитектура, Задачи, План тестирования, Выходит за рамки)
- [ ] Каждая задача имеет: описание, затронутые файлы, критерии приемки, назначение слоев.

**Цепочка зависимостей**
- [ ] Никаких циклических зависимостей между задачами
- [ ] Задачи на более высоких уровнях зависят только от задач на нижних уровнях.
- [ ] Все заявленные зависимости присутствуют в плане

**Существование файла**
- [ ] Каждый файл, указанный для изменения, действительно существует в базе кода (используйте Glob).
- [ ] Новые файлы находятся в соответствующих каталогах в соответствии с соглашениями проекта.

**ADR Согласованность**
- [ ] Плановые решения соответствуют ADR, созданным во время `/plan-pipeline:start`.
- [ ] Нет противоречий с существующими ADR в `docs/adr/`.

**CLAUDE.md Соответствие**
- [ ] План уважает все жесткие правила в CLAUDE.md.
- [ ] Никаких нарушений основных принципов (никаких обходных путей, никаких прокладок обратной совместимости)

**Тестовое покрытие**
- [ ] Каждому новому function/component соответствует тестовое задание.
- [ ] Задачи с пометкой TDD имеют неудачный тест, записанный перед задачей реализации.

Запишите все проблемы уровня 1 с указанием серьезности (БЛОКИРОВКА / ПРЕДУПРЕЖДЕНИЕ / ИНФОРМАЦИЯ), прежде чем переходить к уровню 2.

---

## Уровень 2: Обзор специалиста

Выберите агентов, применив правила триггера к содержимому плана. Никакого пользовательского ввода не требуется; триггеры объективны.

**Пул агентов проверки:**

| Агент | Курок | Модель |
|-------|---------|-------|
| `security-reviewer` | Аутентификация, платежи, персональные данные, RBAC, новые общедоступные API | Opus |
| `db-migration-reviewer` | Новые таблицы, столбцы, индексы или файлы миграции. | Opus |
| `performance-reviewer` | Новые запросы, преобразователи, маршруты или добавленные зависимости. | Sonnet |
| `design-system-reviewer` | Новые компоненты пользовательского интерфейса или изменения визуального стиля. | Sonnet |
| `ux-reviewer` | Новые страницы, формы, модальные окна или шаблоны взаимодействия. | Sonnet |
| `cross-platform-reviewer` | Изменения, касающиеся как веб-сайтов, так и мобильных устройств, а также общих пакетов. | Sonnet |
| `native-app-reviewer` | Мобильные экраны, изменения в пакете собственного пользовательского интерфейса | Sonnet |
| `integration-reviewer` | Новые внешние службы, библиотеки или конфигурация OTEL. | Opus |

Параллельно запускать активируемые агенты (инструмент Task, run_in_background: true). Каждый агент получает: файл плана, соответствующие ADR и целевые вопросы, основанные на его домене.

Мониторинг через `Read` на пути вывода, указанном агентом (TaskOutput был удален в версии 2.1.278). Сообщайте о прогрессе пользователю.

Каждый агент должен возвращать структурированные результаты:
```
FINDING: [BLOCKER|WARNING|INFO]
Location: [plan section or file reference]
Issue: [concrete description]
Risk: [what breaks if this isn't addressed]
Suggestion: [specific fix or alternative]
```

## Фаза автоисправления

Объедините структурные проблемы уровня 1 + выводы специалистов уровня 2 в единый список проблем. Каждый вопрос должен быть решен. Никаких пропусков.

**Проверка каждой проблемы:**

**Корзина A: автоматическое разрешение**
- Проблема соответствует существующему решению ADR → указать ADR, отметить решенным
- Проблема соответствует подтвержденному шаблону в PATTERNS.md → шаблон цитирования, отметка решена
- Проблема, решаемая на основе основных принципов в CLAUDE.md → применить правило, отметить решенную

**Объект B: требуется участие человека**
- Новый архитектурный вопрос, не охваченный существующими решениями
- Противоречивые ADR без явного прецедента
- Блокировщик без очевидного решения

Для элементов сегмента B: изложите проблему, объясните, почему ее нельзя решить автоматически, предложите варианты, дождитесь решения. Запишите решение в разделе `## Decisions` плана и создайте новый ADR, если он значим с архитектурной точки зрения.

**Примените все исправления одним пакетом** после того, как все проблемы будут отсортированы. Обновите файл плана. Зафиксируйте обновленный план.

## Постоянство проблемы

Записывайте каждую проблему в `docs/plans/metrics/{name}.json` под `validation.issues`:

```json
{
  "id": "S-001",
  "layer": 1,
  "severity": "WARNING",
  "category": "test-coverage",
  "description": "No test task for the new webhook handler",
  "reporting_agent": "structural",
  "triage": "A",
  "resolution_source": "first-principles",
  "resolution": "Added test task in Layer 2 of the plan"
}
```

---

## Auto-transition

Если все проблемы решены автоматически (только для сегмента A): автоматически запустите `/plan-pipeline:execute` без запроса.

Если требовалось вмешательство человека (блок B): спросите: «Все проблемы решены. Готовы к выполнению?» прежде чем продолжить.

---

## Использование

```
/plan-pipeline:validate
```

Автоматически выбирает самый последний незафиксированный план. Или укажите:

```
/plan-pipeline:validate plan-user-authentication
```

## Выход

```
Layer 1: Structural validation...
  ✓ Format complete
  ✓ Dependencies valid
  ⚠ WARNING S-001: Missing test task for webhook handler
  ✓ CLAUDE.md compliant

Layer 2: Triggering specialist agents...
  → security-reviewer (auth changes detected) [Opus]
  → db-migration-reviewer (new users table) [Opus]
  → performance-reviewer (new query in /api/users) [Sonnet]
  Monitoring... 1/3 complete... 2/3 complete... done.

  BLOCKER B-001 [security-reviewer]: JWT expiry not validated on refresh endpoint
  WARNING B-002 [db-migration-reviewer]: Migration lacks rollback strategy

Auto-fix phase:
  S-001 → auto-resolved (first principles: test coverage rule)
  B-001 → NEEDS INPUT (no existing ADR for JWT refresh strategy)
  B-002 → auto-resolved (ADR-0003: migration rollback pattern)

[User input requested for B-001]
Decision recorded. ADR-0011 created.

All 3 issues resolved. Plan updated.
→ Auto-starting /plan-pipeline:execute
```

## <a name="when-to-use"></a>Когда использовать

Всегда запускайте перед любым вызовом `/plan-pipeline:execute`. Стоимость проверки (0,20–3,00 доллара США) незначительна по сравнению со стоимостью обнаружения проблем в середине выполнения.

## Положение трубопровода

```

/plan-pipeline:eng-review    → architecture locked

/plan-pipeline:execute       → execute to merged PR
```
