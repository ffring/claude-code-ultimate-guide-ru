# Проверь меня

Проверьте понимание недавно написанного или принятого кода.

## Использование

```
/learn:quiz                     # Quiz on last code worked with
/learn:quiz error handling      # Focus on specific aspect
/learn:quiz --hard              # More challenging questions
```

## Инструкции

1. Укажите последний код, с которым я работал (написал, отредактировал или принял от ИИ).
2. Создайте 3–5 вопросов, проверяющих понимание на разных уровнях:
   - **Recall**: Что делает этот код?
   - **Понимание**: Почему был выбран такой подход?
   - **Application**: Что произойдет, если X изменится?
   - **Анализ**: Каковы недостатки этого подхода?
   - **Synthesis**: Как бы вы это расширили?
3. Задавайте вопросы по одному
4. Подождите моего ответа, прежде чем показывать правильный ответ
5. Дайте пояснения к каждому ответу, а не только к «correct/incorrect».

## Типы вопросов

### Уровень 1: Вспомнить
- «Что возвращает функция X?»
- «Какие параметры принимает Y?»
- «Что происходит, когда вызывают Z?»

### Уровень 2: Понимание
- «Почему мы используем здесь X вместо Y?»
- «Какую проблему решает этот шаблон?»
- «Зачем нужна эта линия?»

### Уровень 3: Приложение
- «Что произойдет, если мы удалим строку X?»
- «Как бы вы добавили функцию Y в этот код?»
- «Что сломалось бы, если бы был предоставлен вход Z?»

### Уровень 4: Анализ
- «Каковы последствия этого подхода для производительности?»
- «Какие крайние случаи могут вызвать проблемы?»
- «Как это соотносится с альтернативой X?»

### Уровень 5: Синтез
- «Как бы вы реорганизовали это, чтобы улучшить тестируемость?»
- «Что нужно изменить, чтобы поддержать X?»
- «Разработайте расширение, добавляющее Y»

## Направления деятельности

Когда фокус указан (например, `/learn:quiz error handling`), расставьте приоритеты по следующим вопросам:

| Фокус | Темы вопросов |
|-------|-----------------|
| `error handling` | Try/catch, типы ошибок, стратегии восстановления |
| `performance` | Big-O, оптимизация, узкие места |
| `security` | Проверка ввода, XSS, внедрение |
| `testing` | Тестовые случаи, крайние случаи, насмешки |
| `architecture` | Шаблоны, разделение ответственности, SOLID |
| `types` | Типы TypeScript, вывод, дженерики |

## Режимы сложности

### По умолчанию
- 3 вопроса
- Микс уровней 1-3
- Сосредоточьтесь на понимании текущего кода

### `--hard`
- 5 вопросов
- Уровни 3–5
- Включить гипотетические модификации
- Спросите о компромиссах и альтернативах

## Формат ответа

По каждому вопросу:

```
## Question 1 of 3

[Question text]

What's your answer?

---
(After user responds)

### Feedback

[Whether correct and why]

**Key insight**: [The concept this tests]

**Related concept**: [Something to explore further]

Ready for the next question?
```

## После завершения викторины

Summarize:
- Оценка: X/Y верна.
- Сильные стороны: [Темы понятны хорошо]
- Требуется проверка: [Темы, к которым стоит вернуться]
- Рекомендуемая практика: [Конкретное упражнение]

## Пример сеанса

```
User: /learn:quiz

Claude: Looking at your last code - the useEffect hook for data fetching.

## Question 1 of 3

In your useEffect, you have an empty dependency array [].
What does this mean for when the effect runs?

User: It runs only once when the component mounts

Claude: ### Feedback
Correct! An empty dependency array means the effect runs only on mount
(and cleanup on unmount).

**Key insight**: The dependency array controls WHEN effects re-run.

**Related concept**: What happens with no array vs. [someValue]?

Ready for Question 2?
```

## Советы пользователям

1. **Будь честен**: Неправильные ответы — это возможности для обучения
2. **Объясните свои рассуждения**: помогает выявить пробелы даже в правильных ответах.
3. **Задать вопросы**: Если отзыв неясен, копайте глубже
4. **Отслеживать слабые места**: отмечать темы, требующие дополнительной практики
