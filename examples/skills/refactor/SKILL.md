# Помощник по рефакторингу SOLID

Анализируйте код на наличие нарушений SOLID и предлагайте целевые улучшения.

## Цель

Определите возможности рефакторинга на основе:
- ТВЕРДЫЕ нарушения принципов
- Запахи кода и антишаблоны
- Метрики сложности
- Обнаружение дублирования

## Инструкции

### Шаг 1: Анализ объема

Определите объем рефакторинга на основе данных пользователя:
- Отдельный файл: Глубокий анализ
- Каталог: Обнаружение шаблонов в файлах
- Function/class: Целенаправленные предложения по извлечению

```bash
# Get file/directory stats
if [ -f "$TARGET" ]; then
  wc -l "$TARGET"
  echo "Single file analysis"
elif [ -d "$TARGET" ]; then
  find "$TARGET" -type f \( -name "*.ts" -o -name "*.js" -o -name "*.py" \) | wc -l
  echo "Directory analysis"
fi
```

### Шаг 2. Обнаружение нарушений SOLID

#### S – единая ответственность

Искать:
- Файлы > 300 строк
- Функции > 50 строк
- Классы с > 10 методами
- Смешанные проблемы (данные + пользовательский интерфейс + бизнес-логика)

```bash
# Find large files
find . -name "*.{ts,js,py}" -exec wc -l {} + 2>/dev/null | sort -rn | head -10

# Functions with high line count (approximate)
grep -rn "function\|def \|fn " --include="*.{ts,js,py,rs}" . | head -20
```

#### О - принцип open/closed

Искать:
- Операторы Switch/case для типов
- Повторная проверка типа if/else
- Прямые модификации и расширения

#### L - замена Лискова

Искать:
- Переопределенные методы, которые выдают сообщение «не реализовано».
- Проверки типов перед вызовами методов
- Пустые переопределения метода

#### I - разделение интерфейса

Искать:
- Большие интерфейсы (> 10 методов)
- Классы, реализующие неиспользуемые методы интерфейса
- Классы обслуживания жира

#### D – инверсия зависимости

Искать:
- Прямое создание зависимостей (`new Service()`)
- Жестко запрограммированные ссылки на классы
- Отсутствует внедрение зависимостей

### Шаг 3. Код пахнет

```bash
# Duplication patterns
grep -rn --include="*.{ts,js,py}" . 2>/dev/null | \
  awk -F: '{print $3}' | sort | uniq -c | sort -rn | head -10

# Long parameter lists (> 4 params)
grep -rn "function.*,.*,.*,.*," --include="*.{ts,js}" . 2>/dev/null | head -10

# Deep nesting (4+ levels)
grep -rn "^\s\{16,\}" --include="*.{ts,js,py}" . 2>/dev/null | head -10
```

### Шаг 4: Оценка сложности

По каждой обнаруженной проблеме оцените:
- **Impact**: Какой объем кода затронут?
- **Risk**: Что может сломаться?
- **Effort**: Строки, которые нужно изменить, нужны тесты?

## Контрольный список безопасности рефакторинга

Прежде чем применять предложения:

- [ ] Существуют тесты для затронутого кода.
- [ ] Создать ветку функций
- [ ] Зафиксировать текущее состояние
- [ ] Применяйте один рефакторинг за раз
- [ ] Запускайте тесты после каждого изменения
- [ ] Просмотрите разницу перед фиксацией

## Использование

**Анализ конкретного файла:**
```
/refactor src/services/user.ts
```

**Анализ каталога:**
```
/refactor src/api/
```

**Сосредоточьтесь на конкретном принципе:**
```
/refactor --focus=srp src/services/
```

**С порогом сложности:**
```
/refactor --threshold=high
```
