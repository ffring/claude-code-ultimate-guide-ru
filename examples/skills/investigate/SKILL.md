# Исследование: устранение первопричин

Систематическая отладка с обязательным расследованием первопричин перед любым изменением кода.

**Железный закон: НЕТ ИСПРАВЛЕНИЙ БЕЗ ПЕРВОГО РАССЛЕДОВАНИЯ ПРИЧИНЫ.**

Исправление симптомов приводит к отладке по принципу «ударь крота». Каждое исправление, не устраняющее основную причину, затрудняет поиск следующей ошибки.

## Инструкции

### Этап 1: Сбор симптомов

Прежде чем формировать какую-либо гипотезу, соберите весь доступный контекст.

1. Полностью прочтите сообщения об ошибках, трассировки стека и этапы воспроизведения.
2. Задайте ОДИН целевой вопрос, если пользователь не предоставил достаточно контекста:
   - «Какое именно сообщение об ошибке вы видите?»
   - «Можете ли вы воспроизвести это последовательно?»
   - «Когда это начало происходить?»
3. Определите затронутый компонент и его границы.

**Output**: точное описание симптомов: что происходит, когда и с какой ошибкой.

---

### Этап 2. Прочтите код.

Проследите путь кода от симптома до потенциальных причин. Не угадывайте.

```bash
# Find all references to the failing component
grep -rn "ComponentName\|function_name\|error_string" src/ --include="*.{ts,js,py,rb,go}" | head -30

# Check recent changes to affected files
git log --oneline -15 -- <affected-file>

# Read the actual diff for each recent commit
git show <commit-hash> -- <affected-file>
```

Используйте Grep, чтобы найти все ссылки. Прочтите, чтобы понять логику. Никогда не пропускайте чтение кода.

---

### Этап 3. Проверьте последние изменения.

```bash
# What changed recently across the whole repo
git log --oneline -20

# Changes to files related to the symptom
git log --oneline -20 -- <affected-files>

# Full diff of the last N commits
git diff HEAD~3..HEAD -- <affected-directory>
```

**Ключевой вопрос**: Это работало раньше? Если да, то основная причина кроется в недавнем diff.

- Регрессия = основная причина в изменениях, а не в исходном коде.
- Всегда сломанный = архитектурная проблема или неверное предположение

---

### Этап 4: Воспроизведение

Прежде чем что-либо исправлять, убедитесь, что вы можете детерминированно вызвать ошибку.

```bash
# Run the test suite targeting the affected area
npm test -- --testPathPattern="affected-module" 2>/dev/null || \
pnpm test -- --testPathPattern="affected-module" 2>/dev/null || \
pytest tests/test_affected.py -v 2>/dev/null

# Check logs if available
tail -50 logs/error.log 2>/dev/null || \
journalctl -u app-service --lines=50 2>/dev/null
```

Если вы не можете воспроизвести: соберите больше доказательств. Не чините то, что вы не можете проверить, сломано.

---

### Этап 5: Анализ закономерностей

Сопоставьте симптом с известными шаблонами ошибок:

| Шаблон | Подпись | Где искать |
|---------|-----------|---------------|
| Состояние гонки | Периодические, зависящие от времени сбои | Параллельный доступ к общему состоянию, упорядочивание async/await |
| Распространение нуля | TypeError, неопределенное не является функцией | Отсутствуют меры защиты необязательных значений, непроверенные ответы API. |
| Государственная коррупция | Противоречивые данные, частичные обновления | Транзакции, обратные вызовы, мутация общих объектов |
| Сбой интеграции | Тайм-аут, неожиданная форма ответа | Внешние вызовы API, границы сервиса, изменения схемы |
| Дрейф конфигурации | Работает локально, не работает в staging/prod | Переменные окружения, флаги функций, состояние базы данных, недостающие секреты |
| Устаревший кэш | Показывает старые данные, исправления на restart/clear | Redis, CDN, кеш браузера, мемоизация |
| Ошибка Import/module | «Невозможно найти модуль», «не является функцией» | Версии пакетов, циклический импорт, артефакты сборки |

Также проверьте:
- `TODOS.md` или средство отслеживания известных проблем в той же области.
- `git log` для предыдущих исправлений в тех же файлах; повторяющиеся ошибки в одном и том же месте — это архитектурный запах

**Внешний поиск:** Если шаблон не соответствует, выполните поиск:
`{framework} {sanitized-error-type}` (удалить имена хостов, пути к файлам, внутренние данные). Ищите категорию ошибки, а не необработанное сообщение.

**Сформулируйте гипотезу**: «Гипотеза о первопричине: [конкретное, проверяемое утверждение о том, что не так и почему]»

---

### Этап 6: Проверка гипотез

Прежде чем писать какое-либо исправление, проверьте свою гипотезу.

1. **Подтвердите гипотезу**: добавьте временный оператор журнала, утверждение или вывод отладки для предполагаемой основной причины. Запустите воспроизведение. Доказательства совпадают?

```javascript
// Example: temporary diagnostic
console.log('[DEBUG investigate]', { value, expected, type: typeof value });
```

```python
# Example: temporary diagnostic
import sys; print(f'[DEBUG investigate] value={value!r} type={type(value)}', file=sys.stderr)
```

2. **Если гипотеза неверна**: Соберите больше доказательств. Вернитесь к этапу 2. Не гадайте.

3. **3-правило**: Если 3 гипотезы не выдвинуты, СТОП. Это может быть архитектурная проблема.

   Представьте это пользователю:
   ```
   3 hypotheses tested, none confirmed. This likely requires deeper investigation.

   Options:
   A) I have a new hypothesis: [describe], continue investigating
   B) Add instrumentation and wait: capture the bug in the act next time
   C) Escalate: this needs someone with deeper system knowledge
   ```

**Красные флажки, немедленно сбавьте скорость:**
- «Быстрое решение на данный момент»: «на данный момент» не существует
- Предложение исправления перед отслеживанием потока данных: это предположение
- Каждое исправление выявляет новую проблему где-то в другом месте: не тот слой, а не неправильный код.

---

### Этап 7: Реализация

После подтверждения основной причины:

1. **Устраните основную причину, а не симптом.** Наименьшее изменение, устраняющее реальную проблему.

2. **Минимальная разница**: изменено наименьшее количество файлов, изменено наименьшее количество строк. Сопротивляйтесь рефакторингу смежного кода.

3. **Напишите регрессионный тест**, который:
   - **Fails** без исправления (доказывает, что тест имеет смысл)
   - **Passes** с исправлением (доказывает, что исправление работает)

4. **Запустите полный набор тестов** и вставьте выходные данные. Никакие регрессии не допускаются.

5. **Проверка радиуса взрыва**: Если исправление затрагивает более 5 файлов, остановитесь и подтвердите:

   ```
   This fix touches N files. That's a large blast radius for a bug fix.

   A) Proceed: the root cause genuinely spans these files
   B) Split: fix the critical path now, defer the broader cleanup
   C) Rethink: there may be a more targeted approach
   ```

## Выходной формат

```
DEBUG REPORT
════════════════════════════════════════════════════
Symptom:          [what the user observed]
Root cause:       [what was actually wrong, specific not vague]
Fix:              [what was changed, with file:line references]
Evidence:         [test output or reproduction showing fix works]
Regression test:  [file:line of the new test]
Related:          [known issues, prior bugs in same area, architectural notes]
Status:           DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════════════════
```

**Определения статуса:**
- **DONE**: найдена основная причина, применено исправление, написан регрессионный тест, все тесты пройдены.
- **DONE_WITH_CONCERNS**: исправлено, но невозможно полностью проверить (периодически, требует подготовки)
- **BLOCKED**: основная причина неясна после полного расследования.

**Формат эскалации (при БЛОКИРОВКЕ):**
```
STATUS: BLOCKED
REASON: [1-2 sentences explaining what was tried and why it failed]
ATTEMPTED: [list of hypotheses tested]
RECOMMENDATION: [what the user should do next: add logging, escalate, or request an architectural review]
```

## Важные правила

- **Никогда не применяйте исправление, которое не можете проверить.** Если вы не можете воспроизвести и подтвердить, не отправляйте его.
- **Никогда не говорите: «Это должно исправить ситуацию».** Проверьте и докажите это. Запустите тесты.
- **Никогда не исправляйте >3 несвязанных между собой вещей за одно расследование.** Если вы обнаружите другие ошибки, отметьте их, но сохраняйте концентрацию.
- **Удалите все записи журнала отладки** перед фиксацией исправления.
- **3+ неудавшиеся гипотезы → подвергайте сомнению архитектуру**, а не свои навыки гипотезы.
