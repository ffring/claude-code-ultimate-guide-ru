# Обнаружение вариантов использования в рутинах

Анализирует эту базу кода и выявляет действенных кандидатов подпрограмм по трем типам триггеров.

**Usage**: `/routines-discover` — аргументы не нужны. Запустите его в корне любого проекта.

---

## Что такое рутины

Подпрограмма — это автономный сеанс Claude Code, работающий в облачной инфраструктуре, управляемой Anthropic, который запускается тремя способами:

| Курок | Как это срабатывает |
|---------|-------------|
| **Расписание** | Повторяющаяся частота хрона (минимум 1 час) |
| **API** | HTTP POST к стандартной конечной точке с токеном носителя |
| **GitHub события** | События репозитория: PR opened/merged, push, выпуск, запуск рабочего процесса и т. д. |

Каждый запуск клонирует новую копию репозитория GitHub, запускает полный сеанс Claude Code с настроенными коннекторами MCP (Slack, Linear, GitHub, Google Drive…) и может создавать ветки, открывать PR, публиковать сообщения и вызывать внешние API. Локальная машина не требуется.

**Дневные лимиты**: Pro 5/day · Макс 15/day · Team/Enterprise 25/day.

## Инструкции

### Шаг 1. Прочтите кодовую базу

Прежде чем генерировать какой-либо вывод, прочитайте молча:
- `README.md` или `CLAUDE.md`, чтобы понять цель и стек проекта.
- `package.json`, `Cargo.toml`, `pyproject.toml` или эквивалент для зависимостей.
- `.github/workflows/` для понимания существующей автоматизации CI/CD.
- Любая конфигурация мониторинга, развертывания или эксплуатации, которую вы найдете.

Если MCP разъемы настроены в `.claude/settings.json`, обратите внимание, какие внешние службы подключены.

### Шаг 2. Анализируйте по пяти измерениям

По каждому измерению подумайте конкретно об этом конкретном проекте, прежде чем что-либо писать.

**1. Плановое техническое обслуживание**
Какую повторяющуюся работу в настоящее время требует от человека выполнять вручную или не забывать?
Подумайте: аудит зависимостей, устаревшая сортировка issue/PR, отчеты о нестабильности тестов, отклонение покрытия, отслеживание комментариев TODO, обнаружение мертвого кода, ежедневные или еженедельные сводки.

**2. Реакции, управляемые событиями**
Что должно произойти автоматически, когда PR открывается, объединяется или закрывается, но сегодня этого не происходит, потому что никто до него не доходит?
Подумайте: просмотрите контрольные списки, обновления журнала изменений, синхронизацию между репозиториями, уведомления Slack с контекстом, принудительное соблюдение меток, обновления документации по изменениям API.

**3. Оповещение и реагирование на инциденты**
Какие сигналы мониторинга существуют? Когда что-то ломается, что первым делом делает разработчик?
Подумайте: сопоставление оповещения с недавними коммитами, сортировка неудачной сборки, составление посмертного скелета, перенаправление ошибки нужной команде.

**4. Межсистемная синхронизация**
Что сегодня происходит из-за того, что синхронизация между двумя системами осуществляется вручную?
Подумайте: синхронизация двух SDK, обновление сайта документации при изменении API, синхронизация проблем GitHub с Linear, поддержание актуальности раздела статистики README.

**5. Выпуск и развертывание автоматизации**
Какие шаги происходят до или после развертывания, которое человек выполняет вручную?
Подумайте: дымовые тесты, примечания к выпуску, обновления версий, уведомления заинтересованных сторон, сводки go/no-go.

### Шаг 3: Вывод

Для каждого выявленного варианта использования создайте карточку в следующем формате:

---

**[Имя]** · `schedule` / `api` / `github`

*Trigger*: [что запускает: выражение cron, какое событие, какая внешняя система]

*Input*: [что получает Claude: состояние репозитория, полезная нагрузка события, тело оповещения]

*Output*: [что производит Claude: открыт PR, опубликовано сообщение, обновлен файл, создана проблема]

*Value*: [сэкономленное время или сниженный риск, уточните]

*Blockers*: [отсутствует разъем, необходимы секреты, требуется приложение GitHub и т. д., или «нет»]

---

Сортировка карт по **соотношению стоимости/затраченных усилий**, начиная с самого высокого значения.

После всех карточек добавьте раздел **Quick Wins**: два или три варианта использования, которые можно настроить менее чем за 15 минут с текущим репозиторием и конфигурацией соединителя.

---

## Пример вывода (только для справки, не копируйте, анализируйте реальный проект)

**Ночной PR-отчет** · `schedule`

*Trigger*: Каждый будний день в 8 утра.

*Input*: Состояние репо: все открытые заявки на поставку старше 5 дней.

*Output*: сообщение Slack для #engineering со списком устаревших запросов на поставку, правопреемника и последней активности.

*Value*: экономит ~15 минут ручной сортировки каждое утро, снижает порчу PR.

*Blockers*: требуется разъем Slack MCP.
