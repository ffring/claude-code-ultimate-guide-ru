# Каталог семантических якорей

> **Каталог по теме**: [LLM-Coding/Semantic-Anchors](https://github.com/LLM-Coding/Semantic-Anchors) (Apache-2.0)
> **Scope**: избранные термины для рабочих процессов Claude Code, а не полная копия каталога сообщества.

## Что такое семантические якоря?

Семантическая привязка называет в подсказке установленный метод, шаблон или структуру. Имя может быть полезным сокращением, если модель его распознает, но оно не определяет ограничения вашего проекта и не гарантирует правильную реализацию. Соедините этот термин с нужным вам поведением и способом проверки результата.

 [критерии качества каталога сообщества](https://llm-coding.github.io/Semantic-Anchors/about/) спросите, является ли термин точным, богатым, последовательным и объяснимым. Его [план оценки](https://llm-coding.github.io/Semantic-Anchors/evaluations/) отличает признание от применения. Этот каталог представляет собой набор примеров, а не эталон качества продукции.

Используйте термин только тогда, когда базовый метод соответствует задаче. Если Claude неправильно применяет его, дополните имя явными инструкциями или процитируйте первоисточник. Избегайте объединения архитектурных шаблонов без демонстрации необходимости.

## Шаблоны подсказок

### <a name="anti-anchoring-techniques"></a>Техники борьбы с якорем

LLM могут зациклиться на своем первом предложении, сужая пространство для решения. Эти шаблоны борются с предвзятостью привязки:

| Шаблон | Шаблон подсказки | Эффект |
|---------|-----------------|--------|
| Новый старт | «Игнорируйте любые предыдущие идеи. Создайте 4 новых подхода к [X]» | Разнообразие сил |
| Петля отражения | «Создайте 3 варианта, затем оцените каждый, а затем порекомендуйте» | Self-correction |
| Количественное сравнение | «Ранг по [показатель1], [показатель2], [показатель3] с баллами 1–10» | Объективные компромиссы |
| Адвокат дьявола | «Каковы самые сильные аргументы против вашей рекомендации?» | Поверхностные скрытые затраты |
| Переворот ограничений | «Теперь решите с [противоположным ограничением]» | Расширить пространство решений |

### Подсказки к исследованию

Используйте их, когда вам нужно несколько подходов перед фиксацией:

| Цель | Подсказка семантического якоря |
|------|------------------------|
| Выбор архитектуры | «Сравните [A], [B], [C], используя критерии модели C4: соответствие контексту, сложность контейнера, количество компонентов» |
| Компромисс производительности | «Анализ временной сложности (Big O), пространственной сложности и удобства кэширования для каждого подхода» |
| Команда подходит | «Оцените кривую обучения, сложность отладки и зрелость экосистемы (шкала от 1 до 10)» |
| Оценка риска | «Для каждого варианта: каков наихудший вариант отказа и стоимость восстановления?» |

## Шаблон CLAUDE.md с семантическими якорями

```markdown
# Project Architecture

## Principles (Semantic Anchors)

### Architecture
- **Pattern**: Hexagonal Architecture (Ports & Adapters)
- **Domain modeling**: Domain-Driven Design tactical patterns (Aggregates, Value Objects, Domain Events)
- **Documentation**: ADR (Architecture Decision Records) for significant decisions

### Code Quality
- **Design**: SOLID principles, especially SRP and DIP
- **Refactoring**: Apply Fowler's catalog - Extract Method, Replace Conditional with Polymorphism
- **Naming**: Intention-revealing names, Screaming Architecture for packages

### Testing
- **Methodology**: TDD London School - outside-in, mock collaborators
- **Structure**: Arrange-Act-Assert (AAA) pattern
- **Coverage**: Test Pyramid - 70% unit, 20% integration, 10% E2E

### Error Handling
- **Pattern**: Railway Oriented Programming with Result<T, E>
- **Never**: Return null, throw for control flow
- **Always**: Use Option/Maybe for optional values

### API Design
- **Style**: REST Level 2 with proper HTTP verbs and status codes
- **Documentation**: OpenAPI 3.0 spec-first
- **Security**: OAuth 2.0 + PKCE for authentication

### Requirements
- **Format**: EARS syntax for formal requirements
- **User stories**: Connextra format with acceptance criteria
- **Discovery**: Event Storming for domain exploration
```

## Советы по использованию

1. **Объединить якоря**: «Применить гексагональную архитектуру с тактическими шаблонами DDD и обработкой ошибок, ориентированной на железную дорогу»

2. **Укажите versions/authors**: «По следам TDD Кента Бека (2003)» более конкретно, чем «TDD».

3. **Справочники**: «Соглашения об именах в главе 2 чистого кода» активирует конкретные знания.

4. **Назовите шаблоны явно**: «Шаблон стратегии» > «подключаемое поведение»

5. **Использовать с тегами XML**: комбинируйте привязки с тегами `<constraints>` и `<quality_criteria>` для максимального эффекта.

---

> **Используйте с осторожностью**: отдайте предпочтение термину, который вы можете определить и проверить для этой задачи. Если модель не применяет его правильно, опишите поведение и укажите первоисточник метода.
