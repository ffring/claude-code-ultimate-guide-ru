## Краткое содержание

- Представляет TypeScript DSL для декларативного определения состояний рабочего процесса Claude Code: каждое состояние определяет идентификатор эмодзи, путь к файлу инструкций агента, разрешенные переходы между состояниями, разрешенные операции и функции защиты перехода.
- Трехмодульная архитектура: `workflow-engine` (выполняет правила, независимо от предметной области), `workflow-dsl` (язык определения шагов), `workflow-definition` (агрегированный корень с реальной логикой рабочего процесса и инвариантами).
- Безопасность типов через типы объединения TypeScript `as const` — недопустимые переходы между состояниями завершаются неудачно во время компиляции, а не во время выполнения.
- Структура доменно-ориентированного проектирования: рабочий процесс как явный совокупный корень, шаблон адаптера отделяет его от инфраструктуры Claude Code.
- Встроенная возможность наблюдения: каждая операция добавляется во внутренний журнал событий (тип операции, временная метка, контекстные сведения). Позволяет воспроизводить и проверять выполнение рабочего процесса.
- «Принцип государственной собственности»: каждое государство проверяет свои собственные предварительные условия, а не полагается на защитные проверки в движке.
- Повторное внедрение инструкций при каждом переходе состояний И при сбое команды — механизм, отличный от повторного внедрения контекстного сжатия (компенсирует потерю контекста агента во время выполнения, а не сжатие).
- Тестирование «черного ящика» с помощью общедоступных методов класса `Workflow`; никакого внутреннего государственного тестирования.
- Ссылки на репозиторий GitHub `NTCoding/autonomous-claude-agent-team` для полной реализации.
- Продолжение: https://nick-tune.me/blog/2026-02-28-hook-driven-dev-workflows-with-claude-code/ (уже оценивалось отдельно).

## Рекомендации по интеграции

**Выборочное извлечение — создание нового файла верхнего уровня не гарантируется до тех пор, пока не будет принято сообществом.**

Три хирургические интеграции в приоритетном порядке:

### 1. Шаблон наблюдения журнала событий (Приоритет: высокий)
**Где:** Документация по хукам или `guide/workflows/event-driven-agents.md`
**What:** Шаблон добавления каждой операции агента во внутренний журнал событий (с типом + меткой времени + контекстом) – это метод отладки и проверки, который в руководстве нигде не рассматривается. Извлеките это как отдельный шаблон, независимый от кадра DDD.

### 2. Повторное внедрение инструкций в случае сбоя (Приоритет: средний).
**Where:** `guide/workflows/event-driven-agents.md` или перехватывает лучшие практики
**What:** Повторное внедрение инструкций агента при сбое команды (а не только сжатие контекста) устраняет дрейф контекста во время выполнения. Отличие от существующего шаблона повторного впрыска уплотнения — стоит выделить абзац с явным различием.

### 3. Вызов проверки состояния во время компиляции (приоритет: низкий)
**Where:** `guide/core/architecture.md` возле строки 1227 (раздел конечных автоматов)
**What:** Руководство по архитектуре предостерегает от сложных конечных автоматов. Выноска, подтверждающая, что типы объединения TypeScript могут сделать простые переходы между состояниями безопасными при компиляции, является полезным нюансом — без одобрения полного шаблона из трех модулей.

## Вызов (агент технического писателя)

**Основной вывод из задачи:** Оценка изначально была объединена с предыдущей статьей Ника Тьюна (28 февраля 2026 г., рабочие процессы, управляемые перехватчиками). Это две разные статьи, и эта статья о DSL отличается по архитектуре: статья о хуках посвящена проводке, а эта — о языке определения состояний.

**Оценка балла:** 3/5 держится. Аргументом в пользу 4/5 является то, что проверка состояния во время компиляции с помощью типов объединения `as const` является действительно новой. Аргумент против: отсутствие проверки сообществом, реальная когнитивная сложность в трехмодульной конструкции и структура DDD — это академические накладные расходы для большинства пользователей Claude Code.

**Исправление ключа из проблемы:** Наблюдаемость журнала событий при первом чтении недооценена. Это наиболее действенный метод извлечения информации, который стоит возглавить любую интеграционную инициативу. Кадр DDD является вторичным.

**Риск неинтеграции:** В целом низкий. Единственная реальная цена — отсутствие шаблона наблюдения журнала событий. Полную архитектуру можно безопасно пропустить, пока ее распространение не вырастет.
