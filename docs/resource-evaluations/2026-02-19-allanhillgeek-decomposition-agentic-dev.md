## 📄 Резюме

Аллан Хилл описывает конвейер разработки производственных агентов, построенный на тезисе о том, что дисциплина декомпозиции важнее, чем сложность ИИ:

- **Основной тезис**: «ИИ — это легкая часть. Разложение — сложная часть». — Узким местом в разработке агентов является разбиение работы на удобоваримые ИИ блоки перед передачей агентам, а не оперативная оптимизация.
- **Ключевая единица работы**: Вертикальный срез — тонкая сквозная функция, охватывающая все уровни стека для одного полного поведения пользователя (например, «сброс пароля по электронной почте»); идеально подходит для агентов, поскольку четкие границы → проверяемый PR
- **3-этапный конвейер**: Фаза 0 (агенты PM создают небольшие PRD с 6-мерной проверкой качества) → Фаза 1 (Оркестратор разлагает PRD на упорядоченные независимые фрагменты, требуется одобрение Slack от человека) → Фаза 2 (для каждого фрагмента: сценарии Gherkin → ATDD → ​​реализация → PR)
- **Инфраструктура**: многопроходные виртуальные машины (1 на билет), Node.js опрос диспетчера GitHub API каждые 60 с, детерминированный CI (ESLint/Playwright/SonarQube) + AI CI (5 параллельных агентов проверки через GitHub Actions)
- **Открытые проблемы подтверждены**: хрупкость состояния возобновления, правило бойскаутов и баланс объема PR, ложноположительная настройка агента по проверке

## 🎯 Оценка: 3/5 — Соответствует, бесплатная интеграция

### Обоснование

**Аргументы в пользу 3 (не 4):**
- Конвейер слишком тесно связан с конкретным стеком (Multipass/GCP/Jira/Slack) → ~80% необходимо переписать для общего использования; низкий уровень повторного использования
- Никаких производственных показателей: никаких данных о времени цикла, уровне дефектов, пропускной способности — это архитектурное повествование, а не проверенный практический пример.
- Основные концепции (вертикальные срезы, сначала декомпозиция) берут свое начало в литературе по Agile (Дэн Норт BDD 2003, Дэвид Хассман) — это Agile, примененный к агентам ИИ, а не новая теория.
- Открытые проблемы не решены (возобновление нестабильности состояния, ложноположительная настройка) — документирование нестабильных практик в качестве справочной информации рискованно.
- Claude Code явно не упоминается; автор использует термин «агенты» в общем — сопоставление с руководством является косвенным.

**Аргументы против 5 (подтвержденные пробелы реальны, но не критичны):**
- Пробел в «декомпозиции задач» является законным, но частично устраняется с помощью существующего `spec-first.md`.
- Контрольный список шестимерного обзора PRD является извлекаемым и универсальным — это единственный наиболее действенный контент в статье.
- ATDD действительно отсутствует в руководстве (описан только TDD)

## 📍Рекомендации

**Приоритет: средний — интегрируйте два конкретных шаблона, а не весь конвейер**

### Интеграция 1: `guide/workflows/spec-first.md` — добавить раздел «Детализация задач».

Извлеките контрольный список качества шестимерного PRD в качестве общего контрольного списка перед кодированием:

```markdown
## PRD Quality Checklist (before handing to agents)

Before assigning work to an agent, verify the task definition covers:

1. **Problem Clarity** — Is the problem statement unambiguous?
2. **Testable Acceptance Criteria** — Can completion be verified automatically?
3. **Scope Boundaries** — What is explicitly OUT of scope?
4. **Observable Done Definition** — What does "done" look like to an end user?
5. **Requirements Clarity** — No ambiguous terms, no implementation details
6. **Terminology Consistency** — Same terms used throughout (not "user" and "account" interchangeably)
```

**Location**: После раздела «Шаблон» в `spec-first.md` (~ строка 60).
**Effort**: Низкий (20–30 строк)

### Интеграция 2: `guide/core/methodologies.md` — Добавить раздел ATDD

ATDD действительно отсутствует. Добавьте раздел, объясняющий, как ATDD расширяет TDD для рабочих процессов агентов:
- Сценарии корнишонов как договор между намерениями премьер-министра и их реализацией
- Сначала напишите Gherkin → агент пишет неудачные тесты → реализация

**Location**: После раздела TDD в `guide/core/methodologies.md`.
**Effort**: Средний (50–80 строк)

### Чего НЕ делать

❌ НЕ создавайте `guide/workflows/agentic-pipeline.md` — конвейер слишком специфичен для стека, проблемы автора не решены, и он будет документировать нестабильный шаблон как авторитетный. Прежде чем создавать специальное руководство по рабочему процессу, дождитесь второго независимого источника.
