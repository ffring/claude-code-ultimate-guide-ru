## 📄 Резюме содержания

- **Spec-Driven Development с изоляцией выполнения**: выполнение отдельных рабочих пакетов в собственном git worktree, устранение хаоса ветвей при параллельной сборке
- **Явное управление**: `next → review → accept → merge`, с отложенными командами
- **Dashboard kanban local**: версия миссии в репозитории (спецификации, планы, рабочие пакеты, критерии принятия, статус проверки, решения о слиянии)
- **Явная позиция против шума**: документ подтверждает, что «не черный ящик с отключенным светом по умолчанию», поэтому определение человека intention/architecture/критерии принятия, агенты, реализуемые в отслеживаемых рабочих деревьях, рецензенты accept/reject/merge с контрольным журналом
- **Совместимый** Claude Code, Codex, Курсор, Gemini, Copilot, OpenCode, Kiro и другие

## 🔥 Вызов

**Проверяемое возражение**: "1 397 звезд на основе полученного результата, это не так, как нужно для интеграции?"

**Ответ**: Я не думаю, что это уникальное число звезд, больше всего уникального узора. Spec-Kitty — это отдельный проект, идентифицированный в рамках этого исследования, который сочетает в себе изоляцию выполнения + канбан + контрольный журнал в одном из документов MIT. Альтернативные и популярные варианты (Spec Kit, BMAD) не подходят для этой конкретной комбинации. Любезное упоминание (после завершения раздела) - это хорошая дозировка: сигнал о существовании образца без сомнений в отношении усыновления на бис.

**Риск неинтеграции**: возможен. Концепция изоляции рабочего дерева — это документированная версия в руководстве (`guide/security/sandbox-isolation.md`, git Worktrees Natifs от Claude Code), спецификация не является пакетом реализации, который может быть другим.
