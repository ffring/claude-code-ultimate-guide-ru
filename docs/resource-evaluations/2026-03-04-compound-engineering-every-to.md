## Управляющее резюме

**Окончательный результат**: **4/5 (ВЫСОКОЕ ЗНАЧЕНИЕ)**

Compound Engineering — это проверенная на производстве инженерная философия от Every.to, реализованная в виде полноценного плагина Claude Code: 29 специализированных агентов проверки, 22 команды рабочего процесса, 20 предметных навыков. Философия формализует цикл «План → Работа → Обзор → Составной цикл» с явным распределением 50/50 между работой над функциями и улучшением системы. Некоторые шаблоны отсутствуют в руководстве и переносимы без установки плагина: именованные перспективные агенты (DHH, Кент Бек в качестве ярлыков для мнений), режим роя (специальные параллельные рецензенты), контрольные показатели качества навыков (явный контрольный список помимо основной темы) и рабочий процесс «мозговой штурм перед планированием». Многофункциональный конвертер AI (синтаксис Claude → GPT-4 → Gemini) является инновационным, но выходит за рамки данного руководства.

## Обзор ресурса

### Структура плагина

| Компонент | Считать | Примеры |
|-----------|-------|---------|
| Агенты | 29 | Рецензент DHH, рецензент Кента Бека, роевой оркестратор |
| Команды | 22 | /workflows:план, /workflows:работа, /workflows:обзор, /workflows:соединение |
| Навыки | 20 | безопасность, производительность, архитектура, доступность |
| Структура каталогов | 4 | docs/brainstorms/, docs/plans/, docs/solutions/, все/ |

### Основные понятия

- **План → Работа → Обзор → Составной цикл**: 40 % план, 10 % реализация, 40 % проверка, 10 % соединение.
- Правило **50/50**: половина времени на создание функций, половина на улучшение системы
- **Названные перспективные агенты**: Агенты, названные в честь известных инженеров (DHH, Кент Бек) в качестве кратких ссылок на мнения
- **Swarm Mode**: параллельный обзор специалистов по требованию, без предопределенной структуры команды
- **Мозговой штурм перед планированием**: проверьте существующие мозговые штурмы перед созданием плана, избегайте повторного решения уже решенных проблем.
- **Docs-as-memory**: Структурированная иерархия каталогов заменяет произвольное разрастание CLAUDE.md

### Производственный контекст

Compound Engineering работает в Every.to на Cora, их продукте для создания заметок и знаний на базе искусственного интеллекта. Киран Клаассен — инженер-основатель. Описанные шаблоны взяты из реальной базы кода, а не из теоретической основы.

## <a name="evaluation"></a>Оценка

### Оценка: 4/5 (ВЫСОКОЕ ЗНАЧЕНИЕ)

**Justification**:

1. **Достоверный источник**: Every.to — серьезная компания, занимающаяся искусственным интеллектом. Киран Клаассен — практик, а не блоггер. Плагин имеет открытый исходный код и содержит реальных агентов с реальными подсказками, а не маркетинговыми копиями.

2. **Портативные шаблоны**: именованные перспективные агенты, режим роя, контроль качества навыков и рабочий процесс «мозговой штурм перед планированием» — все они работают с любой настройкой Claude Code. Нулевая зависимость от самого плагина.

3. **Реальная реализация**: 29 агентов означают 29 реальных системных подсказок, которые вы можете читать и учиться. Большая часть контента Claude Code описывает шаблоны без демонстрации реальных реализаций. Здесь показан код.

4. **Новые шаблоны**: Именованные перспективные агенты и режим роя нигде в текущем руководстве не описаны. Оба они применимы немедленно и отличаются от существующих шаблонов (агенты, ориентированные на объем, команды агентов).

5. **Глубина философии**: Правило распределения 50/50 и лестница внедрения (этапы 0–5) представляют собой конкретные инструменты принятия решений, а не расплывчатые рекомендации.

**Почему бы не 5/5**:

- Никаких количественных показателей — никакого «улучшения на X%» в скорости доставки, коэффициенте обнаружения отзывов или проценте дефектов. Все претензии качественные.
- Именованные перспективные агенты основаны на мнениях — надежно ли агент DHH кодирует «толстые модели, тонкие контроллеры» зависит от обучения Claude, которое зависит от версии.
- Некоторые агенты короткие (менее 20 строк) и могут быть не более эффективными, чем хорошо продуманная встроенная подсказка.
- Многофункциональный AI-конвертер — самая новая функция, но она выходит за рамки данного руководства.

### Предостережения

- **Отклонение риска от названных персон**: Мнения DHH меняются. Статический «агент DHH» может устареть или отойти от своего текущего мышления по мере изменения обучающих данных Claude.
- **Swarm против Teams**: режим Swarm (специальный) и команды агентов (постоянные, скоординированные) решают разные проблемы. Их объединение является распространенной путаницей.
- **Установка плагина не требуется.**: Установка плагина добавляет в каждый проект 29 агентов + 22 команды, что может быть избыточно. Шаблоны работают и без него.

## Портативные выкройки

### 1. Названные перспективные агенты

Вместо обычных агентов-рецензентов назовите агентов в честь инженеров, чьи взгляды вы хотите представить:

```markdown
---
name: dhh-reviewer
description: Review code from DHH's perspective (Rails conventions, fat models, thin controllers, pragmatic REST)
---
```

Имя служит сжатой подсказкой — оно объединяет узнаваемый набор мнений в один токен, а не проговаривает их. Работает для: DHH (Rails, REST), Кента Бека (TDD, простота), Мартина Фаулера (рефакторинг, шаблоны).

**Constraint**: работает только для инженеров, взгляды которых были обучены Claude и чьи мнения соответствуют четкому, стабильному стилю.

### 2. Режим роя

Параллельная проверка по запросу несколькими специалистами без заранее определенной координации:

```bash
/slfg                      # Start swarm
/workflows:review --swarm  # Launch all relevant reviewers in parallel
```

В отличие от команд агентов (которые имеют постоянную структуру «ведущий + участники»), Swarm не имеет состояния: каждый рецензент получает PR/diff независимо, сообщает о результатах, а человек синтезирует. Подходит для: окончательной проверки перед слиянием, незнакомых областей кодовой базы, тщательности координации.

### 3. Врата качества навыков

Помимо проверки исходных данных, Compound Engineering определяет четкие критерии качества контента для навыков:

- Frontmatter должен включать имя, описание и разрешенные инструменты.
- Раздел «Когда подавать заявку» обязателен (необязательно)
- Методология должна быть структурирована (шаги, а не параграфы).
- Никаких TODO или языка-заполнителя.
- разрешенные инструменты сведены к минимуму
- Формат вывода должен быть документирован
- Нет AskUserQuestion в кроссплатформенных навыках.

### 4. Рабочий процесс «мозговой штурм перед планированием»

Прежде чем создавать план, проверьте, существует ли уже мозговой штурм:

```
docs/brainstorms/    <- Thinking documents (problem exploration)
docs/plans/          <- Active implementation plans
docs/solutions/      <- Solved problems with context
todos/               <- Task tracking
```

Инструкция агенту: «Прежде чем создавать план для X, проверьте docs/brainstorms/ на предмет существующих мнений по этой теме».
