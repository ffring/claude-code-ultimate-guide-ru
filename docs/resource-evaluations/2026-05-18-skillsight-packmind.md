## Краткое содержание

Skillsight — это автономная информационная панель, которая принимает телеметрию Claude Code OTEL и визуализирует, какие навыки фактически используются в команде или организации. Два пути приема: передача через OTLP HTTP/JSON (Claude Code → Skillsight напрямую) или получение через Loki (реле Grafana Cloud). Использование навыков отображается для каждого пользователя, для каждого сеанса, для каждого плагина, с когортной сегментацией.

**Что на самом деле поставляется (проверено по коду):**
- Панель мониторинга с диаграммами использования навыков, разбивкой по уровням команды и отслеживанием плагинов.
- Синхронизация с торговой площадкой: извлекает каталоги навыков из источников Git (GitHub PAT или на основе токенов).
- Аутентификация: JWT HS256 (jose) + хеширование пароля argon2, файлы cookie сеанса + отдельные токены приема.
- Страница событий SSE в реальном времени (`/live-events`)
- Журнал аудита всех административных действий
- Когортная сегментация (в плане, но уже реализована)
- Страница регистрации, на которой автоматически генерируется фрагмент Claude Code settings.json.

**Стек:** Bun monorepo, серверная часть Hono, Drizzle ORM + PostgreSQL, React 18 + Vite 7 + Tailwind 4 + Recharts. Шестиугольная архитектура. 28K LOC, 33 тестовых файла, Biome lint, CI на GitHub Actions (lint+test+build+docker), многоэтапный Dockerfile, Apache 2.0.

**Автор:** Седрик Тейтон, Packmind (см. также [#076](076-packmind-contextops-platform.md)).

## Рекомендации по интеграции

**Target:** `guide/ecosystem/third-party-tools.md` — новый подраздел «Наблюдаемость навыков»

**Когда интегрировать:** Теперь с явными оговорками. Повышение до полной рекомендации (4/5), когда будут устранены три критические проблемы (см. Условия ниже).

**Обрамление в руководстве:**
- Позиционируйте себя как единственный инструмент с открытым исходным кодом для отслеживания того, какие навыки Claude Code на самом деле использует ваша команда, а не те, которые, по вашему мнению, они используют.
- Обязательные предостережения:
  1. Никогда не развертывайте без переопределения `JWT_SECRET` и `ADMIN_PASSWORD_INITIAL` — значения по умолчанию общедоступны, и предупреждение во время загрузки не выдается.
  2. Запускайте миграцию Drizzle вручную при обновлениях, пока не будет добавлена ​​автоматическая точка входа.
  3. Установите `PUBLIC_BASE_URL` в `.env`, даже если не сбалансирована нагрузка — влияет как на политику CORS, так и на корректность встроенного фрагмента.
- Обратите внимание на соответствующую платформу Packmind ContextOps (eval #076) для распространения дополнительных стандартов.

**Условия повышения до 4/5:**
1. Ошибка загрузки или явное предупреждение, если `JWT_SECRET` соответствует поставке по умолчанию.
2. Отдельный `ENCRYPTION_KEY` для шифрования неактивных учетных данных (отдельно от ротации JWT).
3. Автоматическое выполнение миграции Drizzle при запуске контейнера

## Выводы по безопасности (резюме аудита)

Перед самостоятельным размещением любому оператору стоит сообщить о четырех выводах:

**Риск дефолта при развертывании.** `JWT_SECRET=change-me-in-production-please-at-least-32-chars` и `ADMIN_PASSWORD_INITIAL=admin` — это буквальные значения по умолчанию в `docker-compose.yml`. Нет предупреждения во время загрузки. Проверка Zod принимает значение JWT по умолчанию, поскольку оно соответствует минимальному количеству символов. `docker compose up` без `.env` создает экземпляр с полным доступом за секунды. README предупреждает, но ничто не обеспечивает его соблюдение во время выполнения.

**Общий ключ шифрования.** `JWT_SECRET` также является ключом шифрования для хранения учетных данных Loki и GitHub (`encrypt.ts`: `getKey() = SHA-256(JWT_SECRET)`). Изменение секрета JWT (поддерживается через `JWT_SECRET_PREVIOUS`) автоматически делает все сохраненные учетные данные нерасшифрованными. Утечка секрета JWT также раскрывает внешние учетные данные. Отсутствие AAD для каждой строки означает, что хранимые большие двоичные объекты взаимозаменяемы при интеграции.

**Permissive CORS.** `PUBLIC_BASE_URL` по умолчанию повторяет источник запроса с помощью `credentials: true` (`app.ts:55-65`). Этой переменной нет в `.env.example`. Администратор, подключенный к экземпляру Skillsight и посещающий страницу, контролируемую злоумышленником, может получить перекрестный запрос от администратора API.

**Ограничение скорости отсутствует.** Ни `/api/auth/login`, ни конечная точка приема OTLP `/api/v0/telemetry/v1/logs` не имеют ограничения скорости. Размер тела в конечной точке приема не ограничен.

## Основные моменты архитектуры

Шестиугольная архитектура реальна, а не карго-культ: порты — это интерфейсы, варианты использования зависят от абстракций, тестовое покрытие использует подделки в памяти со значимыми поведенческими утверждениями. Схема PostgreSQL имеет соответствующие ограничения (FK, NOT NULL, функциональные индексы, включая частичные индексы JSONB).

Стоит отметить три структурные проблемы:

- В конвейере приема нет транзакции БД, которая завершает 6 последовательных шагов обновления — частичный сбой автоматически создает противоречивое состояние.
- Планировщики Loki и Marketplace глотают ошибки с помощью `.catch(() => {})` — неудачная интеграция не оставляет следов в журналах или пользовательском интерфейсе.
- Конфигурация источника Marketplace фиксируется во время создания расписания (устаревает после любого редактирования пользовательского интерфейса до перезапуска).

## Документы и выводы DX

Две проблемы напрямую блокируют первоначальную настройку:

1. **Несоответствие имени изображения**: README использует `ghcr.io/packmindhub/skills-obs:latest` в 7 местах. Фактический образ `docker-compose.yml` — `ghcr.io/packmindhub/skillsight:latest`. Пользователи, следуя инструкциям по быстрому запуску, сразу же столкнутся с этим.

2. **OTLP несоответствие переменной конечной точки**: README документирует `OTEL_EXPORTER_OTLP_ENDPOINT` (общий). Пользовательский интерфейс регистрации генерирует `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` (зависит от журналов, более высокий приоритет). Два источника, разные результаты конфигурации.

В остальном процесс адаптации хорошо продуман: страница пользовательского интерфейса автоматически генерирует полный фрагмент `settings.json` с предварительно созданным токеном приема. Время ввода в эксплуатацию для подготовленного разработчика: 30–75 минут в зависимости от того, устранены ли вышеперечисленные проблемы.
