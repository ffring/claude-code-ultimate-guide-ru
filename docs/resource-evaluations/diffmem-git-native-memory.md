## Оценка: 3/5 (средний, только пример)

**Decision**: Интеграция в качестве примера и концепции в `guide/core/memory-systems.md` §3.7, а не в качестве рекомендуемого инструмента. Документально подтвержденная идея — это **LLM-агент git-shell извлечения** (LLM, который ищет и обвиняет репозиторий вместо запроса к какому-либо индексу), момент в области проектирования памяти, который не был затронут в руководстве. Не рекомендуется внедрение: коэффициент шины один, файл лицензии отсутствует, ядро ​​извлечения не тестировалось и переписывается. Оставьте один острый момент обучения (извлечение соответствия форме запроса) и два примитива многократного использования.

## Идея перевернута: DiffMem удалил BM25.

Исходное предположение (из опроса Perplexity) было «Markdown + Git + BM25 в памяти». Это уже не относится к коду. Commit `c4fe4a3` («извлечение на основе git») удалил весь модуль `bm25_indexer/` (реальная реализация `rank_bm25.BM25Okapi`, 114 строк, с собственной меткой «минимальный PoC») и заменил его агентом командной оболочки, управляемым LLM. В текущем README это указано дважды (README:9, README:345): «Никаких векторных баз данных, никаких вложений, никакого BM25, только git и LLM». Старый BM25 можно восстановить только через `git show c4fe4a3^:src/diffmem/bm25_indexer/indexer.py`.

Это важно для нашего собственного контекста: DiffMem не является проверкой подхода «файл плюс BM25». Они попробовали это и пошли дальше, к полному извлечению LLM. Для формы лексического запроса (строки ошибок, символы) это, возможно, неправильное направление. См. раздел обучения ниже.

## Что это такое (проверено по коду)

- **Storage**: файлы Markdown в репозитории git, настоящий многопользовательский макет. В одном центральном репозитории каждый пользователь хранится как ветка **orphan** `user/<id>`, смонтированная через `git worktree` (`local_storage.py:83-111`). Сиротские ветки не имеют общей истории, поэтому изоляция — это настоящая гарантия git, а не соглашение о папках. Файлы для каждого пользователя: `<user>.md`, `memories/{people,contexts}/*.md`, `timeline/YYYY-MM.md`, автоматически генерируемые `index.md`. Frontmatter — это YAML, анализируемый с помощью чистого PyYAML, без LLM (`frontmatter.py:23-56`).
- **Retrieval**: алгоритм ранжирования вообще отсутствует. `run_retrieval_agent()` (`retrieval_agent/agent.py:197-308`) запускает цикл вызова инструмента LLM (по умолчанию 4 оборота) ровно с одним инструментом, `run(command=...)`. Модель поддерживает команды из белого списка (`cat, head, tail, grep, ls, wc, git log/diff/blame/show/rev-list`) через `command_router.py`, ограничение вывода 150 строк / 30 КБ, тайм-аут 10 с, выполняется через `subprocess.run(shell=True)` (`command_router.py:265`). Детерминированная базовая линия без LLM загружает объект пользователя плюс пять последних файлов временной шкалы (`baseline.py`, строка документации: «Нет BM25, нет внедрений, нет вызовов LLM, чистое чтение файлов»).
- **Временная/дифференциальная память**: проводная, но управляемая LLM. История Git — это запрашиваемые данные, которые агент извлекает по требованию (`git blame`, чтобы определить, когда факт последний раз менялся). `_link.py:29-56` консолидатора выполняет программный анализ совместных изменений: он просматривает недавние коммиты для построения графа совместного появления сущностей, затем LLM предлагает вики-ссылки. Настоящий дифференциальный сигнал LLM для записи.
- **Machinery** (основное или дополнительное): ядро — это библиотека Python (`DiffMemory` в `api.py`) с зависимостями **4** (запросы, openai, gitpython, python-dotenv). Вокруг него: агент записи (1276 строк, самый большой файл), консолидатор (4 инструмента: dedupe/link/redistribute/reabsorb, ~1300 строк), подключаемый исполнитель (`inline` по умолчанию, `hatchet` устойчивая очередь опционально), сервер FastAPI на 890 строк, подключаемые онтологии (personal/corporate). Дополнительные слои скрыты за переменными окружения и `requirements-server.txt`. Раскол core/server честный.

## Единственный учебный момент, который стоит сохранить: сопоставление извлечения с формой запроса.

DiffMem собрал BM25, а затем удалил его для полного извлечения LLM. Это реальный сигнал, и причина поучительна. Запросы DiffMem — это **вопросы на естественном языке о людях, событиях и отношениях** (собеседник, вспоминающий «что пользователь сказал о своей сестре в марте»). Это форма семантического запроса, в которой ключевое слово BM25 неэффективно, а рассуждения entity/temporal имеют значение, поэтому они переросли в LLM, который может `git blame` и рассуждать.

Обратное справедливо для системы retex кодирующего агента: запросы представляют собой строки ошибок **, трассировки стека и символы кода**, форма лексического запроса, в которой перекрытие терминов велико, и BM25 не просто достаточен, он часто лучше, чем встраивания, и намного дешевле, чем цикл LLM. Таким образом, отказ DiffMem от BM25 не является доказательством того, что BM25 неправ. Это свидетельствует о том, что поиск **должен соответствовать форме запроса**. Та же подложка (файлы + git), противоположный выбор извлечения, потому что запросы разные. Это самый острый и наиболее переносимый урок из всего анализа, и он заслуживает внимания в руководстве.

## Паттерны, которые стоит извлечь (для руководства и для системы ретекса)

1. **LLM-агент получения git-shell** (`command_router.py`, `retrieval_agent/agent.py`). Вместо поискового DSL или индекса укажите LLM `grep` + `git log/blame/diff` за белым списком базовой команды, усечением вывода и тайм-аутом. Около 351 строки для очень гибкой поверхности поиска и `git blame`Стиль «когда это было правдой в последний раз» предоставляется бесплатно. Роман против руководства. Предостережение к документу: проверка на уровне аргумента отсутствует (только `tokens[0]` проверяется перед `shell=True`), так `$(...)` внутри аргумента представляет собой реальный риск внедрения, если он когда-либо подвергается воздействию ненадежных входных данных.
2. **Orphan-ветвь для каждого пользователя + изоляция рабочего дерева** (`local_storage.py:83-111`). Реальная изоляция файловой системы и истории между арендаторами с одним общим хранилищем объектов, более чистая, чем «одна папка на пользователя».
3. **Frontmatter в качестве поверхности запроса, проза в качестве полезной нагрузки** (`frontmatter.py`). Структурированные запрашиваемые поля в YAML, описание в теле. Непосредственно сопоставляется с файлом retex: `severity`, `tags`, `prevention_rule` во вступительной части, история в теле.
4. (Незначительный) **PID-файл блокировки с восстановлением устаревшего состояния** (`lock.py`) и **commit, отделенный от удаленного резервного копирования** (`repo_manager.py:97-117`). Хорошие минимальные примитивы для файловой памяти, работающей как служба.

Явно стоит копировать **not**: режим без LLM. Каждое чтение и запись осуществляется через OpenRouter (`api-surface.md:9-10`), запись занимает 60–600 с, чтение 5–30 с, по цене за операцию. Для системы retex, постоянно запрашиваемой во время отладки, фильтр keyword/BM25/frontmatter-tag позволяет избежать задержки и затрат.

## Слабые стороны

- **Bus Factor one**: Alex / Growth Kinetics — это 78% из 60 коммитов под 7 псевдонимами git. Если Алекс остановится, проект остановится.
- **Пробел в лицензии**: MIT заявлен только в классификаторе pyproject, файл LICENSE отсутствует, GitHub не обнаруживает лицензию. Юридический блокатор усыновления.
- **Ядро извлечения не тестировалось и находится в процессе изменения.**: компонент с наибольшим радиусом действия (LLM, свободно генерирующий команды оболочки) имеет нулевое тестовое покрытие, а ветвь `rebuilding-retrieval` открыта. Не стройте на движущейся, непроверенной части.
- **Неверный консольный скрипт**: `pyproject.toml:62` объявляет `diffmem = "diffmem.cli:main"`, но `cli.py` не существует. `pip install -e . && diffmem` вылетает.
- **«Производство» перепродано**: производство для одной рабочей нагрузки (Аннабель), дорожная карта признает, что стратегия индексирования PoC все еще нуждается в усилении (слишком интенсивно использует память), «нулевые внешние зависимости» противоречит обязательному LLM API, «50-летняя долговечность» не имеет подтверждающих данных.

## Для угла retex/smart-suggest-routing

DiffMem подтверждает контрпримером, что существующий механизм маршрутизации интеллектуальных предложений **BM25** является подходящим инструментом для формы retex-запроса (строки лексических ошибок) и что DiffMem не является конкурентом для копирования. Идея многократного использования из DiffMem — это уровень **escalation**: BM25 или фильтр frontmatter-tag в качестве дешевого значения по умолчанию, а LLM-агент git-shell проходит только в случае отсутствия лексического соответствия. Это прагматичный гибрид, построенный на уже находящемся в производстве движке, а не на стеке с одним сопровождающим, предназначенном только для клонов DiffMem и требующем LLM.
