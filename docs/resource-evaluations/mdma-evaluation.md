## Управляющее резюме

MDMA — это проект с открытым исходным кодом, определяющий диалект Markdown со встроенным YAML для интерактивного пользовательского интерфейса (форм, кнопок, таблиц, шлюзов утверждения), предназначенный для надежного создания небольшими или тонко настроенными LLM и детерминированной проверки перед рендерингом. Три независимых агента по аудиту изучили дерево исходного кода и пришли к единому мнению: базовая разработка (парсер, валидатор, конвейер исправлений, методология оценки) действительно надежна, но несколько маркетинговых заявлений не выдерживают контакта с кодом, а в поставляемом компоненте формы есть реальная функциональная ошибка.

**Почему 3/5**: Архитектуру validator/fixer и честную структуру оценки стоит задокументировать в качестве эталонного шаблона для всех, кто строит аналогичный конвейер надежности вывода малых моделей. Но разрыв между заявленным и фактическим поведением (компонент формы, чьи «обязательные» поля не обязательны, «работает где угодно», что не применимо к рендерингу, некриптографические хэши, продаваемые вместе с ключевыми словами «audit-log»/«pii») означает, что это не рекомендация «перейти к использованию этого в производстве» без предварительного самостоятельного устранения пробела в проверке.

## Контент-анализ

### Ключевые факты (проверенные)

1. **Детерминированный конвейер validator/fixer**: один проход, без дополнительного вызова LLM, извлечение на основе регулярных выражений, допускающее некорректную уценку, 22 файла правил в `packages/validator/src/rules` (19 задокументированы в README, 22 учитываются в исходном коде во время аудита), упорядоченные исправления для вывода типа поля, опечатка ключа YAML коррекция и ремонт переплета.
2. **Стандартный синтаксический анализ**: построен на remark/unified как полноценный плагин с явной обработкой состояния потоковой передачи (отличает блок, который все еще генерируется, от блока, который действительно искажен).
3. Методология **Eval**: использует Promptfoo с пользовательскими утверждениями, документированными в формате «не 100%, наблюдения, а не выводы» в `evals/own-model/README.md`. Измеренный результат: 41% успеха с простым приглашением по сравнению с 90,5% с DSL и валидатором вместе взятыми, с их собственной точно настроенной моделью, обслуживаемой через Modal/Hugging Face.
4. **«Запускается где угодно» для основных пакетов.**: Пакеты `spec`, `parser`, `validator` и `runtime` не содержат импорта, специфичного для узла (`fs`, `path`, `crypto`), что подтверждается grep во всех четырех деревьях исходного кода пакета.
5. **CI гигиена**: GitHub Actions закреплен с помощью SHA фиксации в `.github/workflows/ci.yml` и `release.yml` (например, `actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6`), управление версиями каждого пакета на основе наборов изменений, набор тестов `turbo run test`, охватывающий все пакеты.
6. **Структура пакета**: 10 пакетов (`spec`, `parser`, `validator`, `runtime`, `attachables-core`, `renderer-react`, `cli`, `mcp`, `agui`, `prompt-pack`), каждый из которых имеет независимые версии и опубликован под `@mobile-reality` npm org.

## Ошибка проверки формы (обнаружена независимо двумя агентами аудита)

Это наиболее важный вывод, поскольку он противоречит собственной документации проекта, а не маркетинговому слогану.

- `FormRenderer.tsx` оборачивает каждое поле в простой `<div className="mdma-form">`, а не в элемент `<form>` (`packages/renderer-react/src/components/FormRenderer.tsx`, строка 152).
- Элементом управления отправки является `<button type="button">` с `onClick`, который отправляет действие `ACTION_TRIGGERED` напрямую, минуя любое событие отправки формы (тот же файл, строки 119-125 и 247-258).
- Встроенная проверка ограничений HTML5 (атрибут `required`, передаваемый каждому входу) срабатывает только при фактическом событии отправки формы. Поскольку нет кнопки `<form>` и `type="submit"`, она никогда не срабатывает.
- Объект `validation` уровня поля (`pattern`, `min`, `max`, `message`) определен в схеме по адресу `packages/spec/src/schemas/components/form.ts` (строка 18) и нигде не считывается ни в средстве визуализации, ни в обработчике формы Attachables-Core (`packages/attachables-core/src/form/form-handler.ts`).
- `docs/reference/component-catalog.md` документирует этот точный объект `validation` с помощью рабочего примера (`pattern`, соответствующий домену электронной почты компании, строки 71–72), и та же конструкция появляется в собственном `examples/approval-workflow/document.md` репозитория.

**Net effect**: поле, отмеченное `required: true` с ограничением `pattern`, может быть отправлено пустым или несоответствующим, без отображения ошибки пользователю, несмотря на то, что в документации это представлено как рабочее поведение с конкретными примерами, взятыми из самого репозитория. Это по сути отличается от пробела в вебхуке, который честно указан как будущая работа в дорожной карте проекта. Пробел в валидации нигде не раскрывается.

## Рекомендации по интеграции

### Где

**Раздел 7.1** в `guide/ecosystem/ai-ecosystem.md`, сразу после раздела 7 (Прототипы пользовательского интерфейса) и перед разделом 8 (Оркестрация рабочих процессов).

### Что было включено

1. Почему существует категория генеративного пользовательского интерфейса (агенту нужен интерактивный вывод внутри одного хода чата, а не отдельный артефакт)
2. Таблица сравнения: A2UI, MCP Apps, Vercel AI, генеративный пользовательский интерфейс SDK и MDMA
3. Практический пример MDMA: что верно, что преувеличено, ошибка проверки формы, примечание по безопасности хэша
4. Честное замечание: категория молодая (2025–2026 гг.), ни один стандарт не победил, а распространение (за которым стоит поставщик) имеет такое же значение, как и технические качества.

### Что НЕ было включено

- Никаких учебных пособий или инструкций «Как принять MDMA». В этом руководстве документирован Claude Code, а не рекомендация использовать конкретный сторонний DSL.
- Никакого глубокого погружения в план интеграции MDMA-AG-UI (`mdma-agui-integration-plan.md`), он слишком умозрительный и находится на стадии предварительной реализации, чтобы ссылаться на него как на факт.
- Никакое сравнение с MCP-UI (отдельный, связанный, но отдельный проект, на который ссылаются соавторы MCP Apps), выходит за рамки данной оценки.

### Приоритет

**Умеренный**. Это не срочно (без этого ни одна программа чтения не блокируется), но реальный пробел в содержании: в руководстве подробно рассматриваются приложения MCP, но нет ничего по сравнению с A2UI, шаблоном Vercel AI SDK или MDMA, и ничего об этом конкретном шаблоне надежности для создания пользовательского интерфейса для малых моделей.

## Челлендж (технический писатель)

- **Оценка оправдана**: правильно 3/5, а не 4/5, потому что практический вывод для пользователя Claude Code ограничен (MDMA — это сторонняя библиотека для определенного стека рендеринга, предназначенная только для React, а не то, что большинство читателей примут напрямую). Не 2/5, потому что архитектура validator/fixer и честная методология оценки малых моделей являются действительно полезным эталонным шаблоном, а более широкое сравнение генеративного пользовательского интерфейса само по себе (A2UI против MCP Apps против Vercel AI SDK против MDMA) было настоящим пробелом, который стоит закрыть, независимо от собственных недостатков MDMA.
- **Риск перекредитования**: первоначальный проход агентов аудита был склонен к похвале за разработку валидатора без достаточного взвешивания ошибки проверки формы. Эта ошибка исправлена ​​в первом счете в тексте тематического исследования именно потому, что она противоречит документированному поведению, что является более серьезной категорией проблем, чем амбициозная маркетинговая линия.
- **Оценка скорректирована**: 3/5 (не изменилась после испытания).
