## Краткое содержание

Fusion позиционирует себя как «фабрику программного обеспечения, управляемую мультиагентным оркестратором». Конкретно: монорепозиторий pnpm TypeScript (12 пакетов, 18 связанных плагинов), который управляет агентами кодирования AI по канбан-доске, одно рабочее дерево git на задачу, с информационной панелью реального времени, настраиваемым механизмом рабочего процесса и плагинами среды выполнения для подключения сторонних интерфейсов командной строки.

Сосуществуют две иерархии доменов, которые скрывает структура канбана README:

- **Task** на доске: `triage` (показано как «Планирование») — `todo` — `in-progress` — `in-review` — `done` — `archived`, каждая задача изолирована в рабочем дереве `fusion/{task-id}`.
- **От миссии к этапу, от фрагмента к объекту**, с автопилотом, активирующим следующий фрагмент, когда завершается текущий, и с утверждениями контракта (введенными критериями приемки), проверяемыми запуском валидатора.

Четыре адаптера CLI имеют встроенную телеметрию (Claude Code, Codex, Droid и Pi, собственный CLI). Cursor и Grok существуют, но в отдельной, более слабой категории («плагины среды выполнения», без структурированной телеметрии). Автономия — это настройка, а не доктрина: `planner oversight` принимает `off`, `observe`, `steer`, `autonomous`, по умолчанию — `autonomous`. Единственные непроходимые человеческие ворота — это слияние, плюс деструктивные или внешнеслужебные действия.

## Единственная идея, которую стоит принять: состязательная проверка с двойной проверкой.

`packages/engine/src/mission-verification.ts` (986 строк) реализует самый точный ответ, который мы когда-либо видели, на основную проблему кодирования с помощью ИИ: **— агент, который объявляет «готово» неработающему коду**.

Механизм, проверенный в коде:

- Судья ИИ, доступный только для чтения, явно **подчиненный**, не авторитетный (строки 4–6): «Судья ИИ, доступный только для чтения, не может запускать код, поэтому его «передача» поведенческого утверждения носит только рекомендательный характер».
- Настоящая одноразовая касса: `fs.mkdtemp(os.tmpdir(), "fn-verify-")`, затем `git worktree add --detach <tmp> <revision>` (строки 338-341). Ни живое рабочее дерево, ни корень репо.
- **Античит** (строка 26, логика вердикта в строке 555): предоставленный агентом регрессионный тест должен **FAIL** на второй одноразовой проверке в базе слияния (перед исправлением) и передать реализацию. Тест, который проходит обе стороны, ничего не доказывает и отклоняется. Это убивает `expect(true).toBe(true)` как способ сделать задачу зеленой.
- Три типизированных вердикта (строка 63): `pass | fail | inconclusive`. `inconclusive` маршрутизируется всякий раз, когда инфраструктура не может завершиться, и никогда не сворачивается в `fail` (строка 581), поэтому нестабильный CI не приводит к оттоку исправлений.

**Этот модуль является мертвым кодом в производстве.** `mission-execution-loop.ts` импортирует его только `import type` (строки 28 и 112). Реальная реализация импортируется тремя тестовыми файлами и ничем больше. `verificationCapability` никогда не подключается к единственной точке создания экземпляра (`runtimes/in-process-runtime.ts:543-570`), и код обрабатывает этот случай, оставляя поведенческие утверждения неудачными (строка 813). История Git: создан 12 июня 2026 г., последнее изменение 19 июня 2026 г., всего 5 коммитов.

Изготовлен, протестирован, никогда не отправлялся. Шаблон остается превосходным и имеет лицензию MIT, поэтому его можно напрямую копировать.

## Уровень безопасности: по умолчанию слабый на всех трех уровнях.

| Слой | Реальная защита по умолчанию |
|---|---|
| Выполнение агента | Никто. `sandbox.backend = native` по умолчанию. Бэкэнд bubblewrap существует, но он доступен только по согласию и только для Linux (`docs/sandbox.md`). Рабочее дерево является единственной границей. |
| Сердцебиение агента | Никто. `agent-heartbeat.ts:595` — это буквальная системная подсказка, предоставляющая «инструменты рабочего пространства с возможностью кодирования (read/write/edit/bash)». Реальный список разрешений только для чтения (`workflow-step-tool-policy.ts:4-25`, повышение `ReadonlyViolationError`) охватывает только шлюзовые узлы этапов рабочего процесса. Ноль вхождений `toolMode` в `agent-heartbeat.ts`. |
| Плагины | Никто. Плагины запускаются в процессе Fusion. Два барьера (сканирование AI при загрузке, проверка подписи) являются необязательными и отключены по умолчанию. |

Схема последовательна: механизмы закрытия при сбое в старом пути рабочего процесса, безопасность по запросу в новом пути агента. Типично для проекта, который реализуется быстрее, чем затвердевает.

## Решение

**Интегрировать в качестве примера в течение недели. Не рекомендую в качестве инструмента.**

Три ракурса, которые можно перенести в руководство:

1. **Модель двойной кассы** заслуживает отдельного раздела. Это конкретный ответ на ловушку «декоративного CI», уже описанную в `guide/workflows/spec-first.md:979-988`, а также на статью «Опровергать или продвигать» (arXiv:2604.19049), цитируемую там же. Fusion предоставляет читаемую эталонную реализацию, лицензированную MIT.
2. **Fusion как выход на рынок** в `guide/ecosystem/agentic-tools.md`, в категории оркестраторов, с явным предупреждением о ранней предварительной версии и коэффициенте шины 1.
3. **Непроизвольный урок, который является самой ценной частью.** Fusion доказывает, что один разработчик с агентами может поставить 727 тысяч строк менее чем за 4 месяца. Это также доказывает, что это дает: документацию, описывающую продукт, которого еще не существует, протестированный, но неподключенный код, файл размером 19 КБ и два параллельных хранилища. Это не «как построить фабрику программного обеспечения». Это **, что происходит, когда скорость агента не ограничена никакой архитектурой**. Никто это не документирует, а измерения здесь взяты из первых рук.

## Примечание к методу

Первый проход статистики git вернул ложную дату первой фиксации (13 июля 2026 г.) и подозрительно округленное значение «50 коммитов», поскольку локальный прокси-сервер сжатия токенов RTK усекает выходные данные команды. Повторный запуск `rtk proxy` привел к реальной истории. Об этом стоит помнить при любых будущих измерениях состояния репо в этой среде.

Также стоит помнить: `import type` и `import("...").Type` стираются во время компиляции и не доказывают отсутствия связи во время выполнения. Проверка существования файла или даже его импорта ничего не говорит о том, запускается ли он. Именно это различие отличает рекламируемый уровень проверки Fusion от его фактического поведения, и, вероятно, это общая ловушка для всего рынка.
