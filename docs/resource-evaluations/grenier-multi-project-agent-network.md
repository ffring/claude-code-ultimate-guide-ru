## Краткое содержание

Автор запускает агентскую сеть, построенную на **Pi** (сторонняя обвязка, состояние под `~/.pi/`), а не на собственных примитивах Claude Code. До этой недели в каждом проекте был один оркестратор, делегировавший функции субагентам (кодер, бегун, разведчик, куратор памяти) без канала между оркестраторами. В статье документируется переход к многопроектной работе, обеспечиваемый уровнем двунаправленного обмена сообщениями.

**Transport**: сокеты unix под `~/.pi/coms/sockets/`, реестры для каждого проекта, конверты JSON (`prompt`, `response`, `ping`, `nudge`), подтверждения и ограничение в пять переходов. Представленные инструменты: `coms_send`, `coms_get`, `coms_await`, `coms_reply`, `coms_check`.

**Центральный агент**: метаоркестратор `.pi`, который явно ничего не пилотирует. Организаторы проекта отправляют ему жалобы, которые он сортирует по четырем категориям (Двусмысленность, Ложная информация, Борьба, Предложение), передает сортировку человеку на проверку, делегирует реализацию, а затем проверяет, читая результат, а не доверяя отчету.

**Исправления, встроенные в `~/.pi/extensions/`**: `coms.ts` повторно определяет отправителя во время `coms_reply`, сохраняет ожидающие сообщения по тайм-ауту, увеличивает срок жизни входящих сообщений с 5 до 30 минут, кэширует уже доставленные ответы и обнаруживает неработающего или сменившегося получателя. Автоматическое подталкивание через 5 минут. `pi-delegate.ts` поддерживает файл состояния JSON для каждого делегата (предварительный просмотр вывода, шаги, код выхода) для неблокирующего контроля.

**Заявленный масштаб**: в работе пять-шесть проектов. Автор ясно дает понять, что это еще не настоящий параллелизм и что следующим шагом станут координаторы домена (агенты, владеющие набором проектов, а не одним).

## Что действительно полезно

Два пункта являются конкретными, переносимыми и отсутствуют в руководстве.

**Правило управления.** «Если вы управляете агентом, который развивается, то это агент, который прогрессирует». Усвоил на собственном горьком опыте: бычок с благими намерениями делал петлю бегуна примерно 10 минут, отвечая на сообщения, вместо того, чтобы продвигаться вперед. Это правило противоречит здравому смыслу, оно является общим для любой системы контролируемого агента и требует больших затрат на его обнаружение в одиночку. В статье приведены обратные случаи, когда управление было правильным: бегун застрял на 12 минут при написании сценария, так и не выполнив его (объявлен неудачным и перезапущен), цикл grep, который уничтожил сам себя (перенаправлен в пять строк, «исправления PID, па-де-букле»), бегун `cache:clear` дрейфовал 22 секунды в бесполезном обнаружении каталога (переотправляется с абсолютным рабочим каталогом: 18 секунд, выход 0).

**К агентам применяется шаблон с одной записью.** Куратор памяти внешнего интерфейса не имеет разрешения на запись. После создания трех элементов он запросил по шине сообщений своего оркестратора удалить пакет из плана оркестрации. Запись выполнял оркестратор. Результат: нет дубликатов, нет конфликтов записи. Это стандартный принцип одного записывающего устройства, перенесенный в контекст редактирования файла с участием нескольких агентов, и это прямое смягчение режима отказа из-за конфликта записи, который возникает, когда несколько агентов совместно используют файл плана.

Стоит отметить третью деталь, которая сама по себе не является шаблоном: метаоркестратор проверяет делегированную работу, считывая артефакт, а не по слову делегата. Редкая дисциплина, дешевая в освоении.

## Претензия на новизну не имеет силы.

В статье говорится, что «le multi-projet / multi-repo comme unité d'orchestration de premier ordre n'apparaît nulle part dans la Litérature» и что центральный мета-оркестратор, опрашивающий своих суб-оркестраторов для улучшения инструментов, - это «réellement nouveau comme Pattern nommé de bout en bout».

Процитированные источники объясняют этот пробел: LangGraph (январь 2024 г.), групповой чат AutoGen, Metaswarm (февраль 2026 г.), Microsoft Agent Framework A2A (апрель 2026 г.), а также три общие страницы оркестровки на французском языке. Поиск охватывал корпоративные и академические мультиагентные платформы и пропустил всю волну оркестраторов агентов кодирования 2026 года.

| Требовать | Counter-evidence |
|---|---|
| Двунаправленный обмен сообщениями между оркестраторами — недостающее звено | Claude Code **Команды агентов** поставляют почтовый ящик с настоящим одноранговым обменом сообщениями между товарищами по команде, изолированным контекстом 1M на каждого агента (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). Задокументировано в `guide/workflows/agent-teams.md:207-219` после исправления от 09 февраля 2026 г. Межсеансовый `SendMessage` стал полноценным одноранговым сеансовым обменом сообщениями в выпусках за июль-август 2026 г. (`guide/core/claude-code-releases.md`, 16 случаев). |
| Мультипроект/мультирепо как первоклассная единица оркестровки недокументирована. | `github.com/steveyegge/gastown` координаты Claude Code, Второй пилот, Codex и Gemini в отдельных рабочих пространствах с сохранением состояния git-hook. ComposioHQ/AgentWrapper's `agent-orchestrator` описывает себя как «Организовать параллельные агенты кодирования ИИ в любой среде выполнения, **любое репо**, любой трекер проблем" (уже оценено: `docs/resource-evaluations/agent-orchestrator-composio.md`). OpenAI **Симфония** (Apache-2.0, апрель 2026 г.) изолирует рабочую область для каждой проблемы. |
| Метаагент, улучшающий свой собственный уровень делегирования, представляет собой новый именованный шаблон. | **Hermes** запускает цикл GEPA: после каждой задачи он анализирует, что сработало, извлекает повторно используемые шаблоны и автоматически генерирует навыки. Задокументировано в `guide/ecosystem/agentic-tools.md:121-142`. По сообщениям сообщества, ускорение работы увеличивается на 40 % при накоплении более 20 навыков. |
| Центральный координатор, который осуществляет диспетчеризацию, не выполняя работу по домену | Координатор **Hub-and-Spoke** в `guide/workflows/agent-teams.md:1526` дословно заявляет то же самое ограничение: «Он сам не выполняет ни доменной работы, ни исследований, ни анализа, ни генерации». Также `guide/core/architecture.md:648` |

То, что может оставаться оригинальным, уже, чем заявлено, и его стоит сохранить: таксономия жалоб **по четырем категориям** (двусмысленность, ложная информация, борьба, предложение), человеческая проверка такого рода перед любой реализацией и проверка обратного чтения. Это методологический вклад, а не новая архитектура.

Автор хеджирует («je le dis prudemment, ce n'est pas une preuve d'unicité absolue»), и это честно, и формулировка здесь должна учитывать это, а не рассматривать это утверждение как утверждение факта.

## Технические слепые зоны

Уровень отказоустойчивого обмена сообщениями **A перестраивается с нуля.** Посмотрите на список исправлений: TTL увеличен с 5 до 30 минут, кеш уже доставленных ответов, повторное разрешение отправителя во время ответа, обнаружение неработающего или повернутого получателя, автоматическое перемещение через 5 минут, ограничение в пять переходов, молчаливые недоставленные письма, подтверждения. Это канонические проблемы распределенного обмена сообщениями, решаемые с 1980-х годов. NATS, Redis Streams или ZeroMQ предоставляют все это, включая идемпотентность и постоянство. Ограничение в пять переходов — это TTL пакета под другим именем. Проблема «номеров оркестраторов, которые не соответствуют сеансу» — это нестабильная идентичность, стандартным решением которой является реестр с идентификатором, отделенным от имени сеанса.

**Стоимость нигде не указана.** Пять-шесть действующих проектов, в каждом из которых есть оркестратор и субагенты, все обмениваются сообщениями, а также мета-оркестратор, опрашивающий всех. `guide/workflows/agentic-software-factories.md:35` помещает команды агентов в **3x или более в токенах** по сравнению с одним агентом, а сетка между оркестраторами умножает это снова. В сопоставимых публичных отчетах о местах указываются их цифры (u/croovies показывает доллары за сеанс, другой практик показывает $115/day по ставкам API). Здесь не указано ничего, и это первый вопрос, который задаст любой читатель.

**Ограничение прыжков не является обнаружением петель.** Пять прыжков ограничивают длину цепочки, а не циклов. Три оркестратора, повторно запуская друг друга по сквозной проблеме, каждый раз сжигают квоту по кругу короткими цепочками. Идентификатор диалога плюс бюджет токенов для каждого дерева обмена закроют это.

## Решение

**Частичная интеграция в `guide/workflows/agent-teams.md`, раздел «Расширенные шаблоны оркестровки» (строка 1526).**

1. **Правило управления** в виде именованного подраздела: перенаправить дрейфующего агента, а не прогрессирующего. Включите контрпример (управление здорового бегуна стоило ~10 минут ответа на сообщения вместо работы) и положительные случаи (12-минутный невыполняющий бегун, самозавершающийся цикл grep, 22-секундное смещение рабочего каталога). Источник-атрибут статьи.
2. **Шаблон с одним записывающим устройством для файлов общего плана**: агент только для чтения запрашивает запись по шине сообщений, оркестратор выполняет ее. Подключите его к существующему разделению read/write, уже описанному для агентов-следователей, и к `guide/core/memory-systems.md:740` (многоагентная общая память).

**Не интегрировать**: заявление о новизне, транспортная архитектура (пять прыжков, реестр сокетов, настройка TTL) и структура метаоркестратора. Первое противоречит собственному содержанию руководства, второе представляет собой повторную реализацию стандартных примитивов обмена сообщениями, а третье дублирует Координатор Hub-and-Spoke, уже задокументированный в том же файле.

**Необязательное упоминание в одну строку.**: таксономия жалоб по четырем категориям с проверкой человеком такого рода, как упрощенный метод подачи сообщений о трении, сообщаемых агентом, обратно в инструменты. Подходит для `guide/roles/agent-evaluation.md` вместе с существующими материалами по самосовершенствованию навыков, а не для команд агентов.

**Вернитесь к триггеру**: расширения com и делегирования `.pi` публикуются по лицензии, данные о затратах раскрываются для настройки пяти-шести проектов, или объявленные координаторы домена поставляются с документированным механизмом арбитража (который действительно выходит за рамки того, что сегодня охватывают команды агентов и Gas Town).
