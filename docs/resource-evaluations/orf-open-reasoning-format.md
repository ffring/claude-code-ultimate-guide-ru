## Оценка: 2/5 (Маргинальный)

**Примечание (доработка после испытания)**: первоначальная оценка была 3/5.. Скептический обзор показал, что новизна была завышена. `memory-systems.md` §3.1 уже документирует трехуровневое прогрессивное раскрытие (claude-mem), а §2.2-2.3 (Auto Memory + Auto Dream) уже представляет собой собственную файловую, безвекторную систему памяти с индексированием и сокращением. Итак, большая часть того, что выглядело романом, раскрыта. Пересмотрено до 2/5..

**Decision**: Минимальное упоминание. Единственная действительно ценная, проверенная рекомендация не зависит от ORF: процитируйте статью ReasoningBank (arXiv 2509.25140) в `memory-systems.md`, поскольку `grep -rli "reasoningbank" guide/` возвращает ноль совпадений и является академическим якорем для памяти агентов об успехах и неудачах. При желании добавьте примечание в один абзац в §4 о сценариях взаимодействия с git-commitable в качестве пути для обмена информацией в команде. Не добавляйте запись об инструменте, не рекомендуйте к производству (самоописанный POC, не прошедший боевые испытания), не указывайте контрольные цифры.

**Что на самом деле содержит руководство (записано 15 сентября 2026 г.)**: `memory-systems.md` §3.7 содержит полное описание ORF внутри файловой дорожки playbook в сочетании с DiffMem в качестве противоположного варианта поиска. В этой записи уже применены исправления этой редакции: в ней говорится, что трехуровневое раскрытие информации соответствует той же схеме, что и в §3.1 claude-mem, цитируется ReasoningBank, и описывается зрелость как доказательство концепции с контрольными показателями, слишком маленькими, чтобы что-либо значить. Оценка 2/5 означает ORF как рекомендацию по инструменту; этот раздел заслуживает своего места как документально подтвержденный контраст, а не как одобрение.

## Что это такое

ORF позволяет агенту кодирования записывать и повторно загружать оперативные знания между сеансами. Когда агент решает сложную проблему, он записывает «сценарий» в виде файла Markdown с заголовком YAML под `./experiences/`. В следующем сеансе агент, столкнувшийся с аналогичной задачей, извлекает сценарий и пропускает тупики, за которые уже однажды заплатили.

Три компонента:

1. `experiences/INDEX.md`: корневой каталог. Фронтальная часть YAML определяет категории доменов; Тело Markdown связывает каждую книгу пьес с однострочным резюме. Вспомогательный скрипт автоматически добавляет новые записи, поэтому индекс остается синхронизированным без редактирования вручную.
2. `experiences/<domain>/EXP-<date>-<seq>.md`: одна книга пьес на файл, строгая схема из 5 разделов (Цель, Ловушка, Абстрактное понимание, Проверенный путь, Контрольный список проверки).
3. `manage-experience/`: навык агента (формат SKILL.md), поддерживаемый `experiences.py`, эталонный Python CLI с `list-categories`, `get-frontmatter`, `read-experience` и `create-experience`.

Два жестких ограничения дизайна:

- **Нулевая серверная инфраструктура.** Никакой векторной БД, никакого встраивания API, никакого дополнительного модуля. Просто простые файлы, которые подлежат контролю версий.
- **Загрузка по требованию посредством постепенного раскрытия.** Три шага: прочитать небольшой указатель (~ 200 жетонов), просмотреть описания вступительных частей сборников пьес в соответствующей категории (~ 500 жетонов), загрузить только конкретную соответствующую книгу пьес (~ 800 жетонов).

## Фундаменты (проверенные)

| Цитируемый источник | Статус | Что ORF извлекает из этого |
|--------------|--------|------------------------|
| **ReasoningBank** (Google, arXiv 2509.25140) | Настоящий, заслуживающий доверия. «Саморазвивающийся агент масштабирования с памятью рассуждений» | Основная идея: выделить обобщаемые стратегии из *оба* успешные и неудачные траектории в элементы структурированной памяти, извлеките несколько из них во время тестирования. |
| Формат открытых знаний (OKF) | Формат сообщества | Удобочитаемый Markdown + заголовок YAML. |
| Навыки агента (SKILL.md) | Спецификация Anthropic, описанная в этом руководстве. | Навык `manage-experience` загружается по требованию, поэтому базовая подсказка остается чистой. |
| Анализ антигравитационной траектории | Ранняя работа автора | Мотивация: выявлять ненужные шаги в траекториях агентов. |

**Ключевое отличие конструкции от ReasoningBank.** ReasoningBank извлекает элементы памяти посредством встроенного поиска (сходство векторов). ORF намеренно отбрасывает вложения и извлекает данные по имени файла и описаниям заголовка, читаемым LLM. В этом вся ставка: заменить отзыв семантических векторов на нулевую инфраструктуру и файлы, фиксируемые Git. Цена – качество поиска. При сканировании однострочных описаний LLM будут пропущены совпадения, которые может обнаружить векторный индекс, и сам автор отмечает это в своих открытых вопросах («слишком специфичный опыт не сработает для других случаев»).

**Ближайшие аналоги уже есть в руководстве (добавлены после вызова).** Две существующие записи структурно ближе к ORF, чем источники, которые цитирует сам ORF, и обе имеют значение для новизны:

- **claude-mem (§3.1)** уже документирует *«Прогрессивное раскрытие (3 уровня для сохранения токенов)»* с тем же индексом → средний → полный бюджет на промежуточный этап и токен. ORF применяет его к файлам playbook вместо сводок сеансов, но этот шаблон не нов для руководства.
- **Автопамять + Автосон (§2.2-2.3)** является Claude Code's *родной* файловая, безвекторная, созданная агентом память с consolidate/prune/index цикл. Это те же самые «простые файлы, без вложений», которые формируют шаг ORF в качестве его дифференциатора.

Что остается по-настоящему новым, если их вычесть: git-commitable, для каждого домена, созданные агентами сборники сценариев с фиксированной 5-секционной схемой failure/fix, которыми `git commit experiences/` делится между всей командой. Это узкое утверждение вполне реально (Auto Memory — это gitignored/per-user, claude-mem — это SQLite, а не файлы с поддержкой версий), но оно уже, чем «прогрессивное раскрытие памяти», которое уже рассматривалось.

## Шаблоны, которые стоит извлечь

### Схема 1: Трехуровневое постепенное раскрытие для восстановления памяти (уже в руководстве)

ORF осуществляет извлечение с явным бюджетом токенов: индекс (~200) → заголовок категории (~500) → единая книга пьес (~800). **Исправление после вызова**: это не новость для руководства. `memory-systems.md` §3.1 уже документирует *Claude-Mem «Прогрессивное раскрытие (3 уровня для сохранения токенов)»* с той же стадией (поиск 50-100 токенов → временная шкала 500-1000 → полная информация). ORF применяет его к файлам playbook, а не к сводкам сеансов. Нечего извлекать; узор покрыт.

### Схема 2. Отделите абстрактное понимание от проверенного конкретного пути.

Схема из 5 разделов разделяет «Абстрактное понимание» (принцип многократного использования, например «привязка регулярного выражения заголовка YAML к началу строки») от «Проверенного пути» (конкретное исправление, которое здесь сработало). Это отражает фильтрацию на уровне стратегии ReasoningBank. Это механизм, предназначенный для борьбы с проблемой чрезмерного опыта: сохраняйте принцип, а не просто одноразовое исправление. Работает ли это на практике, не доказано, но решение по схеме правильное.

### Шаблон 3. Автоматически синхронизируемый индекс при записи.

`create-experience` автоматически добавляется к `INDEX.md` в соответствующей категории. Индекс никогда не может отклоняться от файлов книги воспроизведения, поскольку при написании книги воспроизведения запись индекса записывается в той же операции. Небольшой, но устраняет целый класс ошибок устаревшего индекса.

## Где это соответствует разрыву команды

`memory-systems.md` §4.7 утверждает, что разрыв в распределении команд является структурным, поскольку каждый ведущий инструмент создавался в первую очередь для одного пользователя и зависит от инфраструктуры для каждого пользователя. ORF является частичным противоположным примером, который стоит назвать: поскольку плейбуки представляют собой простые файлы без сервера, `git commit experiences/` автоматически делится одним исправлением агента разработчика со всей командой. Он не решает проблему консолидации или разрешения конфликтов между участниками (автор называет оба вопроса открытыми), но механизм распределения — это именно тот путь Git, который, по словам руководства, отсутствует. Это примечание в один абзац к §4, а не целый раздел.

## Слабые стороны (будьте честными)

- **Бенчмарки, как заявлено, бессмысленны.** SWE-bench Lite «66,7% → 100%» — 3 задачи; один перевернулся. Показатель «-52% шагов» — это одиночный сценарий (frontmatter-parser). Автор прямо пишет "отнюдь не научная оценка... горстка случаев". Прочтите это как демонстрацию, а не доказательство. Никаких цифр из него не привожу.
- **Извлечение без вложений — это непроверенное ядро.** Весь шаг с нулевым значением инфра основан на LLM, надежно сопоставляющем задачу с однострочным описанием. Никакой оценки точности поиска или полноты не существует.
- **Открытые проблемы — самые сложные, и все они нерешены.** Консолидация перекрывающихся или конфликтующих сценариев, устаревание по мере развития фреймворков, распределение команд за пределами сырого Git. Автор называет все три и не решает ни одного.
- **Не используется в производстве.** «Я еще не использовал навык ORF в гневе». Самостоятельно сообщил.
