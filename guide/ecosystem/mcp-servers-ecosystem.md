## <a name="official-vs-community-servers"></a>Официальные серверы против серверов сообщества

| Тип | Примеры | Характеристики | Использовать, когда |
|------|----------|-----------------|----------|
| **Официальный** | файловая система, память, храбрый поиск, github | Поддерживается Anthropic, гарантированная стабильность | Выбор по умолчанию, основные функции |
| **Сообщество** | Playwright, Семгреп, Kubernetes | Поддерживается orgs/individuals, может быть готов к работе. | Особые потребности, интеграция экосистемы |

**Ключевое отличие**: Официальные серверы имеют поддержку SLA Anthropic, серверы сообщества требуют индивидуальной оценки.

## <a name="evaluation-framework"></a>Система оценки

Все серверы сообщества оцениваются по следующим критериям:

| Критерий | Порог | Обоснование |
|-----------|-----------|---------------|
| **GitHub Звезды** | ≥50 | Минимальная проверка сообщества |
| **Последний выпуск** | <3 месяцев | Активное обслуживание |
| **Документация** | README + примеры + конфиг | Уменьшает трудности внедрения |
| **Tests/CI** | ✅ Автоматизированный | Обеспечивает стабильность |
| **Случай использования** | Не распространяется на официальные серверы | Избегает избыточности |
| **Лицензия** | Требуется OSS | Устойчивость и проверяемость |

**Компоненты с показателем качества**:
- Техническое обслуживание (10 баллов): частота выпусков, время ответа на проблему.
- Документация (10 баллов): комплектность README, примеры, устранение неполадок.
- Тесты (10 баллов): Тестовое покрытие, автоматизация CI/CD.
- Производительность (10 баллов): Время отклика, эффективность использования ресурсов.
- Внедрение (10 баллов): использование сообществом, промышленное развертывание.

**Общий балл**: `/50` → нормализован до `/10` для окончательного рейтинга.

### <a name="usage-principles-beyond-the-evaluation-checklist"></a>Принципы использования (помимо контрольного списка оценки)

**Сохраняйте небольшое количество активных инструментов.** Каждая схема инструмента, представленная в модели, использует токены контекста и добавляет поверхность принятия решений. Производственные наблюдения показывают, что одновременное воздействие большого количества инструментов увеличивает частоту галлюцинаций: в модели появляется больше нерелевантных вариантов, которые можно спутать с правильными. Предпочитайте несколько специализированных серверов (каждый из которых привязан к домену) одному омнибусному серверу с десятками инструментов. (Зинеб Бендиба, главный инженер-программист Red Hat, [IFTTD, эп. 326 «Серверы MCP»](https://www.ifttd.io/episodes/mcp-servers)). Фактические измерения токенов на популярных серверах, а не общие принципы, см. в разделе [, сколько на самом деле стоят серверы MCP в токенах](https://www.florian.bruniaux.com/guides/mcp-servers-token-cost/).

**Разрабатывайте инструменты MCP с учетом полных намерений пользователя, а не отдельных операций API.** Инструмент, обрабатывающий один вызов API, заставляет агента составить пять последовательных вызовов, каждый из которых представляет независимую вероятность отказа. Инструмент, который инкапсулирует полный рабочий процесс («размещение заказа, включая применение активной скидки»), сохраняет модель на одном, четко определенном пути. (Фредерик Бартеле, инженер, [IFTTD, эп. 329 «Front Agentique»](https://www.ifttd.io/episodes/front-agentique))

**LLM не имеет состояния; клиент хранит всю информацию о маршрутизации.** Модель получает схемы инструментов при каждом запросе, но не имеет памяти о предыдущих вызовах сервера, выполненных ранее в сеансе. Claude Code (как клиент MCP) отвечает за маршрутизацию, повторные попытки и формирование результатов. Понимание этого разделения предотвращает распространенную ошибку, когда удаленный сервер MCP рассматривается как интеллектуальный соавтор, а не как API без сохранения состояния. (Зинеб Бендиба, главный инженер-программист Red Hat, [IFTTD, эп. 326 «Серверы MCP»](https://www.ifttd.io/episodes/mcp-servers))

**MCP лучше всего воспринимать как стандартизированный уровень интеграции, а не как новую парадигму.** Вместо написания одной специальной интеграции для каждого источника данных или инструмента, протокол позволяет одному клиенту говорить на одном языке со многими серверами. Подобная формулировка позволяет преодолеть большую часть ажиотажа вокруг MCP: это та же проблема, которую ранее решала система при проектировании шлюзов и сервисных сетей API, применительно к тому, как LLM достигает инструментов. (ByteByteGo, «MCP», 2025 г.)

**Определение размера сервера для агентного клиента начинается с той же предварительной формулы, что и для любого API, с одной оговоркой.** Грубая оценка: QPS равняется количеству активных пользователей, умноженному на действия на пользователя, разделенному на 86 400 секунд в день, при этом пиковая нагрузка обычно в два-три раза превышает это среднее значение. Этот пиковый множитель был откалиброван с учетом структуры человеческого трафика и, вероятно, является заниженным для агентов, которые имеют тенденцию попадать на сервер пакетами, а не сглаженным потоком в течение дня; размер высоты соответственно. (ByteByteGo, «Предварительная оценка», 2022 г. и «Сокращатель URL-адресов», 2025 г.)

## <a name="ecosystem-evolution"></a>Эволюция экосистемы

**Основные события (январь 2026 г.)**:

### Linux Базовая стандартизация

MCP становится официальным стандартом через **Agentic AI Foundation** под управлением Linux Foundation.

- **Объявление**: [YouTube - Linux Foundation](https://www.youtube.com/watch?v=btNbIY7KYwg)
- **Impact**: корпоративное внедрение, долгосрочная гарантия стабильности

### Расширенное использование инструмента MCP

Anthropic внедряет оптимизации для управления контекстом MCP:

- **Отложенная загрузка**: инструменты загружаются по требованию, а не заранее.
- **Инструменты на основе поиска**: Эффективное обнаружение инструментов в больших наборах
- **Объявление**: [Джош Твист LinkedIn](https://www.linkedin.com/posts/joshtwist_anthropic-recently-dropped-advanced-mcp-activity-7399492619581718528-g-Ip)

### Формат пакета MCPB

Стандартизированный формат пакета для установки сервера MCP одним щелчком мыши (заменяет управление зависимостями во время выполнения).

- **Обсуждение**: [Reddit - r/ClaudeAI](https://www.reddit.com/r/ClaudeAI/comments/1qkzdh0/mcp_server_installs_are_nondeterministic_heres/)
- **Преимущество**: детерминированная установка, снижение сложности установки

### MCP Приложения (инструменты интерактивной работы)

Claude теперь поддерживает интерактивные инструменты через спецификацию приложений MCP:

- **Примеры**: Slack-черчение, диаграммы Figma, временные шкалы Asana
- **Объявление**: [Информационный бюллетень Smol.ai](https://news.smol.ai/issues/26-01-26-mcp-apps)
- **Глубокое погружение**: см. [guide/core/architecture.md:656](../core/architecture.md#mcp-extensions-apps-sep-1865)

### Интеграция IDE

**Visual Studio 2026** изначально интегрирует сервер Azure MCP, чат GitHub Copilot и клиенты MCP.

- **Объявление**: [Блоги разработчиков Microsoft](https://devblogs.microsoft.com/visualstudio/azure-mcp-server-now-built-in-with-visual-studio-2026-a-new-era-for-agentic-workflows/)

### Дорожная карта протокола (середина 2026 г.)

Model Context Protocol не имеет никакого органа по стандартизации в стиле IETF или W3C, стоящего за самим термином; Ближе всего к институциональной формализации является собственная версионная версия спецификации MCP, которая теперь находится под управлением Linux Foundation (см. выше).

Кандидат на выпуск, опубликованный 28 июля 2026 г., добавляет четыре изменения, которые стоит отслеживать:

- **Ядро протокола без сохранения состояния**: базовый вариант, не требующий состояния сеанса, полезный для бессерверного и периферийного развертывания серверов MCP.
- **Extensions framework**: формальный механизм для добавления возможностей (приложения MCP выше — первый поставляемый пример) без пересмотра базовой спецификации.
- **Tasks**: поддержка длительных операций, актуальная для серверов MCP, использующих асинхронные серверные части.
- **Официальная политика прекращения поддержки**: документированный процесс прекращения использования спецификационных функций, а также дальнейшее ужесточение авторизации.

Источник: [MCP блог о дорожной карте](https://blog.modelcontextprotocol.io/posts/2026-mcp-roadmap/), [28 июля 2026 г., объявление о выпуске кандидата](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).

### Руководство АНБ по безопасности (июнь 2026 г.)

Агентство национальной безопасности США опубликовало руководство по безопасности для MCP в июне 2026 года ([CSI_MCP_SECURITY.PDF](https://media.defense.gov/2026/Jun/02/2003943289/-1/-1/0/CSI_MCP_SECURITY.PDF)), что стало первым вниманием агентства национальной безопасности к этому протоколу на уровне руководства. Это руководство по безопасности, а не методологический стандарт, но оно отмечает переход MCP от удобства для разработчиков к чему-то, что учреждения рассматривают как поверхность атаки, достойную документирования. Перекрестная ссылка на контрольный список безопасности [](#security-checklist) ниже при оценке нового сервера MCP для производственного использования.

## Контроль версий (официальные серверы)

Эти базовые серверы MCP обеспечивают автоматизацию контроля версий для всех рабочих процессов разработки. **Официальные серверы Anthropic** с гарантированной стабильностью.

### <a name="git-mcp-anthropic"></a>Гит MCP (Anthropic)

**Официальный сервер Anthropic** для взаимодействия с репозиторием Git через Model Context Protocol. Обеспечивает программный доступ к операциям Git со структурированным выводом и кроссплатформенной безопасностью.

**Репозиторий**: [modelcontextprotocol/servers/git](https://github.com/modelcontextprotocol/servers/tree/main/src/git)
**Лицензия**: MIT
**Status**: Ранняя разработка (API может быть изменен)
**Stars**: 88 957 (родительский репозиторий, проверен 27 июля 2026 г., 77 908+)

**Случаи использования**:
- **Автоматические рабочие процессы фиксации**: ИИ генерирует сообщения о фиксации, поэтапно вносит изменения, фиксирует
- **Анализ журнала**: фильтрация коммитов по дате, автору и ветке со структурированным выводом.
- **Управление ветвями**: создание ветвей функций, оформление заказа, фильтрация по SHA
- **Различия с эффективным использованием токенов**: строки контекста управления для целенаправленной проверки кода.
- **Автоматизация нескольких репозиториев**: управление несколькими репозиториями в конфигурациях с одним репозиторием

#### Ключевые особенности

| Инструмент | Описание | Параметры |
|------|-------------|------------|
| `git_status` | Статус рабочего дерева (подготовлено, неподготовлено, неотслеживается) | - |
| `git_log` | История коммитов с расширенной фильтрацией | `max_count`, `skip`, `start_timestamp`, `end_timestamp`, `author` |
| `git_diff` | Разница между commits/branches | `target`, `source`, `context_lines` |
| `git_diff_unstaged` | Неустановленные изменения | `context_lines` |
| `git_diff_staged` | Поэтапные изменения | `context_lines` |
| `git_commit` | Создать фиксацию | `message` |
| `git_add` | Этап files/patterns | `files` |
| `git_reset` | Выключить файлы | `files` |
| `git_branch` | List/filter филиалы | `contains`, `not_contains` |
| `git_create_branch` | Создать новую ветку | `name` |
| `git_checkout` | Переключатель branches/commits | `ref` |
| `git_show` | Показать детали коммита | `revision` |

**Расширенная фильтрация** (`git_log`):
- **ISO 8601 даты**: `2024-01-15T14:30:25`
- **Относительные даты**: `2 weeks ago`, `yesterday`, `last month`
- **Абсолютные даты**: `2024-01-15`, `Jan 15 2024`
- **Фильтрация авторов**: `--author="John Doe"`

#### <a name="setup"></a>Настройка

**Установка (3 способа)**:

```bash
# Method 1: UV (recommended) - one-liner
uvx mcp-server-git --repository /path/to/repo

# Method 2: pip + Python module
pip install mcp-server-git
python -m mcp_server_git

# Method 3: Docker (sandboxed)
docker run -v /path/to/repo:/repo ghcr.io/modelcontextprotocol/mcp-server-git
```

Конфигурация **Claude Code** (`~/.claude.json`):

```json
{
  "mcpServers": {
    "git": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/Users/you/projects/myrepo"]
    }
  }
}
```

**Поддержка нескольких репозиториев**:

```json
{
  "mcpServers": {
    "git-main": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/path/to/main-repo"]
    },
    "git-docs": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/path/to/docs-repo"]
    }
  }
}
```

#### <a name="decision-matrix-git-mcp-vs-github-mcp-vs-bash-tool"></a>Матрица решений: Git MCP против GitHub MCP против инструмента bash

**Когда какой инструмент использовать**:

| Операция | Гит MCP | GitHub MCP | Инструмент Баш | Обоснование |
|-----------|---------|------------|-----------|---------------|
| **Локальные коммиты** | ✅ Лучший | ❌ | ⚠️ ОК | Структурированный вывод, кроссплатформенная безопасность |
| **Управление филиалом** | ✅ Лучший | ❌ | ⚠️ ОК | Фильтрация `git_branch`, SHA contains/excludes |
| **Diff/log анализ** | ✅ Лучший | ❌ | ⚠️ ОК | Управление `context_lines`, эффективное использование токенов |
| **Промежуточные файлы** | ✅ Лучший | ❌ | ⚠️ ОК | Сопоставление с образцом (`git_add`), безопаснее |
| **PR создание** | ❌ | ✅ Лучший | ⚠️ х CLI | GitHub API, ярлыки, правопреемники, рецензенты |
| **Управление проблемами** | ❌ | ✅ Лучший | ⚠️ х CLI | Операции, специфичные для GitHub |
| **CI/CD проверка статуса** | ❌ | ✅ Лучший | ⚠️ х CLI | Интеграция GitHub Actions |
| **Интерактивная перезагрузка** | ❌ | ❌ | ✅ Лучший | Git MCP не поддерживает флаг `-i` |
| **Reflog восстановление** | ❌ | ❌ | ✅ Лучший | Расширенные операции Git |
| **Отладка Git пополам** | ❌ | ❌ | ✅ Лучший | Сложные рабочие процессы отладки |
| **Многоинструментальные конвейеры** | ✅ | ✅ | ❌ | Серверы MCP компонуются с другими инструментами MCP. |

**Дерево решений**:

```
Is it a GitHub-specific operation (PRs, Issues, Actions)?
├─ YES → Use GitHub MCP
└─ NO → Is it a core Git operation (commit, branch, diff, log)?
    ├─ YES → Use Git MCP (structured, safe, token-efficient)
    └─ NO → Is it an advanced Git feature (rebase -i, reflog, bisect)?
        ├─ YES → Use Bash tool (flexibility)
        └─ NO → Default to Git MCP (safer, structured)
```

**Примеры рабочих процессов**:

| Рабочий процесс | Цепочка инструментов | Обоснование |
|----------|-----------|---------------|
| **Разработка функций** | Git MCP (`git_create_branch` + `git_commit`) → GitHub MCP (PR) | Атомарный, структурированный, полный жизненный цикл |
| **Анализ истории коммитов** | Git MCP (`git_log` с `start_timestamp: "2 weeks ago"`) | Токен-эффективная фильтрация, относительные даты |
| **Подготовка к проверке кода** | Git MCP (`git_diff` с `context_lines: 3`) | Сфокусированный контекст, уменьшенное количество токенов |
| **Очистка коммитов (перебазирование)** | Инструмент Bash (`git rebase -i HEAD~5`) | Интерактивный режим отсутствует в Git MCP |
| **Восстановить потерянные коммиты** | Инструмент Bash (`git reflog`) | Рефлог не отображается в Git MCP |
| **Охота на ошибки с помощью bisect** | Инструмент Bash (`git bisect start/good/bad`) | Рабочий процесс Bisect отсутствует в Git MCP |
| **Автоматизированный процесс выпуска** | Git MCP (фиксация + тег) → GitHub MCP (создать выпуск) | Полная автоматизация, структурированная |

#### Часовой MCP

**Официальный сервер Sentry** для мониторинга и наблюдения за ошибками. Замыкает цикл диагностики: срабатывает оповещение Sentry → Claude считывает проблему + трассировку стека → диагностирует основную причину → предлагает или записывает исправление.

**Maintainer**: Sentry (официальный)

| `get_event` | Конкретное событие по идентификатору, полезно для расследований, ограниченных по времени. |
| `search_events` | Полнотекстовый поиск по необработанным событиям с фильтрами по полям |
| `list_projects` | Перечислите проекты в вашей организации Sentry |

#### Грепай MCP

**Сервер сообщества** для семантического поиска кода и анализа графа вызовов с помощью локальных вложений Ollama. Ищет код по намерению («поток платежей», «логика аутентификации»), а не по точным шаблонам, и отслеживает взаимосвязи вызовов функций.

**Репозиторий**: [yoanbernabeu/grepai](https://github.com/yoanbernabeu/grepai)
**Лицензия**: MIT
**Status**: Активная разработка
**Privacy**: полностью локально (Ollama + nomic-embed-text), никакие данные не покидают ваш компьютер.

**Используйте Case**: разработчику необходимо понимать незнакомую кодовую базу → grepai находит соответствующий код по описанию на естественном языке и сопоставляет зависимости функций, не читая целые файлы.

**Основные характеристики**:

| Возможность | Подробности |

| `grepai_trace_callees` | Найдите все функции, вызываемые данным символом |
| `grepai_trace_graph` | Полный граф вызовов (вызывающие + вызываемые абоненты) с настраиваемой глубиной |
| `grepai_index_status` | Проверка работоспособности: индексированные файлы, фрагменты, конфигурация |

#### Сембл

**Сервер сообщества** для семантического поиска кода по коду, документации и файлам конфигурации. Использует встраивания Model2Vec с ранжированием BM25 и слиянием RRF, работает только на ЦП без зависимости от внешнего сервиса.

**Репозиторий**: [MinishLab/semble](https://github.com/MinishLab/semble)
**Лицензия**: MIT
**Status**: Активен (v0.3.3, июнь 2026 г.), ~5718 звезд (27 июля 2026 г., было ~5000)
**Privacy**: полностью локально (только для процессора Model2Vec), никакие данные не покидают вашу машину.

**Используйте Case**: разработчику нужен семантический поиск кода без локального запуска Ollama. Semble создает локальный индекс (Model2Vec + BM25 + RRF) при первом запуске и кэширует его. Ищет код, документацию и файлы конфигурации по запросу на естественном языке.

**Основные характеристики**:

| Возможность | Подробности |
|------------|---------|
| Семантический поиск | Запросы на естественном языке в коде, документации и файлах конфигурации. |
| MCP сервер | Встроенная интеграция (`semble mcp`), оболочка CLI не требуется. |
| Нет внешнего сервиса | Model2Vec работает только с процессором; нет Олламы, не требуется ключ API |
| Индекс | Создается при первом запуске, автоматически кэшируется (каждый новый каталог требует сборки) |

**Эффективность токена**:

| Рабочий процесс | Токены | Вердикт |
|----------|--------|---------|
| Grep + Чтение файлов (грубая сила) | ~15K | Шумно, много нерелевантного контекста. |
| Поиск по семблу (код + документация + конфиг) | ~2-4K | Целевые результаты, более широкий охват, чем только код |

В описании репозитория MinishLab/semble (прочитано 30 сентября 2026 г.) заявлено «на 99% меньше токенов, чем grep+read». Это утверждение поставщика оценивается по рабочему процессу «grep-then-read-files», а не по всему сеансу, и цифры в таблице выше носят иллюстративный характер, а не измеряются здесь.

**Setup**:

```bash
pip install semble

# Start the MCP server
semble mcp
```

**Claude Code Конфигурация**:

```bash
claude mcp add semble -- semble mcp
```

**Сравнение с Grepai**:

| Аспект | Грепай | Сембл |
|--------|--------|--------|
| Внешний сервис | Да (Оллама + nomic-embed-text) | Нет (только для процессора Model2Vec) |
| Интеграция MCP | CLI превращается в MCP | Родной сервер MCP |
| Область поиска | Только код | Код + документация + конфигурация |
| Анализ графа вызовов | Да (trace_callers,trace_callees,trace_graph) | Нет |
| Поддержка сообщества | Активный сопровождающий | ~ 5718 звезд GitHub (27 июля 2026 г.) |

**Когда следует выбирать Semble вместо Grepai**: Вам нужен семантический поиск кода, но не запускайте Ollama локально. Более широкая область применения Semble также помогает в монорепозиториях, где навигация по конфигурации и документации имеет такое же значение, как и навигация по коду. Выбирайте Grepai, когда необходим анализ графа вызовов; Semble не предлагает такой возможности.

> **Примечание по поводу заявлений об отсутствии индекса.**: в некоторых сообщениях сообщества Semble описывается как не требующий индекса. Это неверно. Semble создает локальный индекс при первом запуске и кэширует его. Для каждого нового каталога требуется отдельная сборка индекса.

**Показатель качества**: **7.2/10** (область: узкая оценка, ожидается более широкий сигнал сообщества)

### <a name="customer-support--crm"></a>Поддержка клиентов и CRM

Примечание **A об «официальном» для этой категории.** Репозиторий `modelcontextprotocol/servers` GitHub не является реестром обнаружения: его README явно подчиняется официальному реестру MCP (`registry.modelcontextprotocol.io`) для поиска опубликованных серверов и содержит лишь несколько эталонных реализаций руководящей группы, которые он помечает как «не готовые к производству». В самом официальном реестре есть список нескольких самостоятельно опубликованных серверов HubSpot и Zendesk (можно запросить по адресу `/v0/servers?search=<name>`), но наличие реестра означает только то, что сопровождающий представил запись, а не то, что HubSpot или Zendesk проверили или одобряют ее. Ни одна из компаний не публикует собственный сервер. Приведенные ниже серверы были выбраны по количеству звезд и давности коммитов на GitHub, что является более сильным сигналом, чем наличие только реестра на момент оценки.

### <a name="security-checklist"></a>Контрольный список безопасности

- [ ] Ключи **API** хранятся в `.env`, а не в файлах конфигурации.
- [ ] **RBAC/permissions** рассмотрен (особенно Kubernetes, Semgrep)
- [ ] **Ограничения скорости** понятны (сложность Linear GraphQL, Vercel API)
- [ ] **Реализованы механизмы возврата** для простоя API.
- [ ] **Мониторинг + журналирование** включен для всех серверов MCP

### Обработка ошибок и надежность

Инструменты MCP могут выйти из строя по многим причинам, и важно то, как вы сообщите об этих сбоях Claude. Протокол предоставляет специальный механизм: флаг `isError` в ответах инструмента.

**Флаг `isError`**

При сбое вызова инструмента установите `isError: true` в ответе вместо того, чтобы вызывать исключение или возвращать ложный успех. Это сообщает Claude, что вызов не удался, и предлагает ему решить, что делать дальше: повторить попытку, попробовать другой подход или сообщить о проблеме пользователю.

```json
{
  "content": [
    {
      "type": "text",
      "text": "Database connection refused: ECONNREFUSED 127.0.0.1:5432"
    }
  ],
  "isError": true
}
```

Без `isError: true` Claude может интерпретировать сообщение об ошибке как данные и уверенно продолжать работу в неисправном состоянии. Благодаря этому Claude понимает, что шаг не выполнен, и может рассуждать о восстановлении.

**Таксономия ошибок: четыре категории**

Различные типы сбоев требуют разных стратегий восстановления. Структурирование сообщений об ошибках по этим четырем категориям позволяет Claude выбрать правильное действие по восстановлению:

| Категория | Когда | Ожидаемый ответ Claude | Пример |
|----------|------|---------------------------|---------|
| **Переходный** | Временная недоступность, нестабильность сети, ограничение скорости | Повторить попытку после задержки | `503 Service Unavailable`, тайм-аут |
| **Проверка** | Неправильный ввод: неверный тип, отсутствует поле, ошибка формата. | Исправьте ввод, повторите попытку немедленно | `invalid date format: expected ISO8601` |
| **Бизнес** | Ввод правильный, но операция не разрешена правилами домена | Эскалация или пропуск | `cannot delete: record has active dependencies` |
| **Разрешение** | У звонящего нет авторизации | Остановитесь и объясните пользователю | `403 Forbidden: insufficient scope` |

**Шаблон реализации**

Включите категорию в сообщения об ошибках, чтобы Claude мог действовать, не догадываясь:

```python
def call_tool(params):
    try:
        result = execute(params)
        return {"content": [{"type": "text", "text": result}], "isError": False}
    except NetworkError as e:
        return {
            "content": [{"type": "text", "text": f"[transient] {e}. Retry in a few seconds."}],
            "isError": True
        }
    except ValidationError as e:
        return {
            "content": [{"type": "text", "text": f"[validation] {e}. Check the input format."}],
            "isError": True
        }
    except PermissionError as e:
        return {
            "content": [{"type": "text", "text": f"[permission] {e}. Cannot proceed without elevated access."}],
            "isError": True
        }
    except BusinessError as e:
        return {
            "content": [{"type": "text", "text": f"[business] {e}. Operation not permitted by domain rules."}],
            "isError": True
        }
```

Временные ошибки — единственная категория, где имеет смысл автоматический повтор. Ошибки проверки следует повторить с исправленными входными данными, а не вслепую. Бизнес-ошибки и ошибки разрешений должны останавливаться и показываться пользователю, а не зацикливаться.

### Шаблоны проектирования описания инструмента

Описания инструментов — наиболее важная часть сервера MCP. Claude использует их, чтобы решить, какой инструмент вызывать. Расплывчатое или дублирующее описание приводит к неправильной маршрутизации с большей вероятностью, чем любая другая ошибка проектирования.

**Основная проблема: перекрывающиеся описания приводят к неправильной маршрутизации**

Два инструмента со схожими описаниями создают двусмысленность. Claude выберет один, часто непоследовательно, потому что он угадывает по описанию, какой из них подходит.

```json
// Bad — ambiguous, Claude will guess
{ "name": "analyze_content", "description": "Analyzes content" }
{ "name": "analyze_document", "description": "Analyzes document content" }

// Good — each description carves out a specific input type
{ "name": "analyze_content", "description": "Analyzes raw text strings or inline content (not files). Use for clipboard content, API responses, or text passed directly as a string." }
{ "name": "analyze_document", "description": "Analyzes content from a file path or URL. Use when the content lives on disk or at a remote endpoint, not when you already have the text in memory." }
```

Тест: можете ли вы прочитать описание и точно знать, когда НЕ использовать этот инструмент? Если нет, добавьте границу.

**Описание анатомии**

Хорошее описание инструмента состоит из трех частей в следующем порядке:

1. **Что он делает**: одно предложение, настоящее время, глагол действия
2. **Что требуется**: тип ввода ключа или ограничение (путь к файлу или строка, одиночный или пакетный)
3. **Когда использовать его по сравнению с аналогичными инструментами**: граница принятия решения четко указана

```json
{
  "name": "search_codebase",
  "description": "Searches source code files by regex pattern across the repository. Use for finding symbol definitions, function calls, and string literals in code. Not for searching documentation, configs, or prose — use search_docs for those."
}
```

**Соглашения об именах, предотвращающие ошибочную маршрутизацию**

| Шаблон | Пример пары | Почему это работает |
|---------|-------------|--------------|
| Глагол различает намерение | `get_user` против `search_users` | Получить известный идентификатор или обнаружить по критериям |
| Существительное определяет тип ввода | `analyze_file` против `analyze_text` | Путь на диске и встроенная строка |
| Суффикс области действия | `list_tickets` против `list_project_tickets` | Глобальный или ограниченный |
| Детализация действий | `create_record` против `bulk_create_records` | Один против партии |

Избегайте синонимов в названиях инструментов: `fetch`, `get`, `retrieve` означают одно и то же, что и Claude. Выберите одно семейство глаголов для каждой семантической операции.

**Анти-паттерны, которых следует избегать**

- **Общие глаголы без области действия**: `process`, `handle`, `manage` ничего не сообщают Claude о том, когда следует вызывать инструмент.
- **Пропуск границы**: «Ищет базу данных». Какая база данных? Все это? Конкретная таблица?
- **Булевы флаги, меняющие семантику**: Инструмент, который делает совершенно разные вещи на основе флага, должен состоять из двух инструментов.
- **Описания длиной более 3 предложений**: Если вам нужно больше, значит, инструмент делает слишком много

**`input_examples` в качестве дополнения**

Если схемы недостаточно, чтобы указать, какие комбинации параметров являются допустимыми или типичными, добавьте `input_examples` (поддерживается Anthropic API с февраля 2026 г.). На них показаны конкретные шаблоны использования Claude, что особенно полезно для дополнительных параметров:

```json
{
  "name": "create_ticket",
  "input_examples": [
    { "title": "Login page 500 error", "priority": "critical", "assignee": "oncall" },
    { "title": "Add dark mode toggle", "priority": "low" },
    { "title": "Update API docs for v2.1" }
  ]
}
```

Примеры показывают то, чего не может показать описание: `assignee` устанавливается только для критических элементов, а `priority` можно опустить для рутинных задач.

## <a name="advanced-mcp-tool-design"></a>Усовершенствованная конструкция инструмента MCP

Помимо базовой таксономии ошибок, три проектных решения существенно влияют на то, как Claude использует инструменты MCP в производстве: семантика реагирования на ошибки, различие между ресурсами и инструментами и наименование инструментов.

---

### <a name="isretryable-application-level-convention"></a>isRetryable: соглашение на уровне приложения.

Спецификация MCP не включает поле `isRetryable` в схему ответа на ошибку. Однако соглашение о встраивании рекомендаций по повторным попыткам в `structuredContent` стало практическим шаблоном для инструментов, вызывающих ошибочные внешние службы.

```json
{
    "isError": true,
    "content": [
        {
            "type": "text",
            "text": "Database query timed out after 30s. Retrying with the same parameters is likely to succeed."
        }
    ],
    "structuredContent": {
        "error": {
            "code": "DATABASE_TIMEOUT",
            "message": "Query timed out",
            "isRetryable": true,
            "retryAfterMs": 5000,
            "suggestedAction": "Retry the same query after 5 seconds"
        }
    }
}
```

Для неповторяемых ошибок:

```json
{
    "isError": true,
    "content": [
        {
            "type": "text",
            "text": "Record not found. No record with ID 'usr_99999' exists in the database."
        }
    ],
    "structuredContent": {
        "error": {
            "code": "RECORD_NOT_FOUND",
            "message": "No record found for ID: usr_99999",
            "isRetryable": false,
            "suggestedAction": "Verify the ID is correct before retrying"
        }
    }
}
```

Флаг `isRetryable` — это не то, что Claude изначально читает из спецификации MCP. Он считывается вашим уровнем оркестрации, который решает, следует ли повторить попытку или перейти на более высокий уровень. Шаблон работает, потому что `structuredContent` машиночитаем, и ваш код может проверить его до того, как это сделает Claude.

---

### <a name="iserror-false--empty-content-vs-iserror-true"></a>isError: false + пустое содержимое против isError: true

Эти две формы ответа имеют совершенно разную семантику. Их путаница приводит к скрытым сбоям, которые трудно отладить.

| Ответ | Значение |
|---|---|
| `isError: false` + непустое содержимое | Инструмент удался, вот результат |
| `isError: false` + пустой контент | Инструмент выполнен успешно, ноль результатов найдено (допустимое пустое состояние) |
| `isError: true` | Ошибка инструмента: операция не может быть завершена |

```json
// Search returning no results: NOT an error
{
    "isError": false,
    "content": [
        {
            "type": "text",
            "text": "No documents found matching query: 'quarterly report Q5 2024'"
        }
    ]
}

// Search that failed to execute: IS an error
{
    "isError": true,
    "content": [
        {
            "type": "text",
            "text": "Search service unavailable. Could not execute query."
        }
    ]
}
```

Когда поиск возвращает нулевые результаты, Claude должен сообщить об этом пользователю и, возможно, попробовать другие термины. Если поиск не удается выполнить, Claude должен сообщить о сбое инструмента, а оркестратор должен рассмотреть возможность повторной попытки или эскалации. Эти пути расходятся, и только правильная семантика ошибок заставляет их расходиться правильно.

### <a name="mcp-resources-vs-tools"></a>Ресурсы MCP против инструментов

Ресурсы и инструменты служат разным целям и контролируются разными субъектами. Их смешение приводит к появлению инструментов, которые невозможно индексировать, и ресурсов, которые невозможно параметризовать.

| Измерение | Ресурсы | Инструменты |
|---|---|---|
| Кто контролирует доступ | Приложение (заранее определенное, не инициируемое моделью) | Модель (звонит по необходимости во время разговора) |
| Параметры | Нет (читается по URI) | Полная схема параметров |
| Вариант использования | Каталог данных только для чтения: файлы конфигурации, справочные данные, документы. | Параметризованные операции: поиск, вычисление, запись, вызовы API. |
| Открытие | В списке при запуске, доступен для просмотра | Описано в системной подсказке, вызывается по требованию |
| Побочные эффекты | Нет (по соглашению только для чтения) | Допустимый |
| Пример | Политический документ компании | `search_policy_documents(query, date_range)` |

```python
# Resource: static reference data, application-controlled
@server.list_resources()
async def list_resources():
    return [
        Resource(
            uri="config://database/schema",
            name="Database Schema",
            description="Current production database schema",
            mimeType="application/json"
        ),
        Resource(
            uri="docs://api/reference",
            name="API Reference",
            description="Internal API documentation",
            mimeType="text/markdown"
        )
    ]

@server.read_resource()
async def read_resource(uri: str) -> str:
    if uri == "config://database/schema":
        return json.dumps(get_current_schema())
    elif uri == "docs://api/reference":
        return read_file("docs/api-reference.md")
    raise ValueError(f"Unknown resource: {uri}")

# Tool: parameterized operation, model-controlled
@server.list_tools()
async def list_tools():
    return [
        Tool(
            name="search_database",
            description="Search the database with a structured query",
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string"},
                    "table": {"type": "string"},
                    "limit": {"type": "integer", "default": 10}
                },
                "required": ["query", "table"]
            }
        )
    ]
```

**ResourceLink Bridge:** Когда инструмент возвращает ссылку на ресурс (а не встроенный контент), используйте ResourceLink:

```json
{
    "isError": false,
    "content": [
        {
            "type": "resource",
            "resource": {
                "uri": "docs://reports/Q3-2024",
                "mimeType": "application/pdf",
                "text": "Q3 2024 Financial Report (use read_resource to access full content)"
            }
        }
    ]
}
```

### <a name="tool-naming-and-system-prompt-conflicts"></a>Конфликты имен инструментов и системных подсказок

Имена инструментов, которые появляются в качестве ключевых слов в системной подсказке, приводят к тому, что Claude связывает инструмент с несвязанными инструкциями. Инструмент под названием `process` будет мысленно ассоциироваться с любым появлением слова «процесс» в системной подсказке, создавая непредсказуемые шаблоны активации.

Правила названий инструментов:
- Используйте конкретные составные имена: `search_customer_records`, а не `search`.
- Избегайте общих глаголов, которые появляются в системных подсказках: `run`, `process`, `execute`, `handle`, `manage`.
- Используйте символы подчеркивания, а не верблюжий регистр или дефисы (соглашение MCP).
- Префикс с доменом, если инструментов много: `crm_get_contact`, `crm_update_contact`, `crm_search`.

```python
# Bad: generic names that conflict with system prompt keywords
tools = ["search", "process", "run", "execute", "get", "update"]

# Good: specific compound names with domain prefix
tools = [
    "crm_search_contacts",
    "crm_get_contact_by_id",
    "crm_update_contact_status",
    "billing_create_invoice",
    "billing_get_invoice_status"
]
```

### <a name="task-scoped-tool-profiles"></a>Профили инструментов с указанием задач

Предоставление всех доступных инструментов для каждого вызова агента является расточительным и увеличивает риск непреднамеренной записи во время фаз только чтения. Профили инструментов на уровне задачи ограничивают доступные инструменты в зависимости от текущей фазы задачи.

```python
TOOL_PROFILES = {
    "exploration": [
        "search_documents",
        "get_document_by_id",
        "list_categories",
        "read_config"
    ],
    "analysis": [
        "search_documents",
        "get_document_by_id",
        "calculate_metrics",
        "compare_versions"
    ],
    "execution": [
        "create_document",
        "update_document",
        "delete_document",
        "send_notification"
    ]
}

def get_tools_for_phase(phase: str) -> list[str]:
    return TOOL_PROFILES.get(phase, TOOL_PROFILES["exploration"])
```

Профиль исследования доступен только для чтения. Профиль выполнения добавляет операции записи. Claude не может случайно вызвать `delete_document` на этапе анализа, поскольку инструмент просто не присутствует в вызове.

Для многоролевых систем, в которых разные роли пользователей могут получать доступ к различным инструментам, используйте область на уровне роли, а не фильтруйте пост-вызов:

```python
ROLE_TOOL_ACCESS = {
    "viewer": ["search_documents", "get_document_by_id"],
    "editor": ["search_documents", "get_document_by_id", "create_document", "update_document"],
    "admin": ["*"]  # all tools
}

def get_tools_for_role(role: str, all_tools: list) -> list:
    if role == "admin":
        return all_tools
    allowed = ROLE_TOOL_ACCESS.get(role, [])
    return [t for t in all_tools if t.name in allowed]
```

Ограниченный доступ особенно ценен для шаблона инструмента `verify_fact`: субагенту, которому необходимо проверить только одно утверждение, можно предоставить только `verify_fact`, что снижает как задержку (меньше инструментов для описания в контексте), так и риск (нет инструментов записи в области действия).

## <a name="documenting-an-mcp-for-claude-the-reference-file-pattern"></a>Документирование MCP для Claude: шаблон справочного файла

Когда вы интегрируете сервер MCP в навык, Claude должен самостоятельно определять синтаксис запроса, необходимые комбинации параметров и необычное поведение. Для простых MCP это нормально. Все, что связано с производством (инструменты наблюдения, API-интерфейсы управления проектами, агрегаторы журналов), быстро выходит из строя. Claude угадывает формат параметра, получает загадочную ошибку, повторяет попытку с другим предположением и тратит свой бюджет на шум.

Исправление от команды инженеров Packmind (с открытым исходным кодом под Apache 2.0): добавьте файл `references/<mcp-name>.md` рядом с навыком, и навык прочитает его в качестве первого шага перед любым вызовом MCP.

### Что находится в справочном файле

Три типа контента, которые Claude не может достоверно определить самостоятельно:

**1. Семантика параметров, отличающаяся от имени инструмента**

Например, инструмент «поиска» Datadog, который использует синтаксис запросов Datadog (а не регулярное выражение). Или инструмент Sentry, для которого требуется `organization_slug` (фрагмент URL-адреса, а не отображаемое имя). Это не ошибки в MCP; они просто неочевидны.

**2. Известные шаблоны ошибок и их причины**

Например: «Если вы используете псевдонимы `SELECT` в `GROUP BY` с DDSQL, вы получите загадочную ошибку. Вместо этого повторите полное выражение». Это превращает 10-минутный сеанс отладки в поиск, занимающий нулевую секунду.

**3. Примеры рабочих запросов для случая 80%**

Примеры копирования и вставки, охватывающие наиболее распространенные запросы. Claude может адаптировать их, а не создавать с нуля.

### Структура файла

```
.claude/skills/my-mcp-skill/
├── SKILL.md                    # Main skill file
└── references/
    └── <mcp-name>.md           # MCP reference file (this pattern)
```

SKILL.md считывает эталонный файл на первом этапе:

```markdown
## Step 1: Read the MCP Reference File

Before doing anything else, read `references/<mcp-name>.md`.
This contains the query syntax and known gotchas for this MCP.
Do not skip this step.
```

### Почему это работает

Справочный файл не является документацией для людей. Это структурированная инъекция контекста. Каждая часть информации в нем снижает вероятность неправильного вызова MCP со стороны Claude. Если все сделано правильно, он устраняет циклы повторов, вызванные синтаксическими ошибками, и делает навык достаточно надежным, чтобы работать по расписанию без присмотра.

Этот шаблон распространяется на любой MCP с неочевидным поведением: Datadog, Sentry, PagerDuty, Linear, Jira, Mixpanel, Posthog. Если MCP имеет язык запросов, особенности нумерации страниц или обязательные параметры с неинтуитивными именами, справочный файл окупается при первом запуске.

### Готовый к работе шаблон

Полный шаблон навыка, демонстрирующий этот шаблон (с примером Sentry), доступен по адресу:

`examples/skills/mcp-integration-reference/` в этом репозитории

Шаблон включает в себя:
- `SKILL.md` с 5-этапной структурой (чтение ссылки, сбор данных, выборка, анализ, отчет)
- `references/sentry-mcp.md` с полной документацией по параметрам, ошибками, примерами запросов и списком исключений шума.
- Инструкция по адаптации под любой сервер MCP

> Создан на основе справочного файла Datadog MCP из репозитория [Packmind с открытым исходным кодом](https://github.com/PackmindHub/packmind) (Apache 2.0, Седрик Тейтон). Полную информацию об авторстве см. в [Credits](../core/credits.md).
