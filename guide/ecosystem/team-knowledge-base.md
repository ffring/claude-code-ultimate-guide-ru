# База знаний команды для Claude Code + Cowork

**Время чтения**: 18 минут
**Уровень навыка**: Месяц 1+ (руководитель группы, развертывающий оба инструмента)

> **Scope**: В этом разделе описывается, как настроить общую базу знаний компании (KB), которую могут читать как Claude Code (разработчик CLI), так и Claude Cowork (настольное приложение для неразработчиков, предварительный просмотр исследования). Это первый инфраструктурный вопрос, с которым сталкивается большинство команд при развертывании обоих инструментов. Если вы используете Claude Code только в одной кодовой базе, шаблон repo-as-KB в [§9.25 Harness Engineering](../ultimate-guide.md#925-harness-engineering-at-agent-throughput) уже удовлетворяет ваши потребности. Этот раздел предназначен для всей команды: общие документы, работающие системы и многократно используемые рабочие процессы для разработчиков и информационных работников.

## <a name="the-one-tool-for-three-needs-trap"></a>Ловушка «Один инструмент для трёх потребностей»

Команда развертывает Claude Code для инженеров и Cowork для менеджеров по проектированию, эксплуатации и поддержки. Кто-то задает очевидный вопрос: «Где нам разместить знания компании, чтобы оба инструмента могли использовать их?» Инстинкт состоит в том, чтобы выбрать один ответ. Вики. Рабочая область Notion. База данных векторов. Одно место, один разъем, готово.

Этот инстинкт и есть ловушка. Он производит шесть месяцев работы по миграции, наполовину проиндексированное пространство Confluence и агент, который все еще пропускает половину ответов.

Причина в том, что «знание компании» — это не одно и то же. Когда вы смотрите на то, к каким командам на самом деле нужен доступ агенту, появляются три различные формы, каждая из которых имеет свой наиболее подходящий механизм хранения и доступа. Объединение всех трех в один инструмент означает, что как минимум два из них подходят плохо.

Три формы:

| Характер знаний | Меняется как? | Оптимальный инструмент |
|-------------------------|--------------|---------------|
| **Статические документы** (runbooks, ADR, стандарты кодирования, адаптация, политики) | Через редактирование файла, зафиксировано | Версионный репозиторий Markdown (Obsidian необязательно сверху) |
| **Live системы** (тикеты Jira, страницы Confluence, записи CRM, внутренние API) | Постоянно, другими людьми и процессами | MCP разъем/плагин к источнику истины |
| **Многоразовые командные рабочие процессы** (слэш-команды, навыки, агенты, подсказки) | Через командную итерацию самого рабочего процесса | Плагин распространяется через торговую площадку |

Ошибка состоит в том, чтобы рассматривать все три как «документы, которые нужно где-то хранить». Статические документы требуют контроля версий и прямого чтения файлов. Живым системам требуется соединение с местом, где данные уже находятся, а не копия, которая устаревает в момент их синхронизации. Рабочие процессы вообще не являются документами; это поведение, а поведение упаковывается и распространяется иначе, чем контент.

Как только вы классифицируете каждую часть знаний по ее природе, выбор инструментов становится механическим. Оставшаяся часть этого раздела описывает каждый уровень с конкретными шагами настройки, затем описывает шаблон плагина для рабочих процессов, предостережения по управлению конфиденциальными данными и таблицу решений о том, что создавать в первую очередь.

### Почему Claude Projects не подходит

Перед тремя уровнями: сначала следует назвать один антишаблон, потому что команды достигают его раньше любого из трех. Проекты Claude (веб-функция, с помощью которой вы загружаете файлы и общаетесь с ними) выглядят как очевидная общая база знаний. Это не так для команды, использующей Code и Cowork.

| Ограничение | Последствия для команды КБ |
|------------|---------------------------|
| Web-only | Ни Claude Code, ни Cowork не могут прочитать проект программно. |
| Upload-only | Нет прямой синхронизации; вы перезагружаете при каждом изменении |
| ~Практическая шапка на 20 файлов | Не масштабируется за пределы небольшого количества документов. |
| Нет доступа к файловой системе | Агент не может перемещаться, использовать grep или перекрестные ссылки. |

Проекты подходят для тех, кто изучает фиксированный набор PDF-файлов в веб-приложении. Как общая командная инфраструктура, из которой оба агентских инструмента должны читать данные, они являются тупиком. Используйте их для специального анализа, а не в качестве основы базы знаний.

## <a name="tier-1-versioned-markdown-vault-static-docs"></a>Уровень 1. Хранилище уценок с поддержкой версий (статические документы).

Большая часть того, что команда называет «базой знаний», представляет собой статическую документацию. Runbook, записи решений по архитектуре, стандарты кодирования, руководства по адаптации, документация о том, как мы развертываем, анализ инцидентов. Они меняются посредством преднамеренных изменений, и вы хотите, чтобы каждое изменение было проверено и обратимо. Это описание является определением репозитория git.

### Почему репозиторий Markdown, а не вики

Ключевой вывод: и Claude Code, и Cowork читают локальные файлы напрямую. Claude Code клонирует репозиторий и имеет полный доступ к файловой системе (чтение, grep, перекрестные ссылки на тысячи файлов). Cowork предоставляет доступ к той же локальной папке на компьютере пользователя. Оба инструмента указывают на один и тот же источник. Не существует отдельной «копии AI», которую нужно было бы синхронизировать, поскольку сам источник — это то, что читает агент.

Вики (Confluence, размещенный Notion, внутренний портал) помещает контент в API или веб-интерфейс. Чтобы сделать это доступным для чтения агентом, вы добавляете соединитель, и теперь вы поддерживаете соединитель и беспокоитесь о его актуальности и ограничениях скорости. Репозиторий Markdown с поддержкой версий пропускает весь этот слой для статического контента. Агент читает файл. Git обрабатывает историю. Запросы на включение обрабатывают проверку.

| Свойство | Репозиторий уценки | Размещенная вики |
|----------|---------------|-------------|
| Доступ агента | Прямое чтение файла (без разъема) | Требуется разъем MCP/API. |
| История версий | Родной (git) | Зависит от инструмента, часто слабый |
| Обзор рабочего процесса | Запросы на вытягивание | Ручной или нет |
| Офлайн/локально | Да | Нет |
| Разница и вина | Родной | Ограниченный |
| Стоимость миграции позже | Низкий (обычный текст) | Высокая (экспортная боль) |

### <a name="setup"></a>Настройка

Создайте специальный репозиторий для общих знаний, отдельный от какой-либо кодовой базы. Клонируйте его в стабильный общий путь на каждом компьютере. В этом руководстве уже используется соглашение о каталоге `~/Shared/`:

```bash
# On each team member's machine
git clone git@github.com:yourcompany/knowledge-base.git ~/Shared/knowledge-base
```

Создайте структуру, отражающую мышление команды, а не то, как выглядит организационная структура:

```
~/Shared/knowledge-base/
├── CLAUDE.md                  # Root index (the table of contents)
├── engineering/
│   ├── deploy-runbook.md
│   ├── incident-response.md
│   └── adr/                   # Architecture decision records
│       ├── 001-postgres-over-mongo.md
│       └── 002-event-sourcing.md
├── product/
│   ├── roadmap-process.md
│   └── spec-template.md
├── ops/
│   ├── oncall-rotation.md
│   └── vendor-contacts.md
└── policies/
    ├── security-baseline.md
    └── data-handling.md
```

### <a name="the-root-claudemd-as-index"></a>Корень CLAUDE.md как индекс

Самый полезный файл — это корень `CLAUDE.md`. Он действует как оглавление, сообщающее агенту, что существует и где это найти. Claude Code автоматически читает `CLAUDE.md`, когда каталог находится в области видимости. Cowork читает его, когда ему предоставляется доступ к папке. Хороший корневой индекс не содержит знаний; он указывает на него, поэтому агент загружает только то, что необходимо текущей задаче (прогрессивное раскрытие через файловую систему).

```markdown
# Company Knowledge Base

This repo holds shared static documentation for engineering, product, and ops.
Read the file relevant to your task. Do not guess; if it is not written here,
it is not a company convention.

## Engineering
- Deploy procedure: engineering/deploy-runbook.md
- Incident response: engineering/incident-response.md
- Architecture decisions: engineering/adr/ (one file per decision)

## Product
- How we run roadmap: product/roadmap-process.md
- Spec format: product/spec-template.md

## Ops
- On-call rotation and escalation: ops/oncall-rotation.md
- Vendor and account contacts: ops/vendor-contacts.md

## Policies (read before any external-facing or data work)
- Security baseline: policies/security-baseline.md
- Data handling rules: policies/data-handling.md
```

Это шаблон `~/Shared/CLAUDE.md`, упомянутый в другом месте руководства, расширенный до рабочей структуры. Один и тот же файл обслуживает оба инструмента, поскольку оба инструмента читают файловую систему.

### Обсидиан как дополнительный человеческий слой

Репозиторий — это источник истины и машиночитаемый интерфейс. Людям по-прежнему нужен удобный способ просмотра и редактирования. Obsidian идеально помещается сверху, потому что хранилище Obsidian — это просто папка с файлами Markdown. Наведите Obsidian на `~/Shared/knowledge-base/`, и вы получите обратные ссылки, графическое представление и быстрый редактор, в то время как git внизу сохраняет историю версий, а агент продолжает читать необработанные файлы `.md`.

Ничего об Обсидиане не требуется. Это программа просмотра и редактор для людей, которым она нравится. Агент никогда не видит Обсидиан; он видит Markdown. Если половина вашей команды предпочитает VS Code или обычный текстовый редактор, это работает одинаково. Сохраняйте специфичный для Obsidian синтаксис (вики-ссылки, такие как `[[note]]`, выноски), если вы хотите, чтобы файлы читались чисто, как стандартный Markdown для агента, поскольку глубоко вложенные плагины Obsidian создают синтаксис, который агент должен анализировать.

### Когда достаточно прямого чтения файла

Для статических документов прямое чтение файлов является одновременно самым простым и наиболее точным подходом. Агент открывает файл и считывает точное содержимое без промежуточного слоя поиска. Не существует ни одного шага внедрения, на котором можно было бы пропустить соответствующий отрывок, ни разделения процедуры на два извлеченных фрагмента. Пересечение, при котором масштабирование прекращается, относится к уровню 3. Для типичной команды КБ, состоящей из десятков или нескольких сотен документов, уровень 1 является правильным ответом, и вам следует воздерживаться от добавления инфраструктуры поиска до того, как она вам действительно понадобится.

## <a name="tier-2-mcp-connectors-for-live-systems"></a>Уровень 2: разъемы MCP для работающих систем

Статические документы — это легкая половина. Более сложная половина — это знания, которые живут в системах, которые другие люди обновляют весь день: бэклог Jira, пространство Confluence, CRM, внутренние метрики API. Вы не можете скопировать это в репозиторий Markdown, потому что оно устаревает в тот момент, когда вы его копируете. Доска для спринта меняется каждый час. Запись о клиенте меняется, когда ее касается служба поддержки. Правильный подход — подключить агента к системе записи, чтобы он считывал текущее состояние по требованию.

Механизм — MCP (Model Context Protocol). Сервер MCP представляет действующую систему как набор инструментов, которые может вызывать агент. Claude Code добавляет серверы MCP через свою конфигурацию. Cowork поставляет собственные коннекторы и плагины для распространенных коннекторов. Принцип один и тот же в обоих случаях: агент запрашивает действующий источник, а не синхронизированную копию.

### Atlassian (Jira + Confluence)

Atlassian — наиболее распространенный случай, поскольку многие команды используют Jira и Confluence вместе. Хорошей новостью является то, что одно соединение охватывает оба.

Для Cowork есть собственный плагин Jira. Менеджер проекта, не являющийся разработчиком, может установить его и попросить Cowork прочитать заявки, подвести итоги спринта или составить проект обновления статуса из состояния активной доски, и все это без необходимости прикасаться к терминалу.

Для Claude Code используйте сервер Atlassian Remote MCP, который охватывает как Jira, так и Confluence через одно аутентифицированное соединение:

```bash
# Add the Atlassian Remote MCP server to Claude Code
claude mcp add --transport http atlassian https://mcp.atlassian.com/v1/sse
```

Первый вызов запускает поток OAuth в браузере. После авторизации Claude Code может читать задачи Jira и страницы Confluence с разрешениями аутентифицированного пользователя.

Важное следствие: **, если ваши статические документы уже находятся в Confluence, возможно, вам вообще не понадобится их мигрировать.** То же самое соединение Atlassian MCP, которое читает билеты, также читает страницы Confluence. Это дает агенту постоянный доступ к существующей базе знаний без необходимости миграции. Компромисс по сравнению с уровнем 1 реален (нет истории git, нет проверки pull-запросов, зависимость от коннектора), поэтому решение заключается в том, достаточно ли вы цените эти свойства репо для перемещения контента. Для документов, которые уже хорошо поддерживаются в Confluence и часто изменяются через пользовательский интерфейс вики, оставить их на месте и подключиться через MCP — это путь с меньшими усилиями.

### <a name="notion"></a>Понятие

Notion предлагает официальный удаленный сервер MCP по адресу `mcp.notion.com`, а также плагин Claude Code, который объединяет навыки, специфичные для Notion.

```bash
# Add the official Notion MCP server
claude mcp add --transport http notion https://mcp.notion.com/mcp
```

После установления связи OAuth агент может выполнять поиск в рабочей области, читать страницы и базы данных и (с помощью областей записи) создавать или обновлять контент. Если ваша команда использует свою базу знаний в Notion, это прямой эквивалент случая Atlassian: подключайтесь к действующей рабочей области, а не экспортируйте ее. Уровень плагина добавляет тщательно подобранные навыки (например, структурированный рабочий процесс «создать страницу проекта на основе этой спецификации»), поэтому команда не переописывает одни и те же операции Notion в каждом сеансе.

### GitBook

Если ваша опубликованная документация работает на GitBook, вы получаете доступ к MCP без каких-либо настроек, кроме знания URL-адреса. Каждый опубликованный сайт GitBook предоставляет собственную конечную точку MCP по адресу `/~gitbook/mcp`.

```bash
# Point Claude Code at a GitBook site's native MCP endpoint
claude mcp add --transport http docs https://docs.yourcompany.com/~gitbook/mcp
```

Это дает агенту возможность осуществлять поиск по текущим опубликованным документам, всегда отражая то, что на самом деле видят читатели. Для команд, чья внешняя или внутренняя документация уже находится на GitBook, это самое простое доступное соединение с живой документацией, поскольку нечего размещать и нечего синхронизировать.

### Выбор уровня 1 или уровня 2 для документации

Оба уровня могут содержать «документацию», и выбор между ними не всегда очевиден. Решающий вопрос заключается в том, как меняются документы и какой обзор вы хотите по ним сделать.

| Сигнал | Бережливый уровень 1 (репозиторий Markdown) | Бережливый уровень 2 (MCP в вики) |
|--------|------------------------------|----------------------------|
| Документы изменяются посредством преднамеренных, проверенных изменений. | ✅ | |
| Документы постоянно меняются через веб-интерфейс многими людьми. | | ✅ |
| Вы хотите, чтобы каждое изменение было рассмотрено с помощью запроса на включение | ✅ | |
| Контент уже находится в Confluence/Notion/GitBook и поддерживается. | | ✅ |
| Вам нужна история git, различия и обвинения | ✅ | |
| Вы хотите нулевую миграцию | | ✅ |
| Тот же агент должен также прочитать tickets/records из этой системы. | | ✅ (один разъем охватывает оба) |

Многие команды в конечном итоге получают и то, и другое: технические стандарты и ADR в хранилище Markdown (уровень 1), вики-страницу продукта и билеты через Atlassian или Notion MCP (уровень 2). Это правильно. Эти два уровня не являются конкурентами; они предоставляют контент с разными шаблонами изменений.

## <a name="tier-3-rag-at-scale"></a>Уровень 3: RAG в масштабе

Уровни 1 и 2 охватывают почти каждую команду. Уровень 3 существует для одной конкретной ситуации: у вас так много документов, что агент не может прочитать их напрямую, а поиск по коннектору слишком груб. На этом этапе вы добавляете уровень поиска (RAG, генерация с расширенным поиском), который индексирует корпус и возвращает наиболее релевантные фрагменты для каждого запроса.

### <a name="the-threshold-when-to-add-rag"></a>Порог: когда добавлять RAG

Не добавляйте RAG по умолчанию. Это инфраструктура, а обслуживание инфраструктуры требует затрат. Эталонная картина 2026 года остается неизменной в отношении компромисса:

- **Прямое чтение файла является более точным.** Агент читает фактический документ, поэтому ничего не теряется из-за несоответствия при разбиении на фрагменты или встраивании.
- **RAG ​​быстрее масштабируется.** Он позволяет избежать загрузки больших корпусов в контекст, возвращая только соответствующие фрагменты.

Практическое пересечение составляет примерно от **100 до 1000 документов**, в зависимости от размера документа и объема каждого запроса. Ниже этого диапазона читайте файлы напрямую (уровень 1) или подключайтесь к источнику (уровень 2); агент может перемещаться по нескольким сотням файлов, и вы сохраняете точность прямого чтения. Выше этого диапазона корпус больше не соответствует модели прямого чтения, и уровень RAG, доступный агенту как сервер MCP, становится целесообразным для установки.

| Размер корпуса | Рекомендуемый подход |
|-------------|----------------------|
| < ~100 документов | Прямое чтение файлов (уровень 1) или активное соединение (уровень 2) |
| От ~100 до ~1000 документов | Судебный вызов; начните напрямую, добавьте RAG, если качество поиска упадет |
| > ~1000 документов | Уровень RAG как сервер MCP (уровень 3) |

Сигнал о том, что вы пересекли порог, конкретен: агент начинает пропускать соответствующие документы, о существовании которых вы знаете, потому что он не может хранить или сканировать достаточное количество корпуса для каждой задачи. Если это происходит неоднократно, добавьте извлечение. Не раньше.

### <a name="onyx-self-hosted-open-source"></a>Onyx (самостоятельное размещение, с открытым исходным кодом)

[Onyx](https://github.com/onyx-dot-app/onyx) (ранее Danswer) — это корпоративная RAG-платформа с открытым исходным кодом, которую вы запускаете самостоятельно. Он поставляется как Docker, включает более 50 соединителей (Slack, Google Drive, Confluence, GitHub, Notion и т. д.), выполняет гибридный поиск (ключевое слово плюс вектор) и совместим с Anthropic на стороне генерации.

```bash
# Onyx runs via Docker Compose (self-hosted)
git clone https://github.com/onyx-dot-app/onyx.git
cd onyx/deployment/docker_compose
docker compose -f docker-compose.dev.yml up -d
```

Onyx — хороший выбор, когда данные должны храниться в вашей собственной инфраструктуре и вам нужен единый индекс для многих источников. Одно предостережение, чтобы правильно определить ожидания: Onyx — это, прежде всего, собственная чат-платформа. Он не подключен к Claude Code или Cowork изначально, как разъемы уровня 2. Чтобы использовать его из Claude Code, вы подключаетесь через поверхность API Onyx (представленную перед ним как сервер MCP). Это требует больше работы по интеграции, чем описанные ниже управляемые варианты, и вы берете на себя управление стеком. Результатом является полный контроль и локальное размещение данных, а это именно то, что требуется некоторым командам (см. раздел «Управление»).

### <a name="llamacloud-managed"></a>LlamaCloud (управляемый)

[LlamaCloud](https://cloud.llamaindex.ai/) — это управляемая служба RAG с официальным сервером MCP, что означает, что Claude Code может запрашивать ее напрямую, без запуска стека извлечения.

```bash
# Connect Claude Code to LlamaCloud's managed RAG via its MCP server
claude mcp add --transport http llamacloud https://mcp.llamaindex.ai/sse
```

Вы загружаете и индексируете свой корпус в LlamaCloud, а агент запрашивает индекс с помощью инструментов MCP. LlamaCloud сочетается с LlamaParse для документов, которые не поддаются простому извлечению: сложные PDF-файлы с таблицами, многоколоночные макеты, отсканированные формы. Если ваша база знаний насыщена источниками такого типа (финансовые отчеты, контракты, технические спецификации), LlamaParse — это та часть, которая имеет значение, поскольку чистый анализ — это то, что определяет, возвращает ли извлечение пригодные для использования фрагменты.

### <a name="ragie-fastest-managed-setup"></a>Ragie (самая быстрая управляемая установка)

[Ragie](https://www.ragie.ai/) — это управляемая служба RAG, предназначенная для быстрого повышения рабочего индекса. Если цель состоит в том, чтобы «извлечь наши документы сегодня днем, а не в этом спринте», Ragie — это управляемый вариант с минимальными настройками. Вы указываете ему на свои источники, он индексирует и запрашиваете его у агента. Компромиссом по сравнению с LlamaCloud является широта возможностей синтаксического анализа и настройки управления; Компромисс по сравнению с Onyx заключается в том, что он управляемый (без локального резидентства). Выбирайте его, когда скорость работы индекса важнее, чем точный контроль.

### Сравнение вариантов уровня 3

| Вариант | Хостинг | Усилия по настройке | Родной MCP для кода | Лучше всего, когда |
|--------|---------|--------------|---------------------|-----------|
| **Onyx** | Самостоятельный хостинг (Docker) | Высокий | Нет (через API) | Данные должны оставаться локальными; много источников, один индекс |
| **ЛамаОблако** | Удалось | Середина | Да | Сложные PDF-файлы (LlamaParse); хочу управляемый, но настраиваемый |
| **Раги** | Удалось | Низкий | Да | Самый быстрый путь к рабочему индексу |

## <a name="the-plugin-pattern-distributing-team-workflows"></a>Шаблон плагина: Распределение рабочих процессов команды

Третья форма знаний из первой таблицы – это вообще не документы. Это многократно используемое поведение: команды, навыки, агенты и подсказки, которые кодируют работу вашей команды. Команда `/deploy-checklist`, навык `incident-summary`, агент проверки кода, настроенный на ваши стандарты. Это не контент для хранения; это поведение для распространения, а механизм распространения — это плагин.

### Храните контент в хранилище, поведение в плагине

Четкое разделение, которое сохраняется на всех трех уровнях: контент **находится в хранилище (уровень 1) или в исходной системе (уровень 2/3); поведение живет в плагине.** Плагин не встраивает базу знаний. Он ссылается на это. Навык, который суммирует инциденты, читает документацию по инцидентам из `~/Shared/knowledge-base/engineering/`; навык — это поведение, документация — это контент. Это позволяет каждому обновляться в своем собственном цикле. Вы вносите изменения в Runbook, не перевыпуская плагин, и улучшаете рабочий процесс, не затрагивая документацию.

### Какие пакеты плагинов

Пакеты плагинов Claude Code в одном устанавливаемом модуле:

- **Slash-команды** (`commands/`): именованные рабочие процессы, которые вызывает команда, например `/release` или `/oncall-handoff`.
- **Skills** (`skills/`): структурированные возможности, которые агент загружает при необходимости.
- **Agents** (`agents/`): специализированные субагенты со своими инструкциями и инструментами.
- **MCP configs**: определения разъемов Tier 2/3, поэтому установка плагина также обеспечивает доступ к работающей системе.

Именно этот последний момент делает плагин подходящим местом для всего уровня доступа к базе знаний. Новый член команды устанавливает один плагин и получает настроенные команды команды, навыки команды и соединения MCP команды с Jira, Notion или индексом RAG. Они не редактируют вручную конфигурацию MCP и не копируют командные файлы.

### Распространение через marketplace.json

Плагины распространяются через торговую площадку — репозиторий git с манифестом `marketplace.json`, в котором перечислены доступные плагины. Команда публикует свой плагин во внутреннем (или общедоступном) репозитории торговой площадки, и участники устанавливают из него:

```bash
# Add the team's marketplace, then install the KB plugin
claude plugin marketplace add yourcompany/claude-plugins
claude plugin install knowledge-base
```

Минимальная запись `marketplace.json`:

```json
{
  "name": "yourcompany-plugins",
  "plugins": [
    {
      "name": "knowledge-base",
      "description": "Team KB access: commands, skills, and live-system MCP connectors",
      "source": "./plugins/knowledge-base"
    }
  ]
}
```

Когда вы улучшаете команду или добавляете навык, вы отправляете ее в репозиторий Marketplace, и команда обновляется с помощью одной команды. Знания о рабочих процессах остаются версионированными и проверяются, как и статические документы, и распространяются среди всех без копирования файлов вручную. Это именно та модель, которую использует собственная экосистема [plugins](https://github.com/FlorianBruniaux/claude-code-plugins) этого руководства: шаблоны, созданные однажды, которые распространяются в виде устанавливаемых плагинов.

## Предостережение в отношении управления и чувствительности

Приведенная выше архитектура оптимизирована для доступа. Прежде чем подключить к нему конфиденциальный корпус, честно взвесьте сторону управления, потому что здесь два агентских инструмента находятся на разных уровнях зрелости.

### Текущие пробелы Cowork

По состоянию на середину 2026 года Cowork является предварительной исследовательской версией, и в ее управлении предприятием есть пробелы, которые имеют значение для регулируемых или конфиденциальных данных. В частности, два:

- **Журналы аудита**: журналы аудита корпоративного уровня, доступные для запроса, о том, к чему получал доступ и что делал агент, еще не завершены. Если ваша позиция по соблюдению требований требует полной записи каждого прочитанного документа и каждого предпринятого действия, Cowork пока не предоставляет вам этого.
- **DLP (предотвращение потери данных)**: интеграция с корпоративными инструментами DLP ограничена. Средства контроля, предотвращающие выход конфиденциальных данных за утвержденные границы, не настолько зрелы, как в устоявшемся корпоративном программном обеспечении.

Практическая рекомендация: Cowork подходит для внутренних, но не секретных знаний (документация процессов, контекст продукта, общие операции), пока эти пробелы закрываются. Это еще не инструмент, позволяющий выявить наиболее конфиденциальный корпус данных, если вы работаете в соответствии со строгими требованиями аудита или DLP. Claude Code с его более устоявшейся системой разрешений и перехватов дает вам больше точек контроля, но вам все равно следует проверять соответствие вашим конкретным требованиям соответствия, а не предполагать покрытие.

### Когда данные должны оставаться локальными

Если данные настолько конфиденциальны, что вообще не могут покинуть вашу инфраструктуру, ответом будет не «подключить облачный сервис RAG». Это значит держать все внутри границ, которые вы контролируете. Соответствующий шаблон, находящийся в предварительной версии исследования по состоянию на май 2026 года, — это самостоятельные корпоративные песочницы с частными туннелями MCP: агент работает в изолированной программной среде в вашей инфраструктуре, а его соединение с внутренней базой знаний осуществляется через частный туннель MCP, который никогда не раскрывает данные извне. Вариант с автономным размещением уровня 3 (Onyx) соответствует этой модели со стороны поиска, поскольку индекс и документы остаются на вашем оборудовании.

Это больше настройки, чем любой управляемый путь. Дело в том, что такая опция существует, поэтому «наши данные слишком чувствительны для облака» — это вопрос конфигурации, а не повод полностью отказаться от агентской базы знаний. Сопоставьте развертывание с конфиденциальностью данных, а не навязывайте один подход ко всем этим данным.

### <a name="a-documented-reference-point"></a>Документированная точка отсчета

В собственной документации Anthropic показан шаблон live-KB-via-MCP в действии. Пример конечной точки `https://kb.internal.example.com/mcp`, описанной как «Внутренняя база знаний и поиск документации», представляет собой каноническую форму: внутренняя база знаний, представленная как сервер MCP, который агент запрашивает по требованию. Это уровень 2 (или уровень 3 за ним) для самостоятельной базы знаний, и это шаблон, который обеспечивает описанный выше подход к изолированной программной среде с собственным размещением.

## Что делать в первую очередь

Ошибка в начале этого раздела заключалась в использовании одного инструмента. Исправление состоит в том, чтобы классифицировать каждую часть знаний по ее характеру, а затем применить соответствующий уровень. Вот путь принятия решения, начиная с самой распространенной отправной точки и далее.

### <a name="decision-table"></a>Таблица решений

| Если ваша ситуация... | Начните с | Зачем |
|-------------------------|------------|-----|
| Статические командные документы, от десятков до нескольких сотен файлов. | **Tier 1**: хранилище уценки в `~/Shared/`, корневой индекс `CLAUDE.md` | Оба инструмента читают его напрямую, полная история, без разъема. |
| Документы уже хорошо поддерживаются в Confluence/Notion/GitBook. | **Tier 2**: разъем MCP для этой системы. | Нулевая миграция; один разъем также охватывает tickets/records |
| Нужны живые билеты, состояние спринта, записи CRM | **Tier 2**: Atlassian/Notion/источник MCP | Живой источник истины, никогда не устаревшая копия |
| Более ~1000 документов и агент что-то упускает | **Tier 3**: RAG как MCP (управляемый LlamaCloud/Ragie, автономный хостинг Onyx) | Масштабируемость извлечения превышает предел прямого чтения |
| Многоразовые командные команды, навыки и агенты, которыми можно поделиться | **Плагин** через `marketplace.json` | Поведение распространяется как один устанавливаемый модуль, включая конфигурации. |
| Конфиденциальные данные, которые не могут покинуть вашу инфраструктуру | **Самостоятельное размещение** (Onyx + частный туннель MCP/корпоративная песочница) | Резиденция на территории, агент остается внутри вашей границы |

### Рекомендуемая последовательность действий для новой команды

1. **Сначала поднимитесь на уровень 1.** Создайте общий репозиторий Markdown, запишите корневой индекс `CLAUDE.md`, клонируйте его в `~/Shared/` на каждом компьютере. Одно это покрывает большую часть того, что нужно как Code, так и Cowork, и его дешево поддерживать. Не поддавайтесь добавлению инфраструктуры поиска до того, как у вас появятся доказательства того, что она вам нужна.

2. **Подключите одну или две наиболее важные работающие системы.** Обычно Jira (Atlassian MCP) для проектирования и разработки продуктов, а также любая вики, в которой хранятся ваши существующие документы, если вы решите не переносить их. Добавляйте соединители уровня 2 по одному, а не все сразу.

3. **Упакуйте свои повторяющиеся рабочие процессы в виде плагина**, как только вы заметите, что команда переописывает одни и те же операции в каждом сеансе. Опубликуйте его на внутреннем рынке, чтобы установка стала одной командой. Сохраняйте содержимое в хранилище, а поведение — в плагине.

4. **Добавляйте слой RAG только тогда, когда корпус перерастает прямое чтение.** Сигналом является то, что агент постоянно пропускает документы, о существовании которых вы знаете. Пока этого не произойдет, уровень 3 представляет собой затраты без выгод.

5. **Проверьте управление в соответствии с фактической конфиденциальностью ваших данных**, прежде чем направлять любой инструмент на конфиденциальный корпус, уделяя особое внимание текущему аудиту Cowork и пробелам в DLP. Для данных, которые не могут покинуть вашу инфраструктуру, с самого начала размещайте их на собственном хостинге, а не модернизируйте их позже.

Команды, добившиеся успеха, рассматривают эти проблемы как три отдельные проблемы с тремя отдельными инструментами, объединенными вместе через MCP и плагины, а не как одно решение по хранению, которое им нужно заранее получить идеально. Начните с хранилища Markdown, подключите работающие системы, которые вы фактически запрашиваете, и добавляйте масштабирование и упаковку по мере необходимости.
