# MCP против CLI: Руководство по принятию решений

**Последнее обновление**: май 2026 г.

> Интерактивная версия с таблицей рекомендаций и цитатами специалистов: [cc.bruniaux.com/ecosystem/mcp-vs-cli/](https://cc.bruniaux.com/ecosystem/mcp-vs-cli/)

Дебаты возникли из-за быстрой смены парадигм интерфейса: ИИ на основе браузера (2022–2023 гг.), затем ИИ в IDE с MCP, подключающим агентов к внешним сервисам (2024–25 гг.), затем полные агенты CLI, которые выполняют команды и записывают файлы без промежуточного слоя (2025–26 гг.). Эта прогрессия объясняет, почему этот вопрос вообще существует.

На этой странице сравниваются два шаблона интеграции для предоставления Claude Code доступа к внешним инструментам и сервисам: серверам MCP и инструментам CLI. Ни то, ни другое не лучше в целом. Правильный выбор зависит от вашего контекста, и в большинстве реальных рабочих процессов используются оба варианта.

---

## Что делает каждый подход

Серверы **MCP** внедряют схемы инструментов в контекст Claude при запуске сеанса. Claude видит структурированный список доступных инструментов с параметрами, типами и описаниями. Затем он вызывает эти инструменты естественным образом, получая структурированные ответы.

**CLItools** — это команды оболочки, которые Claude вызывает через Bash. Claude управляет ими так же, как это делает разработчик: создает командные строки, анализирует текстовый вывод. Никакого внедрения схемы при запуске. Оболочка — это интерфейс.

## <a name="tradeoffs"></a>Компромиссы

### Сильные стороны MCP

| Преимущество | Деталь |
|-----------|--------|
| **Структурированный интерфейс** | Схемы инструментов точно направляют Claude, меньше галлюцинаторных флагов или аргументов. |
| **Комплексная аутентификация** | OAuth, обновление токена, ротация секретов обрабатывается сервером, а не запросом |
| **Структурированный выход** | Ответы JSON могут анализироваться напрямую Claude и нижестоящими агентами. |
| **Наблюдаемость** | Удаленные серверы MCP могут регистрировать каждый вызов, что важно для отслеживания использования предприятия и определения рентабельности инвестиций. |
| **Распространение в масштабе** | Обновите сервер один раз, и все подключенные клиенты получат изменения. Нет управления пакетами на каждой машине. |
| **Нетехнические пользователи** | Пользователи, которые никогда не прикасаются к терминалу, могут получить прозрачный доступ к инструментам через разъемы MCP. |
| **Слабые модели** | Структурированная схема компенсирует ситуацию, когда модель менее способна анализировать текст справки CLI. |

### Сильные стороны CLI

| Преимущество | Деталь |
|-----------|--------|
| **Нулевые издержки контекста** | Никакая схема не внедряется при запуске. Начиная с версии 2.1.7 отложенная загрузка закрывает большую часть разрыва, но CLI по-прежнему остается абсолютным минимумом. |
| **Детерминированные действия** | Явные команды с предсказуемым выводом легче проверять и тестировать. |
| **Использование человека и искусственного интеллекта** | Одна и та же оболочка CLI работает для разработчика, запускающего ее вручную, и для Claude. |
| **Модели Frontier** | Claude Opus/Sonnet (текущее поколение) может управлять сложными интерфейсами командной строки (aws-cli, glab, gh) без структурированной схемы. |
| **Скорость** | Нет настройки соединения, нет подтверждения связи MCP, прямое выполнение подпроцесса |
| **Простота** | Легче отлаживать, регистрировать и рассуждать, чем цепочку вызовов удаленного сервера. |
| **Инкапсуляция навыков** | CLI, завернутый в навык, прозрачен для пользователя и обеспечивает контроль версий логики инструмента. |

### Слабые стороны MCP

| Слабость | Деталь |
|----------|--------|
| **Стоимость токена схемы** | Начиная с версии 2.1.7, отложенная загрузка (поиск инструментов MCP) означает, что неиспользуемые инструменты вводят только свое имя, а не полную схему. Стоимость по-прежнему не равна нулю: имена инструментов загружаются при запуске, полные схемы загружаются при первом использовании. Худший случай до версии 2.1.7 (~55 тыс. токенов для установки из 5 серверов) теперь составляет в среднем ~8,7 тыс. (снижение на 85%), но не ноль. |
| **Накладные расходы на соединение** | Запуск сеанса занимает больше времени, если подключено много серверов MCP. |
| **Трудность отладки** | Сбои внутри сервера MCP труднее отследить, чем неудачную команду оболочки. |
| **Сложность обслуживания** | Запуск, обновление и защита удаленных серверов MCP расширяет инфраструктуру. |
| **Overkill для простых API** | GitLab MCP, который отображает 20% функциональности glab, хуже, чем сам glab. |

### Слабые стороны CLI

| Слабость | Деталь |
|----------|--------|
| **Нет наблюдаемости** | Команды оболочки на локальном компьютере невидимы для инструментов ops/management. |
| **Проблема с распространением** | Обновление CLI в команде требует дисциплины управления пакетами (brew, scoop и т. д.). |
| **Борьба с более слабыми моделями** | Менее способная модель может галлюцинировать флаги или неправильно читать текст справки; схемы помогают |
| **Нет мультиагентной структуры** | Вывод CLI требует синтаксического анализа; структурированные ответы MCP более надежны при передаче обслуживания от агента к агенту |
| **Нетехнический пользовательский барьер** | Нельзя ожидать, что у нетехнического пользователя будет настроенная среда CLI. |

## Шаблон оболочки API

Большинство производственных серверов MCP для инструментов SaaS работают поверх существующих API-интерфейсов REST или GraphQL. Сервер преобразует вызовы инструментов в запросы HTTP к этим API, обрабатывает ответы и возвращает структурированный вывод агенту. Он не добавляет серверных возможностей, которых нет в базовом API.

Официальная документация четырех крупных провайдеров подтверждает это напрямую:

- **Notion**: «преобразованы вызовы инструментов MCP в вызовы HTTP API в общедоступный API Notion» (блог Notion Engineering)
- **Sentry**: «промежуточное программное обеспечение для вышестоящего Sentry API, оптимизированное для помощников по кодированию, таких как Cursor и Claude Code» (sentry-mcp README)
- **Slack**: «обертка внешнего API, такая как Slack» (документация разработчика Slack)
- **GitHub**: «интегрируется с GitHub, позволяя LLM взаимодействовать с репозиториями через GitHub API» (github-mcp-server README)

Практический вывод: скрипт CLI, вызывающий тот же REST или GraphQL API, имеет те же возможности. MCP и CLI достигают одного и того же бэкэнда с одинаковыми учетными данными и запускают одни и те же операции. Разница заключается в уровне интерфейса, а не в том, что может делать серверная часть.

Что добавляет MCP и что CLI не может реплицировать:

- **OAuth управление токенами**: аутентификация на сервере с потоками перенаправления браузера (Slack, Google Drive, Figma, размещенный Notion). CLI может содержать ключ API в переменной env, но не токен обновления или обмен PKCE, для которых требуется состояние на стороне сервера.
- Схемы, настроенные на **LLM**: тщательно подобранный инструмент, а не полная поверхность API, с типами параметров и описаниями, откалиброванными для рассуждений агента.
- **Централизованный хостинг**: одно развертывание обслуживает множество клиентов; Интерфейсы командной строки требуют установки для каждого компьютера и настройки учетных данных для каждого пользователя.
- **Атрибуция использования**: удаленные серверы MCP связывают каждый вызов инструмента с пользователем и сеансом, предоставляя информационные панели наблюдения. Локальные вызовы CLI на машинах разработчиков невидимы.

Это обостряет критерий принятия решения. Если служба аутентифицируется с помощью ключа API или токена среды, CLI, вызывающий тот же API, функционально эквивалентен серверу MCP. Возникает вопрос, нужен ли вам OAuth, централизованная наблюдаемость или межклиентская стандартизация. Если ни один из них не применим, CLI избегает накладных расходов схемы и достигает того же бэкэнда.

## <a name="the-four-decision-dimensions"></a>Четыре аспекта принятия решения

Прежде чем спрашивать «MCP или CLI?», ответьте на эти четыре вопроса. Они ранжируются от наиболее ограничивающих к наименее ограничивающим.

### 1. Кто конечный пользователь?

Это доминирующая переменная. Все остальное вторично.

- **Пользователь без технических знаний** (использует интерфейс чата, без терминала) → **MCP или CLI**с инкапсулированными навыками. Вы не можете предоставить необработанный CLI пользователю, не являющемуся разработчиком. Соединители должны быть основаны на MCP или скрытно заключены в навык, который внутренне обрабатывает CLI.
- **Технический пользователь/разработчик** → перейти к вопросу 2.

### 2. Какая модель управляет инструментом?

- **Frontier модель** (Claude Opus/Sonnet, текущее поколение) → достаточно мощная, чтобы напрямую управлять сложными интерфейсами командной строки. Структурированная схема MCP добавляет накладные расходы без пропорциональной выгоды.
- **Меньшая или локальная модель** (Qwen, Mistral, более легкие варианты развертывания) → структурированные схемы MCP компенсируют более слабую способность анализа CLI. MCP здесь надежнее.

### 3. Нужна ли вашей организации наблюдаемость?

- **Да** (корпоративный, отчетность уровня C, соответствие требованиям, атрибуция рентабельности инвестиций в ИИ) → **MCP Удаленный сервер**. Локальные вызовы CLI невидимы. Удаленный сервер MCP может регистрировать каждый вызов инструмента, связывать его с пользователем и передавать информационные панели. Вы не можете повторить это с помощью CLI на локальных машинах.
- **No** (индивидуальная разработка, локальный рабочий процесс) → наблюдаемость не является ограничением. CLI в порядке.

### 4. Как часто меняется схема инструмента?

- **Стабильный API** (зрелый инструмент, интерфейс с поддержкой версий) → Инвестиции в MCP со временем окупаются.
- **Быстрая смена** или **тонкая обертка** → CLI дешевле в обслуживании. Свернутая вручную оболочка, которая отображает только 5 команд, которые вы действительно используете, более долговечна, чем GitLab MCP, которая дублирует всю поверхность API.

## <a name="guidance-by-situation"></a>Руководство по ситуации

Краткая справка, не правила, а направления по умолчанию.

| Ситуация | Наклониться к | Обоснование |
|-----------|-------------|-----------|
| Нетехнический пользователь, интерфейс чата | **MCP / Навык** | CLI недоступен; разъемы должны быть незаметны |
| Модель Frontier (Claude, текущее поколение), рабочий процесс разработчика | **CLI** | Модель обрабатывает это изначально; схемы являются накладными |
| Модель Smaller/local | **MCP** | Схема надежно направляет модель |
| Предприятие, требуется наблюдаемость | **MCP Пульт дистанционного управления** | Единственный способ регистрации, атрибутирования и составления отчетов об использовании. |
| Распределение команд (10+ разработчиков) | **MCP** | Централизованное обновление или обслуживание CLI для каждой машины |
| Индивидуальная разработка, локальная машина | **CLI или навык** | Проще, быстрее, без инфраструктуры |
| Детерминированные действия (git, CI, развертывание) | **CLI** | Явные команды, предсказуемый результат, проверяемый |
| Сложная аутентификация (OAuth, обновление токена) | **MCP** | Сервер обрабатывает аутентификацию; CLI потребует удостоверения сантехника |
| Ограниченный контекстный бюджет / загружено много инструментов | **CLI** | Все еще вариант с минимальными накладными расходами. Отложенная загрузка (v2.1.7+) значительно снижает стоимость MCP, но CLI изначально имеет нулевую стоимость схемы. |
| Структурированный вывод от агента к агенту | **MCP** | Ответы JSON более надежны, чем анализируемый текст CLI. |
| Отладка/прототипирование новой интеграции | **CLI** | Легче проверять, быстрее выполнять итерации |
| Автоматизация браузера (безграничная модель) | **MCP** | Playwright MCP надежно структурирует взаимодействие. |
| Автоматизация браузера (пограничная модель, Claude Code) | **CLI + навык** | playwright-cli + навык сообщается быстрее и эффективнее на практике |
| Доступ GitLab / GitHub | **CLI** (глаб, гх) | Официальные интерфейсы командной строки богаче, чем большинство оболочек MCP. |
| Поиск документации (Context7) | **MCP** | Нет эквивалента CLI; структурированный поиск документов не имеет аналога оболочки |

## Рекомендация для каждого сервера

В таблице ниже четыре параметра принятия решений применяются к 18 наиболее часто обсуждаемым серверам MCP. «Вердикт» — значение по умолчанию для разработчика, использующего пограничную модель на локальном компьютере. Ваш контекст (нетехнические пользователи, корпоративная наблюдаемость или меньшая модель) может сместить любую строку в сторону MCP.

| MCP Сервер | Вердикт | CLI Альтернатива | Причина |
|------------|---------|-----------------|--------|
| GitHub MCP | **Используйте CLI** | `gh` | `gh` покрывает всю поверхность API; модель знает это по тренировкам; официальный GitHub MCP был заархивирован |
| GitLab MCP | **Используйте CLI** | `glab` | Официальный CLI богаче обертки MCP; консенсус практиков подтверждает |
| Гит MCP (Anthropic) | **Используйте CLI** | `git` | Git — это CLI, который модель знает лучше всего; Схема MCP увеличивает стоимость без структурных преимуществ для передовых моделей. |
| Файловая система MCP | **Используйте CLI** | `cat`, `ls`, `find` | Команды оболочки универсальны; никакой пользы от накладных расходов на схему |
| Docker MCP | **Используйте CLI** | `docker` | Docker CLI широко известен; отсутствие широко распространенного MCP не добавляет сопоставимой ценности |
| АВС MCP | **Используйте CLI** | `aws-cli` | aws-cli v2 покрывает всю поверхность; модель исходит из знаний обучения |
| Терраформировать MCP | **Используйте CLI** | `terraform` | Детерминированный рабочий процесс plan/apply; Вывод CLI структурирован и доступен для проверки. |
| Семгреп MCP | **Используйте CLI** | `semgrep` | Зрелый CLI, хорошо документированный; MCP повышает ценность главным образом в контексте наблюдаемости CI/CD. |
| Playwright MCP | **Зависит** | `playwright-cli` + навык | Модель Frontier: CLI + навык быстрее. Меньшая модель: MCP надежно структурирует взаимодействие с браузером. |
| Kubernetes MCP | **Зависит** | `kubectl` | Сложность аутентификации и многокластерные настройки отдают предпочтение MCP; простые операции предпочитают kubectl |
| Версель MCP | **Зависит** | `vercel` CLI | CLI для развертывания, окружения и доменов; MCP за интеграцию информационной панели и комментарии к рабочему процессу команды. |
| Часовой MCP | **Используйте MCP** | `sentry-cli` (с областью действия CI/CD) | `sentry-cli` обрабатывает выпуски, загрузку исходных карт и операции CI/CD, но не имеет эквивалента для интерактивного запроса проблем. MCP обеспечивает структурированную сортировку ошибок для агентов кодирования. |
| Слабый MCP | **Используйте MCP** | никто | Требуется OAuth; нет практичного CLI для доступа к рабочей области со стороны агента |
| Понятие MCP | **Используйте MCP** | никто | Требуется OAuth; Доступ по ключу API ограничен интеграциями, а не доступом к рабочей области на уровне пользователя. |
| Гугл Диск MCP | **Используйте MCP** | никто | OAuth 2.1 с ротацией токенов обновления; не может быть воспроизведен навыком или CLI |
| Фигма MCP | **Используйте MCP** | никто | Требуется OAuth; доступ к файлу проекта не имеет эквивалента CLI |
| Линейное MCP | **Используйте MCP** | никто | MCP обрабатывает сложность GraphQL; структурированное управление проектами без сырых вызовов API |
| Контекст7 MCP | **Используйте MCP** | никто | Нет эквивалента CLI для курируемого поиска документов по конкретной версии. |

Шаблон: если у сервиса есть зрелый CLI, который модель знает из обучения, используйте CLI. Если служба требует OAuth или не имеет CLI, используйте MCP. «Зависит» означает, что решение зависит от возможностей модели или конкретных потребностей рабочего процесса.

## Гибрид по умолчанию

Большинство производственных рабочих процессов не выбирают один. Они используют оба, каждый из которых покрывает тот слой, с которым он лучше всего справляется.

**A Практический пример** (от практиков):

- **Внутренний слой** (локальная итерация разработки, git, операции с файлами, сценарии оболочки) → CLI, быстрый, детерминированный, без накладных расходов
- **Внешний уровень** (CI/CD, общая инфраструктура, межгрупповые услуги) → MCP Удаленный, наблюдаемый, централизованный, масштабируемый
- **Skill Layer** (действия с пользователем, инструменты CLI, инкапсулированные для нетехнических пользователей) → CLI, обернутые навыками, прозрачные для конечного пользователя

Ошибка заключается в применении одного ответа к обоим слоям. Индивидуальный разработчик, создающий для себя рабочий процесс Claude Code, должен в основном использовать CLI. Команда, предоставляющая ИИ-помощника коллегам, не имеющим технических знаний, в основном должна использовать MCP.

## <a name="token-cost-of-mcp-schemas-what-the-numbers-look-like"></a>Стоимость токена схем MCP: как выглядят цифры

Начиная с версии 2.1.7 (январь 2026 г.), Claude Code по умолчанию использует **MCP Tool Search** (отложенная загрузка). Это существенно меняет математику токена, но не устраняет полностью стоимость схемы.

**Как работает отложенная загрузка:** вместо внедрения всех схем инструментов в начале сеанса Claude получает только имена инструментов в блоке `<available-deferred-tools>`. Полные схемы извлекаются через `ToolSearch` только тогда, когда Claude решает вызвать определенный инструмент. Неиспользуемые инструменты в сеансе стоят только их имени в контексте (~0 токенов схемы), а не полного определения.

**Измеренное влияние** (тесты Anthropic, установка с 5 серверами):

| Сценарий | Накладные расходы токена | Примечание |
|----------|---------------|------|
| До версии 2.1.7 (быстрая загрузка) | ~55 000 токенов | Все схемы предварительно загружены |
| После версии 2.1.7 (ленивая загрузка) | ~8700 токенов | снижение на 85% |
| CLI (нет MCP) | ~0 жетонов | Базовый уровень |

Старое утверждение о наихудшем случае «500–2000 токенов на сервер» описывало нетерпеливую загрузку, которая больше не используется по умолчанию. При отложенной загрузке стоимость неиспользуемого сервера близка к нулю. Стоимость одного сервера *used* (около 600 токенов на каждую схему инструмента, загружаемую по требованию) остается реальной, но теперь оплата по факту использования, а не постоянная.

**Что еще добавляет накладные расходы даже при отложенной загрузке:**

- Имена инструментов по-прежнему вводятся при запуске (одна строка на инструмент на сервере).
- Схемы загружаются при первом вызове; длительные сеансы с использованием множества инструментов приводят к накоплению затрат
- Настройка соединения для каждого сервера не изменилась (задержка, а не токены)
- Многие подключенные серверы MCP по-прежнему означают больше имен в контексте, даже если схемы остаются отложенными.

**Configuration** (v2.1.9+): переменная среды `ENABLE_TOOL_SEARCH` управляет пороговым значением. `auto:N` запускает отложенную загрузку, когда инструменты MCP превышают N% контекста (по умолчанию 10%).

**Стратегии смягчения последствий** (все еще актуально, более низкая срочность):

- Загружайте серверы MCP выборочно для каждого проекта (конфигурация уровня проекта или глобальная конфигурация)
- Используйте инструменты CLI для высокочастотных узких контуров, где любые накладные расходы (компилировать → тестировать → исправлять)
- Отслеживайте использование токенов за сеанс, чтобы определить, какие схемы загружаются во время вызова.
- Рассмотрите оболочку CLI для инструментов, которые вы используете постоянно, но не нуждаетесь в структурированном выводе из

## <a name="mcp-vs-skills"></a>MCP против навыков

Навыки (`.claude/skills/*.md`) — это третья парадигма интеграции, отличная как от серверов MCP, так и от инструментов CLI. Объединение их с CLI — самая распространенная ошибка в этой области.

**Что делает каждый слой:**

- **Skills** кодирует *как должен вести себя агент*: пошаговые рабочие процессы, деревья решений и СОПы, написанные в уценке. Они загружаются по требованию в контекст агента и направляют его рассуждения без внедрения схем внешних инструментов.
- Серверы **MCP** обеспечивают *структурированный доступ к внешним системам* (API, базам данных, файловым системам) с помощью типизированных интерфейсов инструментов, которые агент вызывает напрямую.
- Инструменты **CLI** обеспечивают *доступ к внешним системам через командную строку.*: агент создает команды оболочки и анализирует текстовый вывод.

Навыки и MCP касаются разных уровней, а не одной и той же проблемы. Навык может описывать, когда и как вызвать инструмент MCP (отметьте это поле, затем вызовите этот инструмент), в то время как сервер MCP обрабатывает фактическое соединение. Спрашиваю: «Написать навык или сервер MCP?» обычно означает, что слои объединяются.

### <a name="the-oauth-boundary"></a>Граница OAuth

Это самое явное структурное преимущество MCP перед навыками, и это не вопрос удобства.

Навык может дать указание агенту «пройти аутентификацию на Google Диске, прежде чем продолжить». Чего он не может сделать, так это хранить токен обновления, выполнить перенаправление браузера или управлять обменом PKCE. Для этих операций требуется состояние на стороне сервера, которого нет в файле уценки.

Для корпоративных SaaS API (Google Workspace, Salesforce, Slack, GitHub) требуется OAuth 2.1 с ротацией токенов обновления. Когда используется такой механизм аутентификации, MCP не просто более удобен: это единственный вариант, который работает без запроса пользователя вручную вставлять учетные данные в начале каждого сеанса.

Практический тест: если служба аутентифицируется с помощью ключа API в заголовке, с этим может справиться навык или CLI. Если для этого требуется токен перенаправления браузера или токен обновления на сервере, он принадлежит MCP.

### Консенсус сообщества (2026 г.)

Дебаты в основном остановились на трехуровневой модели, а не на бинарном выборе:

- **Навыки** обрабатывает *что делать и когда*: оркестровка рабочего процесса, руководство принятием решений, воспроизводимое поведение агента
- **MCP** обрабатывает *подключение и аутентификацию.*: внешние системы, которым требуются структурированные интерфейсы, OAuth или корпоративная наблюдаемость.
- **CLI** обрабатывает *детерминированные локальные операции*: git, операции с файлами, средства запуска тестов и все, что модель может использовать непосредственно на основе знаний обучения.

Конвергенция теперь является частью спецификации: SEP-2640 («Навыки выше MCP») предлагает распределять навыки в виде ресурсов MCP, поэтому пользователи устанавливают рабочие процессы так же, как они устанавливают серверы инструментов. Две парадигмы скорее объединяются, чем вынуждаются конкурировать.
