# Шаблоны проектирования навыков

> **Связанные**: [Методологии разработки](./methodologies.md) | [Координация нескольких агентов](../ultimate-guide.md#920-agent-teams-multi-agent-coordination)

Практические шаблоны для развития навыков, выходящие за рамки командной строки для одного агента и одного файла. Эти шаблоны касаются конкретных режимов сбоев: субагенты, которые повторно обнаруживают одни и те же факты, правила, которые применяются к неправильным файлам, навыки, которые размывают обнаружение и исправление.

---

## <a name="shared-ground-truth-injection"></a>Совместное внедрение истины

**Проблема**: Когда вы запускаете N параллельных субагентов для аудита или анализа набора артефактов, каждый агент независимо обнаруживает одни и те же базовые факты (список файлов, структура навигации, команды CLI, схема). Это N избыточных операций чтения, N независимых фактов, которым можно доверять, и N шансов, что один агент увидит устаревшее состояние файла.

**Pattern**: Оркестратор один раз вычисляет общую фактическую базовую линию, а затем дословно вводит один и тот же блок в каждое приглашение субагента.

```
Orchestrator (Phase 1)
  ├── Read nav structure → extract groups
  ├── Glob files → get current list
  ├── List CLI commands → get current commands
  └── Compile into "Ground Truth" string

Orchestrator (Phase 2)
  ├── Agent 1 prompt: "## Ground Truth\n{shared block}\n\n## Your Scope\nSection A"
  ├── Agent 2 prompt: "## Ground Truth\n{shared block}\n\n## Your Scope\nSection B"
  └── Agent 3 prompt: "## Ground Truth\n{shared block}\n\n## Your Scope\nSection C"
```

**Что находится в общем блоке**:
- Навигация или иерархия файлов (чтобы каждый агент знал, что существует)
- Текущие команды CLI или конечные точки API (для перехвата ссылок на удаленные команды)
- Список сущностей домена (пакеты, модули, сервисы)
- Текущая дата (чтобы отследить ссылки на устаревшие версии)

**Почему это работает**: Каждый агент запускается с одного и того же снимка. Агент не может галлюцинировать существующую команду CLI, если основной список истины показывает, что это не так. Оркестратор — единственный источник истины для структуры; Субагенты являются единственным источником достоверной информации о содержимом назначенного им раздела.

**Компромисс токенов**: общий блок добавляет токены к каждому приглашению субагента. Для параллельного аудита с участием 5 агентов блок наземных данных из 500 токенов стоит 2500 токенов авансом. Устранение повторного обнаружения каждого агента экономит эти затраты, а то и некоторые. Размер блока соответствует тому, что действительно необходимо, а не всему, что вы могли бы включить.

**Примечание по реализации**: Блок основной истины должен быть строкой, а не ссылкой на файл. Если вы укажете агентам «прочитать `docs.json`», каждый агент прочитает его независимо. Скомпилируйте его один раз в оркестраторе и вставьте.

## <a name="pre-filtered-references-via-frontmatter-paths"></a>Предварительно отфильтрованные ссылки по путям заголовка

**Проблема**: у вас есть набор файлов правил (стандарты кодирования, политики безопасности, руководства по стилю). Каждый из них применяется к определенному подмножеству файлов в базе кода. Если вы передаете все правила агенту проверки, агент применяет правила к файлам, для которых они не были написаны, что приводит к ложным срабатываниям и потере контекста.

**Pattern**: добавьте поле заголовка `paths:` в каждый файл правил с шаблоном glob. Перед запуском агентов проверки оркестратор считывает этот заголовок, сопоставляет glob со списком измененных файлов и передает каждому агенту только применимые правила.

```yaml
# .claude/rules/standard-testing-good-practices.md
---
name: Testing Good Practices
paths: "**/*.spec.ts,**/*.test.ts"
alwaysApply: false
description: Testing conventions for TypeScript unit and integration tests
---

## Rules
- Use `describe` blocks for grouping related tests
...
```

Логика оркестратора (простые шаги):

```
1. Glob .claude/rules/**/*.md → list all rule files
2. For each rule file:
   a. Read YAML frontmatter → extract paths (glob pattern)
   b. If alwaysApply: true → include unconditionally
   c. If alwaysApply: false → match paths against modified files list
   d. Include if at least one modified file matches the glob
3. Pass the filtered rule set to each review agent
```

**Основные преимущества**:
- Тестовый файл не проверяется на соответствие правилам безопасности серверной части.
- Файл миграции не проверяется на соответствие руководствам по стилю интерфейса.
- Контекст каждого агента содержит только действенные правила для того, что он просматривает.

**Scaling**: при наличии 50 файлов правил типичный PR, касающийся 8 файлов спецификаций TypeScript, может соответствовать 3 правилам. Без фильтрации агент читает 50 правил. При фильтрации получается 3. Соотношение сигнал/шум для агента пропорционально улучшается.

**Когда добавлять `paths:` frontmatter**: Любое правило, имеющее четкую область действия типа файла (тестовые файлы, файлы миграции, компоненты внешнего интерфейса, маршруты API). По-настоящему глобальные правила используют `alwaysApply: true` и пропускают этап сопоставления.

## <a name="detection-only-scope-boundary"></a>Граница области только обнаружения

**Проблема**: Навык, который одновременно обнаруживает проблемы и устраняет их, имеет два режима сбоя: ложное срабатывание (обнаружено и исправлено то, что не является проблемой) и неполные исправления (обнаружено правильно, но исправлено неправильно). Смешение этих двух факторов ухудшает ситуацию и не дает пользователю контрольной точки проверки.

**Pattern**: Явно ограничивайте навыки только обнаружением. Навык создает отчет. Исправление — это отдельный шаг, инициируемый пользователем после прочтения отчета.

Укажите это в верхней части навыка:

```markdown
**This skill only detects issues. It does not fix them.**
```

Затем примените его: никакая запись в файл, никакое редактирование, никакие коммиты git внутри навыка. Выходными данными всегда являются отчет об уценке или результаты консоли.

**Когда следует нарушать это правило**: Навыки, специально разработанные для автоматического исправления (навыки в стиле codemod, навыки обновления зависимостей), являются исключением. Они должны четко указать, что записывают изменения, и должны включать режим пробного запуска.

**Практическая ценность**: Навыки, предназначенные только для обнаружения, можно безопасно запускать в основных конфигурациях, в CI и в производственных конфигурациях. Пользователь может вызывать его, не опасаясь непреднамеренных изменений, поэтому его стоит запускать чаще и на большем количестве баз кода.

> Повторяющийся шаблон проверки качества, аудита playbook и аудита документов в репозитории [Packmind](https://github.com/PackmindHub/packmind) (Apache 2.0). См. [Credits](./credits.md).

## <a name="input-handler-dispatch"></a>Отправка обработчика ввода

**Проблема**: Навык, который обрабатывает два или более разнородных типов ввода (изображения или текст, проблемы GitHub и макеты дизайна), либо приводит к созданию сложного разветвленного основного файла, либо становится слишком жестким для различных точек входа.

**Pattern**: сохраните по одному файлу обработчика ввода для каждого типа ввода в подкаталоге `inputs/`. Основной SKILL.md спрашивает пользователя, какой тип применяется, а затем загружает соответствующий файл-обработчик.

```
.claude/skills/my-skill/
├── SKILL.md                 # Orchestrator: asks user, dispatches to input handler
└── inputs/
    ├── github-issue.md      # Handler for GitHub issue input
    └── visual-mockup.md     # Handler for screenshot/image input
```

SKILL.md (в сокращении):

```markdown
## Step 1: Identify Input Type

Ask the user: "Are you providing a GitHub issue or a visual mockup?"

- If GitHub issue → follow the instructions in `inputs/github-issue.md`
- If visual mockup → follow the instructions in `inputs/visual-mockup.md`
```

Каждый файл обработчика содержит полные инструкции по синтаксическому анализу для этого типа входных данных, включая извлечение полей, нормализацию формата и проверку. Основной файл остается чистым.

**Когда использовать**: Когда типы входных данных требуют существенно разной логики синтаксического анализа (а не просто разных имен полей). Если два входных параметра отличаются менее чем на 5 шагов, обрабатывайте их в строке. Этот шаблон окупается, когда каждый обработчик превышает 100 строк.

> Наблюдается в навыке [Packmind create-em-spec](https://github.com/PackmindHub/packmind) (.claude/skills/create-em-spec/inputs/). См. [Credits](./credits.md).

## <a name="versioned-sub-directories-for-tool-version-coupling"></a>Версионные подкаталоги для связи версии инструмента

**Problem**: навык включает в себя инструмент CLI, который меняет поведение между версиями. Навыку необходимо определить, какая версия установлена ​​у пользователя, и соответствующим образом адаптировать свои инструкции.

**Pattern**: сохраните один подкаталог для каждой версии инструмента, каждый из которых содержит инструкции для конкретной версии:

```
.claude/skills/update-playbook/
├── SKILL.md                         # Detects CLI version, dispatches
└── tool-versions/
    ├── v1.21/
    │   └── apply-changes.md         # Instructions for v1.21
    ├── v1.23/
    │   └── apply-changes.md         # Instructions for v1.23 (different API)
    └── v1.24/
        └── apply-changes.md         # Instructions for v1.24 (breaking change)
```

SKILL.md определяет версию во время выполнения:

```markdown
## Step 1: Detect Tool Version

Run: `my-cli --version`

- If output starts with "1.21" → read `tool-versions/v1.21/apply-changes.md`
- If output starts with "1.23" → read `tool-versions/v1.23/apply-changes.md`
- If output starts with "1.24" → read `tool-versions/v1.24/apply-changes.md`
- If version not recognized → stop and tell the user which versions are supported
```

**Антишаблон, которого следует избегать**: не создавайте каталог `my-skill-v2/` рядом с исходным `my-skill/`. Версируйте содержимое *внутри* навыка, а не самого навыка. Два почти идентичных навыка труднее поддерживать, и их сложнее использовать.

**Когда его использовать**: Когда инструмент CLI, который вы используете, имеет критические изменения между версиями, и вам необходимо поддерживать несколько версий одновременно. Если вам нужна только поддержка последней версии, просто обновите навык на месте.

> Наблюдается в учебнике по обновлению [Packmind](https://github.com/PackmindHub/packmind) (.claude/skills/packmind-update-playbook/). См. [Credits](./credits.md).

## <a name="two-tier-standards"></a>Двухуровневые стандарты

**Проблема**: Комплексный стандарт кодирования длинный (1000–5000 слов). Загрузка полного стандарта в контекст для каждой проверки файла увеличивает стоимость токена и снижает внимание.

**Pattern**: сохраните краткое описание (100–300 слов, с глобусом вступительной части `paths:`) в `.claude/rules/`. Храните полный канонический стандарт в отдельном месте, которое Claude сможет прочитать по требованию.

```
.claude/rules/standard-testing.md          # Summary + paths glob (200 words)
.standards/standard-testing-full.md        # Full canonical standard (2,000 words)
```

Сводка в `.claude/rules/` включает в себя:
- 3-5 предписывающих правил (повелительный залог: «Используй X», «Не Y»)
- Фронтальная часть `paths:`, поэтому она загружается только для совпадающих файлов.
- Ссылка на полный стандарт для случаев, когда необходимы подробности

Полный канонический стандарт находится за пределами `.claude/rules/`, поэтому он не загружается автоматически.

**Когда использовать**: Команды с более чем 10 файлами правил или файлами правил, которые в среднем содержат более 500 слов. Для небольших конфигураций одноуровневый подход проще.

**Maintenance**: При обновлении канонического стандарта также обновите сводку. Двухуровневое разделение создает риск дублирования. Смягчите это, сохранив в резюме правила только по пунктам (без прозы), чтобы оно нечасто менялось.

> Наблюдается в конфигурации правил [Packmind](https://github.com/PackmindHub/packmind) (.claude/rules/packmind/). См. [Credits](./credits.md).

## <a name="plans-and-specs-as-committed-artifacts"></a>Планы и спецификации как зафиксированные артефакты

**Проблема**: планы на уровне сеанса (режим `/plan`, файлы блокнота) исчезают после завершения сеанса. В следующем сеансе нет доступных для поиска записей о том, почему было принято проектное решение, какие варианты рассматривались или какой этап реализации был завершен последним.

**Pattern**: зафиксируйте планы и связанные с ними проектные спецификации непосредственно в `.claude/` в виде датированных пар уценок:

```
.claude/
├── plans/
│   └── 2026-03-15-auth-refactor.md        # High-level plan: phases, tasks, commit messages
└── specs/
    └── 2026-03-15-auth-refactor-design.md  # Companion spec: context, alternatives, rationale
```

Файл плана содержит разбивку реализации с явными сообщениями о фиксации для каждой задачи:

```markdown
# Auth Refactor Plan

## Task 1: Extract token validation middleware
- Move validation logic from controller into `middleware/auth.ts`
- git commit -m "refactor(auth): extract token validation into middleware"

## Task 2: Add refresh token rotation
- Implement rotation logic with 7-day expiry
- git commit -m "feat(auth): add refresh token rotation with 7-day expiry"
```

В файле спецификаций отражено то, что послужило основой для плана: ограничения, отклоненные альтернативы и аргументы, которые не будут очевидны из кода шесть месяцев спустя:

```markdown
# Auth Refactor Design

## Context
Session token storage flagged by legal review (ISO 27001 compliance gap).
Rotation required per new internal security policy v2.3.

## Rejected approaches
- HttpOnly cookie approach: requires cross-domain config changes (deferred)
- Redis session store: ops team not ready to manage another stateful service
```

Оба файла фиксируются вместе и остаются в репозитории на неопределенный срок.

**Почему это лучше, чем планы только для сеансов**: Зафиксированные планы можно сохранять, изменять и возобновлять. Новый сеанс может читать `.claude/plans/`, чтобы понять выполняемую работу, не восстанавливая ее из журнала git. В спецификации отражены рассуждения, которые исчезают из памяти, но имеют значение при повторном рассмотрении решения шесть месяцев спустя.

**Соглашение об именах**: `YYYY-MM-DD-<slug>.md` для плана, `YYYY-MM-DD-<slug>-design.md` для сопутствующей спецификации, оба с одинаковой датой и номером. Это позволяет визуально ассоциировать пары в списках каталогов.

**Когда использовать**: Задачи многосессионной реализации, где важна непрерывность. Не стоит переплачивать за односессионную задачу, умещающуюся в одном коммите. Порог примерно такой: если работа длится более одного дня или более одной сессии Claude, зафиксируйте план.

> Наблюдается в соглашении [Packmind .claude/plans/](https://github.com/PackmindHub/packmind) (Apache 2.0). См. [Credits](./credits.md).

## <a name="runtime-prompt-logging"></a>Ведение журнала подсказок во время выполнения

**Проблема**: Когда время вызова провайдера искусственного интеллекта истекает или происходит сбой, точное отправленное приглашение исчезает. Если вы создаете конвейер навыков или оценки с несколькими агентами, работающими параллельно, вы теряете возможность диагностировать то, что было сказано каждому агенту. Флаг `--debug` помогает только в том случае, если вы не забываете его передать.

**Pattern**: Запишите приглашение на диск как операцию блокировки ПЕРЕД вызовом поставщика. Используйте постоянный каталог с именем файла с отметкой времени. Никогда не бросайте вызов журнала.

```typescript
// Run BEFORE provider.invoke(), not after
await writeFile(
  `prompts/debug/${evaluatorName}-${timestamp}.md`,
  fullPrompt,
  "utf-8",
);
// Only now call the provider
const response = await provider.invoke(fullPrompt);
```

Три ограничения заставляют этот шаблон работать:

1. **Блокировка записи** (`await`, не по принципу «выстрелил и забыл»): файл существует на диске до начала вызова провайдера. Сбой во время вызова провайдера оставляет приглашение нетронутым для проверки.
2. **Always-on** (не ограничивается флагом отладки): накладные расходы представляют собой запись одного файла для каждого агента. Преимущество состоит в том, что любой неожиданный результат фиксируется навсегда.
3. **Никогда не бросайте**: ошибки регистрации не должны нарушать вычисления. Оберните запись в try/catch, зарегистрируйте предупреждение об ошибке, продолжайте.

**Соглашение о каталоге**: используйте путь относительно корня проекта (`prompts/debug/` или `claudedocs/debug/`), а не временный каталог. Временные каталоги очищаются; вы хотите, чтобы они сохранялись во время выполнения.

**Стоимость токена**: ноль (диск I/O, который происходит вне вызова AI). Приглашение уже находится в памяти, вы просто сохраняете его.

**Когда использовать**: Любой навык, который вызывает провайдера ИИ и где подсказка собирается динамически (а не просто статическая строка). Значение пропорционально сложности подсказки: если подсказка содержит основную информацию, инструкции оценщика и содержимое файла, одна запись перед вызовом — это дешевая страховка.

> Наблюдается в [PackmindHub/context-evaluator](https://github.com/PackmindHub/context-evaluator) (`src/shared/evaluation/runtime-prompt-logger.ts`, MIT). См. [Credits](./credits.md).

## <a name="adaptive-unifiedparallel-mode"></a>Адаптивный режим unified/parallel

**Проблема**: У вас есть N файлов для оценки, и вам необходимо решить: отправить все файлы одному агенту (лучше для проблем с несколькими файлами, более высокая стоимость контекста) или отправить каждый файл отдельному параллельному агенту (дешевле, быстрее, но не замечая противоречий между файлами)?

**Pattern**: оцените общее количество токенов, прежде чем переходить к стратегии. Если общая сумма соответствует пороговому значению, используйте единый режим (один агент видит все). Если оно превышает пороговое значение, вернитесь к использованию независимых параллельных агентов для каждого файла.

```typescript
const DEFAULT_MAX_UNIFIED_TOKENS = 100_000;

function canUseUnifiedMode(context: MultiFileContext, maxTokens = DEFAULT_MAX_UNIFIED_TOKENS) {
  if (context.totalTokenEstimate > maxTokens) {
    return {
      viable: false,
      reason: `Combined content (~${context.totalTokenEstimate} tokens) exceeds limit (${maxTokens})`,
    };
  }
  return { viable: true };
}
```

Вызовите это перед созданием подсказок агента. Решение закрывает остальную часть конвейера:

```
estimateTokens(all files)
  ↓
< 100K → runUnifiedEvaluation(allFiles)   // 1 agent, cross-file detection
> 100K → runAllEvaluators(file)           // N agents, per-file, parallel
```

**Почему порог имеет значение**: В унифицированном режиме агент может видеть противоречия между корневым каталогом `CLAUDE.md` и подкаталогом `CLAUDE.md`. В параллельном режиме каждый агент видит только один файл и не может обнаружить эти противоречия. Порог сохраняет межфайловый интеллект для небольших репозиториев, оставаясь в пределах практических ограничений контекста для более крупных.

**Пороговая калибровка**: 100 тысяч токенов оставляют место для подсказки оценщика (обычно 2–5 тысяч) и буфера ответов модели. Для вашего собственного варианта использования установите пороговое значение `model_context_window - evaluator_prompt_tokens - response_buffer`. `DEFAULT_MAX_UNIFIED_TOKENS = 100_000` Pac является консервативным значением по умолчанию для большинства современных моделей.

**Оценка токена**: точный подсчет не требуется. Грубая оценка (`chars / 4` для большинства текстов на английском языке) достаточна для принятия решения о режиме. Цена ошибки в оценке на 10 % намного ниже, чем цена дополнительной точности.

> Наблюдается в [PackmindHub/context-evaluator](https://github.com/PackmindHub/context-evaluator) (`src/shared/evaluation/runner.ts` `canUseUnifiedMode()`, MIT). См. [Credits](./credits.md).

## <a name="multi-directory-skill-discovery-for-cross-cli-compatibility"></a>Открытие навыков Multi-Directory для совместимости с CLI

**Проблема**: Репозиторий работает с более чем одним AI-кодированием CLI (Claude Code, плюс Codex, Amp или другое оборудование). Каждый CLI ожидает настройки навыков или среды в своем собственном обычном каталоге. Объединение всего в одном каталоге означает, что большинство интерфейсов командной строки никогда его не обнаружат; три почти дублирующихся каталога на первый взгляд выглядят как дезорганизация.

**Pattern**: храните один каталог навыков для каждого соглашения CLI рядом в корне репозитория, каждый из которых содержит навыки, специфичные для CLI, а не копии одного и того же контента: `.claude/skills/` для Claude Code, `.agents/skills/` для общего или общего соглашения агентов, `.skills/` для общего набора на уровне проекта, можно указать любой CLI at и `.codex/environments/` для конфигурации среды, специфичной для Codex. Считайте это конвергенцией в репозитории с несколькими CLI, а не беспорядком: каждый каталог представляет собой отдельный реальный путь обнаружения, а не избыточную копию.

```
.claude/skills/      # 3 skills, Claude Code's own convention
.agents/skills/       # shared/generic agent convention
.skills/              # 6 skills: cli-release, effect-atom-optimistic-updates,
                      #   effect-http-testing, effect-use-pattern, graphite,
                      #   warden-security-review
.codex/environments/  # Codex-specific environment config
```

Соглашение, связанное с **A, которое стоит позаимствовать отдельно.**: кураторский раздел «Ссылки» в проекте README, в котором именуются базы кода, на которые команда намеренно указывает своему агенту кодирования как на шаблоны для подражания (система плагинов, адаптер хранилища, общий стиль кода). Это отличается от приведенных выше каталогов навыков: это список чтения для агента, а не путь открытия, но он служит той же цели: сделать неявные знания типа «агент уже знает, как здесь хорошо выглядит» явными и версионными, а не племенными.

**Когда использовать**: Любой репозиторий, над которым работает более одного ИИ CLI, где интерфейсы командной строки не разделяют соглашение об обнаружении навыков. Для репозитория с одним CLI один каталог проще, и этот шаблон ничего не добавляет.

Полная оценка, включая другие соглашения агентской инженерии репо: [`docs/resource-evaluations/executor-integration-governance-layer.md`](../../docs/resource-evaluations/executor-integration-governance-layer.md).
