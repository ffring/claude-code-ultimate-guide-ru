## Методология – это не владение собственностью

Методологии определяют, как работа планируется, проверяется и улучшается. Они не определяют, владеет ли продукт циклом агента. Разделите четыре уровня: модель генерирует токены, среда выполнения выполняет цикл, система репозитория предоставляет обратную связь по конкретному проекту, а оркестратор координирует несколько запусков.

Используйте [Agent Harness Engineering](./agent-harness.md) для этой модели и [Agent Harness Map](../ecosystem/agent-harness-landscape.md) для сравнения строгих жгутов времени выполнения, не путая их с более широким каталогом платформ и плоскостей управления. [Agent Tools: Beyond Claude Code](../ecosystem/agentic-tools.md) охватывает эти смежные инструменты. Для производственного метода соедините рабочий процесс с [Agent Evaluation](../roles/agent-evaluation.md), [Session Observability](../ops/observability.md)и [Security Hardening](../security/security-hardening.md). Общие термины приведены в глоссарии [](./glossary.md).

## Методологическая карта

Здесь каждая методология опирается на две оси: **Spec-First против Code-First** (Y) и **Lightweight/Solo против Governed** (X). Вторая ось описывает стоимость настройки рабочего процесса и координации. Он не классифицирует производственную систему Toyota или бережливое управление; информацию об ограниченном применении потока и дзидока для доставки с помощью ИИ см. в [допуск пропускной способности обзора](./loop-graph-engineering.md#limit-admission-to-verification-capacity).

```
                      SPEC / PLANNING FIRST
                                ▲
  ── light · spec ──            │             ── governed · spec ──
                                │
  [Doc-Driven]  [SDD]           │    [BDD]  [ATDD]   [Req-Driven]
  [GSD]  [Plan-First]           │ [CDD] [ADR-Driven]  [DDD]  [BMAD full]
                                │
  LIGHTWEIGHT ──────────────────┼────────────────────────────────► GOVERNED
                                │
  ── light · code ──            │             ── governed · code ──
                                │
  [Context Eng.]   [TDD]        │       [Multi-Agent]
  [Prompt Eng.]  [Iterative]    │       [Eval-Driven]       [FDD]
  [Ralph Loop]                  │           [JiTTesting]
                                │
                         CODE / EMERGENT
```

**Как это читать:**

- **Вверху слева** (первый легкий вес по спецификации): `SDD`, `Doc-Driven`, `Plan-First`. Естественная отправная точка для индивидуальных разработчиков и небольших команд, отходящих от принципа «код прежде всего».
- **Вверху справа** (в первую очередь регулируется Spec): полный путь планирования `BMAD`, `Req-Driven`, `ATDD`, `DDD`. Координация и отслеживаемость могут оправдать появление большего количества артефактов; BMAD также поддерживает прямое построение за небольшую сдачу.
- **Слева внизу** (легкий вес в первую очередь по коду): естественная местность Claude Code. `TDD` + `Ralph Loop` + `Iterative` = основной одиночный рабочий процесс.
- **Внизу справа** (код в масштабе первый): `Multi-Agent`, `Eval-Driven`, `JiTTesting` (мета, 100M+ LoC). Новые модели для больших команд.
- **На оси**: `Plan-First`, `CDD`, `ADR-Driven`, `GSD`, гибридные подходы, адаптирующиеся к любому контексту.

## <a name="lean-software-engineering-as-a-delivery-lens"></a>Бережливая разработка программного обеспечения как призма доставки

Бережливое производство не занимает ни одного квадранта этой карты. Адаптация программного обеспечения [](https://res.infoq.com/articles/poppendieck-implementing-lean/en/resources/poppendieck_ch02.pdf) Мэри и Тома Поппендиек требует от команд обеспечить качество и оптимизировать весь поток от потребностей клиента до развертывания программного обеспечения, которое их удовлетворяет. Метод может создать лучшую спецификацию или более быстрый код, пока запрос ожидает решения, проверки, выпуска или принятия.

| Бережливый вопрос | Методы уже на этой странице | Что проверить в реальном рабочем процессе |
|---|---|---|
| Стоит ли выполнять требование? | SDD, BDD, БМАД | Прежде чем расширять спецификацию, назовите проблему пользователя и условие приемки. Упадок или сужение работы, которая не может быть привязана к необходимости. |
| Где ждет работа? | BMAD, GSD, SDD, мультиагентный | Сопоставьте один запрос посредством проверки и выпуска. Установите четкую политику незавершенной работы на ограниченном этапе вместо создания новых черновиков. |
| Заложено ли качество в работу? | TDD, ATDD, BDD, управляемый оценкой | Запускайте проверки заранее и прекращайте затронутую работу в случае сбоя теста, оценки или проверки доказательств. Один только окончательный обзор — это поздние ворота. |
| Может ли план измениться при наличии доказательств? | SDD, OpenSpec, БМАД | По возможности сохраняйте обратимость решений. Обновите спецификацию или план, когда обучение изменит требования; не сохраняйте устаревший артефакт для обеспечения соответствия процессам. |
| Улучшился ли процесс? | Ретроспективы, ADR, циклы проверки | Превратите повторяющийся сбой в конкретную проверку или правило, а затем посмотрите, снизятся ли повторения и усилия по исправлению. |
| Является ли один блок действительно полным? | SDD, ATDD, TDD, инкрементная миграция | Для устаревшей работы охарактеризуйте существующее поведение перед его изменением, доставьте один пригодный к использованию модуль путем проверки и выпуска и проверьте, можно ли удалить старый путь. Ссылка на источник или проходящая сборка сами по себе не устанавливают поведенческий паритет. |
| Сколько стоит сам метод? | BMAD, SDD, Multi-Agent, обзор рабочих процессов | Подсчитайте ожидание, ложные блокировки, повторные проверки, поглощения и обслуживание людьми, а также принятые изменения. Сохраняйте ворота только тогда, когда они предотвращают сбой или предоставляют доказательства, достойные задержки. |

 [Канбан-руководство](https://kanbanguides.org/the-kanban-guide/) делает поток работоспособным: определяет, когда элемент начинается и заканчивается, как контролируется незавершенная работа и как изменяется рабочий процесс. Четыре минимальных показателя потока — это незавершенное производство, пропускная способность, возраст рабочего элемента и время цикла. Выберите границы, включающие очередь, которую необходимо диагностировать. Эти показатели по-прежнему требуют отдельного пользовательского результата; Готовый запрос на включение не является доказательством того, что проблема клиента была решена. [Карта разработки продуктов Института бережливого предпринимательства](https://www.lean.org/the-lean-post/articles/why-value-stream-mapping-is-essential-to-product-and-process-development/) является полезным источником для сопоставления решений и передачи функций между функциями.

Примените тот же тест к самой методологии. Спецификация, предотвращающая одну неправильную реализацию, может выиграть время на подготовку и проверку; обязательная спецификация для небольшого обратимого исправления может только добавить очередь. Сравните один и тот же класс запроса до и после изменения метода, включая переработку и время до принятия результата. Цикл противодействия использованию репозитория [](./agent-harness.md#lean-countermeasure-loop-for-a-repository-harness) показывает, как протестировать элемент управления, прежде чем сделать его постоянным правилом.

Рабочий процесс также зависит от репозитория, в который он входит. Модель готовности агента [Factory](https://docs.factory.com/agent-readiness/overview) проверяет, позволяют ли инструкции, сборки, тесты и рабочие сигналы проверять работу агента. Это дополняет спецификации SDD или BMAD и проверки TDD; он не заменяет вопрос бережливого производства о том, доходит ли завершенное изменение до пользователя. Исправьте повторяющийся сбой репозитория, прежде чем увеличивать параллелизм агентов, а затем сравните тот же тип задачи и нисходящую очередь. См. пример рабочего процесса [agent](loop-graph-engineering.md#limit-admission-to-verification-capacity).

Два репозитория предоставляют более узкие механизмы. [RaiSE](https://github.com/humansys/raise) описывает постоянное состояние рабочего процесса и детерминированные проверки на границах фаз. [Andon](https://github.com/PrimeFoldTools/andon) записывает повторяющиеся дефекты агента и предлагаемые контрмеры. Их репозитории позволяют контролировать выбор дизайна; ни одна из них не предоставляет независимых доказательств улучшения результатов работы клиентов. Для составления карты запросов с помощью ИИ и ее пределов доказательств используйте [Lean и путь чтения ИИ](https://cc.bruniaux.com/lean-ai/) и главу [командные метрики](../ops/team-metrics.md).

### <a name="skill-packs-useful-controls-not-a-lean-result"></a>Пакеты навыков: полезные элементы управления, а не бережливый результат

Эти пакеты документируют повторяемые шаги. Их актуальность для бережливого производства — это интерпретация для тестирования в реальном потоке поставок, а не утверждение, сделанное или измеренное проектами.

| Пакет | Проверяемый механизм | Бережливый вопрос и предел |
|---|---|---|
| [gstack](https://github.com/garrytan/gstack) | `/office-hours` бросает вызов спросу; `/review` и `/qa` проверяют работу; `/landing-report` открывает очередь на отправку; `/retro` размышляет о проделанной работе. | Сокращает ли полный путь время достижения принятого пользователем результата или добавляет очереди планирования и проверки? Его `/ship` также выполняет действия Git и PR, поэтому используйте его только на границе предполагаемого выпуска. |
| [Навыки Мэтта Покока](https://github.com/mattpocock/skills) | `/triage` классифицирует входящие запросы; [`/to-spec`](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-spec.md) зарезервирован для рабочих сеансов; [`/to-tickets`](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-tickets.md) делает тонкие, проверяемые вертикальные срезы; `/tdd` и `/retro` поддерживают качество и обучение. | Может ли команда отклонить, сузить и завершить один ценный фрагмент, прежде чем приступить к следующему? Навыки описывают элементы управления, а не измеренный лимит незавершенного производства или результат для клиента. |

Пакет [Superpowers](https://github.com/obra/superpowers) — еще один существующий пример руководства по планированию, TDD и воротам обзора. Большее количество шлюзов может помочь предотвратить повторяющиеся сбои, но также может увеличить время ожидания. Сохраняйте наименьший набор, который учитывает наблюдаемое ограничение, и измеряйте незавершенное производство, время цикла, доработку и результаты пользователя для одного и того же типа запроса.

## <a name="the-15-methodologies"></a>15 методологий

Организовано в виде шестиуровневой пирамиды: от стратегического оркестрирования до методов оптимизации.

### <a name="tier-1-strategic-orchestration"></a>Уровень 1: Стратегическая оркестровка

| Имя | Что | Лучшее для | Claude Подходит |
|------|------|----------|------------|
| **BMAD** | Мышление и построение рабочих процессов, адаптированных к изменениям | Небольшие исправления посредством комплексных инициатив | ⭐⭐ Полезно, когда его артефакты окупают свою стоимость. |
| **GSD** | Шестиэтапный рабочий процесс с мета-подсказками и свежими контекстами для каждой задачи. | Индивидуальные разработчики, Claude Code CLI | ⭐⭐ Аналогично шаблонам в руководстве. |

**BMAD (революционный метод для гибкой разработки на основе искусственного интеллекта)** предлагает навыки мышления и построения рабочих процессов с дополнительными артефактами планирования для более масштабных или неопределенных работ. В текущей документации [](https://docs.bmad-method.org/) говорится, что небольшое ясное исправление можно сразу перенести в `bmad-build`; более крупные изменения могут начаться с `bmad-spec` или с более полного пути планирования. Агенты на основе ролей являются необязательной частью этой системы, а не свидетельством того, что для каждого изменения требуется несколько агентов.

- **Ключевая концепция**: Определите путь планирования и анализа изменений и примите решения, которые потребуются на последующих этапах.
- **Когда использовать**: используйте прямую сборку для понятных небольших изменений; добавьте планирование, когда этого требуют решения или затраты на координацию.
- **Когда следует избегать**: Не запускайте полную цепочку артефактов для четкого обратимого исправления только потому, что платформа предоставляет его. Возвращайтесь к артефактам, когда требования меняются.
- **Установите и запустите**: см. [spec-first.md § С BMAD-METHOD](../workflows/spec-first.md#with-bmad-method-multi-role-planning) для установщика и возможностью выбора между прямой сборкой и более структурированным планированием.
- **Канонический репозиторий**: [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD). Порт сообщества, указанный ниже (BMAD-AT-CLAUDE), является форком Claude Code, а не исходным проектом.

**GSD (Get Shit Done)** устраняет разрушение контекста посредством систематического шестиэтапного рабочего процесса (Инициализация → Обсуждение → Планирование → Выполнение → Проверка → Завершение) с новыми контекстами по 200 тысяч токенов для каждой задачи. Основные концепции (многоагентная оркестровка, новое управление контекстом) во многом совпадают с существующими шаблонами, такими как Ralph Loop, Gas Town и BMAD. Подробное сравнение см. в разделе «Оценка ресурсов [](../../docs/resource-evaluations/gsd-evaluation.md)».

> **Emerging**: [Ralph Inferno](https://github.com/sandstream/ralph-inferno) реализует автономные многопользовательские рабочие процессы (Аналитик→PM→UX→Архитектор→Бизнес) с выполнением на базе виртуальных машин и самокорректирующими циклами E2E. Экспериментально, но интересно для «масштабного кодирования вибрации».

### Основная дисциплина: рабочий процесс Plan-First

> **"Если план хорош, то и код хорош."**
> Борис Черный, создатель Claude Code

**A систематическая дисциплина, а не просто функция (команда `/plan`).**

> **Контекстная инженерия**: Thoughtworks называет этот более широкий подход «контекстной инженерией» в своем технологическом радаре (ноябрь 2025 г.)[^ Thoughtworks2025], систематическом проектировании информации, предоставляемой LLM во время вывода. Три основных метода: настройка контекста (минимальные системные подсказки, несколько примеров), управление контекстом для долгосрочных задач (суммирование, внешняя память, архитектура субагентов) и динамическое извлечение информации (JIT-загрузка контекста). Связанные шаблоны в Claude Code: AGENTS.md, MCP Context7, режим планирования.

[^thoughtworks2025]: Thoughtworks Technology Radar Vol 33, Nov 2025. [PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2025/11/tr_technology_radar_vol_33_en.pdf). See also: [Macro trends blog post](https://www.thoughtworks.com/insights/blog/technology-strategy/macro-trends-tech-industry-november-2025).

**Ментальная модель**:

Планирование не является обязательным для сложных задач. Это разница между:
- ❌ 8 итераций «попробовать → исправить → повторить → исправить снова»
- ✅ 1 итерация «план → проверка → чистое выполнение»

**Когда планировать в первую очередь**:

| Сложность задачи | План сначала? | Зачем |
|----------------|-------------|-----|
| >3 файла изменены | ✅ Да | Межфайловые зависимости нуждаются в архитектуре |
| изменено >50 строк | ✅ Да | Достаточно сложности для ошибок |
| Архитектурные изменения | ✅ Да | Требуется анализ воздействия |
| Незнакомая кодовая база | ✅ Да | Прежде чем действовать, необходимо исследование |
| Typo/obvious исправление | ❌ Нет | Планирование накладных расходов > времени выполнения задачи |
| Однострочное изменение | ❌ Нет | Просто сделай это |

**Как работает принцип «сначала план»**:

1. **Этап исследования** (режим планирования через `Shift+Tab`):
   - Claude читает файлы, изучает архитектуру
   - Редактирование не допускается → заставляет думать, прежде чем действовать
   - Предлагает подход с компромиссами

2. **Фаза проверки** (вы проверяете):
   - План раскрывает предположения и пробелы
   - Легче исправить направление сейчас, чем после написания 100 строк.
   - План становится контрактом на исполнение

3. **Фаза выполнения** (переключиться обратно в обычный режим с помощью `Shift+Tab`):
   - План → код становится механическим переводом
   - Меньше сюрпризов, более чистая реализация
   - В целом быстрее, несмотря на «более медленный» старт

**Рабочий процесс Бориса Черного**:

> «Я запускаю много сеансов, начинаю в режиме плана, а затем перехожу к выполнению, когда план выглядит правильным. Обновление сигнатуры — это проверка, давая Claude возможность протестировать и подтвердить свои собственные выходные данные».

**Преимущества по сравнению с «просто начните программировать»**:

- **Меньше итераций исправлений**: План выявляет проблемы до того, как они станут кодом
- **Лучшая архитектура**: Вынуждены сначала подумать о структуре
- **Более четкое общение**: План — это общее понимание с team/Claude
- **Снижение затрат**: одна чистая итерация < несколько беспорядочных итераций (даже если на этапе планирования стоят жетоны)

**Интеграция с CLAUDE.md**:

Задокументируйте триггеры вашей команды, ориентированные на планирование:
```markdown
## Planning Policy
- ALWAYS plan first: API changes, database migrations, new features
- OPTIONAL planning: Bug fixes <10 lines, test additions
- NEVER skip: Changes affecting >2 modules
```

**См. также**: [Документация по режиму планирования](#23-plan-mode) для использования команд `/plan`.

> **Расширенный шаблон**: итеративный подход к разработке на основе планов, основанный на аннотациях, см. в разделе [Пользовательские планы уценки (шаблон Бориса Тане)](../workflows/plan-driven.md#advanced-custom-markdown-plans-boris-tane-pattern).

### Уровень 2: Спецификация и архитектура

| Имя | Что | Лучшее для | Claude Подходит |
|------|------|----------|------------|
| **SDD** | Спецификации перед кодом | API, контракты | ⭐⭐⭐ Основной узор |
| **Doc-Driven** | Документы = источник истины | Межкомандное согласование | ⭐⭐⭐ CLAUDE.md родной |
| **Req-Driven** | Богатый контекст артефактов (более 20 артефактов) | Сложные требования | ⭐⭐ Тяжелая установка |
| **DDD** | Язык домена в первую очередь | Бизнес-логика | ⭐⭐ Время разработки |

**SDD (Разработка на основе спецификаций)**: четко обозначьте предполагаемое поведение перед реализацией и пересматривайте спецификацию, когда данные изменят требование. Файл инструкций проекта, такой как `CLAUDE.md`, имеет стабильные соглашения; это не является автоматически спецификацией функции. Документация SDD [Spec Kit](https://github.com/github/spec-kit/blob/main/docs/concepts/sdd.md) охватывает как новые, так и существующие проекты.

**Разработка на основе документов**: Живая документация, созданная в git, становится единственным источником истины. Изменения в спецификациях вызывают внедрение.

**Разработка на основе требований**: использует CLAUDE.md в качестве комплексного руководства по внедрению с более чем 20 структурированными артефактами.

**DDD (Domain-Driven Design)**: Согласовывает программное обеспечение с бизнес-языком посредством:
- Вездесущий язык: общий словарь в коде
- Ограниченные контексты: изолированные границы домена
- Дистилляция доменов: ядро, поддержка и общие домены

### <a name="tier-3-behavior--acceptance"></a>Уровень 3: Поведение и принятие

| Имя | Что | Лучшее для | Claude Подходит |
|------|------|----------|------------|
| **BDD** | Сценарии «Дано-когда-то» | Сотрудничество заинтересованных сторон | ⭐⭐⭐ Тесты и характеристики |
| **ATDD** | Критерии приемки в первую очередь | Соответствие, регулируется | ⭐⭐ Сложный процесс |
| **CDD** | API контракты как интерфейс | Микросервисы | ⭐⭐⭐ Собственный OpenAPI |

**BDD (Разработка, основанная на поведении)**: Помимо тестирования, это процесс сотрудничества.
1. Открытие: привлекайте разработчиков и бизнес-экспертов.
2. Формулировка: напишите примеры «Дано когда-то»
3. Автоматизация: преобразование в исполняемые тесты (Gherkin/Cucumber)

```gherkin
Feature: Order Management
  Scenario: Cannot buy without stock
    Given product with 0 stock
    When customer attempts purchase
    Then system refuses with error message
```

**ATDD (Разработка на основе приемочного тестирования)**: Критерии приемки определяются ДО начала совместного написания кода («Три друга»: Бизнес, Разработка, Тестирование).

При разработке агентов ATDD особенно эффективен, поскольку агентам необходимы однозначные условия успеха. Поток четко соответствует задачам агента:

1. **Определить критерии приемки** в Gherkin (человекочитаемый, машиноисполняемый)
2. **Агент записывает неудачные тесты** на основе сценариев (а не реализации)
3. **Агент реализует** до тех пор, пока тесты не пройдут

```gherkin
Feature: Password Reset
  Scenario: User resets via email
    Given a registered user with email "user@example.com"
    When they request a password reset
    Then they receive a reset email within 60 seconds
    And the reset link expires after 24 hours
```

Этот сценарий «Огурца» представляет собой контракт между намерением и реализацией. Агент не может неправильно интерпретировать область действия, поскольку функция Done определяется до написания строки кода.

> **Применяется к агентам.**: перед реализацией передайте файл Gherkin в Claude Code. «Напишите неудачные тесты для этого файла функций, а затем реализуйте их, пока они не пройдут». Роль автора сценария (человека или агента) устанавливает явную область действия до начала выполнения.

**CDD (Разработка на основе контрактов)**: контракты API (спецификации OpenAPI) в качестве исполняемого интерфейса между командами. Шаблоны: Контракт как тест, Контракт как заглушка.

**JiTTesting (Тестирование «точно в срок»)**: тесты, создаваемые «на лету» при отправке PR, рассчитанные на провал, а затем отбрасываемые после слияния. Никаких затрат на обслуживание и никакого расширения набора тестов.

Все TDD/BDD/ATDD предполагают, что разработчик контролирует темп написания кода. Агентская разработка нарушает это предположение: агент может генерировать 200 строк в час, быстрее, чем может справиться любой рабочий процесс написания тестов человеком. JiTTests — это промышленный ответ на это несоответствие.

Механизм: во время PR LLM делает вывод о цели сравнения, генерирует мутанты кода (намеренно сломанные варианты), пишет тесты, которые ловят эти мутанты, запускает оценщики на основе правил ансамбля и LLM для фильтрации ложных срабатываний и отображает инженеру только реальные регрессии. Тесты никогда не попадают в базу кода.

Компания Meta развернула это в масштабе (100 млн+ LoC): четырехкратное улучшение выявления регрессий по сравнению с традиционными тестами на усиление защиты, сокращение нагрузки на проверку человеком на 70%, предотвращение 4 серьезных производственных сбоев у 41 проверенного кандидата.

Реализации с открытым исходным кодом пока не существует. Вы можете приблизить это сегодня: перед объединением любого PR, созданного агентом, предложите Claude «создать тесты, которые бы выявляли регрессии, вызванные именно этим различием. Я запущу их локально и отброшу после закрытия PR». Эфемерная структура фокусирует создание тестов на том, что действительно изменилось, а не на общем охвате.

> **Reference**: [Срочная генерация тестов на перехват в Meta](https://arxiv.org/abs/2601.22832) (Harman, 2026).

| Имя | Что | Лучшее для | Claude Подходит |
|------|------|----------|------------|
| **FDD** | Доставка по функциям | Функциональные команды с параллельной доставкой | ⭐⭐ Структура |

### <a name="tier-5-implementation"></a>Уровень 5: Реализация

| Имя | Что | Лучшее для | Claude Подходит |
|------|------|----------|------------|
| **TDD** | Red-Green-Refactor | Код качества | ⭐⭐⭐ Основной рабочий процесс |
| **Eval-Driven** | Оценки выходов LLM | ИИ-продукты | ⭐⭐⭐ Агенты |
| **Multi-Agent** | Организуйте работу субагентов | Сложные задачи | ⭐⭐⭐ Инструмент задач |

**TDD (Разработка через тестирование)**: Классический цикл:
1. **Red**: Запись неудачного теста
2. **Green**: Минимальный код для передачи.
3. **Refactor**: очистка, тесты остаются зелеными

С Claude: будьте откровенны. «Напишите НЕВЕРНЫЕ тесты, которых еще не существует».

> **Циклы проверки**: формализованный шаблон для автономной итерации (более широкий, чем TDD):
>
> **Основной принцип**: Предоставьте Claude механизм проверки собственного вывода.
>
> ```
> Code generated → Verification tool → Feedback loop → Improvement
> ```
>
> **Почему это работает** (Борис Черный): *«Агент, который может «видеть» то, что он сделал, дает лучшие результаты».*
>
> **Механизмы проверки по домену**:
>
> | Домен | Инструмент проверки | Что Claude «видит» |
> |--------|-------------------|-------------------|
> | **Фронтенд** | Предварительный просмотр в браузере (живая перезагрузка) | Визуальный рендеринг, макет, взаимодействие |
> | **Backend** | Тесты (unit/integration) | Статус Pass/fail, сообщения об ошибках |
> | **Типы** | Компилятор TypeScript | Типовые ошибки, несовместимости |
> | **Стиль** | Линтеры (ESLint, Prettier) | Нарушения стиля, проблемы с форматированием |
> | **Производительность** | Профилировщики, бенчмарки | Время выполнения, использование памяти |
> | **Доступность** | axe-core, программы чтения с экрана | Нарушения WCAG, проблемы с навигацией |
> | **Безопасность** | Статические анализаторы (Семгреп) | Шаблоны уязвимостей |
> | **UX** | Пользовательское тестирование, записи | Проблемы с юзабилити, путаница |
>
> **TDD как канонический пример**:
> 1. Claude пишет тесты для этой функции.
> 2. Claude повторяет код до тех пор, пока тесты не пройдут
> 3. Продолжать до тех пор, пока не будут выполнены явные критерии завершения.
>
> **Официальное руководство**: *«Скажите Claude продолжать работу, пока все тесты не пройдут. Обычно это занимает несколько итераций».* ([Anthropic Best Practices](https://www.anthropic.com/engineering/claude-code-best-practices))
>
> **Шаблоны реализации**:
> - **Hooks**: ловушка PostToolUse запускает проверку после каждого редактирования.
> - **Расширение браузера**: Claude в Chrome видит визуализированный вывод
> - **Наблюдатели за тестированием**: режим просмотра Jest/Vitest обеспечивает мгновенную обратную связь
> - **CI/CD Gates**: GitHub Actions запускает полный пакет проверки
> - **Multi-Claude проверка**: Один Claude коды, другой отзывы
>
> **Анти-шаблон**: Слепая итерация без обратной связи. Без механизма проверки Claude не может прийти к правильному решению: он угадывает.

Информацию о режиме отказа на стороне реализации, который это предотвращает, см. в разделе [Пробел в проверке](../workflows/tdd-with-claude.md#the-verification-gap) в рабочем процессе TDD.

**Разработка на основе оценки**: TDD для LLM. Поведение агента тестирования посредством оценок:
- На основе кода: `output == golden_answer`
- На основе LLM: еще один Claude оценивает
- Человеческая оценка: Эталонная, медленная.

> **Eval Harness**: инфраструктура, которая выполняет сквозные оценки, предоставляет инструкции и инструменты, одновременно выполняет задачи, записывает шаги, оценивает результаты и агрегирует результаты.
>
> См. подробное руководство Anthropic: [Демистификация оценок для агентов ИИ](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Мультиагентная оркестрация**: От одного помощника до организованной команды:
```
Meta-Agent (Orchestrator)
├── Analyst (requirements)
├── Architect (design)
├── Developer (code)
└── Reviewer (validation)
```

### Развитие на основе ADR

**Pattern**: напишите ADR на простом английском языке → используйте навыки реализации adr → выполните нативно

Записи об архитектурных решениях (ADR) в сочетании с навыками Claude Code создают рабочий процесс, в котором архитектурные решения напрямую влияют на реализацию.

**Этапы рабочего процесса**:
1. **Документ решения** в формате ADR (контекст, решение, последствия)
2. **Создать навык реализации** (общий или специализированный `implement-adr`)
3. **Передать ADR в качестве подсказки** специалистам с четкими критериями приемки
4. **Claude выполняет** на основе архитектурного руководства в ADR.

**Пример шаблона ADR**:
```
# ADR-001: Database Migration Strategy

## Context
Legacy MySQL schema needs migration to PostgreSQL for better JSON support.

## Decision
Use incremental dual-write pattern with feature flags.

## Consequences
- Positive: Zero-downtime migration
- Negative: Temporary code complexity during transition
```

**Рабочий процесс реализации**:
```bash
# 1. Write ADR (plain English)
vim docs/adr/001-database-migration.md

# 2. Feed to implementation skill
/implement-adr docs/adr/001-database-migration.md

# 3. Claude executes based on ADR guidance
# → Creates migration scripts
# → Updates ORM configuration
# → Adds feature flags
# → Implements dual-write logic
```

**Benefits**:
- ✅ **Управление документацией**: Архитектура и код остаются синхронизированными.
- ✅ **Нативное исполнение**: внешние фреймворки не нужны.
- ✅ **Отслеживаемые решения**: Четкий контрольный журнал от решения до реализации
- ✅ **Согласование команды**: ADR сообщают о намерениях как людям, так и ИИ.

**Источник**: [Гур Санников, рабочий процесс встроенного проектирования](https://www.linkedin.com/posts/gursannikov_claudecode-embeddedengineering-aiagents-activity-7423851983331328001-DrFb)

### Уровень 6: Оптимизация

| Имя | Что | Лучшее для | Claude Подходит |
|------|------|----------|------------|
| **Итеративные циклы** | Автономная доработка | Оптимизация | ⭐⭐⭐ Ядро |
| **Свежий контекст** | Сброс для каждой задачи, состояние в файлах | Длительные автономные сеансы | ⭐⭐⭐ Опытные пользователи |
| **Быстрое проектирование** | Основа техники | Все | ⭐⭐⭐ Обязательное условие |

**Итеративные циклы уточнения**: Автономная сходимость:
1. Выполнить приглашение
2. Наблюдайте за результатом
3. Если результат ≠ «ГОТОВО» → уточните и повторите.

**Быстрое проектирование**: Основы для ВСЕХ вариантов использования Claude:
- Нулевая цепочка мыслей: «Думайте шаг за шагом»
- Обучение за несколько шагов: 2–3 примера ожидаемого шаблона
- Структурированные подсказки: XML-теги для организации
- Позиция имеет значение: для длинных документов поместите вопрос в конце.

**Шаблон свежего контекста (цикл Ральфа)**: устраняет разрушение контекста путем создания новых экземпляров агента для каждой задачи. Состояние сохраняется в файлах git + прогресса, а не в истории чата. Идеально подходит для длительных автономных сессий (миграции, ночные пробеги). Для реализации см. [Ultimate Guide — Fresh Context Pattern](#fresh-context-pattern-ralph-loop).

### Spec Kit (новые и существующие проекты)

5-этапный рабочий процесс:
1. Конституция: `/speckit.constitution` → ограждения
2. Укажите: `/speckit.specify` → требования
3. План: `/speckit.plan` → архитектура
4. Задачи: `/speckit.tasks` → декомпозиция
5. Реализация: `/speckit.implement` → код

### OpenSpec (Браунфилд)

Двухпапочная архитектура:
```
openspec/
├── specs/      ← Current truth (stable)
└── changes/    ← Proposals (temporary)
```

Рабочий процесс: Предложение → Обзор → Подать заявку → Архивировать.

### Specmatic (контракты API)

- **Contract as Test**: автоматически генерирует тысячи тестов из спецификации OpenAPI.
- **Contract как Stub**: макет сервера для параллельной разработки.
- **Обратная совместимость**: обнаруживает критические изменения.

## <a name="writing-effective-specs"></a>Написание эффективных спецификаций

> На основе анализа более 2500 файлов конфигурации агентов.
> Источник: [Адди Османи](https://addyosmani.com/blog/good-spec/)

### Шесть основных компонентов

| Компонент | Что включить | Пример |
|-----------|-----------------|---------|
| **Команды** | Исполняемый файл с флагами | `npm test -- --coverage` |
| **Тестирование** | Структура, покрытие, локации | `vitest, 80%, tests/` |
| **Структура проекта** | Явные каталоги | `src/`, `lib/`, `tests/` |
| **Стиль кода** | Один пример > абзацы | Показать реальную функцию |
| **Рабочий процесс Git** | Филиал, коммит, формат PR | `feat/name`, обычные коммиты |
| **Границы** | Уровни разрешений | См. ниже |

### Уровни разрешений

| Уровень | Символ | Использовать для |
|------|--------|---------|
| Всегда делай | ✅ | Безопасные действия, без одобрения (ворс, формат) |
| Сначала спроси | ⚠️ | Важные изменения (удалить, опубликовать) |
| Никогда не делай | 🚫 | Жесткие остановки (фиксация секретов, принудительное нажатие главной) |

### Проклятие инструкций

> ⚠️ Тот же анализ выявил **больше инструкций = худшее соблюдение** к каждой из них.
>
> Решение. Подавайте только соответствующие разделы спецификаций для каждой задачи, а не весь документ.

### Монолитные и модульные характеристики

| Размер проекта | Подход |
|--------------|----------|
| Маленький (<10 файлов) | Один файл спецификации |
| Средний (10–50 файлов) | Разделенная спецификация, подача по задачам |
| Большой (более 50 файлов) | Маршрутизация субагента по домену |

## <a name="combination-patterns"></a>Комбинированные узоры

Это стартовые комбинации, а не измеренный прирост производительности. Добавляйте метод, когда он касается реального решения, дефекта или передачи управления. Проверьте полученную очередь и стоимость обслуживания.

| Ситуация | Стартовая комбинация | Что проверить |
|-----------|----------------------|----------------|
| Соло-изменение с рискованным поведением | Краткая спецификация задачи + TDD | Приемлемое поведение и усилия по исправлению |
| Команда с периодически возникающими недопониманиями в требованиях | Комплект спецификаций + BDD + TDD | Меньше спорных примеров без большого количества невыполненных спецификаций |
| Сервисы с явными контрактами API | CDD + Спекматик | Сбои в контракте обнаружены до интеграции |
| Существующий продукт с меняющимся поведением | ОпенСпец + BDD | Текущие характеристики соответствуют поведению при поставке после каждого изменения. |
| Сложная работа за пределами границ сервиса | БМАД + Спекматик | Один источник планирования, полезные проверки контрактов и управляемое ожидание рассмотрения |
| Продукт LLM с повторяющимися сбоями вывода | управляемый оценкой; добавить мультиагент только для отдельной роли | Оцените качество и результаты пользователей после выпуска |
