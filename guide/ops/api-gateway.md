# Шлюз API для предприятия Claude Code

> **Audience**: инженеры платформ и команды DevOps, развертывающие Claude Code в организации.
>
> **Scope**: настройка прокси-уровня между клиентами Claude Code и восходящей моделью для централизации контроля затрат, соблюдения бюджета и прозрачности использования. Для оценки стоимости отдельного сеанса см. [observability.md](./observability.md). Информацию об управлении MCP см. в разделе [enterprise-governance.md §3](../security/enterprise-governance.md#3-mcp-governance-workflow).

## TL;DR: примеры сторонних шлюзов

В таблице и настройке ниже описаны примеры LiteLLM и Portkey на этой странице. Они не описывают шлюз приложений Claude.

| Проблема | Пример стороннего шлюза |
|---------|-----------------|
| Нет разбивки затрат по командам | Виртуальные ключи с метаданными команды, агрегированные на информационных панелях |
| Разработчики могут назвать любую модель | Списки разрешенных моделей для каждого ключа (несанкционированные вызовы возвращают код 403) |
| Издержки, связанные с неконтролируемыми действиями агентов, находящихся без присмотра | Ограничение бюджета терминала на ключ, ежемесячный сброс, возвращает 429 при нажатии |
| Расходы разработчиков интерактивных приложений резко возросли | Телеметрия шлюза может передавать предупреждения, утверждения и понижение модели; одно только бюджетное поле не реализует эту политику |
| Нет общей телеметрии API. | Маршрутизируемые запросы с указанием ключевого псевдонима, команды, модели и токенов; ведение журнала полезной нагрузки зависит от конфигурации |

**Сторонний подход**: Установите `ANTHROPIC_BASE_URL` на каждом компьютере разработчика, чтобы он указывал на совместимый шлюз вместо `api.anthropic.com`. В приведенных ниже примерах пересылаются запросы, добавляются настроенные ведение журнала и принудительное соблюдение бюджета, а также выдаются виртуальные ключи, поэтому ключ поставщика не обязательно должен присутствовать на компьютерах разработчиков.

## <a name="current-first-party-surface-claude-apps-gateway"></a>Текущая собственная поверхность: шлюз приложений Claude.

Шлюз приложений [Claude](https://code.claude.com/docs/en/claude-apps-gateway) — это автономный шлюз Anthropic. Он поставляется в двоичном формате `claude` и работает с `claude gateway --config gateway.yaml`. Он находится между клиентами Claude Code и восходящим потоком. Его обычная конфигурация может маршрутизироваться и переключаться при сбое между пятью задокументированными вариантами вышестоящих поставщиков: Anthropic, API, Amazon Bedrock, Claude Platform на AWS, агентской платформы Google Cloud и Microsoft Foundry.

Используйте его, когда организации требуется автономный шлюз для Claude Code с корпоративным единым входом, доступом к модели для каждой группы удостоверений, доставкой управляемых параметров и телеметрией протокола OpenTelemetry. Шлюз сохраняет восходящие учетные данные в инфраструктуре организации. Разработчики проходят аутентификацию через поставщика корпоративных удостоверений и получают кратковременные токены на предъявителя вместо учетных данных поставщика.

### Граница развертывания

Для официального краткого руководства требуется Claude Code v2.1.195 или более поздняя версия на хосте шлюза и компьютерах разработчиков, поставщик удостоверений OIDC, PostgreSQL, восходящие учетные данные и адрес шлюза частной сети. Требование частного адреса — это элемент управления безопасностью, поскольку доверенный шлюз может предоставлять настройки, которые запускают команды на компьютерах разработчиков. Поместите его за внутренним балансировщиком нагрузки или VPN; не раскрывайте его как общедоступную конечную точку.

Документированный процесс входа представляет собой единый вход в интерактивном браузере. У нее нет потока сервисных токенов для автоматической CI, поэтому система CI, в которой разработчик не утверждает поток устройств, вместо этого должна проходить аутентификацию непосредственно у своего провайдера. Компьютер, на котором выполнен вход разработчика, может использовать существующий сеанс шлюза для запуска `claude -p` и агента SDK в соответствии с политикой шлюза.

### Что контролирует шлюз, а что нет

| Поверхность | Документированное поведение |
|---|---|
| Идентификация и восходящие учетные данные | Шлюз аутентифицирует разработчиков с помощью IdP, выдает кратковременные токены на предъявителя (по умолчанию один час) и использует восходящие учетные данные поставщика организации. |
| Модель и клиентская политика | Группы IdP сопоставляются со списками разрешенных моделей и управляемыми настройками. Запрос непредоставленной модели возвращает `400`. Заблокированные управляемые настройки нельзя переопределить локально. |
| Телеметрия | Шлюз пересылает метрики OTLP с количеством токенов, моделью, идентификаторами и задержкой. Он не регистрирует и не сохраняет содержимое подсказок или завершения. Журналы и трассировки настраиваются для каждого места назначения и могут включать команды и пути к файлам. |
| Плоскость данных Anthropic | Плоскость данных шлюза ничего не отправляет на Anthropic, если Anthropic API не настроен как восходящий. |
| Другой клиентский трафик | Проверки версий и загрузки по-прежнему могут осуществляться напрямую с Claude Code на Anthropic и требуют отдельной политики исходящего трафика или документированного контроля несущественного трафика. |

![Подписки пользователей обходят бюджеты шлюза и атрибуцию, в то время как CI, общие агенты, запланированные рабочие процессы и внутренние службы проходят через централизованные ключи, квоты, списки разрешенных моделей, резервный вариант и возможность наблюдения](../images/gateway-visibility-boundary.webp)

Шлюз не обеспечивает автоматическую безопасность настольного приложения, локальной файловой системы или плагина. [Использование компьютера](../core/computer-use.md) имеет отдельную границу доверия к рабочему столу, а распространение плагинов [](../ecosystem/plugin-distribution.md) имеет отдельную границу цепочки поставок расширений.

### Проверьте перед внедрением

В официальном кратком руководстве описаны три первоначальные проверки: получение документа обнаружения OAuth, запрос авторизации устройства и завершение входа в браузер. Они последовательно проверяют загрузку, доступ к базе данных и перенаправление поставщика удостоверений. Успешная загрузка шлюза не является доказательством того, что восходящий путь вывода работает, поскольку некоторые облачные учетные данные разрешаются только при первом запросе. Запустите разрешенный тестовый запрос через предполагаемый восходящий поток и проверьте первый сбойный уровень, если он не пройден.

Подтвердите отпечаток сертификата TLS шлюза во время первого подключения, опубликуйте полный ожидаемый отпечаток SHA-256 для разработчиков и запланируйте ротацию сертификатов. Прежде чем объявлять принудительное применение политики шлюза, проверьте запрос отклоненной модели, ограничение управляемых параметров, отмену подготовки IdP, назначение телеметрии и аварийно-закрытый запуск для сеанса с входом в шлюз. Обеспечьте выходной трафик провайдера отдельно, если требуется маршрутизация только через шлюз.

Информацию об общей архитектуре шлюза и ограничениях внешнего шлюза см. в обзоре шлюза [Anthropic](https://code.claude.com/docs/en/gateways). Оставшаяся часть этой страницы посвящена примерам шлюзов сторонних производителей и не является спецификацией продукта Anthropic.

## Примеры сторонней реализации

Оставшийся материал по LiteLLM и Portkey представляет собой стороннее руководство по реализации. Его виртуальные ключи, отклонение модели `403`, поведение бюджета `429` и ведение журнала request/response не являются утверждениями о шлюзе приложений Claude.

## <a name="1-why-a-gateway-layer"></a>1. Зачем нужен шлюзовой уровень

Claude Code может напрямую позвонить Anthropic или другому поддерживаемому провайдеру, используя учетные данные и конечную точку, настроенные организацией. Без прокси-слоя:

- Атрибуция команды и проекта зависит от отчетности поставщика и того, как организация разделяет ключи.
- Ограничения модели зависят от средств контроля вышестоящего провайдера.
- Исполнение бюджета зависит от вышестоящих механизмов контроля или уровня внешней политики.
- У всех поставщиков нет общей телеметрии запросов.

Шлюз находится между настроенными экземплярами Claude Code и их вышестоящими поставщиками. Он выдает виртуальные ключи разработчикам (применительно к команде или проекту), хранит учетные данные поставщика на стороне сервера и применяет политики к запросам, маршрутизируемым через него. Трафик, аутентифицированный по подписке, и клиенты, использующие учетные данные прямого поставщика, остаются за пределами этой плоскости управления.

## <a name="2-litellm-gateway"></a>2. Шлюз LiteLLM

[LiteLLM](https://github.com/BerriAI/litellm) — это прокси-сервер Python LLM с открытым исходным кодом. Он поддерживает Anthropic, выдает виртуальные ключи, может обеспечивать соблюдение настроенных бюджетов и предоставляет метрики для внешних панелей мониторинга.

### 2.1 Установка

```bash
pip install 'litellm[proxy]'

# Docker is recommended for production
docker pull ghcr.io/berriai/litellm:main-latest
```

### 2.2 Конфигурация

Создайте `litellm_config.yaml` для маршрутизации к Anthropic:

```yaml
model_list:
  - model_name: claude-haiku-5-5
    litellm_params:
      model: anthropic/claude-haiku-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

  - model_name: claude-sonnet-5-5
    litellm_params:
      model: anthropic/claude-sonnet-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

  - model_name: claude-opus-5-5
    litellm_params:
      model: anthropic/claude-opus-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL  # PostgreSQL required for persistent keys

litellm_settings:
  drop_params: true  # Ignore unknown params silently
```

Запустите прокси:

```bash
litellm --config litellm_config.yaml --port 4000
```

### 2.3 Подключение Claude Code

Установите эти две переменные среды на каждом компьютере разработчика (распространите через диспетчер секретов, репозиторий точечных файлов или сценарий адаптации):

```bash
# Point Claude Code to your LiteLLM instance
# Note the /anthropic path suffix, required for Anthropic Messages API format
export ANTHROPIC_BASE_URL=http://your-litellm-host:4000/anthropic

# Developer uses a virtual key, not the real Anthropic key
export ANTHROPIC_API_KEY=sk-litellm-team-backend-abc123
```

Claude Code не требует каких-либо других изменений. Он читает `ANTHROPIC_BASE_URL` и использует его прозрачно. Требуется суффикс пути `/anthropic`: LiteLLM предоставляет формат сообщений Anthropic API по адресу `/anthropic/v1/messages` отдельно от OpenAI-совместимой конечной точки по адресу `/v1/chat/completions`.

## <a name="3-virtual-keys-and-team-budgets"></a>3. Виртуальные ключи и бюджеты команд

Создайте виртуальные ключи через управление LiteLLM API. Каждый ключ соответствует команде или проекту и имеет дополнительный ежемесячный лимит бюджета.

```bash
# Backend team: Sonnet + Haiku only, $50/month budget
curl -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "key_alias": "team-backend",
    "team_id": "team-backend",
    "max_budget": 50,
    "budget_duration": "monthly",
    "models": ["claude-haiku-5-5", "claude-sonnet-5-5"],
    "metadata": {"team": "backend", "project": "api-v2"}
  }'

# Leads: all models, $300/month
curl -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "key_alias": "lead-full-access",
    "team_id": "leads",
    "max_budget": 300,
    "budget_duration": "monthly",
    "models": ["claude-haiku-5-5", "claude-sonnet-5-5", "claude-opus-5-5"]
  }'
```

Когда бюджет исчерпан, Claude Code получает `429 BudgetExceededError`. Ключ автоматически сбрасывается в начале следующего бюджетного цикла.

```bash
# Check current spend for a key
curl http://localhost:4000/key/info?key=sk-litellm-team-backend-abc123 \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"
```

### <a name="31-progressive-spend-policy-for-interactive-users"></a>3.1 Политика прогрессивных расходов для интерактивных пользователей

В приведенном выше примере LiteLLM показана крышка терминала. Он не демонстрирует прогрессивных предупреждений, ворот одобрения или безопасного для качества понижения передачи модели. Создайте их как явный уровень политики или убедитесь, что выбранный шлюз реализует каждый этап на предполагаемом клиенте и пути трафика.

| Пороговая стадия | Требуемое поведение | Доказательства для сохранения |
|---|---|---|
| **Видимость** | Покажите текущие расходы, уровень расходов, модель и оставшийся запас, не прерывая работу. | Пользователь, команда, модель, временная метка, объем маршрутизируемого трафика |
| **Самоочистка предупреждения** | Попросите разработчика признать необычный уровень расходов. | Порог, подтверждение, идентификатор сеанса или задачи |
| **Ворота утверждения** | Требовать от владельца бюджета одобрения дальнейших расходов на премиальную модель. | Утверждающее лицо, утвержденная сумма или продолжительность, причина, срок действия |
| **Понижение передачи** | Перенесите будущую работу на более дешевую утвержденную модель только для классов задач, прошедших одинаковый контроль качества. | Предыдущая и новая пара модель-жгут, причина маршрутизации, эффект кэша, принятый результат |
| **Подвеска** | Верните явную ошибку терминала с инструкциями по сбросу или эскалации. | Причина отказа, время сброса, владелец, путь восстановления. |

Соблюдайте жесткий терминальный бюджет для автоматических агентов, CI, запланированных заданий и услуг. Никто не может интерпретировать предупреждение, а бесшумное переключение на пониженную передачу может изменить поведение в автоматизированном рабочем процессе. При интерактивной разработке описанные выше этапы могут предотвратить случайные траты до приостановки. Databricks сообщает об этой прогрессивной модели на основе собственного внедрения и бесед с другими компаниями; отчет носит неофициальный характер и не устанавливает, что более высокие расходы означают более высокую производительность. Источник: [Databricks, «Управление затратами на кодирование ИИ в масштабе»](https://www.databricks.com/blog/managing-ai-coding-costs-scale), 7 августа 2026 г.

Шлюз может применять эти элементы управления только к трафику, который он видит. Клиенты, прошедшие проверку подлинности по подписке, и учетные данные прямого поставщика остаются за пределами этой политики. Согласуйте события шлюза с элементами управления кадровым планом и счетами поставщиков, прежде чем объявлять о завершении политики расходов в масштабах всей организации.

## <a name="4-model-allowlists"></a>4. Разрешенные списки моделей

Вызовы моделей, не входящих в список `models` ключа, возвращают `403 ModelNotAllowedError` до того, как запрос достигнет Anthropic. Это обеспечивает соблюдение политики утверждения вашей модели на сетевом уровне независимо от того, что разработчик вкладывает в свою конфигурацию Claude Code.

Трехуровневая структура, отвечающая большинству потребностей организации:

| Уровень | Разрешенные модели | Ежемесячный бюджет | Для |
|------|---------------|---------------|-----|
| Разработчик по умолчанию | Haiku, Sonnet | $30 | Все инженеры |
| Проект повышен | Haiku, Sonnet | $100 | Активная спринтерская работа |
| Lead/Architect | Все модели | $300 | Технические руководители, архитекторы |

Эти цифры представляют собой стартовую структуру, а не измеренный ориентир. Один опубликованный отчет дает сопоставимый порядок величины в масштабе: Back Market сообщил о фиксированной сумме в 200 долларов США на разработчика в месяц, ежемесячно обновляемой примерно для 245 разработчиков, с возможностью эскалации, а не жесткой остановкой. Разработчик, исчерпавший лимит, может самостоятельно обслуживать одно расширение стоимостью 20 долларов, заполнив форму, в которой задается вопрос, сколько сеансов было запущено, какой сеанс стоил больше всего и как расходы распределяются между моделями. Ни один человек не одобряет это расширение; форма существует, поэтому разработчик читает свою собственную консоль. Помимо этого, менеджер представляет смету в комиссию по рассмотрению, и проект получает собственное рабочее пространство OpenRouter вне индивидуальной надбавки. В учетной записи сообщается, что надбавки удерживаются на практике и что форма продления была хорошо принята, но не публикуются данные о выполнении задач, качестве или времени проверки, поэтому он калибрует бюджетную строку и ничего больше. Источник: [Николя Мартиньоле](https://www.youtube.com/watch?v=pbrP--c4alk), опубликовано 14 сентября 2026 г.

Белый список модели не является белым списком поставщика. Агрегатор может предоставлять одну и ту же модель нескольким поставщикам инфраструктуры, каждый из которых имеет разные контракты и пути обработки. Компания Back Market сообщила, что разрешила доступ только небольшой, проверенной внутри компании, группе из примерно 70 провайдеров, доступных тогда через OpenRouter, и назвала среди них Google Vertex, Fireworks и Amazon Bedrock. Автоматически созданная стенограмма искажает размер этого короткого списка, поэтому точное количество не установлено, а выступающий не представил свое заявление в качестве юридической консультации. Более поздний отчет того же докладчика описывает работу примерно с десятью провайдерами и добавляет к названному набору Microsoft Azure и Mistral; эта цифра охватывает фактически используемых поставщиков, которые не обязательно совпадают с утвержденным списком. Рассмотрите и утвердите каждого поставщика отдельно. Источники: [Николя Мартиньоль в 38:17](https://www.youtube.com/watch?v=DRtd8S_3E-w&t=2297s), опубликовано 22 июля 2026 г., и [двухмесячный обзор OpenRouter](https://www.youtube.com/watch?v=pbrP--c4alk), опубликован 14 сентября 2026 г.

В том же аккаунте указано правило, которое только иллюстрирует этот подсчет: маршрутизация к десяти провайдерам означает проверку десяти политик данных. Ответственность не переходит к агрегатору. В учетной записи Back Market ясно указано, что OpenRouter не передает информацию о том, что происходит в Fireworks, Google Vertex или Amazon Bedrock, от имени клиента, поэтому контракт каждого поставщика, путь обработки и средства управления остаются на усмотрении клиента. Единый коммерческий договор с агрегатором упрощает закупки, а не ответственность.

См. Стратегию подписки [](./subscription-strategy.md#6-workforce-plans-and-production-api-traffic-solve-different-problems) для информации о рабочей силе и разделении идентичности API.

## 5. Панели использования

LiteLLM предоставляет метрики Prometheus по адресу `/metrics`. Добавьте конфигурацию очистки в Prometheus:

```yaml
scrape_configs:
  - job_name: litellm
    static_configs:
      - targets: ['litellm-host:4000']
    metrics_path: /metrics
```

Ключевые метрики панелей Grafana:

```
# Total requests by team and model
litellm_requests_total{model, team_id, key_alias}

# Cost by team (USD)
litellm_spend_total{model, team_id}

# Token counts split by input/output/cache
litellm_tokens_total{token_type, model, team_id}

# Error rate by type (budget exceeded, model not allowed, upstream timeout)
litellm_failed_requests_total{model, error_type}
```

Для политики прогрессивных расходов также записывайте настроенный пороговый этап, подтверждения предупреждений, решения об утверждении, понижение передачи, приостановку и результат задачи после каждого вмешательства. Счетчики необработанных расходов и токенов не могут показать, увеличило ли понижение число повторных попыток, время проверки или отклоненную работу.

LiteLLM также предоставляет базовый пользовательский интерфейс на `/ui` (включен с помощью переменных окружения `LITELLM_UI_USERNAME` и `LITELLM_UI_PASSWORD`) для быстрого просмотра разбивки затрат без необходимости полной настройки Grafana.

Счета практиков показывают, что может выявить эта атрибуция в трафике, наблюдаемом шлюзом. Shopify сообщает о распределении затрат предприятия API по командам и людям через внутренний прокси. Отчеты Ramp отслеживают затраты по командам и продуктам. Back Market утверждает, что телеметрия BigQuery выявила расходы Anthropic API от таких клиентов, как Cursor, наряду с существующей стоимостью лицензии. Эти учетные записи не публикуют ни базовые данные о расходах, ни стоимость реализации, ни стоимость принятой задачи. Источники: [Shopify в 22:22](https://www.youtube.com/watch?v=u-3IILWQPRM&t=1342s), опубликовано 2 июля 2025 г.; [Ramp в 24:53](https://www.youtube.com/watch?v=NMs8C2_3M0w&t=1493s), опубликовано 9 марта 2026 г.; и [Back Market в 45:09](https://www.youtube.com/watch?v=kSrEZ57thMg&t=2709s), опубликовано 3 апреля 2026 г.

## 6. Интеграция OpenTelemetry

LiteLLM поддерживает собственный экспорт OTel, который интегрируется со стеком наблюдаемости, описанным в [observability.md §10](./observability.md):

```yaml
litellm_settings:
  otel_endpoint: http://otel-collector:4317
  otel_headers:
    Authorization: Bearer ${OTEL_BEARER_TOKEN}
```

Каждый запрос генерирует диапазон с атрибутами, включая `litellm.model`, `litellm.team_id`, `litellm.key_alias`, `litellm.total_tokens` и `litellm.spend`. Они перетекают в существующие трассировки наряду с диапазонами уровня приложения.

## 7. Развертывание производства

Запустите LiteLLM за обратным прокси-сервером, завершающим TLS (nginx или Caddy). Минимальная настройка Docker Compose:

```yaml
services:
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    ports:
      - "4000:4000"
    environment:
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
      LITELLM_MASTER_KEY: ${LITELLM_MASTER_KEY}
      DATABASE_URL: postgresql://user:pass@db:5432/litellm
    volumes:
      - ./litellm_config.yaml:/app/config.yaml
    command: ["--config", "/app/config.yaml", "--port", "4000"]
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: litellm
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

PostgreSQL необходим для постоянного управления ключами и истории использования. Без него виртуальные ключи и состояние бюджета сбрасываются при перезапуске контейнера.

Для обеспечения высокой доступности запустите два экземпляра LiteLLM за балансировщиком нагрузки. Оба используют одну и ту же базу данных PostgreSQL для обеспечения согласованного состояния ключей.

## <a name="8-portkey-as-a-managed-alternative"></a>8. Портключ как управляемая альтернатива

[Portkey](https://portkey.ai) предлагает те же возможности шлюза, что и размещенная служба, без необходимости управления инфраструктурой. Уровень бесплатного пользования распространяется на небольшие команды (до 10 000 requests/month).

```bash
export ANTHROPIC_BASE_URL=https://api.portkey.ai/anthropic
export ANTHROPIC_API_KEY=your-real-anthropic-key
export PORTKEY_API_KEY=your-portkey-api-key
```

Portkey также поддерживает заголовки `x-portkey-virtual-key` для маршрутизации, регистрации и резервных конфигураций. Компромисс: метаданные вашего запроса покидают вашу инфраструктуру и попадают на серверы Portkey. Ознакомьтесь с их условиями обработки данных, если у вас есть требования соответствия.

## <a name="9-what-the-gateway-does-not-cover"></a>9. Что не охватывает шлюз

Шлюз контролирует запросы, проходящие через него. Он не касается:

- Использование Claude с проверкой подписки отправляется непосредственно на Anthropic.
- Трафик API от клиентов, которые сохраняют учетные данные прямого поставщика или обходят конечную точку шлюза.
- Какие файлы Claude Code читает на машине разработчика (используйте `permissions.deny` в `settings.json`)
- Какие серверы MCP активны локально (см. [enterprise-governance.md §3](../security/enterprise-governance.md#3-mcp-governance-workflow))
- Качество кода на выходе ИИ (используйте механизмы PR-проверки)
- Сохраняет ли предупреждение, одобрение или понижение модели качество принятой задачи
- Журналы аудита на уровне сеанса, показывающие, какие файлы были изменены (см. [ai-traceability.md](./ai-traceability.md#pr-audit-trail)).

Если маршрутизация API только для шлюза является требованием политики, удалите учетные данные прямого поставщика с компьютеров разработчиков и отдельно включите выходной доступ поставщика. Согласование телеметрии шлюза с планом рабочей силы и счетами поставщиков; Панель мониторинга шлюза сама по себе не является полной книгой расходов всей организации.
