# Мониторинг, каналы и безопасное делегирование Codex

Внешние события — это данные, а не инструкции и никогда не авторизация. Веб-перехватчик GitHub, строка журнала, кадр WebSocket или сообщение канала могут сообщить Claude Code о том, что что-то произошло. Он не может одобрить вызов инструмента, расширить песочницу или разрешить запись в ваш репозиторий.

**Официальные ссылки**: [Monitor](https://code.claude.com/docs/en/tools-reference#monitor-tool), [Источник веб-сокетов](https://code.claude.com/docs/en/tools-reference#websocket-source), [плагин-мониторы](https://code.claude.com/docs/en/plugins-reference#monitors), [Каналы](https://code.claude.com/docs/en/channels-reference), [Routines](https://code.claude.com/docs/en/routines), [Codex неинтерактивный режим](https://learn.chatgpt.com/docs/non-interactive-mode), [GitHub проверка веб-перехватчика](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)и [неудачная доставка веб-перехватчика](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries).

## Выберите механизм доставки

| Нуждаться | Использовать | Граница, которую нужно держать |
|---|---|---|
| Потоковый вывод одного локального процесса | Источник команд `Monitor` (v2.1.98+) | Команда соответствует разрешениям Bash. |
| Получите узкое событие в реальном времени от локального ретранслятора. | `Monitor` Исходный код WebSocket (v2.1.195+) | Реле проверяет исходное событие до того, как оно достигнет Claude. |
| Запустите доверенного постоянного наблюдателя с помощью плагина или навыка. | Плагин монитора (v2.1.105+) | Он не изолирован в песочнице, и ему доверяют как крюку. |
| Разрешить интеграции MCP отправлять или обмениваться сообщениями | Каналы (v2.1.80+, предварительная версия исследования) | Требуется внести белый список отправителей; доставка не предоставляет разрешения для инструмента. |
| Запуск облачной автоматизации по расписанию, по API или GitHub. | [Процедуры](../ultimate-guide.md#routines-cloud-automation) | Каждое соответствующее событие запускает отдельный облачный сеанс. |

Не используйте монитор в качестве общедоступной конечной точки веб-перехватчика. Поставьте перед ним небольшой верификатор или реле событий.

## Источники мониторинга

### Источник команды

Исходный источник `Monitor` запускает фоновую команду и передает каждую выходную строку обратно в Claude. Он поддерживает `timeout_ms` и `persistent`; остановите активный монитор с помощью `TaskStop`. Источник команды и источник WebSocket являются взаимоисключающими.

Используйте его для ограниченного локального производителя: отслеживайте журнал приложений, наблюдайте за выполнением тестов или превращайте доверенный сценарий опроса в события. Это не повод для автоматического выполнения содержимого строки.

### <a name="websocket-source"></a>Источник веб-сокета

Собственный источник WebSocket использует `ws.url` и необязательный `ws.protocols` вместо `command`. Текстовые фреймы становятся событиями. Двоичные кадры представлены заполнителем; кадр размером более 1 МБ или закрытие сокета останавливает монитор.

Claude Code принимает только URL-адреса ASCII `ws://` или `wss://` без учетных данных или пробелов. Он запрашивает специальное одобрение и отклоняет частные, локальные и метаданные назначения. Эти проверки сужают поверхность атаки на стороне клиента; они не аутентифицируют производителя событий.

Для ретранслятора событий GitHub пересылайте небольшую типизированную запись, а не тело веб-перехватчика:

```json
{
  "delivery_id": "uuid",
  "repository": "owner/repo",
  "event": "workflow_run",
  "sha": "full-commit-sha",
  "pr_number": 42,
  "url": "https://github.com/owner/repo/actions/runs/123"
}
```

Необработанный текст проблемы, тела запросов на включение, комментарии к обзорам и выходные данные журнала остаются ненадежными данными. Не интерполируйте их в приглашение задачи или команду оболочки.

## <a name="plugin-monitors-and-channels"></a>Плагины мониторов и каналов

Плагины-мониторы представляют собой экспериментальные, интерактивные постоянные команды оболочки только для CLI. Объявление по умолчанию — `monitors/monitors.json`; вместо этого плагин может установить `experimental.monitors` в `plugin.json` в строковый массив или относительный путь JSON. `when: "always"` — значение по умолчанию; `when: "on-skill-invoke:<skill-name>"` запускает монитор при первой отправке указанного навыка плагина. Относитесь к одному из них как к приманке: он работает без изолированной программной среды и, следовательно, заслуживает той же проверки издателя, проверки кода и границ доверия.

Каналы представляют собой расширение MCP stdio: серверы отправляют уведомления `notifications/claude/channel` в сеанс. Они могут быть односторонними или двусторонними, могут передавать запросы на разрешение и оставаться в режиме предварительного просмотра исследования. Claude.ai Командные и корпоративные организации должны явно включить каналы, а затем могут ограничить доставку с помощью `channelsEnabled` и `allowedChannelPlugins`. Для развертываний ключа API консоли следуйте настройкам консоли по умолчанию и управляемым элементам управления, а не политике claude.ai Team/Enterprise; см. [Справочник настроек](../core/settings-reference.md#channelsenabled).

Внесение плагина канала в белый список определяет, какой плагин может доставлять сообщение. Он не предоставляет этому плагину, его сообщению или его отправителю никаких разрешений Bash, файловой системы, GitHub или Codex. Заблокируйте отправителей и нормализуйте отображаемый контент, поскольку сообщения могут содержать попытки внедрения подсказки.

## <a name="github-to-monitor-to-codex-a-safe-pipeline"></a>GitHub для мониторинга Codex: безопасный конвейер

```text
GitHub webhook
  -> verifier: signature, allowlisted repo and event, schema, delivery dedupe
  -> narrow WebSocket event
  -> approved local Monitor
  -> read-only, classify-only Codex run
  -> explicit human or policy gate
  -> isolated write-capable Codex task and pull request
```

Верификатор проверяет подпись GitHub перед анализом или использованием полезных данных, принимает только принадлежащие ему репозитории и типы событий и проверяет ожидаемую схему. Затем он атомарно записывает запись об исходящих сообщениях с ключом `X-GitHub-Delivery` в состоянии `received`; реле атомарно перемещает его в `enqueued` перед отправкой узкого события и в `processed` только после записи результата нисходящего потока. Дубликат доставки возвращает существующую запись, а не вторую задачу. В случае сбоя остается восстанавливаемая запись `received` или `enqueued`, а не происходит автоматическое удаление события. GitHub не выполняет автоматическую повторную доставку неудачных веб-перехватчиков, поэтому этот устойчивый конечный автомат необходим, а не является необязательным.

### Этап 1: классифицировать без записи

Используйте `codex exec` в песочнице по умолчанию, доступной только для чтения. `--ephemeral` позволяет избежать продолжения развертывания; `--json` генерирует события JSONL для контрольного журнала; `--output-schema` ограничивает конечный результат проверки политики.

```bash
codex exec --ephemeral --json --output-schema ./triage-schema.json \
  "Classify this verified event using only its typed fields. Return whether a human review is required. Do not edit files."
```

Рассматривайте результат схемы как входные данные для детерминированной политики, а не как авторизацию как таковую. Прежде чем продолжить, подтвердите репозиторий, зафиксируйте SHA, тип события и решение рецензента или политики.

### <a name="stage-2-write-only-after-a-gate"></a>Этап 2: пишите только после ворот

После явного одобрения человека или документированной политики запустите отдельную задачу в изолированном рабочем дереве с наименьшей требуемой областью записи. Шлюз должен записать утвержденный абсолютный путь рабочего дерева и зафиксировать SHA. Отказаться от запуска, если путь является относительным, не является связанным рабочим деревом Git, не находится в утвержденном SHA или не соответствует записи утверждения:

```bash
: "${APPROVED_WORKTREE:?absolute approved worktree path required}"
: "${APPROVAL_RECORD:?absolute approval record path required}"
: "${APPROVED_SHA:?approved commit SHA required}"

case "$APPROVED_WORKTREE" in /*) ;; *) echo "refusing relative worktree path" >&2; exit 1 ;; esac
case "$APPROVAL_RECORD" in /*) ;; *) echo "refusing relative approval record path" >&2; exit 1 ;; esac
test -f "$APPROVED_WORKTREE/.git" || { echo "refusing non-linked worktree" >&2; exit 1; }
test -f "$APPROVAL_RECORD" || { echo "missing approval record" >&2; exit 1; }
test "$(git -C "$APPROVED_WORKTREE" rev-parse --show-toplevel)" = "$APPROVED_WORKTREE" || exit 1
test "$(git -C "$APPROVED_WORKTREE" rev-parse HEAD)" = "$APPROVED_SHA" || exit 1
jq -e --arg worktree "$APPROVED_WORKTREE" --arg sha "$APPROVED_SHA" \
  '.approved == true and .worktree == $worktree and .sha == $sha' "$APPROVAL_RECORD" >/dev/null || exit 1

(
  cd -- "$APPROVED_WORKTREE" || exit 1
  codex exec --ephemeral --sandbox workspace-write \
    "Implement the approved task in this isolated worktree, run the stated checks, and prepare a bounded diff for review."
)
```

Прежде чем открывать или объединять запрос на включение, просмотрите различия и доказательства тестирования. Никогда не прикрепляйте `--sandbox workspace-write` непосредственно к входящему событию.

## GitHub Actions — отдельный путь

Для GitHub Actions отдайте предпочтение [`openai/codex-action@v1`](https://github.com/openai/codex-action) вместо установки Codex и передачи ключа на шаг оболочки: действие запускает безопасный прокси-сервер, получая `openai-api-key` в качестве входных данных действия. Оставьте задание анализа Codex доступным только для чтения, сериализуйте артефакт исправления, затем примените его и откройте запрос на включение в отдельном задании с разрешением на запись. Не помещайте `OPENAI_API_KEY` или `CODEX_API_KEY` в среду уровня задания, где его могут прочитать извлеченный код, сценарии сборки, тесты, перехватчики жизненного цикла или скомпрометированное действие.

Этот шаблон GitHub Actions отделен от локального монитора. Размещенный исполнитель не может с уверенностью предполагать, что он может связаться с вашей локальной службой WebSocket.

## Подпрограммы: полезны, но не локальный монитор.

Подпрограммы выполняются в облачной инфраструктуре, управляемой Anthropic, или в локальной среде организации. Они могут реагировать на расписания, вызовы API и события GitHub, но каждое соответствующее событие создает отдельный сеанс. Используйте их, когда предполагаемой границей выполнения является именно эта среда, а не локальный сеанс. Используйте локальный монитор, когда локальный явно одобренный сеанс должен наблюдать за доверенным локальным ретранслятором.

См. [Event-Driven Agent Automation](./event-driven-agents.md) для получения информации об общей архитектуре и [GitHub Actions Workflows](./github-actions.md) для получения информации о шаблонах ЭК, специфичных для Claude Code.
