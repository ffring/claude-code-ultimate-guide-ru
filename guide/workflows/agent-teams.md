# <a name="agent-teams-workflow"></a>Рабочий процесс команды агентов

> **Многоагентная параллельная координация для сложных задач**
> **Status**: Экспериментальный (v2.1.32+) | **Model**: любая модель, доступная для сеанса; выбрать для каждого товарища по команде | **Флаг**: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`

**What**: несколько экземпляров Claude работают параллельно в общей базе кода, координируя свои действия автономно, без активного вмешательства человека. Одна сессия действует как руководитель группы, разбивая задачи и обобщая выводы товарищей по команде.

**Когда представлен**: v2.1.32 (05 февраля 2026 г.) в качестве предварительной версии исследования
**Время чтения**: ~30 мин.
**Предварительные требования**: доступная модель и экспериментальный флаг команд агентов, понимание [Суб-агенты](#split-role-sub-agents), знакомство с Task Tool

**🚀 Хотите быстро приступить к работе?** См. **[Краткое руководство по работе с командами агентов](./agent-teams-quick-start.md)** (8–10 минут, копирование шаблонов для ваших проектов)

## Координация команды не является циклом выполнения

Agent Teams координирует несколько сеансов Claude Code. Claude Code остается средой выполнения, которая управляет циклом модели и инструмента каждого сеанса; Репозиторий содержит общие инструкции, настройку, состояние задачи и проверку. Считайте менеджера группы, панель мониторинга или очередь оркестратором, если только он сам не запускает цикл.

Используйте [Agent Harness Map](../ecosystem/agent-harness-landscape.md), чтобы сравнить среды выполнения, владеющие циклами, с отдельным уровнем оркестрации. [Agent Harness Engineering](../core/agent-harness.md) определяет четыре уровня, а [Agent Tools: Beyond Claude Code](../ecosystem/agentic-tools.md) охватывает дополнительные платформы и плоскости управления. Оценивайте передачу обслуживания и восстановление с помощью [Agent Evaluation](../roles/agent-evaluation.md), наблюдайте за работой команды с помощью [Session Observability](../ops/observability.md)и применяйте [Security Hardening](../security/security-hardening.md) перед подключением агентов к конфиденциальным системам. Определения приведены в глоссарии [](../core/glossary.md).

## <a name="1-overview"></a>1. Обзор

### Что такое агентурные команды?

Команды агентов позволяют **несколько Claude экземпляры для параллельной работы** над различными подзадачами, координируя работу через систему на базе git. В отличие от ручных многоэкземплярных рабочих процессов, в которых вы организуете отдельные Claude Если вы проводите сеансы самостоятельно, команды агентов обеспечивают встроенную координацию, при которой агенты заявляют о задачах, непрерывно объединяют изменения и автоматически разрешают конфликты.

**Основные характеристики**:
- ✅ **Автономная координация**: делегаты, ведущие команду, товарищи по команде общаются через почтовый ящик
- ✅ **Одноранговый обмен сообщениями**: прямая связь между агентами (а не только иерархическая)
- ✅ **Блокировка на основе Git**: агенты запрашивают задачи, записывая их в общий каталог.
- ✅ **Непрерывное слияние**: изменения pulled/pushed без ручного вмешательства.
- ✅ **Независимый контекст**: каждый агент имеет собственное окно контекста токена размером 1 млн (изолированное)
- ⚠️ **Experimental**: предварительная версия исследования, стабильность не гарантируется
- ⚠️ **Token-интенсивный**: несколько одновременных вызовов модели означают высокую стоимость.

> **Не то же самое, что обмен сообщениями между сеансами.**: почтовый ящик выше объединяет товарищей по команде, которых руководитель группы создал сам. Чтобы отправить сообщение в сеанс, который уже существует независимо, который вы запустили и управляете самостоятельно, см. [Cross-Session Messaging](./cross-session-messaging.md). Оба используют один и тот же базовый инструмент `SendMessage`.

### Команды агентов против других шаблонов

| Шаблон | Координация | Настройка | Лучшее для |
|---------|--------------|-------|----------|
| **Команды агентов** | Автоматический (встроенный) | Экспериментальный флаг | Сложные задачи чтения, требующие координации |
| **Multi-Instance** | Руководство (человеческая оркестровка) | Несколько терминалов | Независимые параллельные задачи, координация не требуется |
| **Dual-Instance** | Руководство (человеческий контроль) | 2 терминала | Обеспечение качества, разделение планирования и выполнения |
| **Инструмент задач** | Автоматически (субагенты) | Встроенная функция | Делегирование задач одному агенту, последовательная работа |

**Основное отличие**:
- **Multi-Instance** = Вы управляете координацией (отдельные проекты, без общего состояния)
- **Agent Teams** = Claude управляет координацией (общая база кода, связь на основе git)

### Наблюдаются антипаттерны

| Anti-Pattern | Симптом | Исправить |
|-------------|---------|-----|
| **Слишком много агентов** | >5 агентов = затраты на координацию > производительность | Начните с 2-3, постепенно масштабируйте |
| **Over-delegation** | Затраты на переключение контекста превышают прибыль | Активный человеческий контроль над важными решениями |
| **Преждевременная автоматизация** | Автоматизация рабочего процесса не освоена вручную | Ручной → Полуавтоматический → Полностью автоматический (прогрессивный) |

### <a name="when-large-teams-are-justified"></a>Когда большие команды оправданы

Приведенное выше правило «>5 агентов» является разумным по умолчанию, но оно не работает в определенных сценариях, где математика благоприятствует более крупным командам. Настоящий вопрос не в том, «сколько агентов?» но «является ли накладные расходы на координацию менее дорогостоящими, чем переполнение контекста?»

**Контекстное окно как решающий фактор**: Один агент Claude Code с кодовой базой из более чем 50 тыс. строк заполняет 80-90% своего контекстного окна, просто загружая соответствующие файлы (источник: atcyrus.com). В этот момент у агента почти не остается места для рассуждений. Разделение на несколько агентов обеспечивает использование контекста каждым из них примерно на 40 %, что оставляет запас для фактического решения проблем.

| Сценарий | Один агент | Команда из 3 агентов | Команда из 5 агентов |
|----------|-------------|--------------|--------------|
| Кодовая база 10 тыс. строк | ~30% контекст, удобно | Излишнее убийство | Излишнее убийство |
| Кодовая база 50 тыс. строк | 80-90% контекста, деградация рассуждений | Идеальное разделение | Оправданно, если действительно параллельные модули |
| Кодовая база более 100 тыс. строк | Переполнение контекста, агент пропускает файлы | Может все еще переполняться для каждого агента | Оправдано, считайте еще больше |

**Когда имеет смысл использовать больше агентов**:
- Независимые модули с нулевым общим состоянием (нет затрат на координацию)
- Параллельный рефакторинг изолированных файловых деревьев (интерфейс, сервер, инфраструктура)
- Анализ с большим объемом чтения, где каждый агент охватывает отдельную подсистему
- Кодовая база физически не может вписаться в контекст одного агента, если есть свободное место.

**Когда больше агентов причиняют вред**: Если агентам постоянно приходится читать выходные данные друг друга или изменять общие файлы, добавление агентов добавляет конфликты слияния и сообщения координации, которые врезаются в тот самый контекст, который вы пытались сохранить.

> **Выбор модели для каждой роли**: товарищи по команде могут использовать разные модели. Укажите его в запросе на создание или определении агента. В противном случае `CLAUDE_CODE_SUBAGENT_MODEL` или ведущая модель предоставляют значение по умолчанию; принудительная настройка модели субагента может переопределить этот порядок. Товарищи по команде наследуют настройку ведущего усилия. Выбирайте модели по задачам и оценивайте полную стоимость команды. [Официальная документация по командам агентов](https://code.claude.com/docs/en/agent-teams).

В более широком отраслевом контексте: Gartner прогнозирует, что к концу 2026 года 40% корпоративных приложений будут включать в себя агенты для конкретных задач. Шаблоны командной координации, установленные сейчас в Claude Code и подобных инструментах, вероятно, станут стандартной практикой.

### <a name="cost-benefit-analysis"></a>Анализ затрат и выгод

**Команды агентов** против **Многоэкземплярное руководство**:

| Аспект | Команды агентов | Мультиэкземпляр (вручную) |
|--------|-------------|------------------------|

## <a name="2-architecture-deep-dive"></a>2. Глубокое погружение в архитектуру

### Архитектура ведущего коллеги

```
┌─────────────────────────────────────────────────┐
│         Team Lead (Main Session)                │
│  - Breaks tasks into subtasks                   │
│  - Spawns teammate sessions                     │
│  - Synthesizes findings from all agents         │
│  - Coordinates via shared task list + mailbox   │
└─────────────────┬───────────────────────────────┘
                  │
        ┌─────────┴─────────┐
        │                   │
┌───────▼────────┐  ┌───────▼────────┐
│  Teammate 1    │◄─┼────────────────►│  Teammate 2    │
│                │  │ Peer-to-peer    │                │
│ - Own context  │  │ messaging via   │ - Own context  │
│   (1M tokens)  │  │ mailbox system  │   (1M tokens)  │
│ - Claims tasks │  │                 │ - Claims tasks │
│ - Messages     │  │                 │ - Messages     │
│   team/peers   │  │                 │   team/peers   │
└────────────────┘  └─────────────────┘────────────────┘
```

### Координация на основе Git

**Как это работает**:

1. **Задача, требующая**: агенты записывают файлы блокировки в общий каталог (`.claude/tasks/`)
2. **Выполнение работы**: Каждый агент работает независимо в своем контексте.
3. **Непрерывное слияние**: Агенты pull/push вносят изменения в общий репозиторий git
4. **Разрешение конфликтов**: автоматическое слияние (с ограничениями, см. [§6](#6-limitations--gotchas))
5. **Обобщение результатов**: Руководитель группы собирает результаты и представляет единый ответ

**Пример структуры файла блокировки**:
```
.claude/tasks/
├── task-1.lock        # Agent A claimed
├── task-2.lock        # Agent B claimed
└── task-3.pending     # Not yet claimed
```

### Коммуникационная архитектура

**Ключевое отличие от субагентов**: Команды агентов **реализуют настоящий одноранговый обмен сообщениями** через систему почтовых ящиков, а не только иерархическую отчетность.

**Архитектурные компоненты** (Источник: [Addy Osmani](https://addyosmani.com/blog/claude-code-agent-teams/), февраль 2026 г.):

1. **Руководитель группы**: Создает команду, порождает товарищей по команде, координирует работу.
2. **Teammate**: независимые экземпляры Claude Code с собственным контекстом (по 1 млн токенов каждый)
3. **Список задач**: общие рабочие элементы с отслеживанием зависимостей и автоматической разблокировкой.
4. **Mailbox**: система обмена сообщениями на основе папки «Входящие», обеспечивающая прямую связь между агентами.

**Схемы общения**:
- **Лидер → Товарищ по команде**: прямые сообщения или трансляции всем
- **Teammate → Лидер**: Обновления о ходе работы, вопросы, выводы
- **Teammate ↔ Teammate**: Прямой одноранговый обмен сообщениями (подходы к решению проблем, обсуждение решений)
- **Окончательный синтез**: Руководитель группы объединяет все результаты для пользователя.

**Пример потока сообщений**:
```
Team Lead: "Review this PR for security issues"
├─ Teammate 1 (Security): Analyzes → Messages Teammate 2: "Found auth issue in line 45"
├─ Teammate 2 (Code Quality): Reviews → Messages back: "Confirmed, also see OWASP violation"
└─ Team Lead: Synthesizes findings → Presents unified response to user
```

**Что это позволяет**:
- ✅ Агенты активно оспаривают подходы друг друга
- ✅ Обсуждайте решения без вмешательства человека
- ✅ Самостоятельно координировать свои действия (самоорганизация)
- ✅ Делитесь открытиями в ходе рабочего процесса (через сообщения, а не контекст)

**Limitation**: изоляция контекста сохраняется. Агенты не предоставляют общий доступ к своему полному контекстному окну, а только к явным сообщениям.

### Навигация между агентами

**Встроенная навигация**:
- **Shift+Down**: циклическое переключение между товарищами по команде в рабочем режиме.
- **tmux/iTerm2**: режим разделенной панели с `teammateMode: "tmux"` (требуется tmux или iTerm2 с `it2` CLI)
- **Прямое поглощение**: Вы можете взять под контроль работу любого агента, когда это необходимо.

**Example**:
```bash
# Terminal 1: Team lead (with env var set)
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude

# Claude spawns teammates automatically
# You can navigate with Shift+Down to cycle through teammates (in-process mode)
```

### <a name="context-management"></a>Управление контекстом

**Контекст для каждого агента**:
- Каждый агент имеет свое контекстное окно, определяемое выбранной моделью и провайдером.
- ~30 000 строк кода за сеанс
- **Изоляция контекста**: агенты не предоставляют общий доступ к своему полному контекстному окну.
- **Связь**: Через систему почтовых ящиков (одноранговая связь + синтез руководителей группы)

**Общая емкость контекста** (пример 3 агентов):
- Руководитель команды: 1 миллион токенов
- Товарищ по команде 1: 1 миллион жетонов
- Товарищ по команде 2: 1 миллион жетонов
- **Total**: 3 миллиона токенов в команде (контекст изолирован, но общение осуществляется посредством сообщений)

**Важное отличие**:
- ❌ **Контекст НЕ является общим.**: полный контекст токена агента 1, равный 1 млн, невидим для агента 2.
- ✅ **Сообщения ОБЩИЕ.**: Агенты отправляют явные сообщения через почтовый ящик (выводы, вопросы, обсуждения).

**Когда координация имеет значение**:
- ✅ Задачи с зависимостями (Функции А требуется API из Функции Б)
- ✅ Общие интерфейсы (несколько агентов изменяют один и тот же контракт)
- ✅ Качественные ворота (все агенты должны пройти перед слиянием)

**Когда координация не требуется**:
- ❌ Полностью независимые задачи (отдельные проекты)
- ❌ Нет общего состояния (разные репозитории)
- ❌ Простое распараллеливание (запуск одного и того же скрипта на разных данных)

### <a name="cost-trade-offs"></a>Компромиссы по стоимости

**Сравнение потребления токенов** (оценка):

| Рабочий процесс | Один агент | Команды агентов (3) | Множитель |
|----------|-------------|-----------------|------------|
| **Обзор кода (небольшой PR)** | 10 тысяч токенов | 25 тысяч токенов | 2.5x |
| **Обзор кода (большой PR)** | 50 тысяч токенов | 90 тысяч токенов | 1.8x |
| **Расследование ошибок** | 30 тысяч токенов | 70 тысяч токенов | 2.3x |
| **Реализация функции** | 100 тыс. токенов | 200 тыс. токенов | 2x |
| **Рефакторинг (большой)** | 150 тысяч токенов | 250 тысяч токенов | 1.7x |

**Сценарии обоснования затрат**:
- ✅ **Критичное ко времени**: производственные проблемы, требующие быстрого решения.
- ✅ **Complexity**: Многоуровневый анализ (безопасность + производительность + архитектура)
- ✅ **Quality**: важные изменения, требующие нескольких уровней проверки.
- ❌ **Простые задачи**: Простые реализации (излишества)
- ❌ **Ограниченный бюджет**: Персональные проекты с жесткими лимитами токенов.

**Практическое правило**: Команды агентов оправдывают себя, когда экономия времени превышает двукратное увеличение стоимости токенов.

## <a name="6-limitations--gotchas"></a>6. Ограничения и подводные камни

### Компромисс между интенсивным чтением и интенсивной записью

**Основное ограничение**: команды агентов превосходно справляются с задачами, требующими большого количества операций чтения, но с трудом справляются с задачами, требующими большого объема записи, когда несколько агентов изменяют одни и те же файлы.

**Почему это важно**:
```
Read-heavy (✅ Good for teams):
- Code review: Agents read code, provide analysis
- Bug tracing: Agents read logs, trace execution
- Architecture analysis: Agents read structure, identify patterns

Write-heavy (⚠️ Risky for teams):
- Refactoring shared types: Multiple agents modify same file → merge conflicts
- Database schema changes: Coordinated migrations across files
- API contract updates: Interface changes require synchronization
```

**Стратегии смягчения последствий**:
1. **Четкие границы**: назначьте агентам непересекающиеся наборы файлов.
2. **Interface-first**: определение контрактов перед параллельной реализацией.
3. **Шаблон с одной записью**: один агент записывает общие файлы, другие только читают.
4. **Человеческий обзор**: разрешайте конфликты слияния вручную, когда они возникают.

### Объединение сценариев конфликта

**Автоматическое разрешение работает**:
- ✅ Разные файлы, измененные разными агентами
- ✅ Различные функции в одном файле (чистое слияние git)
- ✅ Аддитивные изменения (новые функции, без правок)

**Проблемы с автоматическим разрешением**:
- ❌ Изменены те же строки (классический конфликт слияния)
- ❌ Противоречивая логика (Агент А удаляет проверку, Агент Б добавляет ее)
- ❌ Циклические зависимости (Агенту А нужны выходные данные агента Б, и наоборот)

**Пример конфликта**:
```typescript
// Agent 1 changes:
function processUser(user: User) {
  validateEmail(user.email); // Added validation
  return save(user);
}

// Agent 2 changes (same time):
function processUser(user: User) {
  return save(sanitize(user)); // Added sanitization
}

// Conflict: Both modified same function
// Resolution: Human decides order (validate → sanitize → save)
```

### Последствия интенсивности использования токенов

**Почему требуется много токенов**:
- Каждый агент выполняет **отдельный вывод модели** (3 агента = 3 базовых стоимости).
- Загрузка контекста для каждого агента (1 млн токенов × 3 = емкость токена 3 млн)
- Накладные расходы на координацию (синтез руководителей группы)

**Примерный бюджет** (стандартные тарифы Opus 5.5, без кэширования и дополнительных жетонов координации):
```
Single agent session:
- Input: 50K tokens @ $4/M = $0.20
- Output: 5K tokens @ $20/M = $0.10
- Total: $0.30

Agent teams (3 agents):
- Input: 150K tokens @ $4/M = $0.60
- Output: 15K tokens @ $20/M = $0.30
- Total: $0.90

Cost multiplier: 3x
```

**Требуется обоснование**:
- ✅ Экономия времени > увеличение затрат (проблемы с производством)
- ✅ Критическое качество (финансовые услуги, здравоохранение)
- ✅ Сложность оправдывает распараллеливание (многоуровневый анализ)
- ❌ Простые задачи (используйте одного агента)
- ❌ Персональные учебные проекты (с ограниченным бюджетом)

### Предостережения относительно экспериментального статуса

**Что означает «экспериментальный»**:
- ⚠️ **Нет гарантии стабильности.**: функция может быть изменена или удалена.
- ⚠️ **Ожидаются ошибки**: Сообщайте о проблемах в Anthropic (GitHub Issues)
- ⚠️ **Изменчивость производительности**: Скорость координации может колебаться.
- ⚠️ **Документация развивается.**: Официальная документация по-прежнему минимальна.

**Соображения по производственному использованию**:
1. **Запасной план**: будьте готовы вернуться к использованию одного агента в случае возникновения проблем.
2. **Мониторинг**: тщательно отслеживайте стоимость токенов (может быстро возрастать)
3. **Validation**: Человеческая проверка результатов команды агентов (не доверяйте слепо)
4. **Feedback**: сообщите bugs/experiences, чтобы помочь Anthropic улучшить функцию.

**Отчеты практикующего специалиста** (по состоянию на февраль 2026 г.):
- ✅ Пол Рейнер: «Довольно впечатляюще» (производственное использование подтверждено)
- ✅ Фонтан: на 50% быстрее (развёрнут в производстве)
- ✅ CRED: скорость 2x (15 миллионов пользователей, финансовые услуги)
- ⚠️ Сообщество: смешанные отчеты (некоторые проблемы с конфликтами при слиянии).

### <a name="context-isolation"></a>Изоляция контекста

**Чего агенты не могут делать**:
- ❌ **Поделиться контекстными окнами**: полный контекст агента 1 (1 млн токенов) не виден агенту 2.
- ❌ **Автосинхронизация обнаружений**: агент 2 не увидит результаты агента 1, если об этом не будет получено явное сообщение.
- ❌ **Координация времени**: агенты работают независимо, могут завершить работу в разное время.

**Что МОГУТ делать агенты**:
- ✅ **Отправлять сообщения**: через систему почтовых ящиков (одноранговая сеть или через руководителя группы)
- ✅ **Подходы к вызову**: обсуждайте решения, задавайте вопросы друг другу
- ✅ **Поделиться выводами**: Явный обмен сообщениями (не автоматический обмен контекстом)

**Implications**:
```
Scenario: Agent 1 discovers critical bug that affects Agent 2's work

Without messaging:
- Agent 2 doesn't see Agent 1's discovery automatically
- Agent 2 may continue with flawed assumption

With messaging (built-in):
- Agent 1 messages Agent 2: "Found auth issue in line 45"
- Agent 2 adjusts approach based on message
- Team lead synthesizes all findings at end

Mitigation:
- Agents can message each other via mailbox system
- Team lead synthesizes findings after all agents complete
- Human can interrupt and redirect agents mid-workflow (Shift+Down to cycle teammates)
- Design tasks with minimal inter-agent dependencies
```

### Когда НЕ использовать команды агентов

**Один агент лучше для**:
- ❌ **Простые задачи**: Простые реализации (излишества)
- ❌ **Малые кодовые базы**: затронуто <5 файлов (накладные расходы на координацию не оправданы)
- ❌ **Задачи, требующие большого объема записи.**: множество модификаций общих файлов (риск конфликта слияния).
- ❌ **Последовательные зависимости**: Задача B требует завершения задачи A (никаких преимуществ от распараллеливания).
- ❌ **Бюджетные ограничения**: Личные проекты, обучение (множитель стоимости токена)
- ❌ **Тесные взаимозависимости**: Круговые зависимости между задачами

**Пример плохого соответствия**:
```
Task: Update authentication logic in shared auth.ts file

Why single agent better:
- One file modified (no parallelization benefit)
- Write-heavy (multiple changes to same file)
- No clear subtask boundaries (logic intertwined)
- Sequential flow (test after each change)

Result: Agent teams would create merge conflicts, no time savings
```

- **Architecture**: встроенная функция Claude Code, координация на основе git.
- **Coordination**: блокировка git в реальном времени, автоматическое слияние.
- **Maturity**: официальная функция Anthropic (экспериментальная).

## <a name="8-best-practices"></a>8. Лучшие практики

### Стратегии декомпозиции задач

**Принцип четких границ**:
```
Good decomposition:
- Agent 1: Backend API endpoints (/api/users/*)
- Agent 2: Frontend components (src/components/users/*)
- Agent 3: Database migrations (db/migrations/users/)

Why good:
- Non-overlapping file sets (no merge conflicts)
- Clear interfaces (API contracts)
- Independent testing (each layer testable)
```

```
Bad decomposition:
- Agent 1: User authentication
- Agent 2: User authorization
- Agent 3: User session management

Why bad:
- Overlapping files (auth.ts touched by all 3)
- Interdependencies (auth needs sessions, sessions need auth)
- Sequential coupling (can't parallelize effectively)
```

**Подход с упором на интерфейс**:
1. **Определение контрактов**: Согласование сигнатур функций и схем API перед параллельной работой.
2. **Type stubs**: сначала создайте TypeScript types/interfaces, реализуйте отдельно
3. **Mock borders**: каждый агент изначально работает с имитируемыми зависимостями.
4. **Фаза интеграции**: Руководитель группы координирует окончательную интеграцию

**Example**:
```typescript
// Team lead defines interface first
interface UserService {
  authenticate(email: string, password: string): Promise<User>;
  authorize(user: User, resource: string): Promise<boolean>;
}

// Agent 1 implements authenticate
// Agent 2 implements authorize
// No merge conflicts (different functions)
```

### Модели координации

**Веерный выход, входной вентилятор**:
```
Team lead
  │
  ├─ Agent 1: Task A ──┐
  ├─ Agent 2: Task B ──┼──> Team lead synthesizes
  └─ Agent 3: Task C ──┘
```

**Последовательные этапы с распараллеливанием**:
```
Phase 1 (Sequential):
  Team lead: Define architecture

Phase 2 (Parallel):
  ├─ Agent 1: Implement backend
  ├─ Agent 2: Implement frontend
  └─ Agent 3: Write tests

Phase 3 (Sequential):
  Team lead: Integration + validation
```

**Иерархическое делегирование**:
```
Team lead
  │
  ├─ Agent 1 (Backend lead)
  │   ├─ Agent 1a: Controllers
  │   └─ Agent 1b: Services
  │
  └─ Agent 2 (Frontend lead)
      ├─ Agent 2a: Components
      └─ Agent 2b: State management
```

### <a name="agentsmd-for-compound-learning"></a>AGENTS.md для сложного обучения

Команды агентов получают выгоду от общего файла контекста, в котором накапливаются знания, полученные в ходе нескольких сеансов: шаблоны, которые сработали, подводные камни, которых следует избегать, ошибки, специфичные для кодовой базы. Этот файл называется `AGENTS.md` (аналог `CLAUDE.md`, но применим к агентским рабочим процессам).

**Что положить в AGENTS.md**:
```markdown
## Proven Patterns
- Use Interface-First decomposition for this codebase (see src/types/)
- Backend agent must run `db:migrate` before tests — env is not auto-seeded

## Pitfalls
- Do NOT modify auth.ts and session.ts in parallel — circular imports cause test failures
- Linter runs on save; do not commit with lint errors, the CI gate is strict

## Style
- All API responses must follow the ApiResponse<T> wrapper type
- Error codes live in src/constants/errors.ts — always reuse, never hardcode strings
```

**Критическое правило: никогда не позволяйте агентам писать AGENTS.md напрямую**. Исследование ETH Zürich (Gloaguen et al., 2026) подтверждает, что контекстные файлы, созданные с помощью LLM, снижают успешность выполнения задач примерно на 3 % и увеличивают затраты на логические выводы более чем на 20 % по сравнению с улучшением примерно на 4 % по сравнению с файлами, написанными разработчиками. Механизм: агенты генерируют общий, раздутый контекст, который создает когнитивные издержки для каждого последующего агента, читающего его.

Каждая строка в AGENTS.md должна быть одобрена человеком. Если товарищ по команде определяет новый шаблон, который стоит задокументировать, он отправляет предложение руководителю группы, и руководитель решает, добавлять ли его.

**Maintenance**: Просматривайте AGENTS.md после каждого сеанса команды (ретро-этап заводской модели). Удалите записи, которые больше не актуальны. Устаревшие инструкции активно вредны, а не нейтральны.

### Управление рабочим деревом Git

**Почему рабочие деревья важны**:
- Каждый агент работает в отдельном рабочем дереве git (изолированная файловая система).
- Предотвращает конфликты блокировки файлов
- Обеспечивает параллельную модификацию файлов.

**Setup**:
```bash
# Main repository
git worktree add ../project-agent1 main

# Agent 1 works in project-agent1/
# Agent 2 works in project-agent2/
# Team lead works in project/

# All sync via git commits
```

**Рекомендации**:
- ✅ Одно рабочее дерево на каждого агента
- ✅ Частые коммиты (непрерывное слияние)
- ✅ Описательные названия ветвей (`agent1-backend-api`, `agent2-frontend-ui`)
- ❌ Не изменяйте одни и те же файлы в рабочих деревьях без координации.

### Оптимизация затрат

**Стратегии сохранения токенов**:

1. **Отложенное создание**: Агенты создаются только тогда, когда распараллеливание явно дает преимущества.
   ```
   Bad: "Spawn 3 agents to implement this button"
   Good: "Spawn agents for multi-layer security review"
   ```

2. **Обрезка контекста**: удаление ненужных файлов из контекста агента.
   ```
   # Tell agent what to ignore
   "Review backend API, ignore frontend files"
   ```

3. **Прогрессивная эскалация**: начните с одного агента, при необходимости эскалируйте команду
   ```
   Step 1: Single agent attempts task
   Step 2: If complexity high, spawn team
   ```

4. **Кэширование результатов**: повторное использование результатов агента в аналогичных задачах.
   ```
   "Agent 1 found security issues in auth.ts.
   Agent 2, check if user.ts has same patterns."
   ```

5. **Бюджеты жестких токенов на агента**: назначьте ограничения для конкретного домена, чтобы предотвратить безудержное потребление
   ```bash
   # In task brief to each teammate
   "Frontend agent: stay under 180k tokens total.
   Backend agent: stay under 280k tokens total.
   Auto-pause and report status at 85% of your budget."
   ```
   Стоимость токенов линейно зависит от размера команды: команда из 5 агентов может потреблять в 5 раз больше токенов за одну сессию. Ограничения не позволяют кроличьей норе одного агента потратить весь бюджет сеанса.

### Гарантия качества

**Контрольный список проверки**:
- [ ] **Все агенты выполнены**: зависших задач нет.
- [ ] **Конфликты слияния разрешены**: Очистить историю git
- [ ] **Тесты пройдены**: набор автоматизированных тестов, зеленый
- [ ] **Человеческий обзор**: Проверка кода (не доверяйте слепо)
- [ ] **Межагентная согласованность**: Именование, согласование шаблонов

**Красные флаги**:
- ⚠️ Агенты заканчивали работу в разное время (несбалансированная нагрузка)
- ⚠️ Множество конфликтов слияния (плохая декомпозиция задач)
- ⚠️ Провал тестов после слияния (проблемы с интеграцией)
- ⚠️ Непоследовательный стиль кода (агенты не следовали общим стандартам)

**Mitigation**:
```bash
# After agent teams complete
git diff main..agent-teams-branch  # Review all changes
npm test                           # Run full test suite
npm run lint                       # Check code style
```

### <a name="loop-guardrails"></a>Петлевые ограждения

Команды агентов могут застрять в непродуктивных циклах повторов без жестких ограничений на итерацию. Этому препятствуют два механизма:

**MAX_ITERATIONS на каждого товарища по команде**:

Установите жесткий лимит в брифе задачи для каждого товарища по команде:
```
"Maximum 8 attempts on any single failing task.
Before retrying, answer: What specifically failed? What one change would fix it?
If still blocked after 8 attempts, stop and report to team lead."
```

Обязательная подсказка для размышления («Что не удалось? Какое конкретное изменение могло бы это исправить?») существенно сокращает число застрявших агентов. Это заставляет агента изменить подход, а не повторять одно и то же неудачное действие с небольшими вариациями.

**Уничтожить и переназначить критерии**:
- Застрял на 3+ итерациях одного и того же блокировщика → завершите задачу, переназначьте ее с более конкретным контекстом
- Задача израсходовала >85% бюджета токенов без фиксации → приостановить и сообщить
- Нет прогресса после двух циклов размышлений → перейти к руководителю команды

### <a name="dedicated-reviewer-teammate"></a>Преданный товарищ по команде рецензентов

Для групп производственных агентов добавление агента-рецензента, доступного только для чтения, улучшает качество вывода без снижения пропускной способности:

**Setup**:
```
Reviewer brief:
- Model: Claude Opus 5.5 (an explicit choice to evaluate)
- Tools available: lint, run tests, security-scan only — no file writes
- Trigger: automatically review on every TaskCompleted event
- Scope: the specific files changed in that task, not the full codebase
- Output: structured findings (blocking / non-blocking) added to shared task list
```

**Ratio**: 1 рецензент на 3-4 строителя. При меньшем количестве строителей рецензент становится узким местом; при большем количестве очередь на просмотр резервируется.

**Почему важно только чтение**: рецензент с доступом на запись начнет исправлять проблемы самостоятельно, что создает конфликты слияния и сводит на нет цель параллельной изоляции.

## <a name="9-troubleshooting"></a>9. Устранение неполадок

### Общие проблемы

#### Проблема: агенты не появляются.

**Symptoms**:
- Запрос команды агента принят, но товарищи по команде не созданы
- Действует только сеанс руководства командой

**Causes**:
1. Флаг функции установлен неправильно
2. Выбранная модель товарища по команде недоступна для учетной записи или заблокирована политикой организации.
3. Задача недостаточно сложна (Claude решил, что одного агента достаточно)

**Solutions**:
```bash
# Verify flag
echo $CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS  # Should output "1" or "true"

# Check settings
cat ~/.claude/settings.json | grep CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS  # Should contain "1"

# Force model
/model opus

# Explicit request
"Spawn 3 agents for this task (team lead + 2 teammates)"
```

#### Проблема: слишком много конфликтов слияния

**Symptoms**:
- Многие конфликты git после завершения работы агентов
- Разрешение вручную требуется часто

**Causes**:
- Плохая декомпозиция задач (перекрывающиеся наборы файлов)
- Задача с большим объемом записи (несколько агентов изменяют общие файлы)

**Solutions**:
```
Prevention:
1. Clear boundaries: Non-overlapping file assignments
2. Interface-first: Define contracts before implementation
3. Single-writer: One agent writes shared files, others read

Recovery:
1. Revert: git reset --hard before-agent-teams
2. Sequential: Re-implement with single agent
3. Human merge: Manually resolve conflicts (git mergetool)
```

#### Проблема: высокая стоимость токенов

**Symptoms**:
- Использование токенов в 3 раза выше, чем ожидалось
- Бюджет быстро исчерпан

**Causes**:
- Чрезмерное порождение агентов (3+ агента для простых задач)
- Длительные сеансы (агенты простаивают)
- Большой контекст для каждого агента (1 млн токенов × 3)

**Solutions**:
```
Immediate:
1. Kill extra agents: Shift+Down, exit agent session
2. Reduce scope: Narrow task boundaries
3. Switch to single agent: /model sonnet (cheaper)

Long-term:
1. Cost monitoring: Track token usage per session
2. Lazy spawning: Only spawn when needed
3. Progressive escalation: Start small, scale up if needed
```

#### Проблема: Агенты stuck/hanging

**Symptoms**:
- Один агент завершает работу, другие еще долго обрабатывают заявку.
- Нет обновлений о прогрессе

**Causes**:
- Несбалансированное распределение задач (на одного агента приходится 80% работы)
- Агент ожидает зависимости (последовательное соединение)
- Ошибка в координации git (редко)

**Solutions**:
```bash
# Navigate to stuck agent
Shift+Down  # Switch to agent

# Check status
"What are you working on? Progress update?"

# Manual takeover if needed
"Stop current task, report findings so far"

# Kill and redistribute
Exit agent → Team lead redistributes task
```

#### Проблема: противоречивые результаты у разных агентов.

**Symptoms**:
- Агент 1 говорит: «Нет проблем», агент 2 находит 10 ошибок (та же кодовая база)
- Противоречивые рекомендации

**Causes**:
- Разные контекстные окна (агенты видели разные файлы)
- Неоднозначные инструкции (агенты интерпретируются по-разному)
- Изменчивость модели (стохастические результаты)

**Solutions**:
```
Prevention:
1. Explicit instructions: "All agents: Check for SQL injection"
2. Shared context: Point all agents to same reference docs
3. Validation: Human reviews all agent outputs

Recovery:
1. Reconciliation: "Compare Agent 1 and Agent 2 findings, resolve conflicts"
2. Third opinion: Spawn Agent 3 to arbitrate
3. Human decision: You choose which agent's recommendation to follow
```

## <a name="9-iterative-retrieval-for-sub-agents"></a>9. Итеративный поиск субагентов.

Когда субагенту не хватает контекста для точного выполнения своей задачи, режим отказа по умолчанию таков: он делает предположения и генерирует правдоподобные, но неверные выходные данные. Вывод выглядит достаточно разумным, чтобы его можно было быстро просмотреть, но в дальнейшем он прерывается.

**Шаблон**: дайте субагентам бюджет поиска. Они могут запрашивать больше контекста за N циклов, прежде чем передать ответ, а три цикла охватывают большинство случаев, ограничивая при этом стоимость и задержку.

### Структура

```
Cycle 1: Agent receives task + initial context
         → If confident: produce output
         → If uncertain: identify what's missing, request specific files or symbols

Cycle 2: Agent receives requested context
         → If confident: produce output
         → If still uncertain: one final targeted request

Cycle 3: Agent receives final context
         → Produce best output regardless of remaining uncertainty
         → Flag explicit assumptions made
```

### Что передать субагентам

Самая распространенная ошибка: сообщать субагенту ЧТО без ответа ПОЧЕМУ. Агент, который знает, что он «реализует механизм повторных попыток для платежной службы», имеет контекст, который экономит циклы исправлений:

```markdown
## Objective
[WHY this task exists — the problem being solved, the constraint being met]

## Task
[WHAT to do, specifically]

## Context
Files you have access to: [...]
Known constraints: [...]
What NOT to touch: [...]

## If you need more information
You may request up to 2 additional context cycles. Be specific:
- Name the exact files or symbols you need
- Explain why they're required to complete the task accurately
State explicitly: "I need [X] because [Y]" — not "I might need more context"

## Output format
[...]
```

### Когда это применять

| Ситуация | Использовать итеративный поиск? |
|-----------|------------------------|
| Субагент модифицирует 1–2 известных файла. | Нет: предоставить файлы напрямую |
| Субагенту необходимо понимать поведение системы. | Да: возможно, потребуется отслеживать графики вызовов |
| Субагент принимает архитектурные решения | Да, всегда |
| Субагент пишет тесты для существующего кода | Часто: ему нужно прочитать, что он тестирует. |

Накладные расходы реальны (каждый цикл стоит жетонов и задержек). Применяйте его к задачам, где неверные предположения будут стоить дороже, чем поиск, обычно это касается интерфейсов, контрактов или общедоступных API.

> **Credit**: шаблон итерационного поиска для субагентов из [Everything Claude Code](https://github.com/affaan-m/everything-claude-code) (Аффаан Мустафа). Связывание максимальных 3-х циклов и разделение WHY/WHAT задокументированы в их подробном руководстве.

Задокументированный случай на Picnic продемонстрировал ту же закономерность на уровне команды: воспринимаемая производительность резко выросла в первые недели разработки с помощью ИИ, а затем снизилась, когда код был выпущен быстрее, чем его можно было просмотреть, что привело к повторной доработке одних и тех же функций.

## <a name="advanced-orchestration-patterns"></a>Расширенные шаблоны оркестровки

Эти шаблоны касаются режимов сбоя, которые возникают в масштабе многоагентных конвейеров: координаторы, которые выполняют слишком много работы самостоятельно, агенты, которые действуют без предварительных условий, и конвейеры, которые не могут восстановиться после сбоев в середине выполнения.

### <a name="hub-and-spoke-coordinator"></a>Координатор ступицы и спицы

Схема «ступица и спицы» отделяет координацию от исполнения. Агент-координатор декомпозирует задачу, выбирает субагентов, распределяет работу, отслеживает результаты и агрегирует выходные данные. Он сам не выполняет никакой предметной работы: ни исследований, ни анализа, ни генерации. Именно такое разделение позволяет повторно использовать координатор для разных типов задач.

```python
from dataclasses import dataclass
from typing import Callable, Any

@dataclass
class SubagentResult:
    agent_id: str
    task: str
    result: Any
    success: bool
    error: str | None = None

class ResearchCoordinator:
    def __init__(self, subagents: dict[str, Callable]):
        self.subagents = subagents  # name -> callable

    def run(self, research_question: str) -> dict:
        # Decompose into parallel subtasks
        subtasks = self.decompose(research_question)

        # Dispatch to appropriate subagents
        results = []
        for subtask in subtasks:
            agent_name = self.select_agent(subtask)
            if agent_name not in self.subagents:
                results.append(SubagentResult(
                    agent_id=agent_name, task=subtask,
                    result=None, success=False,
                    error=f"No agent available for: {agent_name}"
                ))
                continue

            try:
                result = self.subagents[agent_name](subtask)
                results.append(SubagentResult(
                    agent_id=agent_name, task=subtask,
                    result=result, success=True
                ))
            except Exception as e:
                results.append(SubagentResult(
                    agent_id=agent_name, task=subtask,
                    result=None, success=False, error=str(e)
                ))

        # Aggregate — coordinator's only domain responsibility
        return self.aggregate(research_question, results)

    def decompose(self, question: str) -> list[str]:
        # Returns subtasks — coordinator decides structure, not domain content
        raise NotImplementedError

    def select_agent(self, subtask: str) -> str:
        # Routing logic — pattern matching or LLM-based selection
        raise NotImplementedError

    def aggregate(self, original_question: str, results: list[SubagentResult]) -> dict:
        successful = [r for r in results if r.success]
        failed = [r for r in results if not r.success]

        return {
            "question": original_question,
            "findings": [r.result for r in successful],
            "coverage": len(successful) / len(results) if results else 0.0,
            "failures": [{"task": r.task, "error": r.error} for r in failed]
        }
```

Координатор никогда не трогает содержание результатов, а только маршрутизирует их, подсчитывает и передает на этап агрегирования. Если вы обнаружите код координатора, содержащий логику анализа, бизнес-правила или обработку, специфичную для предметной области, эта логика принадлежит субагенту.

### <a name="programmatic-prerequisites"></a>Программные предпосылки

Предварительные проверки должны быть детерминированными, а не быстрыми инструкциями. Сказать модели: «Прежде чем продолжить, убедитесь, что данные готовы» — это предложение, а не обязательное условие. Программным предварительным условием является проверка состояния, которая либо позволяет продолжить выполнение, либо возвращает структурированную ошибку.

**Шаблон 1: Ворота государственного флага**

```python
@dataclass
class PipelineState:
    data_ingested: bool = False
    schema_validated: bool = False
    permissions_checked: bool = False

    def can_proceed_to_analysis(self) -> tuple[bool, list[str]]:
        missing = []
        if not self.data_ingested:
            missing.append("data_ingested")
        if not self.schema_validated:
            missing.append("schema_validated")
        if not self.permissions_checked:
            missing.append("permissions_checked")
        return len(missing) == 0, missing

def run_analysis_phase(state: PipelineState, data: dict) -> dict:
    can_proceed, missing = state.can_proceed_to_analysis()
    if not can_proceed:
        return {
            "status": "blocked",
            "reason": f"Prerequisites not met: {', '.join(missing)}",
            "required": missing
        }

    # Proceed with analysis — all prerequisites confirmed
    return perform_analysis(data)
```

**Схема 2: Поэтапная диспетчеризация**

Для конвейеров с последовательными фазами оркестратор осуществляет диспетчеризацию на основе завершенных фаз, а не на основе затраченного времени или количества ходов:

```python
from enum import Enum

class PipelinePhase(Enum):
    INIT = "init"
    INGESTION = "ingestion"
    VALIDATION = "validation"
    PROCESSING = "processing"
    COMPLETE = "complete"
    FAILED = "failed"

@dataclass
class PipelineContext:
    phase: PipelinePhase = PipelinePhase.INIT
    phase_results: dict = None

    def __post_init__(self):
        if self.phase_results is None:
            self.phase_results = {}

def dispatch_next_phase(context: PipelineContext, agents: dict) -> PipelineContext:
    next_phase_map = {
        PipelinePhase.INIT: PipelinePhase.INGESTION,
        PipelinePhase.INGESTION: PipelinePhase.VALIDATION,
        PipelinePhase.VALIDATION: PipelinePhase.PROCESSING,
        PipelinePhase.PROCESSING: PipelinePhase.COMPLETE
    }

    next_phase = next_phase_map.get(context.phase)
    if next_phase is None:
        return context

    agent = agents.get(next_phase.value)
    if agent is None:
        context.phase = PipelinePhase.FAILED
        return context

    try:
        result = agent(context.phase_results)
        context.phase_results[next_phase.value] = result
        context.phase = next_phase
    except Exception as e:
        context.phase = PipelinePhase.FAILED
        context.phase_results["error"] = str(e)

    return context
```

### <a name="dynamic-subagent-selection"></a>Динамический выбор субагента

Вместо жесткого указания того, какой агент какую задачу выполняет, координатор может выбирать субагентов динамически на основе характеристик задачи. Это позволяет одному и тому же координатору обрабатывать новые типы задач без изменения кода.

```python
@dataclass
class AgentCapability:
    name: str
    handles: list[str]  # task type keywords
    cost: float          # relative cost (1.0 = baseline)
    latency: float       # expected seconds

class DynamicSelector:
    def __init__(self, agents: list[AgentCapability]):
        self.agents = agents

    def select(self, task: str, budget_tier: str = "standard") -> str:
        candidates = [
            a for a in self.agents
            if any(keyword in task.lower() for keyword in a.handles)
        ]

        if not candidates:
            return "general"  # fallback agent

        if budget_tier == "economy":
            # Cheapest capable agent
            return min(candidates, key=lambda a: a.cost).name
        elif budget_tier == "performance":
            # Fastest capable agent
            return min(candidates, key=lambda a: a.latency).name
        else:
            # Balanced: cheapest among the fast agents
            fast = [a for a in candidates if a.latency < 10.0]
            pool = fast if fast else candidates
            return min(pool, key=lambda a: a.cost).name
```

### <a name="research-space-partitioning"></a>Разделение исследовательского пространства

Когда несколько агентов исследуют одну и ту же широкую тему, они будут возвращать перекрывающиеся результаты, если координатор явно не разделит пространство поиска. Перекрытие тратит бюджет и усложняет агрегацию.

```python
def partition_research_space(
    topic: str,
    num_agents: int,
    partition_dimensions: list[str]
) -> list[dict]:
    """
    Divide a research topic into non-overlapping partitions.
    Each agent receives a partition with explicit scope boundaries.
    """
    if len(partition_dimensions) >= num_agents:
        dimensions = partition_dimensions[:num_agents]
    else:
        # Create additional partitions if not enough thematic dimensions
        dimensions = partition_dimensions + [
            f"recent_{i}" for i in range(num_agents - len(partition_dimensions))
        ]

    return [
        {
            "agent_id": f"researcher_{i}",
            "topic": topic,
            "scope": dimension,
            "exclusions": [d for j, d in enumerate(dimensions) if j != i],
            "instruction": (
                f"Research '{topic}' focusing exclusively on '{dimension}'. "
                f"Do NOT cover: {', '.join(dimensions[:i] + dimensions[i+1:])}. "
                f"This constraint prevents duplication with parallel researchers."
            )
        }
        for i, dimension in enumerate(dimensions)
    ]

# Example: 3-agent research on "vector database performance"
partitions = partition_research_space(
    topic="vector database performance",
    num_agents=3,
    partition_dimensions=["indexing algorithms", "query optimization", "hardware scaling"]
)
```

### <a name="crash-recovery-manifest"></a>Манифест восстановления после сбоя

Длительно работающие конвейеры агентов (часы, ночные задания) требуют аварийного восстановления. В манифесте фиксируются завершенные работы на границах фаз, чтобы можно было продолжить перезапуск с последней контрольной точки, а не начинать заново.

```python
import json
import os
from dataclasses import dataclass, field, asdict
from datetime import datetime

@dataclass
class PipelineManifest:
    pipeline_id: str
    created_at: str
    task_description: str
    total_items: int
    completed_items: list[str] = field(default_factory=list)
    failed_items: list[dict] = field(default_factory=list)
    phase_checkpoints: dict = field(default_factory=dict)
    status: str = "in_progress"  # "in_progress" | "complete" | "failed"

    def save(self, path: str):
        with open(path, "w") as f:
            json.dump(asdict(self), f, indent=2)

    @classmethod
    def load(cls, path: str) -> "PipelineManifest":
        with open(path) as f:
            data = json.load(f)
        return cls(**data)

    def checkpoint(self, phase: str, result: dict, manifest_path: str):
        self.phase_checkpoints[phase] = {
            "completed_at": datetime.utcnow().isoformat(),
            "result_summary": result.get("summary", "")
        }
        self.save(manifest_path)

    def mark_item_complete(self, item_id: str, manifest_path: str):
        self.completed_items.append(item_id)
        self.save(manifest_path)  # write after every item

class RecoverableOrchestrator:
    def __init__(self, manifest_path: str):
        self.manifest_path = manifest_path

    def run(self, pipeline_id: str, items: list[str], processor) -> PipelineManifest:
        # Load or create manifest
        if os.path.exists(self.manifest_path):
            manifest = PipelineManifest.load(self.manifest_path)
            print(f"Resuming: {len(manifest.completed_items)}/{manifest.total_items} done")
        else:
            manifest = PipelineManifest(
                pipeline_id=pipeline_id,
                created_at=datetime.utcnow().isoformat(),
                task_description=f"Processing {len(items)} items",
                total_items=len(items)
            )

        for item_id in items:
            if item_id in manifest.completed_items:
                continue  # skip completed items

            try:
                processor(item_id)
                manifest.mark_item_complete(item_id, self.manifest_path)
            except Exception as e:
                manifest.failed_items.append({"id": item_id, "error": str(e)})
                manifest.save(self.manifest_path)

        manifest.status = "complete" if not manifest.failed_items else "partial"
        manifest.save(self.manifest_path)
        return manifest
```

Контрольная точка на границах фаз, а не только при завершении задачи. Для трехэтапного конвейера (прием, анализ, отчет) сбой в середине анализа должен возобновляться с начала анализа, а не с начала приема.

### <a name="iterative-refinement-loop"></a>Итеративный цикл уточнения

Некоторые задачи требуют нескольких проходов для достижения приемлемого качества. Итерацией управляет координатор, а не субагент. Такое разделение означает, что субагент остается без сохранения состояния, а координатор управляет критериями остановки.

```python
@dataclass
class RefinementState:
    iteration: int
    current_output: str
    quality_score: float
    feedback: str | None
    max_iterations: int = 5
    target_quality: float = 0.85

    def should_continue(self) -> bool:
        return (
            self.iteration < self.max_iterations
            and self.quality_score < self.target_quality
        )

def iterative_refine(
    initial_task: str,
    generator_fn,
    evaluator_fn,
    max_iterations: int = 5
) -> RefinementState:
    state = RefinementState(
        iteration=0,
        current_output="",
        quality_score=0.0,
        feedback=None,
        max_iterations=max_iterations
    )

    while True:
        # Generate (or refine based on feedback)
        if state.iteration == 0:
            state.current_output = generator_fn(initial_task)
        else:
            state.current_output = generator_fn(
                f"{initial_task}\n\nPrevious attempt:\n{state.current_output}\n\n"
                f"Feedback to address:\n{state.feedback}"
            )

        # Evaluate — separate pass with fresh context
        evaluation = evaluator_fn(state.current_output, initial_task)
        state.quality_score = evaluation["score"]
        state.feedback = evaluation["feedback"]
        state.iteration += 1

        if not state.should_continue():
            break

    return state
```

Критерии остановки имеют значение. «Продолжайте, пока не станете идеально» — это не критерий остановки. Определите `target_quality` как числовой порог на основе набора проверки, а `max_iterations` — как жесткий бюджет. Без того и другого цикл либо завершается слишком рано, либо выполняется бесконечно.

### <a name="narrow-task-decomposition"></a>Узкая декомпозиция задач

Широкая декомпозиция задачи приводит к появлению субагентов с неясными критериями успеха. Используйте тест SPEC для проверки каждой подзадачи перед отправкой:

Тест **SPEC для подзадач:**
- **S**специфический: описание задачи не оставляет двусмысленности относительно того, что производить.
- **P**программно оцениваемый: успех или неудачу можно проверить без человеческого суждения.
- **E**xplicit область действия: то, что входит и выходит за рамки, указано, а не подразумевается.
- **C**onstrained: задача имеет определенный выходной формат, длину или схему.

Подзадача, которая не прошла тест SPEC, должна быть дополнительно декомпозирована или уточнена перед отправкой.

| Подзадача | СПЕЦ прошел? | Проблема |
|---|---|---|
| «Изучите тему» | Нет | Не конкретный, не поддающийся программной оценке |
| «Найдите 3 рецензируемые статьи по векторному индексированию, опубликованные в 2022–2024 годах» | Да | Конкретный, счетный, ограниченный формат |
| «Анализируйте данные» | Нет | Не конкретно, нет схемы вывода |
| «Извлечь имена поставщиков из счетов-фактур 001–050, вывести в виде массива JSON» | Да | Конкретный, ограниченный схемой, с ограниченной областью действия |
| «Напиши что-нибудь хорошее» | Нет | Нет критериев качества, не поддается оценке |
| «Напишите резюме из 150 слов, указав: проблема, подход, результат» | Да | Количество слов, структура и содержание указаны. |

Когда подзадачу невозможно выразить так, чтобы она прошла тест SPEC, это обычно сигнал о том, что у координатора еще недостаточно информации для декомпозиции этой части работы. Соберите больше контекста, прежде чем продолжать декомпозицию.

### <a name="steering-a-running-agent"></a>Управление работающим агентом

Как только координатор может отправить сообщение рабочему агенту в середине выполнения, возникает соблазн исправить все, что выглядит неоптимально. Этот инстинкт ошибочен, и он требует реального времени.

**Правило: управляйте дрейфующим агентом, а не прогрессирующим агентом.**

Сообщение, доставленное работоспособному агенту, не ускоряет его. Он упреждает работу, принудительно переключает контекст и покупает ответ вместо результата. В одном задокументированном случае рулевой из лучших побуждений отправил бегуна примерно на десять минут отвечать на сообщения, вместо того, чтобы продвигаться вперед по своей задаче. У агента все было хорошо, пока ему не сказали иначе.

Дрифт, напротив, стоит сразу прервать, и он распознается, не читая рассуждений агента. Сигнал всегда поведенческий, видимый снаружи:

| Наблюдаемое поведение | Вердикт | Вмешательство |
|---|---|---|
| Написание сценария за 12 минут, ни разу его не выполняя | Дрифт | Объявить об ошибке, перезапустить чисто. Никаких дебатов, никакого цикла ожидания |
| Цикл, завершающий собственный процесс (например, `grep`, соответствующий его собственному PID) | Дрифт | Перенаправление в одну-две строки: «фиксированные PID, без цикла» |
| 22 секунды потрачено на поиск уже заданного каталога | Дрифт | Повторная отправка с абсолютно рабочим каталогом |
| Выдача буквального `$now` в JSON в результате замены сломанной оболочки | Дрифт | Перепишите шаг на языке с реальной передачей аргументов. |
| Столкновение с препятствием и адаптация самостоятельно (например, переключение на `find -o` после искалеченных снарядом петель `for`) | Прогресс | Не вмешивайтесь |
| Файл состояния продвигается, объем вывода растет, ошибок нет. | Прогресс | Не вмешивайтесь |

Практическим следствием является то, что координатору необходим **неблокируемый канал наблюдения**, а не разговорный. Файл состояния каждого агента, содержащий последний предварительный просмотр выходных данных, количество шагов и код выхода, позволяет координатору действовать без отправки чего-либо. Обмен сообщениями затем резервируется для тех случаев, когда наблюдение требует вмешательства, что не позволяет одноранговому почтовому ящику стать узким местом, которое он должен был устранить.

Полезный порог: следите за файлом состояния и рассматривайте управление только в том случае, если оно не продвигается дольше, чем ожидаемая продолжительность шага задачи. Примерно 30 секунд соответствует работе на уровне оболочки; для этапа сборки или тестирования требуется пропорционально более длинное окно.

### <a name="single-writer-for-shared-plan-files"></a>Single Writer для общих файлов плана

Несколько агентов, редактирующих один план, список задач или файл контрольного списка, являются наиболее распространенным источником скрытого повреждения в настройке группы. Два агента ударяют по одному и тому же предмету и создают дубликат. Один записывает, а другой сохраняет устаревшее чтение и перезаписывает изменения. Пакетная запись прерывается на полпути и оставляет файл структурно нарушенным.

Изолированные контекстные окна здесь не помогут, поскольку конфликт происходит на диске, а не в контексте.

**Правило: только один агент имеет доступ на запись к общему файлу. Каждый другой агент запрашивает запись по шине сообщений.**

Запрашивающий агент создает контент и отправляет его. Агент-владелец выполняет запись. Этот механизм стоит одного сообщения туда и обратно и удаляет весь класс ошибок одновременной записи, поскольку по конструкции никогда не бывает более одного записывающего устройства.

```
memory-curator  --(coms: "strike items 4-9, batch complete")-->  orchestrator
                <--(ack)--                                        writes plan file
```

Документированное приложение: агент `memory-curator` без разрешения на запись создал три записи, а затем попросил своего оркестратора по шине удалить соответствующий пакет из плана оркестрации. Оркестратор выполнил одиночную запись. Никаких дубликатов, никаких конфликтов.

Это соответствует разделению read/write, которое уже используется для следователей. Агент, который читает ненадежные входные данные (производственные журналы, текст сторонних проблем, очищенные страницы), не должен иметь доступ на запись к чему-либо из соображений безопасности внедрения; выполнение запроса на запись через владельца удовлетворяет как требованию параллелизма, так и требованию безопасности с использованием одного и того же механизма.

| Общий артефакт | Предполагаемый владелец |
|---|---|
| План оркестрации/список задач | Руководитель группы или координатор |
| Файл состояния каждого агента | Агент, которого он описывает (один писатель по определению) |
| Документ с общими выводами | Координатор, добавляю сообщение |
| Исходные файлы | Тот, кто владеет рабочим деревом, по одному агенту на каждое рабочее дерево. |

Последний ряд объясняет, почему изоляция рабочего дерева и использование одного писателя дополняют друг друга, а не являются избыточными: рабочие деревья дают каждому агенту собственное дерево исходных кодов, а одиночный писатель покрывает артефакты координации, которые обязательно остаются общими. См. также [Multi-Agent Shared Memory](../core/memory-systems.md#5-multi-agent-shared-memory), чтобы узнать о постоянной стороне той же проблемы.
