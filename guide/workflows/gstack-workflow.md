# Переключение когнитивного режима

> **Источник**: [gstack](https://github.com/garrytan/gstack) Гарри Тана. На этой странице выбраны шесть этапов рабочего процесса из более крупного, развивающегося набора навыков; проверьте репозиторий на наличие текущего списка команд.

**Время чтения**: ~10 мин.
**Предварительные требования**: основы навыков Claude Code, режим планирования
**Связанные**: [Plan Pipeline](./plan-pipeline.md), [Plan-Driven Development](./plan-driven.md)

---

## <a name="tldr"></a>ТЛ;ДР

Агент кодирования может смазывать решения по продукту, его реализацию, проверку и выпуск. Этот выбранный путь gstack дает каждому шагу отдельный вопрос, при этом пользователь выбирает, когда дополнительный шаг оправдает себя.

```
/plan-ceo-review  → "Are we building the right thing?"
/plan-eng-review  → "How do we make this buildable?"
/review           → "What can still break?"
/qa               → Test the changed behavior
/ship             → Complete the Git and PR workflow
/retro            → What should change next time?
```

Планирование, анализ и реализация требуют принципиально разных когнитивных позиций. Единственный помощник, оставленный в обычном режиме, плохо их смешивает.

---

## <a name="six-selected-gates"></a>Шесть избранных ворот

| Команда | Роль | Основной вопрос | Когда переключаться |
|---------|------|---------------|----------------|
| `/plan-ceo-review` | Основатель/генеральный директор | «Правильно ли мы строим?» | Когда направление продукта неясно |
| `/plan-eng-review` | Инженер-менеджер / технический руководитель | «Как нам сделать это строительным?» | После блокировки направления |
| `/review` | Штатный инженер-параноик | "Что еще может сломаться в проде?" | Перед слиянием |
| `/qa` | инженер по контролю качества | «Работает ли измененное поведение?» | До принятия решения о выпуске, против безопасной цели |
| `/ship` | Инженер по выпуску | «Готова ли ветка к публикации?» | После проверки и применимого контроля качества |
| `/retro` | Инженерный менеджер | «Насколько хорошо мы отправили товар?» | Еженедельно или после запуска |

## <a name="the-gap-this-fills-pre-implementation-strategic-gate"></a>Пробел, который это заполняет: стратегические ворота до реализации

Самое сложное в работе с помощником по программированию на основе искусственного интеллекта — это не реализация. Прежде всего возникает вопрос: **Правильно ли мы строим?**

Claude Code оптимизирован для создания того, что вы просите. Если вы скажете «добавить загрузку фотографий», фотография будет добавлена. Он не будет спрашивать, действительно ли загрузка фотографий является продуктом. Эту проблему решает `/plan-ceo-review`.

**Example**: Вы создаете листинговое приложение в стиле Craigslist.

- Пожелание: «Разрешить продавцам загружать фото своего товара»
- Буквальная реализация: выбор файла + сохранение изображения.
- Что такое настоящий продукт: помощь продавцам в создании объявлений, которые действительно продают

Если вы сначала запустите `/plan-ceo-review`, помощнику будет явно предложено оспорить буквальный запрос и найти спрятанный внутри него продукт. Результат становится совершенно другим заданием: автоматически идентифицировать продукт по фотографии, получить характеристики и ценовые предложения, набросать название и описание, предложить главное изображение, обнаружить фотографии низкого качества, прежде чем они будут опубликованы.

Это другое, более масштабное предложение. Ему нужны доказательства того, что продавцы этого хотят и что дополнительную работу стоит проделать, прежде чем она заменит более узкий запрос.

**Режимы внутри `/plan-ceo-review`** включают расширение, выборочное расширение, удержание объема и сокращение. Это альтернативные способы оспорить предложение, а не правило, позволяющее расширить сферу применения. Выберите вариант в соответствии с потребностями пользователя и стоимостью уже выполняемой работы.

Пользователь выбирает режим. Ассистент предан этому и не дрейфует.

## /plan-eng-review: Воплощение идеи в жизнь

Как только направление зафиксировано, когнитивный режим переключается с интуитивного понимания продукта на инженерную строгость. `/plan-eng-review` — это место, где заканчивается мышление и начинается архитектура.

Что он должен производить:
- Схема архитектуры (компоненты, границы, поток данных)
- Конечный автомат для основного потока
- Решения о границах синхронизации и асинхронности
- Режимы сбоя и логика повторных попыток
- Границы доверия (где вы принимаете внешние данные?)
- Тестовая матрица

Ключ разблокировки — **, принудительная генерация диаграммы**. Диаграммы обнажают скрытые предположения, которые скрывает проза. Диаграмма последовательности позволяет указать, кто и что вызывает. Конечный автомат заставляет вас перечислять каждый режим отказа. Без них фраза «система справится» остается неопределенной на неопределенный срок.

## /review: режим штатного инженера-параноика.

Прохождение тестов не означает, что филиал безопасен. `/review` существует для класса ошибок, которые выживают при CI и в любом случае попадают в производство.

Что он проверяет:
- N+1 запросов
- Условия гонки (две вкладки перезаписывают одно и то же состояние)
- Нарушения границ доверия (принятие метаданных, предоставленных клиентом, без проверки)
- Потерянные данные о путях отказа
- Отсутствующие индексы
- Неверная логика повтора
- Тесты, которые проходят без реального режима отказа
- Оперативное внедрение, когда выходные данные LLM передаются в дальнейшую обработку.

Поза продумана: представьте себе производственный инцидент до того, как он произойдет.

## <a name="browser-qa-qa-and-browse"></a>Контроль качества браузера: `/qa` и `/browse`.

Текущий gstack отделяет драйвер браузера от рабочего процесса контроля качества. [`/browse`](https://github.com/garrytan/gstack/blob/main/docs/skills.md) открывает страницы и проверяет взаимодействие; `/qa` выбирает глубину тестирования, записывает доказательства и может воспроизвести дефект перед его исправлением. Его путь в браузере использует Aside, если он доступен, а в противном случае — собственный браузер gstack. Эта страница не претендует на преимущество в скорости по сравнению с другим инструментом браузера.

Вопрос бережливого производства заключается в том, выявляет ли эта проверка дефекты до того, как они перейдут дальше по потоку, не увеличивая при этом очередь непроверенных отчетов. Проходящая проверка браузера охватывает только осуществляемое поведение, а не все результаты пользователя.

## <a name="full-cycle-demo"></a>Демо полного цикла

Это иллюстративная последовательность, а не измеренный результат gstack.

```
# 1. Strategic gate — challenge the brief
[plan mode]
You: I want to add seller photo upload to the listing app.
     Sellers should be able to upload a photo and we create the listing from it.

You: /plan-ceo-review   (select SCOPE EXPANSION mode)

Claude: "Photo upload" is not the feature. The real job is helping sellers
        create listings that actually sell. Here's the 10-star version:
        auto-identify the product, pull specs and pricing comps from the web,
        draft title and description, suggest the best hero image...

# 2. Engineering gate — lock the architecture
You: /plan-eng-review

Claude: [Architecture diagram, async job boundaries, state machine for
        upload → classify → enrich → draft pipeline, failure modes,
        trust boundaries, test matrix]

# 3. Implement the plan
[exit plan mode, write code]

# 4. Paranoid review — find what tests missed
You: /review

Claude: Race condition: two tabs can overwrite cover-photo selection.
        Trust boundary: pulling web data into draft generation creates
        a prompt injection vector.
        Missing: orphan cleanup for failed uploads.

You: [fix the issues]

# 5. QA against a safe local or staging target
You: /qa staging.myapp.com

Claude: [Exercises the listing flow, records the cases tried and any failures]
        The tested listing path passes; other user outcomes remain unmeasured.

# 6. Ship after the release decision
You: /ship

Claude: [Runs release checks, then commits, pushes and opens a PR when authorized]
```

## <a name="when-to-use-this-vs-other-workflows"></a>Когда использовать этот и другие рабочие процессы

| Ситуация | Этот рабочий процесс | Альтернатива |
|-----------|---------------|-------------|
| Сложный объект, направление неопределенное | `/plan-ceo-review` первый | [Spec-First](./spec-first.md) |
| Направление четкое, архитектурный комплекс | `/plan-eng-review` | [План трубопровода](./plan-pipeline.md) |
| Требуется независимая проверка плана | [План трубопровода](./plan-pipeline.md) `/plan-validate` | — |
| Разовая проверка браузера | `/browse` или доступный инструмент браузера | Отсутствие результата контроля качества без явной проверки |
| Проверка измененного потока | `/qa` | Записывайте проверенный путь, сбои и непроверенное поведение. |
| Хотите структурированный цикл обучения ADR | [План трубопровода](./plan-pipeline.md) | — |

На этой странице представлена ​​выбранная последовательность, которую вы можете вызвать намеренно; более широкий пакет gstack также включает в себя автоматизированные пути. [Plan Pipeline](./plan-pipeline.md) — это отдельный подход к оркестровке. Сравните оба варианта с фактическим временем ожидания и доработок в вашем потоке доставки, а не предполагайте, что чем больше этапов, тем лучше.
