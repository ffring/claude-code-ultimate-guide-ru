# Межсессионный обмен сообщениями

Межсессионный обмен сообщениями позволяет одному сеансу Claude Code доставлять короткое текстовое сообщение другому, независимо запущенному сеансу Claude Code, без копирования между терминалами. Всю эту функцию выполняют два инструмента: `ListAgents` определяет, какие сеансы доступны, `SendMessage` доставляет текст одному из них по имени. Ни один из инструментов не является тем, что вы называете собой; Claude решает, когда их использовать: сам по себе или по вашему запросу.

**Официальная документация**: [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging)

> **См. также**: [Справочник по инструментам](../core/tools-reference.md#cross-session-messaging-listagents--sendmessage) для записи в таблице инструментов, [Agent Teams](./agent-teams.md) для связанного, но отдельного механизма почтового ящика товарища по команде, [Усиление безопасности: межсессионный обмен сообщениями](../security/security-hardening.md#cross-session-messaging-threat-model) для модели угроз канала, [Native Песочница: межсеансовые сокеты входящих сообщений](../security/sandbox-native.md#cross-session-inbox-sockets) для сдерживания процессов Bash и исключений сокетов Unix, а также [Agent Harness: Creator-Verifier](../core/agent-harness.md#8-creator-verifier-pattern) для проверки и контроля независимости рецензента.

## 1. Что он решает, а что нет

Формулировка Anthropic: «Когда изменение в одном сеансе нарушает то, на чем строится другой, Claude может предупредить этот сеанс прежде, чем вы это заметите. Когда один сеанс решает вопрос, который заблокирован другим, Claude может отправить ответ». Сообщение определяется узко: фрагмент текста, который один Claude записывает другому, а не историю разговоров и никогда файлы. Перемещение всего разговора или его контекста — это другая функция, [возобновление сеанса](../ultimate-guide.md#916-session-teleportation).

Claude Code имеет специальную функцию для каждого способа запуска или подключения нескольких сеансов, а межсессионный обмен сообщениями подходит только для одного из них:

| Вы хотите... | Используйте это вместо этого |
|---|---|
| Продолжите один разговор в другом терминале или поделитесь его контекстом в новом сеансе. | [Возобновить сеанс](../ultimate-guide.md#916-session-teleportation) |
| Слаженная команда сессий Claude порождает и контролирует себя. | [Команды агентов](./agent-teams.md) |
| Смотрите и управляйте множеством сессий из одного места | Просмотр агента (фоновые сеансы) |
| Управляйте сеансом самостоятельно со своего телефона или другого устройства. | [Пульт дистанционного управления](../ultimate-guide.md#922-remote-control-mobile-access) |
| Перенос внешних событий (результатов CI, сообщений чата) в сеанс. | [Каналы](./monitor-event-delegation.md#plugin-monitors-and-channels) |
| **Сообщение между независимыми сеансами, которые вы начинаете и управляете самостоятельно** | **Межсессионный обмен сообщениями** |

В этой последней строке описана остальная часть этой страницы: сеансы без связи друг с другом, каждый из которых открыт в своем терминале, каждый со своим собственным контекстным окном, разрешениями и рабочим каталогом.

## <a name="2-discovery-listagents"></a>2. Открытие: `ListAgents`

Запустите `/list-agents` (псевдоним `/peers`) в любом сеансе, чтобы увидеть, чего может достичь Claude. Первая строка — это собственное имя сеанса (которое партнеры используют для обращения к нему); в строках ниже перечислены все доступные агенты, сгруппированные по типу:

- **Subagents**: агенты, работающие внутри текущего сеанса.
- **Соратники по команде**: собственные товарищи по команде [агента этой сессии](./agent-teams.md). До версии 2.1.239 они не появлялись в списке, хотя `SendMessage` уже мог связаться с ними по имени.
- **Другие локальные сеансы**: сеансы Claude Code, работающие на том же компьютере, включая фоновые сеансы. Сеанс появляется только после привязки сокета «Входящие» (см. §5); бездействующий рабочий процесс, который супервизор фонового сеанса поддерживает в готовности, появляется только после того, как вы отправляете ему работу.
- **Ваши облачные сеансы**: ваш Claude Code в веб-сеансах, отображаемый, когда текущий сеанс подключен к удаленному управлению. Маркируется `cloud`.
- **Ваши сеансы удаленного управления на других машинах**: отображаются в тех же условиях, с пометкой `Remote Control`. Сеанс, соединение с удаленным управлением которого было разорвано, отображается как `offline`.

Текущий сеанс никогда не является строкой в ​​собственном списке. Если Claude адресует сообщение своему собственному имени, Claude Code отклоняет его и сообщает об этом Claude, вместо поведения до версии 2.1.239, сообщающего «нет агента по имени…».

Сеанс отвечает на имя, установленное через `/rename` или `--name`, или в противном случае автоматически сгенерированное. Когда переименование или новый сеанс конфликтует с уже используемым именем, Claude Code сохраняет имя в сеансе, в котором оно уже есть, и назначает вариант новому. Таким образом, два сеанса могут законно иметь одно и то же имя (более старая версия Claude Code или автоматически сгенерированная коллизия); `/list-agents` показывает рабочий каталог каждого локального сеанса, чтобы вы могли отличить их друг от друга, а когда несколько живых сеансов имеют одно и то же имя, Claude перед отправкой спрашивает вас, какой из них вы имеете в виду.

Claude Code сначала считывает список сеансов облака и удаленного управления и останавливается после ограниченного количества страниц. Сеанс, выходящий за рамки этого окна, не отображается в списке и не может быть отправлен по имени; Claude Code так говорит, и Claude видит ту же заметку, когда пытается.

## <a name="3-delivery-sendmessage"></a>3. Доставка: `SendMessage`

Вы можете оставить формулировку сообщения Claude:

```text
Ask the session running in my other terminal whether the migration finished
```

```text
Explain what we just did to the session working on the payments API
```

Или назовите цель самостоятельно, упомянув `@`, тот же механизм, который используется для [, явно адресующего субагенту](../core/tools-reference.md#agent). Введите `@`, затем первые буквы имени сеанса и выберите его из списка (требуется версия 2.1.232+):

```text
Let @api-worker know the schema migration finished
```

Пустой `@` не показывает строк сеанса; введите хотя бы еще одну букву, чтобы вызвать предложения. Сеанс облака или удаленного управления появляется в начале текста только после того, как Claude уже перечислил или отправил сообщения о ваших сеансах за пределами текущего компьютера.

### Что видит принимающий сеанс

Начиная с версии 2.1.247, сообщение появляется в разговоре получателя в виде тусклого однострочного предварительного просмотра под именем сеанса отправителя. Нажмите `Ctrl+O`, чтобы прочитать полный текст в программе просмотра стенограммы; сеанс, начатый с `--verbose`, сразу показывает его полностью. Предварительный просмотр остается в разговоре:

```text
Schema migration finished: the new column is tenant_id, and rebasing on main is safe now.
```

Claude читает полное сообщение независимо от того, разворачиваете ли вы предварительный просмотр или нет. Сеанс-получатель получает имя отправителя и, за исключением случая одностороннего взаимодействия между компьютерами (§4), адрес ответа; он никогда не получает историю разговоров или файлы отправителя. После доставки сообщение засчитывается в счет использования, как введенное вами приглашение.

### Тайминг

Принимающий Claude считывает сообщение между вызовами инструмента во время активного поворота, поэтому работающий инструмент никогда не прерывается. Когда получатель бездействует, Claude Code сразу же начинает новый ход с сообщением.

### Когда в отправке категорически отказано

Claude Code отказывается отправлять сообщение до того, как оно покинет отправителя, в четырех случаях:

1. Размер сообщения превышает ограничение (§7).
2. Быстрый всплеск сеанса на том же компьютере уже достиг того, что принимает почтовый ящик этого сеанса.
3. Цель ответа на этом компьютере не прошла проверку безопасности: путь к символическому сокету или подключенная конечная точка, которая не является ожидаемым процессом. См. [Отказ от отправки межсессионного сообщения](https://code.claude.com/docs/en/errors#refusing-to-send-a-cross-session-message).
4. Claude адресует сообщение на имя отправляющего сеанса.

## <a name="4-same-machine-vs-cross-machine-delivery"></a>4. Доставка на одной машине или на нескольких машинах

Затронет ли сообщение когда-либо инфраструктуру Anthropic, полностью зависит от того, где работает целевой сеанс:

| Где выполняется другой сеанс | Как распространяется сообщение |
|---|---|
| На этой машине | Через доменный сокет Unix для каждого сеанса (macOS/Linux/WSL2) или именованный канал (родной Windows). Никогда через серверы Anthropic. |
| На другой вашей машине | Через серверы Anthropic, поступающие через соединение дистанционного управления этой машины. |
| На Claude Code в сети | Через серверы Anthropic прямо в облачную сессию. |

Доставка на одну машину полностью локальна: каждый сеанс регистрируется в файлах на диске, и `ListAgents`/`SendMessage` читает эти файлы. Два сеанса могут связаться друг с другом только тогда, когда они могут видеть одни и те же файлы регистрации, поэтому контейнер и его хост не могут обмениваться сообщениями (разные файловые системы), а также почему сеанс WSL2 и собственный сеанс Windows на одном и том же компьютере тоже не могут (разные домашние каталоги, разные типы сокетов).

Для начала разговора с сеансом на другом из ваших компьютеров требуется версия 2.1.225 или новее, и цель уже должна появиться в списке. До версии 2.1.225 сеанс мог только ответить на поступившее сообщение, но никогда не открыть его.

Пока сеанс отправки подключен к Remote Control, сообщение для другого вашего компьютера отображается под именем Remote Control отправителя, и получатель может ответить на это имя. Если отправитель не подключен к Remote Control, когда он отправляет сообщение за пределы текущего компьютера, сообщение все равно проходит, но не содержит адреса ответа: принимающий Claude видит его, но не может ответить, и отправителю сообщают об этом.

Чтобы требовать вашего явного одобрения, прежде чем какое-либо сообщение вообще покинет машину, установите `isolatePeerMachines: true` (§6).

## <a name="5-the-sessions-inbox-socket"></a>5. Сокет входящих сообщений сеанса.

Актуально, когда ожидаемый сеанс отсутствует в листинге, когда перехватчик или сценарий необходимо отправить сообщение в сеанс или когда изолированная команда не может достичь сокета.

Claude Code привязывает сокет папки «Входящие» для каждого сеанса с включенным обменом сообщениями: сокет домена Unix на macOS/Linux/WSL2, именованный канал на собственном Windows. Его путь отображается в строке `Peer address` файла `/status` (с префиксом `uds:`) и экспортируется в хуки и команды Bash как `CLAUDE_CODE_MESSAGING_SOCKET`. Вместе с ним экспортируется `CLAUDE_CODE_MESSAGING_TOKEN` для каждого сеанса; сценарий, отправляющий сообщение в сокет своего сеанса, может отправить `{"type":"auth","token":"<token>"}` в качестве первой строки соединения. Для родного Windows эта строка требуется; macOS/Linux/WSL2 принимает соединение с ним или без него.

Сокет доступен только пользователю операционной системы на macOS/Linux; на Windows каждое соединение должно аутентифицироваться с помощью ключа, который может прочитать только пользователь. В любом случае сеанс, запущенный как один пользователь ОС, не может подключиться к сеансу, запущенному как другой, даже на том же компьютере, даже на том же сервере tmux.

Сеансы `claude -p` привязывают входящие сообщения подобно интерактивным. Сеансы, запущенные в режиме [bare](../ultimate-guide.md#headless-mode), не привязывают сокет и никогда не отображаются в списке агентов.

`ListAgents` и `SendMessage` работают в самом Claude Code, за пределами песочницы Bash. Поэтому нормальная доставка между сеансами не требует исключений сокетов Unix. Исключение имеет значение только тогда, когда изолированная команда Bash подключается напрямую к `CLAUDE_CODE_MESSAGING_SOCKET`. В macOS [`sandbox.network.allowUnixSockets`](../core/settings-reference.md#sandboxnetworkallowunixsockets) может определять область действия исключения по пути к сокету. В Linux и WSL2 список разрешенных сокетов для конкретного пути недоступен; [`sandbox.network.allowAllUnixSockets: true`](../core/settings-reference.md#sandboxnetworkallowallunixsockets) удаляет фильтр сокетов Unix для каждого сокета, к которому может добраться команда. Предпочитайте встроенный инструмент `SendMessage` и не расширяйте доступ к сокетам Unix только для того, чтобы обеспечить нормальный обмен сообщениями между сеансами. [Встроенная песочница: межсессионные сокеты входящих сообщений.](../security/sandbox-native.md#cross-session-inbox-sockets) учитывает компромисс, зависящий от платформы.

## <a name="6-security-model"></a>6. Модель безопасности

В конструкции Anthropic три свойства находятся в противоречии: сеансы свободно координируются, но ни один из них не может контролировать другой, а разрешения никогда не передаются вместе с сообщением.

### Чего не может входящее сообщение

Когда сеанс A отправляет сообщение сеансу B, Claude Code явно сообщает Claude B, что текст пришел из другого сеанса, а не от пользователя, и соответствующим образом ограничивает его:

- **Он ничего не может одобрить.** Сообщение от партнера никогда не считается вашим согласием; он не может ответить на ожидающий запрос разрешения от вашего имени.
- **Он не может изменить конфигурацию.** Принимающий Claude получает указание никогда не изменять настройки разрешений, `CLAUDE.md` или любую другую конфигурацию, потому что другой сеанс запросил.
- **Команды не запускаются.** Команда, встроенная в текст сообщения, например `/compact`, поступает в виде обычного текста. Claude Code никогда не выполняет его.
- **Запросы разрешений по-прежнему активируются.** Если для действия над сообщением требуется разрешение, которого нет у принимающего сеанса, пользователь увидит тот же запрос, что и для любого другого запроса.

Claude также получает указание на отправляющей стороне никогда не запрашивать у другого сеанса действие, которое его собственный сеанс уже отклонил, заблокировал или заблокировал бы в соответствии с его собственными правилами разрешений; вместо этого рабочие маршруты возвращаются к пользователю.

### Контроль поступления: `crossSessionInbound`

Каждый сеанс решает, что делать с входящими сообщениями одноранговых узлов, с помощью настройки `crossSessionInbound`:

| Ценить | Поведение |
|---|---|
| `accept` | Claude Code доставляет каждое сообщение Claude. |
| `hold` | Claude Code хранит сообщения, не доставляя их. Более поздний `accept` освобождает их; явный `hold` не создает диалоговое окно утверждения для каждого сообщения и не истекает через `dialogExpiry`. |
| `refuse` | Claude Code удаляет каждое сообщение, не доставляя его. |

Редактируется через `/config` → **Сообщения из других ваших сеансов** (v2.1.232+; скрыто, если управляемые настройки или `--settings` уже установили ключ). Когда ни одно значение не применяется ни в одной области настроек, Claude Code принимает решение для каждого сообщения из класса режима разрешений обоих сеансов: сеансы, которые обходят запросы разрешений, образуют один класс, каждый второй сеанс (включая режим планирования, где доступен обход, а также `auto`/`acceptEdits`/`dontAsk`, которые считаются запросами) формируют другой. Получатель запроса доставляет сообщение по умолчанию и удерживает только сообщение от обходящего отправителя; обходной получатель сохраняется по умолчанию и доставляет только от другого обходного отправителя.

При этом удержании по умолчанию открывается диалоговое окно для каждого сообщения. **Approve** доставляет это сообщение; **Deny** или отклонение удаляет его. Диалоги без ответа обычно истекают после `dialogExpiry` (по умолчанию 5 минут). Такое диалоговое поведение относится к режиму разрешений по умолчанию, а не к явной настройке `crossSessionInbound: "hold"`.

Claude Code хранит не более 100 сообщений отдельно от очереди доставки, удаляя самые старые сообщения после этого.

### Дальнейшая блокировка

`isolatePeerMachines: true` требует вашего явного согласия до того, как какой-либо `SendMessage` достигнет сеанса за пределами текущей машины, даже в режиме `bypassPermissions`. Он никогда не запрашивает отправку на ту же машину. Применяется `true`, установленный в любом месте (включая зарегистрированный файл проекта); нет возможности переопределить его обратно на `false` из более слабой области видимости.

Чтобы полностью отключить направление: `crossSessionInbound: "refuse"` прекращает прием, а правило запрета разрешений, именующее `SendMessage` и `ListAgents` (голые имена инструментов, без спецификатора), прекращает отправку и вывод списка. Отказ от `SendMessage` также приводит к прекращению обмена сообщениями с субагентами и товарищами по команде агентов, поскольку они используют этот инструмент совместно. Блокировка на уровне всей организации в управляемых настройках сочетает в себе оба следующих фактора:

```json
{
  "permissions": {
    "deny": ["SendMessage", "ListAgents"]
  },
  "crossSessionInbound": "refuse"
}
```

При этом сеанс по-прежнему связывает свой сокет входящих сообщений, но удаляет все, что на него поступает. Ничто в `/status` или в `/list-agents` узла не указывает на то, что сеанс заблокирован таким образом; подтвердите это, прочитав применимые настройки, а не наблюдая за поведением.

### Проверки спуфинга конечных точек

Перед доставкой на тот же компьютер, `SendMessage` проверяет, является ли конечная точка тем, чем она себя называет, и отказывает, а не отправляет, если это не так: цель ответа с символической ссылкой, конечная точка, которая подключается, но не является ожидаемым процессом, или конечная точка, личность которой не может быть прочитана, - все они выдают отказ вместо тихой отправки в неправильное место. См. [Отказ от отправки межсессионного сообщения](https://code.claude.com/docs/en/errors#refusing-to-send-a-cross-session-message).

### <a name="where-native-sandboxing-fits"></a>Где подходит нативная песочница

Доставленное одноранговое сообщение может повлиять на то, что принимающий Claude попытается сделать дальше. Четыре границы охватывают различные виды отказов; ни одно не заменяет другое:

| Граница | Что он контролирует | Что не установлено |
|---|---|---|
| `crossSessionInbound`, `isolatePeerMachines` и разрешения для инструментов | Какие сообщения приходят, покидают ли они машину без одобрения и какие инструменты может использовать получатель. | Что предъявленная претензия является правильной или актуальной |
| [Встроенная песочница](../security/sandbox-native.md#cross-session-inbox-sockets) | Файловая система и сетевые эффекты команд Bash и их дочерних процессов | Безопасность встроенных вызовов `Read`, `Edit` или `Write`; корректность сообщения; независимость от сеанса |
| Одно рабочее дерево на одну параллельную запись | Разделение рабочих файлов и индексов при параллельных изменениях | Сдерживание хоста, учетных данных, сети или процесса |
| [Жгут проводов и вентили CI](../core/agent-harness.md#8-creator-verifier-pattern) | Воспроизводимые проверки текущего коммита и независимая проверка на соответствие требованиям. | Политика сдерживания или разрешений на уровне ОС |

Собственная «песочница» ограничивает часть радиуса атаки, если получатель действует в соответствии с вредоносным или неправильным сообщением. Это не предотвращает коррелированный дрейф и не превращает два сеанса, использующих одну кассу, в изолированных рабочих процессов.

### <a name="coordination-safety-correlated-drift-and-false-consensus"></a>Координационная безопасность: коррелированный дрейф и ложный консенсус

Приведенные выше элементы управления отвечают на вопрос, кто может отправлять, куда передается сообщение и какие полномочия оно имеет. Они не устанавливают, что сообщение является правильным, актуальным или находится в пределах предполагаемой области действия пользователя. Равноправное сообщение может быть безопасно доставлено и при этом распространять ложную предпосылку.

Больше общения не обязательно приводит к большему количеству ошибок. Своевременное сообщение может выявить конфликт до того, как какой-либо сеанс отредактирует затронутый код. Риск возрастает, когда получатели повторно используют заключение партнера, не проверяя его, поскольку ошибка одного сеанса становится общим контекстом, и независимые сеансы начинают давать сбои в одном и том же направлении.

| Сбой координации | Пример | Контроль |
|---|---|---|
| **Распространение ложных посылок** | Один сеанс сообщает, что миграция завершена после проверки устаревшего состояния; другой сеанс рассматривает этот отчет как факт хранилища. | Отправьте заявку с ветвью или рабочим деревом, зафиксируйте SHA, выполните команды, соответствующие выходные данные и оставшуюся неопределенность. Получатель перепроверяет состояние, от которого оно зависит. |
| **Незаконченная передача** | Сообщение было верным при одном коммите, но другое изменение произошло до того, как получатель отреагировал на него. | Привяжите передачу к SHA фиксации и сравните ее с текущим `HEAD` получателя перед редактированием или утверждением. |
| **Ложный консенсус** | Рецензент получает рассуждения автора, наследует их формулировку и подтверждает ту же ошибку. | Предоставьте независимому проверяющему исходные требования, артефакты и доказательства без объяснения причин создателя. Добавляйте другие инструменты, доказательства во время выполнения или другие model/provider, когда риск оправдывает затраты. |
| **Раса общего рабочего дерева** | Два сеанса согласовывают владение файлом в чате, но при этом одновременно читают и записывают одну и ту же проверку. | Используйте одно рабочее дерево для каждого параллельного сеанса и явно записывайте право собственности. `SendMessage` не блокирует файлы, не сериализует записи и не предотвращает аннулирование одним сеансом чтения другого сеанса. |
| **Зеленый, но неверный результат** | Оба сеанса соответствуют тестам, но при этом отсутствуют неустановленные требования к продукту или свойства безопасности. | Запустите детерминистические вентили для текущего SHA, а затем проверьте каждое требование на предмет наличия доказательств. Сохраняйте человеческий или политический контроль над двусмысленными, необратимыми или высокоэффективными решениями. |
| **Отмывание масштабов** | Одноранговый узел запрашивает действие, которое его собственный пользователь не санкционировал, но которое подпадает под существующие разрешения инструмента получателя. | Получатель проверяет запрос на соответствие своим пользовательским инструкциям и области действия. Используйте `hold` или `refuse` для конфиденциальных сеансов; Наличие разрешения не является авторизацией задачи. |

Относитесь к каждому сообщению коллег как к утверждению, имеющему происхождение, а не как к доказательству. Компактная передача обслуживания может использовать этот контракт:

```text
Target: @api-worker
Scope: review only; do not edit
Repository state: branch feature/tenant-migration, commit 4f2c1ab
Claim: the tenant_id migration is complete
Evidence: migration test and schema validation passed at that commit
Uncertainty: rollback was not tested
Requested action: verify compatibility against your current HEAD
```

Используйте модель угроз [Security Hardening](../security/security-hardening.md#cross-session-messaging-threat-model) для контроля отправителей, транспорта, входящей политики и границ выполнения. В руководстве [Agent Harness](../core/agent-harness.md#8-creator-verifier-pattern) рассматриваются пакеты независимости верификатора и проверки. Руководство по оценке агентов [](../roles/agent-evaluation.md#evaluate-judgment-allocation-and-reviewer-independence) объясняет, как измерять ложные принятия, ложные отклонения, устраненные сбои и разногласия, вместо того, чтобы предполагать, что второй агент независим.

## <a name="7-limitations"></a>7. Ограничения

Это свойства самого канала, не зависящие от платформы или провайдера (в §8 они рассматриваются отдельно):

- **Только обычный текст.** Структурированные сообщения протокола агент-группа остаются внутри команды; межсеансовые сообщения содержат только текст.
- **Ограничение размера одной и той же машины составляет около 1 048 576 символов.** При этом `SendMessage` отклоняет отправку перед ее отправкой; ничего не доходит до получателя. Поместите большой объем содержимого в файл и вместо этого отправьте его путь, суммируйте или разделите на несколько сообщений.
- **Быстрые пакеты в один сеанс отклоняются отправителем.** Как только пакет в сеанс на том же компьютере достигает того, что принимает почтовый ящик этого сеанса, дальнейшие отправки отклоняются в сеансе отправки, которому приказано объединить то, что осталось, в одно сообщение или подождать. До версии 2.1.236 пакет, превышающий это значение, считался отправленным, в то время как принимающий сеанс молча отбрасывал его.
- Циклы сообщений **ограничиваются получателем.** Claude Code ограничивает скорость повторения сообщений для каждого отправителя, удаляет идентичные повторы, поступающие в коротком окне, и ставит в очередь не более 50 принятых сообщений для чтения Claude, что само по себе останавливает цикл сообщений между двумя сеансами.

## 9. Получайте уведомление, когда другой сеанс простаивает (v2.1.236+)

Вместо опроса попросите Claude подписаться на одно уведомление из сеанса на том же компьютере:

```text
Tell me when the migration session finishes what it's working on
```

Claude подписывается через `SendMessage`'s `notify_when_idle` ввод, либо прикрепленный к сообщению, которое оно уже отправляет, либо сам по себе (который ничего не стоит в отслеживаемом сеансе и срабатывает немедленно, если этот сеанс уже бездействует). Уведомление является одноразовым, и ни один из сеансов не опрашивает другой; если ничего не поступает в течение 12 часов, подписка прекращается и Claude говорят, поэтому он перестает ждать. Подписаться может только основной разговор и только на сеансы на текущем компьютере; субагент, товарищ по команде или сеанс за пределами текущего компьютера, который пытается получить полный отказ, включая сообщение.

## 11. Практические выкройки

**Передайте результат.** Сеанс, который обнаруживает критическое изменение или принимает решение, Claude обобщает его для сеанса, работающего над затронутой областью, вместо того, чтобы человек заново объяснял его там.

**Координация параллельных рабочих деревьев.** Сеансы, работающие с одним и тем же репозиторием в отдельных [worktrees](../ultimate-guide.md#912-git-best-practices--workflows), получают информацию о том, что попало в родственное рабочее дерево, без передачи человеком.

**Не координируйте общее рабочее дерево через чат.** Сообщение о принадлежности файла не является блокировкой. Поместите каждую параллельную запись в отдельное рабочее дерево, а затем интегрируйте посредством коммитов, различий и обычных шлюзов репозитория.

**Разделение труда между ролями.** Один сеанс по миграции баз данных, один по серверной части, один по внешнему интерфейсу, один по документации, каждый из которых работает на своем собственном терминале. Когда миграция завершается, этот сеанс отправляет сообщение серверному сеансу, чтобы он мог продолжить работу без опроса; когда сеанс документации решает вопрос, блокирующий интерфейс, ответ пересекается таким же образом.

**Продолжение на разных устройствах.** Длительная сборка, выполняемая на настольном терминале, отправляет сводную информацию о сеансе документации, доступном с телефона через удаленное управление, после завершения сборки.

Ни для одного из них не требуется `TeamCreate`. Вместо этого используйте [Agent Teams](./agent-teams.md), если вы хотите, чтобы ведущий сеанс сам порождал и контролировал товарищей по команде со структурированным назначением задач; используйте межсессионный обмен сообщениями, когда сеансы уже существуют независимо, и вы просто исключаете человека из ретранслятора.

О схеме координации, лежащей в основе этого выбора, см. [Mediator в шаблонах проектирования AI.](../core/ai-design-patterns.md#mediator): обмен сообщениями между узлами является неопосредованной альтернативой сеансу координации.
