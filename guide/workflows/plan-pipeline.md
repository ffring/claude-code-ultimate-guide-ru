# Конвейер планирования-проверки-выполнения

> **Confidence**: уровень 2, проверенный в боевых условиях производственными группами, поставляющими продукты на базе искусственного интеллекта в больших масштабах. Расширяет собственный режим `/plan` за счет структурированной оркестровки агентов и институциональной памяти.

Полный рабочий процесс разработки, состоящий из трех команд: планирование с помощью динамичной исследовательской группы, проверка с помощью независимых специалистов-рецензентов, выполнение с помощью параллельных агентов. Каждый запуск улучшает следующий за счет цикла обучения ADR, который постепенно сокращает вмешательство человека.

**Время чтения**: ~25 мин.
**Предварительные условия**: субагенты, инструмент задач, рабочие деревья, основные концепции ADR.
**Связанные**: [Плановая разработка](./plan-driven.md), [Команды агентов](./agent-teams.md), [Spec-First](./spec-first.md)

## <a name="tldr"></a>ТЛ;ДР

```
/plan-start    → 5-phase planning: PRD analysis + dynamic research team + ADRs
/plan-validate → 2-layer review: structural checks + trigger-based specialist agents
/plan-execute  → worktree + TDD + parallel execution + PR + merge + cleanup
```

**Чем он отличается от режима `/plan`**:
- Исследования проводятся специализированными агентами параллельно, а не одним агентом последовательно.
- Валидация не зависит от планирования (без предвзятости подтверждения).
- Каждое важное решение генерирует ADR, который автоматически принимает будущие решения.
- Выполнение порождает агентов для каждой задачи в рабочем дереве git, фиксирует каждую задачу, обрабатывает все вплоть до объединенного PR.

**Запускайте `/clear` между каждой командой**, чтобы сбросить контекст и избежать уплотнения накладных расходов.

## <a name="philosophy"></a>Философия

### Непредписывающий AI-first

Скажите Claude **, чего** нужно достичь, но никогда **how**, чтобы это реализовать. В тот момент, когда вы прописываете детали реализации, вы используете свои знания как потолок, а не знания Claude как пол.

Хорошая вступительная подсказка для нового проекта:
```
How should I use you most effectively to build this platform?
```

Пусть Claude предложит архитектуру. Ваша задача — проверять решения, а не диктовать их.

### Никаких бинтов, никаких обходных путей

Жесткое правило для каждого агента в конвейере:

> Мы создаем современное программное обеспечение. Всегда выбирайте лучшую в своем классе архитектуру, самый надежный шаблон и подход, соответствующий отраслевым стандартам.

Время и усилия сборки не имеют значения для архитектурных решений. Никогда не учитывайте сложность реализации при оценке вариантов. Правильное решение всегда является лучшим решением.

**Контрольный список соблюдения требований** (применить перед реализацией):
- [ ] Использую ли я флаг обратной совместимости, прокладку или устаревший режим?
- [ ] Будет ли новый проект, следующий текущим официальным документам, действовать таким же образом?
- [ ] Переношу ли я старые шаблоны вместо того, чтобы изучать новые?
- [ ] Исправляю ли я один компонент, если исправление относится к системному уровню?

Если какой-либо ответ положительный: остановитесь, зафиксируйте на правильном уровне.

### Почему независимая проверка?

Валидаторы, которые не писали план, не привязаны к его предположениям. Исследования показывают, что многоагентная проверка с состязательным подходом выявляет значительно больше проблем, чем самопроверка. В среднем план создает около 18 проблем, когда его проверяет независимая команда. ~95% автоматически решают существующие ADR и основные принципы.

## <a name="the-three-commands"></a>Три команды

### `/plan-start`: 5-этапное планирование

**Фаза 1: PRD и анализ проекта** *(интерактивно, без агентов)*

Прежде чем приступить к работе с любым агентом, прочтите PRD и поверхностные проблемы в трех сегментах:
- Отсутствующие требования (неясные критерии приемки, неуказанные крайние случаи)
- Неоднозначные требования (несколько допустимых интерпретаций)
- Проблемы соответствия (безопасность, конфиденциальность данных, контракты API)

Представляйте варианты с pros/cons, записывайте решения. Пропустить работу, не связанную с PRD (рефакторинг, инфраструктура, исправления ошибок).

Если изменения пользовательского интерфейса входят в объем работ, расширьте его до анализа дизайна: инвентаризация экрана, каталог состояний (empty/loading/populated/error), спецификации взаимодействия, шаблоны анимации, доступность (ARIA), обновления токенов дизайна.

**Фаза 2: Технический анализ** *(1-2 исследования агентов + интерактивный режим)*

Сначала проверьте существующие ADR и PATTERNS.md. Если 3+ подтвержденных нежелательных реакций соответствуют решению → автоматическое разрешение без запроса. В противном случае:
- Агенты Spawn Explore для целевого исследования кодовой базы
- Представление архитектурных решений с вариантами и рекомендациями
- Создавайте документы ADR для важных решений (см. Цикл обучения [ADR](#adr-learning-loop))
- Обновление PATTERNS.md

**Фаза 3: Оценка объема** *(автоматическое + утверждение пользователя)*

Примените правила триггера к пулу агентов (см. [Динамический пул агентов](#dynamic-agent-pool)). Представьте предложенную команду с обоснованием каждого агента. Пользователь может добавлять или удалять агентов до начала исследования.

| Уровень | Количество агентов | Этикетка |
|------|-------------|-------|
| 0 | 0 | Соло (встроенное исследование) |
| 1 | 1-3 | Сосредоточенный |
| 2 | 4-6 | Стандартный |
| 3 | 7-9 | Всесторонний |
| 4 | 10+ | Полный спектр |

**Фаза 4: Исследование и разработка плана** *(динамическая группа)*

- Уровень 0: онлайн-исследования, без агентов
- Уровень 1+: параллельное создание утвержденных агентов (в фоновом режиме), ведение мониторинга путем считывания сообщаемого пути вывода каждого агента.
- `planning-coordinator` (Opus) синтезирует все отчеты в окончательный план.
- Файл плана фиксации, ADR и артефакты создания

Выход: `docs/plans/plan-{name}.md` + `docs/adr/ADR-XXXX.md` + `docs/plans/metrics/{name}.json`

**Автопереход**: нет неразрешенной двусмысленности → автозапуск `/plan-validate`

---

### `/plan-validate`: двухуровневая проверка

**Слой 1: Структурный** *(встроенный, мгновенный)*

Механические проверки, для которых не нужны агенты:
- Формат и полнота плана (присутствуют все необходимые разделы)
- Порядок задач и цепочка зависимостей (без циклических распределений)
- Проверка существования файлов (файлы, перечисленные для изменения, действительно существуют)
- Согласованность ADR (план соответствует ADR)
- Соблюдение правил CLAUDE.md

**Уровень 2: Обзор специалиста** *(на основе триггера, 0–8 агентов)*

| Агент | Курок | Модель |
|-------|---------|-------|
| `security-reviewer` | Аутентификация, платежи, PII, RBAC, новые API | Opus |
| `db-migration-reviewer` | Новые таблицы, столбцы, индексы, миграции. | Opus |
| `performance-reviewer` | Новые резолверы, запросы, маршруты, новые deps | Sonnet |
| `design-system-reviewer` | Новые компоненты пользовательского интерфейса, визуальный стиль. | Sonnet |
| `ux-reviewer` | Новые страницы, формы, взаимодействия | Sonnet |
| `cross-platform-reviewer` | Интернет + мобильная связь или общие пакеты | Sonnet |
| `native-app-reviewer` | Мобильные экраны, собственные пакеты пользовательского интерфейса | Sonnet |
| `integration-reviewer` | Новые сервисы, библиотеки, конфиг OTEL | Opus |

Никакие агенты не выбираются автоматически для тривиальных планов. Функция платежей может вызвать 4+.

**Автоматическое исправление фазы**

Каждая проблема должна быть решена, никаких пропусков. Сортировка:
1. Проблемы, соответствующие существующим решениям ADR → автоматическое решение
2. Проблемы, соответствующие подтвержденным записям PATTERNS.md → автоматическое решение.
3. Проблемы, решаемые на основе основных принципов → автоматическое решение
4. Остаток → человеческое решение → новое правило → автоматически разрешается в следующий раз

**Автопереход**: все проблемы решены → автозапуск `/plan-execute`

---

### `/plan-execute`: Казнь по объединенному PR

Одна команда обрабатывает все:

1. **Создание рабочего дерева**: изолированная ветка от текущей ветки
2. **TDD scaffolding**: сначала записывайте неудачные тесты для задач, отмеченных TDD
3. **Параллельное выполнение на основе уровней**: обнаружение независимых задач, создание агентов для каждой задачи, фиксация каждой задачи
4. **Обнаружение дрейфа**: флаг, если реализация отклоняется от плана
5. **Quality Gate**: параллельные тесты + интеграционный дымовой тест (зонд GraphQL, сканирование журнала контейнера, определенные планом дымовые команды)
6. **Обновление документации перед PR**: сверка PRD + архивирование плана (в рабочем дереве)
7. **PR создание и слияние**: сжатое слияние, очистка сообщения о фиксации
8. **Метрики после слияния**: данные выполнения, зафиксированные в файле метрик
9. **Очистка рабочего дерева**: удалить ветку и рабочее дерево

В случае сбоя контроля качества: до 3 попыток автоматического исправления специальными агентами отладки. По-прежнему не удается → уведомить человека.

## <a name="dynamic-agent-pool"></a>Динамический пул агентов

Агенты **not** жестко запрограммированы в CLAUDE.md. Они определяются во время вызова: описание, критерии триггера и выбор модели встроены в фазу планирования, на которой они создаются. Это сохраняет легкость CLAUDE.md, предоставляя каждому агенту полный контекст для его роли.

### Исследовательский пул (`/plan-start`)

| Агент | Курок | Модель |
|-------|---------|-------|
| `code-explorer` | Всегда | Sonnet |
| `arch-researcher` | Многоуровневые изменения (2+ слоя) | Sonnet |
| `database-analyst` | Любые изменения схемы БД | Sonnet |
| `security-analyst` | Аутентификация, платежи, PII, RBAC | Opus |
| `test-analyzer` | Нетривиальная особенность | Sonnet |
| `cross-platform-specialist` | Требуется мобильный паритет | Sonnet |
| `native-app-specialist` | Задачи касаются mobile/UI | Sonnet |
| `design-system-researcher` | Изменения в области пользовательского интерфейса | Sonnet |
| `dependency-researcher` | Добавляются новые пакеты | Sonnet |
| `devops-specialist` | Docker, переменные окружения, CI/CD | Sonnet |
| `integration-researcher` | Новые услуги, библиотеки, ОТЕЛЬ | Opus |
| `planning-coordinator` | Всегда (при 2+ агентах) | Opus |

**Основные варианты дизайна**:
- Opus только для ответственных ролей (безопасность, интеграция, координация)
- Sonnet для стандартных исследований (хорошее качество, меньшая стоимость)
- `planning-coordinator` появляется только при выборе 2+ агентов: он синтезирует, а не исследует.

### Пул проверки (`/plan-validate`)

См. таблицу уровня 2 выше. Это разные агенты из исследовательского пула, поскольку валидаторы не предвзято относятся к процессу создания.

## <a name="adr-learning-loop"></a>Цикл обучения ADR

Каждое значимое архитектурное решение порождает ADR. Со временем нежелательные реакции складываются в институциональную память, что снижает вмешательство человека.

### Что вызывает ADR

**Всегда создавайте АДР для:**
- Выбор между несколькими допустимыми шаблонами взаимодействия (наложение или страница, ящик или модальное окно)
- Новые шаблоны анимации или перехода, не входящие в существующие соглашения.
- Решения о расхождении платформ (поведение в сети и на мобильных устройствах)
- Загрузка стратегии состояния, которая вводит новый шаблон
- Стратегия аутентификации, подход к схеме БД, решения о границах сервисов
- Новый выбор зависимостей с архитектурными последствиями

**НЕ создавайте АДР для:**
- Решения, продиктованные утвержденным источником или существующей конвенцией
- Незначительный выбор макета в рамках установленных шаблонов
- Очевидные записи каталога состояний (стандартные состояния empty/loading/error)

### Уровни зрелости

```
1 ADR  → Watching   — tracked, not yet prescriptive
2 ADRs → Emerging   — presented as recommended default with precedent context
3+ ADRs → Confirmed — auto-resolved during planning (no human input needed)
          → Candidate for promotion to CLAUDE.md as hard rule
```

### <a name="the-loop"></a>Петля

```
/plan-start Phase 2     →  ADR created
                               ↓
                        PATTERNS.md updated
                               ↓
/adr-review (periodic)  →  Detect patterns across ADRs
                               ↓
                        Propose CLAUDE.md promotions
                               ↓
Future /plan-start      ←  Confirmed rules auto-resolve decisions
```

Запускайте `/adr-review` каждые 10–15 планов для пакетного анализа шаблонов и предложения дополнений к CLAUDE.md.

**Комплексный эффект**: проект с 20 планами автоматически принимает ~80% архитектурных решений. Человеческий вклад сосредоточен только на действительно новых решениях.

## <a name="claudemd-discipline"></a>CLAUDE.md Дисциплина

### Жесткий лимит: 120 строк.

Каждая строка в CLAUDE.md требует контекста при каждом запросе. 300-строчный CLAUDE.md — это служебная информация, которая выполняется перед каждым приглашением. Установите и соблюдайте жесткие ограничения.

**Что дает строку в CLAUDE.md:**
- Первые принципы (жесткие правила, которые отменяют предпочтения агента)
- Подтвержденные модели нежелательных ситуаций (3+ случаев)
- Соглашения, специфичные для проекта, которые агенты не могут вывести из базы кода.
- Указатели на подфайлы

**Чего НЕ должно быть в CLAUDE.md:**
- Полное содержание систем проектирования, конфигураций окружения, документации по архитектуре.
- Правила, применимые к <10 % задач
- Пояснения и обоснование (запишите их в ADR)

### Стратегия указателя

Вместо загрузки всего контекста в CLAUDE.md используйте указатели:

```markdown
## Context Files (load only when relevant)
- @docs/DESIGN_SYSTEM.md    — when UI changes are in scope
- @docs/ARCHITECTURE.md     — when service boundaries are touched
- @docs/ENV_CONFIG.md       — when Docker or env vars are modified
- @docs/ADR_PATTERNS.md     — during planning phases
```

Агенты загружают только то, что требуется для их задачи. Бэкэнд-задача никогда не загружает систему дизайна. Контекст остается чистым.

### Регулярная обрезка

Просматривайте CLAUDE.md каждые 10-15 планов вместе с `/adr-review`. Продвигайте подтвержденные шаблоны, удаляйте правила, которые стали очевидными из-за соглашений в кодовой базе, удаляйте все, на что не было ссылок.

## <a name="context-management"></a>Управление контекстом

### `/clear` между шагами

Запустите `/clear` между `/plan-start`, `/plan-validate` и `/plan-execute`. Каждая команда самостоятельна: файл плана на диске является артефактом передачи обслуживания, а не контекстом в памяти.

Без `/clear`: контекст накапливается на всех этапах, уплотнение триггеров происходит раньше, агенты наследуют нерелевантный контекст от предыдущих этапов, а стоимость токенов значительно увеличивается.

### Почему это работает

Каждая команда считывает входные данные с диска (файлы плана, ADR, кодовая база). Нет состояния, которое должно находиться в контекстном окне между шагами. Дисциплина очистки между шагами — это то, что позволяет конвейеру масштабироваться до крупных проектов, не нарушая контекстных ограничений в середине выполнения.

## <a name="when-to-use"></a>Когда использовать

### ✅ Используйте этот конвейер, когда

- Для функции требуется несколько файлов и слоев (API + DB + UI).
- Изменения, чувствительные к безопасности (аутентификация, платежи, PII)
- Сложные миграции БД
- Новые интеграции внешних сервисов
- Все, что исправить ошибку планирования будет дорого
- Командные проекты, где история решений имеет значение

### ❌ Не используйте, когда

- Исправление опечаток, тривиальный рефакторинг (используйте стандартный режим `/plan`)
- Исследовательское прототипирование, когда требования неизвестны.
- Исправление в условиях нехватки времени (вместо этого используйте планирование с двумя экземплярами)
- Изменения затрагивают не более двух файлов без каких-либо архитектурных решений.

### ⚡ Ярлык уровня 0

Для небольших, но нетривиальных изменений по-прежнему запускайте конвейер, но система обнаружит область уровня 0 и пропустит создание агентов: исследование происходит в реальном времени, проверка — только на уровне 1, выполнение — с одним агентом. Те же команды, меньше накладные расходы.

## <a name="cost-profile"></a>Профиль затрат

| Фаза | Драйвер затрат | Приблизительный диапазон |
|-------|-------------|-------------------|
| `/plan-start` Уровень 0 | Только онлайн-исследования | $0.10-0.30 |
| `/plan-start` Уровень 1-2 | 2-6 агентов Sonnet | $0.50-2.00 |
| `/plan-start` Уровень 3 | 7+ агентов + координатор Opus | $2.00-8.00 |
| `/plan-validate` | 0-8 агентов | $0.20-3.00 |
| `/plan-execute` | Агенты по задачам + контроль качества | $0.50-5.00 |
| **Типичная функция (уровень 2)** | Полный конвейер | **$2-10** |

Затраты растут по мере роста покрытия ADR: требуется меньше агентов, меньше проблем с проверкой, более быстрое выполнение.

Периодически используйте `/plan-metrics` для просмотра исторических тенденций затрат и калибровки оценок.
