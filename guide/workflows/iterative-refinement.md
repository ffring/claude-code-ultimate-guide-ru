## <a name="tldr"></a>ТЛ;ДР

```
1. Initial prompt with clear goal
2. Claude produces output
3. Evaluate against criteria
4. Specific feedback: "Change X because Y"
5. Repeat until done
```

Основная идея: **Конкретный отзыв > неопределенный отзыв**

## <a name="the-loop"></a>Петля

### Шаг 1. Первоначальное приглашение

Начните с четких намерений и ограничений:

```
Create a React component for a user profile card.
- Show avatar, name, bio
- Include edit button
- Use Tailwind CSS
- Mobile-responsive
```

### Шаг 2. Оцените результат

Claude создает код. Оценивать:
- Соответствует ли оно требованиям?
- Чего не хватает?
- В чем дело?
- Что может быть лучше?

### Шаг 3. Конкретная обратная связь

Предоставьте целевые исправления:

```
Good start. Changes needed:
1. Avatar should be circular, not square
2. Edit button should only show for own profile (add isOwner prop)
3. Bio should truncate after 3 lines with "Show more"
```

### Шаг 4: Повторите

Продолжайте, пока не будете удовлетворены:

```
Better. One more thing:
- Add loading skeleton state for when data is fetching
```

## <a name="feedback-patterns"></a>Шаблоны обратной связи

### Эффективная обратная связь

| Шаблон | Пример |
|---------|---------|
| **Конкретное местоположение** | «Строка 23: измените `===` на `==`» |
| **Очистить действие** | «Добавить границу ошибки вокруг формы» |
| **Причина указана** | «Удалите console.log, поскольку из него происходит утечка пользовательских данных» |
| **Приоритет отмечен** | «Критично: исправить SQL-инъекцию. Желательно: добавить нумерацию страниц». |

### Неэффективная обратная связь

| Anti-Pattern | Почему это не удается | Лучшая альтернатива |
|--------------|--------------|-------------------|
| «Сделай лучше» | Нет направления | «Улучшите читабельность за счет извлечения логики проверки» |
| «Это неправильно» | Никакой конкретики | «Формат даты должен быть ISO 8601, а не временная метка Unix» |
| «Мне это не нравится» | Субъективный | «Используйте функциональные компоненты вместо компонентов класса» |
| «Исправь ошибки» | Слишком расплывчато | «Исправлено: 1) проверка нуля в строке 12, 2) проверка на единицу в цикле» |

## <a name="autonomous-loops"></a>Автономные петли

Claude может выполняться самостоятельно с четкими критериями завершения.

### <a name="choose-what-starts-the-next-iteration"></a>Выберите, с чего начнется следующая итерация

| Нуждаться | Механизм | Завершить доказательства |
|---|---|---|
| Уточните требование или оцените дизайн | Ручная обратная связь | Лицо принимает результат в соответствии с заявленным требованием |
| Выполняйте ограниченную, поддающуюся проверке задачу на протяжении всех ходов. | `/goal` | Оценщик судит о состоянии на основе доказательств в разговоре. |
| Периодически перепроверяйте внешнее состояние | `/loop` | Каждая проверка записывает свои наблюдения; отмена и срок действия отделены от принятия задачи |

Для наглядного исправления ошибки сначала определите проверку, которая не удалась из-за обнаруженного дефекта. Укажите, что та же проверка должна пройти после исправления, назовите разрешенные файлы и требуйте соответствующих регрессионных проверок. Установите ограничение хода и выход без прогресса, сохраняя окончательные доказательства, если кто-то из них сработает. Предел является примером политики, а не измеренным оптимумом или доказательством того, что оценщик применяет жесткий счетчик.

Справочник по целям [](../ultimate-guide.md#goal-autonomous-completion-mode-v21139) объясняет ограничения оценщика и резюме. Цикл [и графическое руководство](../core/loop-graph-engineering.md#compose-recurring-triage-with-bounded-work) описывают прием от повторяющегося триггера. Начните с одного из этих механизмов; повторяющееся приглашение, содержащее встроенную команду, само по себе не является проверенной оркестровкой.

### Модель Ральфа Виггама

Назван в честь шаблона цикла самосовершенствования:

```
Keep improving the code quality until:
1. All tests pass
2. No TypeScript errors
3. ESLint shows zero warnings

After each iteration, run the checks and fix any issues.
Stop when all criteria are met.
```

### Примеры критериев завершения

```
Iterate until:
- Response time < 100ms for 95th percentile
- Test coverage > 80%
- All accessibility checks pass
- Bundle size < 200KB
```

### Ограничения итерации

Всегда устанавливайте ограничения, чтобы предотвратить бесконечные циклы:

```
Improve the algorithm performance.
Maximum 5 iterations.
Stop early if improvement < 5% between iterations.
```

## <a name="integration-with-claude-code"></a>Интеграция с Claude Code

### С инструментом задач

Отслеживайте итерации уточнения с помощью `TaskCreate` и `TaskUpdate`:

```
TaskCreate: "Implement initial version"
TaskCreate: "Fix: handle empty arrays"
TaskCreate: "Fix: add input validation"
TaskCreate: "Optimization: memoize expensive calculations"
# Mark completed as you progress with TaskUpdate
```

### С хуками

Автоматическая проверка после каждого изменения с использованием перехватчиков Claude Code (настраивается с помощью команды `/hooks` или `settings.json`). Например, перехватчик `PostToolUse` в инструменте `Edit` может автоматически запускать анализ и тесты. Claude видит сбои и может их исправить.

### С /compact

Когда контекст увеличивается во время итераций:

```
/compact

Continue refining the search algorithm.
We've made good progress, focus on the remaining issues.
```

### Контрольно-пропускной пункт

После значительного прогресса:

```
Good progress. Let's checkpoint:
- Commit what we have
- List remaining issues
- Continue with the next priority
```

## <a name="script-generation-workflow"></a>Рабочий процесс создания скрипта

Генерация сценариев и автоматизация обеспечивают максимальную рентабельность инвестиций в итеративную доработку и экономию времени на 70–90 % при составлении отчетов практикующих специалистов. Скрипты автономны, тестируются изолированно и приносят немедленную пользу.

### Шаблон итерации 3-7

Большинство готовых к использованию скриптов появляются после 3-7 итераций:

| Итерация | Фокус | Подсказка |
|-----------|-------|----------------|
| 1 | Базовый функционал | «Создать сценарий, который [цель]» |
| 2-3 | Ограничения + крайние случаи | «Добавить [ограничение]. Обработать [краевой регистр]». |
| 4-5 | Закалка | «Добавьте обработку ошибок, ведение журнала, проверку ввода» |
| 6-7 | Польский | «Оптимизировать по [метрике]. Добавьте документацию по использованию». |

### Пример: менеджер подов Kubernetes (PowerShell)

**Итерация 1: Базовый**
```
Create a PowerShell function to list pods in a Kubernetes namespace.
```

**Итерация 2: Добавление фильтрации**
```
Add: filter by label selector and pod status.
Show: pod name, status, age, restarts.
```

**Итерация 3: Добавление действий**
```
Add: ability to delete pods matching filter.
Require: confirmation before deletion.
```

**Итерация 4: Обработка ошибок**
```
Handle: kubectl not found, invalid namespace, permission denied.
Add: verbose logging with -Verbose flag.
```

**Итерация 5: Готовность к производству**
```
Add: dry-run mode, output to JSON for piping, help documentation.
Ensure: works on Windows, Linux, macOS.
```

### <a name="common-pitfalls"></a>Распространенные ловушки

| ловушка | Пример | смягчение последствий |
|---------|---------|------------|
| Галлюцинированные команды | `apt-get` на macOS | Укажите ОС: «Только Ubuntu 22.04». |
| Пробелы в безопасности | Нет проверки ввода | Всегда запрашивайте: «проверить все вводимые пользователем данные». |
| Over-engineering | Добавляет ненужные библиотеки | Запрос: «минимальные зависимости, предпочтительнее stdlib» |
| Смещение контекста | Забывает требования после итерации 5 | Подсказка контрольной точки: «Перед следующим изменением повторите текущие требования». |
| Предположения о платформе | Предполагает функции bash в sh | Укажите: «совместимый с POSIX» или «bash 4+». |

### Шаблон итерации скрипта

```
Current script: [paste or reference]

Iteration goal: [specific improvement]

Constraints:
- Must preserve: [existing behavior to keep]
- Must not: [things to avoid]
- Target environment: [OS, shell, runtime]

Success criteria: [how to verify this iteration works]
```

## <a name="iteration-strategies"></a>Стратегии итерации

### Breadth-first

Исправьте все проблемы на одном уровне, прежде чем углубляться:

```
First pass: Fix all type errors
Second pass: Fix all lint warnings
Third pass: Improve test coverage
Fourth pass: Optimize performance
```

### Depth-first

Полностью завершите одну область, прежде чем двигаться дальше:

```
1. Perfect the authentication flow (all aspects)
2. Then move to user management
3. Then move to settings
```

### Priority-based

Адрес по важности:

```
Iterate in this order:
1. Security issues (critical)
2. Data integrity bugs (high)
3. UX problems (medium)
4. Code style (low)
```

## Anti-patterns

### Движущаяся цель

```
# Wrong
"Actually, let's change the approach entirely..."
(Repeated 5 times)

# Right
Commit to an approach, iterate within it.
If approach is wrong, explicitly restart.
```

### Петля перфекционизма

```
# Wrong
Keep improving forever

# Right
Set clear "good enough" criteria:
- Tests pass
- Handles main use cases
- No critical issues
→ Ship it, improve later
```

### Потерянный контекст

```
# Wrong
After 50 iterations, forget what the goal was

# Right
Periodically restate the goal:
"Reminder: we're building a rate limiter.
Current state: basic implementation works.
Next: add Redis backend."
```

## <a name="review-auto-correction-loop"></a>Обзор цикла автокоррекции

Специализированный итеративный шаблон, в котором Claude проверяет, исправляет и перепроверяет в рамках фиксированного бюджета. Принятие требует доказательств; остановка цикла не приводит к успеху.

### Шаблон

```
┌─────────────────────────────────────────┐
│   Review Auto-Correction Loop           │
│                                          │
│   Review (identify issues)               │
│        ↓                                 │
│   Fix (apply corrections)                │
│        ↓                                 │
│   Re-Review (verify fixes)               │
│        ↓                                 │
│   Verify acceptance → Accepted          │
│        ↑                                 │
│        └──── Budget left? Repeat / Stop  │
└─────────────────────────────────────────┘
```

### Шаблон запроса

```
Review this PR with auto-correction:
1. Multi-agent review (3 scope-focused agents)
2. Fix all 🔴 Must Fix issues
3. Re-review to verify fixes didn't introduce new issues
4. Fix all 🟡 Should Fix issues
5. Re-review one final time
6. Accept only when all blocking findings are resolved with evidence,
   required behavior checks pass on the current revision, and the
   designated reviewer accepts the result under the recorded criteria.

Max iterations: 3
Stop as EXHAUSTED when the budget is consumed without acceptance.
Stop as NO_PROGRESS after two passes resolve no blocking finding and
produce no new verification evidence. A small diff is not acceptance.
Keep FAILED, TIMEOUT, ABORTED and UNKNOWN distinct from acceptance.
```

### Гарантии

| Гарантия | Цель | Выполнение |
|-----------|---------|----------------|
| **Максимальное количество итераций** | Предотвращение бесконечных циклов | Жесткий лимит: 3 итерации. |
| **Качественные ворота** | Проверьте указанные свойства | После каждого исправления запускайте тесты типа проекта, lint и соответствующие тесты поведения; запишите ревизию и результаты |
| **Защищенные файлы** | Предотвратите рискованные изменения | Пропустить автоматическое исправление для: package.json, миграций, .env. |
| **Проверка прогресса** | Связанный непроизводительный труд | Отслеживайте решенные выводы о блокировке и новые доказательства проверки; отсутствие прогресса — причина остановки, а не принятия |
| **Возможность восстановления** | Сохранение восстанавливаемого состояния | Запишите контрольную точку перед исправлениями; откат кода не восстанавливает измененные данные или внешние эффекты |

### Пример сеанса

Иллюстративная расшифровка, а не измеренный результат обзора. Каждое требование о разрешении требует связанной проверки или вынесения решения в ходе фактического выполнения.

**Итерация 1: Первоначальный обзор**
```
Claude: Found 8 issues:
- 🔴 3 Must Fix (SQL injection, empty catch, missing auth)
- 🟡 4 Should Fix (DRY violations, N+1 query)
- 🟢 1 Can Skip (naming style)
```

**Итерация 2: исправление должно исправить + повторная проверка**
```
Claude: Fixed 3 Must Fix issues.
Re-review: All 🔴 resolved. No new issues introduced.
Remaining: 4 🟡 Should Fix, 1 🟢 Can Skip
```

**Итерация 3: исправление должно исправить + повторная проверка**
```
Claude: Fixed 4 Should Fix issues.
Re-review: All 🟡 resolved. No new issues.
Remaining: 1 🟢 Can Skip (optional improvement)
```

**Приемка**
```
Claude: Required behavior checks pass on the recorded current revision.
Blocking findings have verified resolutions; the designated reviewer accepts.
Only explicitly deferred optional improvements remain.
Outcome: ACCEPTED within the stated criteria and evidence boundary.
```

### Сравнение: однопроходный и цикл сходимости

| Аспект | Однопроходная проверка | Петля сходимости |
|--------|-----------------|------------------|
| **Обнаружение** | Одна возможность найти проблемы | Найти проблемы → исправить → проверить → повторить; любой подход может пропустить дефекты |
| **Последующая осведомленность** | Проверьте журнал git на предмет «Соавтор: Claude». | Каждая итерация учитывает предыдущие |
| **Ложные срабатывания** | Может предложить исправления для уже исправленного кода. | Повторный обзор улавливает это |
| **Уверенность** | Единая проверка | Несколько проходов проверки |
| **Затраты времени** | Самый быстрый (1 отзыв) | Медленнее (3+ отзывов) |
| **Качество** | Требует оценки результатов | Требует оценки результатов; большее количество проходов само по себе не свидетельствует об улучшении |

**Когда использовать**:
- **Один проход**: простые PR, опытная команда, срочный подход.
- **Ограниченный контур**: Изменения требуют нескольких проходов коррекции; конфиденциальные пути по-прежнему следуют политике своего владельца и подписи.

### Интеграция с мультиагентной проверкой

Назначьте рецензентам отдельные задачи и оцените их выводы; Добавление агентов само по себе не обеспечивает независимости или качества:

```
Each iteration:
├─ Agent 1: Consistency Auditor
├─ Agent 2: SOLID Principles Analyst
└─ Agent 3: Defensive Code Auditor
     ↓
  Fix issues
     ↓
  Re-run 3 agents
     ↓
  Verify fixes + check for new issues
     ↓
  Accept with evidence, or repeat within budget and stop with an explicit reason
```

### Критерии сходимости

Запишите принятие отдельно от выполнения и причину остановки:

1. **Accepted**: обязательные проверки проходят записанную редакцию, результаты блокировки подтверждены, и уполномоченный рецензент принимает ее в соответствии с текущими критериями. Это не доказывает полноту критериев.
2. **Исчерпан или нет прогресса**: сохранить нерешенные выводы и контрольные точки; не сообщать о завершении.
3. **Сбой или истекло время ожидания**: сохранить этап сбоя и доступные доказательства; недостающие результаты не являются четким обзором.
4. **Aborted**: сохранить состояние после авторизованной остановки.
5. **Unknown**: невозможно установить право собственности, покрытие или результат; требуется путь восстановления или эскалации политики.

Если при проверке обнаруживается неполное требование, измените критерии с указанием причины и утвержденного решения, а затем повторно запустите затронутую проверку. Не ослабляйте молча критерий достижения зеленого цвета. См. [вынесение решения](../core/loop-graph-engineering.md#5-allocate-judgment-explicitly).

### Антипаттерны в циклах проверки

| Anti-Pattern | Проблема | Решение |
|--------------|---------|----------|
| **Бесконечный цикл** | Нет условий ограниченной остановки | Устанавливайте бюджеты и проверяйте ход выполнения независимо от принятия |
| **Расползание прицела** | Каждая итерация незаметно меняет требования. | Обнаружение версий через уполномоченный орган; признать недействительным затронутое принятие |
| **Вредные исправления** | Исправление вводит новые ошибки | Повторная проверка после каждого исправления + контроль качества |
| **Защищенные изменения файлов** | Изменяет package.json, миграции | Явный список пропуска для защищенных файлов |
| **Потеря контекста** | Забывает исходные проблемы после итерации 3. | Поддерживать отслеживание проблем на всех итерациях |

## <a name="community-patterns--known-limitations"></a>Модели сообщества и известные ограничения

Сообщество создало несколько шаблонов на основе итеративного цикла Claude Code. Некоторые решают реальные болевые точки, другие выявляют текущие ограничения, о которых стоит знать.

### Цикл Ральфа (автономная итерация, управляемая тестированием)

Источник: nathanonn.com, февраль 2026 г.

Цикл Ральфа ограничивает автономную итерацию одним тестовым примером за цикл вместо того, чтобы каждый раз запускать весь набор. Это сохраняет концентрацию каждого цикла и не позволяет агенту отслеживать несколько сбоев одновременно.

Как это работает:

1. Выберите один неудачный тестовый пример
2. Исправьте это, проверьте, что оно прошло
3. Сохраните прогресс в файле состояния JSON.
4. Переход к следующему неудачному тестовому примеру
5. После 3-х неудачных попыток одного и того же дела отметьте его как `known_issue` и пропустите.

```json
{
  "current_case": "test_auth_token_refresh",
  "attempts": 2,
  "known_issues": ["test_legacy_migration_edge_case"],
  "completed": ["test_login", "test_logout", "test_session_timeout"]
}
```

Государственный файл является здесь ключевым нововведением. Он выдерживает сброс контекста, операции `/compact` и даже полный перезапуск сеанса. Агент читает файл в начале каждого цикла, чтобы точно знать, где он остановился, какие дела выполнены, а какие пропустить.

Ограничение в три попытки предотвращает ловушку бесконечного цикла, которая поражает наивные автономные циклы. Вместо того, чтобы сжигать токены в сложных тестовых случаях, агент движется вперед и отмечает проблему для последующего рассмотрения человеком.

### Навык автоматического продолжения

Источник: mcpmarket.com.

Система продолжения, основанная на доверии, которая решает, должен ли агент продолжать работу или остановиться из-за вмешательства человека. Вместо фиксированного количества итераций он оценивает ситуацию после каждого цикла:

**Авто-продолжает, когда**:
- Тесты пройдены
- Сборка прошла успешно
- Новых типов ошибок не обнаружено
- Показатель уверенности остается выше порогового значения

**Останавливается для ввода данных человеком, когда**:
- Уверенность падает ниже порога
- Появляется новая категория ошибок (а не просто новый экземпляр известной ошибки).
- Сборка или проверка типа завершаются неудачно, чего агент раньше не видел.

Это хорошо сочетается с хуками Stop Claude Code. Навык может запускать проверку после выполнения задачи и принимать решение о возобновлении работы на основе результатов.

### Стопорные хуки для автоматической проверки

Паттерн, который превращает систему хуков Claude Code в автоматический контроль качества между итерациями:

1. Claude завершает задачу (или итерацию)
2. Перехват `PostToolUse` на `TodoWrite` запускает скрипт проверки.
3. Скрипт выполняет проверку типов, анализ и тесты.
4. Ошибки автоматически передаются обратно в Claude.
5. Claude устраняет проблемы без вмешательства человека.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "TodoWrite",
        "command": "bash -c 'npm run typecheck 2>&1; npm run lint 2>&1; npm test 2>&1'"
      }
    ]
  }
}
```

Хук срабатывает каждый раз, когда Claude отмечает задачу как выполненную. Если проверка что-то обнаружит, Claude увидит выходные данные и сможет самостоятельно исправиться, прежде чем перейти к следующей задаче.

### Стратегия эскалации

Что делать, если 3 итерации терпят неудачу при решении одной и той же проблемы. Вместо того, чтобы вечно зацикливаться или сдаваться, следуйте структурированному пути эскалации:

1. **Decompose**: разбейте невыполненную задачу на 2–3 более мелкие подзадачи, которые можно решать независимо.
2. **Собрать контекст**: сохранить все сообщения об ошибках, трассировки стека и попытки исправлений в структурированный файл.
3. **Эскалация модели**: при использовании Sonnet повторите конкретный случай сбоя с Opus для более глубокого обоснования.
4. **Человеческая эскалация**: Если обновление модели не помогает, создайте задачу GitHub с полным контекстом ошибки и отметьте задачу как `known_issue`.

```bash
# Escalation in practice
if [ "$ATTEMPT_COUNT" -ge 3 ]; then
    # Collect context
    cat errors.log attempts.log > escalation-context.md

    # Try with Opus
    claude --model claude-opus-5-5 \
        "Fix this failing test. Context: $(cat escalation-context.md)"

    # If still failing, create issue
    if [ $? -ne 0 ]; then
        gh issue create \
            --title "Auto-escalation: $TEST_NAME fails after 3 attempts" \
            --body "$(cat escalation-context.md)" \
            --label "known_issue,needs-human"
    fi
fi
```

Цель никогда не заключаться в том, чтобы молча бросать работу. Каждый сбой либо устраняется, эскалируется или явно отслеживается.

### <a name="known-limitations"></a>Известные ограничения

Будьте честны в отношении того, что еще не работает, чтобы не тратить время на изобретение несуществующих решений.

**Отдельное собственное продолжение от элементов управления доставкой.**: `/goal` поддерживает неинтерактивное выполнение и восстанавливает активные цели при возобновлении сеанса. Его оценщик читает диалог, а не проводит независимую проверку. Классификация повторов, устойчивые общие бюджеты, полномочия принятия и безопасное воспроизведение внешних эффектов по-прежнему требуют явного контракта. Обратитесь к документации по текущим целям [](https://code.claude.com/docs/en/goal) вместо того, чтобы рассматривать исторические отчеты о проблемах как полное отсутствие поддержки повторных попыток, проверки или возобновления.

**Итерации агента могут быть потеряны.** (проблема GitHub № 28843): в многодневных рабочих процессах итерации агента и их накопленный контекст могут быть уничтожены. Если вы запускаете рабочий процесс, охватывающий несколько сеансов или дней, сохраняйте файлы явного состояния каждые N итераций. Не полагайтесь на память разговоров Claude как на единственный источник истины.

**Хрупкость многодневных рабочих процессов**: длительная автоматизация требует дисциплины контрольных точек. Сохраняйте состояние на диск (файлы JSON, git-коммиты, комментарии) через регулярные промежутки времени. Схема проста, но ее легко забыть: если вы не можете восстановить работу агента только по файлам на диске, ваш рабочий процесс нарушится на границах сеанса.
