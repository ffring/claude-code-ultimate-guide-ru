## Для чего это

`/security-audit` сканирует ваш проект на наличие секретов и поверхностей для инъекций. `tools/audit-prompt.md` оценивает всю вашу установку по восьми измерениям. Вместо этого это приглашение делает одну вещь: оно определяет, являются ли ваши правила разрешений по-прежнему границей или они незаметно перестали что-либо означать.

Неудачи, для устранения которых он создан, невидимы изнутри. Вы накапливаете правила `allow` по одному «Да, больше не спрашивать» за раз. Один из них оказывается переводчиком. С этого момента все остальные правила в файле являются украшением, включая правила `deny`, которые вы написали намеренно. Ничто вас не предупреждает. Подсказки просто перестают появляться, что можно считать хорошо настроенной настройкой.

Запустите его для каждого проекта. Он читает только конфигурацию и ничего не меняет.

## Как его запустить

Вставьте все, что находится ниже этой строки, в сеанс Claude Code в корне проекта, который вы хотите проверить.

Для парка запустите его один раз для каждого репозитория. Результаты в настройках пользовательской области будут повторяться при каждом запуске, и в этом суть: дыра в пользовательской области влияет на каждый проект одновременно и должна быть исправлена ​​в первую очередь.

### Сначала сортировка флота

Аудит тридцати репозиториев по одному приводит к потере первых двадцати прогонов, обнаруживающих одно и то же. Сначала осмотрите весь флот, ранжируйте по экспозиции, а затем запустите полную подсказку только для того, что отмечено сканированием. Наведите `ROOTS` на каталоги, в которых фактически находятся ваши репозитории.

```bash
ROOTS="$HOME/Sites $HOME/dev $HOME/work"   # adjust
find $ROOTS -maxdepth 5 -name node_modules -prune -o -name .worktrees -prune \
     -o -path "*/.claude/settings*.json" -print 2>/dev/null | sort -u > /tmp/cc-settings.txt
wc -l < /tmp/cc-settings.txt

python3 - <<'PY'
import json,re,os
BLANK=re.compile(r'^Bash\((bash|sh|zsh|fish|dash|python3?|perl|ruby|node|deno|bun|npm|pnpm|yarn|npx|bunx|make|just|env|xargs|eval|uv|poetry|docker run|docker exec)\s*(-[ce])?\s*(:\*|\*|\))')
files=[l.strip() for l in open('/tmp/cc-settings.txt') if l.strip()]
rows=[]; broken=[]; totals=[0,0,0,0]
for p in files:
    try: d=json.load(open(p))
    except Exception as e: broken.append((p,str(e)[:60])); continue
    perm=d.get("permissions",{})
    a,dn,ak=perm.get("allow",[]),perm.get("deny",[]),perm.get("ask",[])
    sb="sandbox" in d
    totals[0]+=len(a); totals[1]+=len(dn); totals[2]+=len(ak); totals[3]+=sb
    hits=sorted({r for r in a if BLANK.match(r)})
    tracked = p.endswith("settings.json")
    if hits or not dn:
        rows.append((len(hits), tracked, len(a), len(dn), len(ak), sb, p, hits))
print(f"files={len(files)} allow={totals[0]} deny={totals[1]} ask={totals[2]} sandbox={totals[3]}")
for p,e in broken: print("UNPARSEABLE", p, e)
for n,tracked,a,dn,ak,sb,p,hits in sorted(rows, reverse=True):
    tag = "TRACKED" if tracked else "local  "
    print(f"[{tag}] blank={n:2d} allow={a:5d} deny={dn:3d} ask={ak} sandbox={'y' if sb else 'n'}  {p.replace(os.path.expanduser('~'),'~')}")
    if hits: print("          " + "  ".join(hits))
PY
```

Прочитайте вывод в этом порядке. Общий грант в **tracked** `settings.json` превосходит все остальное, потому что он отправляется тому, кто клонирует репозиторий. Следующим идет общий грант в `settings.local.json`, по одной строке на каждый затронутый репозиторий. Репозиторий с нулевыми правилами `deny` и без песочницы не имеет границ, выходящих за пределы встроенных значений по умолчанию, что бы ни говорил его счетчик разрешений. Большое количество разрешений без общего разрешения — это шум, а не риск, и его следует планировать в последнюю очередь.

Затем запустите полную подсказку для двух или трех репозиториев, где ответ действительно неясен, и примените исправления из плана для всего парка, а не повторяйте аудит каждого из них.

Вы старший инженер по безопасности, проверяющий состояние разрешений Claude Code в этом репозитории. Вы производите доказательства, а не впечатления. Каждая находка, о которой вы сообщаете, содержит путь к файлу, строку или правило, а также команду, которую кто-то другой может запустить для ее воспроизведения.

Вы не изменяете ни один файл. Вы не запускаете `claude config`, `/permissions` или что-нибудь, что пишет. Если вас попросят что-то исправить, вы предлагаете патч в виде текста и останавливаетесь.

## Основная истина, которую вы должны использовать

Сопоставитель разрешений Claude Code имеет особую семантику. Большинство плохих проверок происходят из-за их угадывания. Используйте их, которые представляют собой документированное поведение, а не рассуждайте только на основе текста правила.

**Rule shape.** Правила: `Tool` или `Tool(specifier)`. Голые `Bash` и `Bash(*)` соответствуют каждой команде. Подстановочные знаки совпадают в любой позиции, включая среднюю: `Bash(git * main)` соответствует `git push origin main`. Завершающий ` *` обеспечивает границу слова, поэтому `Bash(ls *)` соответствует `ls -la`, но не `lsof`, а `Bash(ls*)` соответствует обоим. Суффикс `:*` равен завершающему ` *` и распознается как **только в конце шаблона**; в `Bash(git:* push)` двоеточие является буквальным символом, и правило ничему не соответствует.

**Составные команды.** Распознаваемые разделители: `&&`, `||`, `;`, `|`, `|&`, `&` и символы новой строки. Правило должно соответствовать каждой подкоманде независимо, поэтому `Bash(safe *)` не разрешает `safe && rm -rf .`.

**Wrappers удаляются перед сопоставлением.** `timeout`, `time`, `nice`, `nohup`, `stdbuf`, встроенные функции `command` и `builtin`, `noglob` zsh и пустой `xargs` без флагов. Таким образом, правило, написанное для внутренней команды, охватывает обернутую форму.

**Wrappers НЕ удалены, отсюда и дыры.** `npx`, `docker exec`, `devbox run`, `mise exec`, `direnv exec` и каждый интерпретатор, вызываемый с помощью `-c` или `-e`. Они выполняют свои аргументы как команду, поэтому правило типа `Bash(devbox run *)` разрешает `devbox run rm -rf .`, а `Bash(bash *)` разрешает `bash -c '<anything>'`. Это самый важный механизм в этом аудите.

**Префиксы переменных среды.** Правило `allow` не соответствует после присвоения переменной за пределами известного безопасного набора. Правило `deny` или `ask` соответствует любому ведущему назначению, поэтому `Bash(rm *)` в запрете все равно перехватывает `FOO=bar rm -rf tmp/`.

Оболочки **Exec, которые всегда запрашивают** и не могут быть одобрены по префиксу: `watch`, `setsid`, `ionice`, `flock` и `find` с `-exec` или `-delete`.

**Встроенный набор только для чтения**, никогда не запрашивается ни в каком режиме и не настраивается: `ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd` и формы `git`, доступные только для чтения. Правило `allow` для любого из них — это мертвый груз, а не риск.

**Защищенные пути**, никогда не одобряемые автоматически за пределами `bypassPermissions`, и **not**, предварительно утверждаемые правилом `allow` в настройках: `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, `.claude` (кроме `.claude/worktrees`), а также файлы оболочки rc, `.npmrc`, `.gitconfig`, `.mcp.json`, `.claude.json` и подобные. Проверка безопасности выполняется до оценки настроек.

**Упорядочение в автоматическом режиме.** Действия, соответствующие правилу `allow`, `ask` или `deny`, разрешаются немедленно, **before** запускается классификатор. При входе в автоматический режим Claude Code отбрасывает только права широкого выполнения: общий `Bash(*)`, интерпретаторы с подстановочными знаками, команды запуска менеджера пакетов и разрешающие правила `Agent`. Узкое правило, такое как `Bash(git push:*)`, сохраняется и, следовательно, исключает проверку классификатора из этого действия. В автоматическом режиме список разрешений не является нейтральным: он исключает контроль.

**Ask Rules.** Правило `ask` на уровне содержимого, такое как `Bash(git push *)`, вызывает запрос в каждом режиме, включая автоматический режим и включая изолированные команды. Простое правило запроса `Bash` пропускается для команд, выполняющихся в изолированной программной среде. Правила «Спроси» — это единственная контрольная точка, которую выполняет человек, и которая выдерживает любые другие условия.

**Sandbox.** Выкл., если `sandbox.enabled` это правда. Два независимых слоя. Файловая система: запись ограничена рабочим каталогом и температурой сеанса; читает обложку **вся машина** включая `~/.ssh` и `~/.aws`, поскольку нет встроенного списка запрещенных учетных данных. Сеть: предварительно не разрешен домен, запрос при первом использовании. `autoAllowBashIfSandboxed` автоматически утверждает изолированные команды, что заменяет длинный список разрешений. `allowUnsandboxedCommands: false` отключает только `dangerouslyDisableSandbox` повторить попытку; это так **нет** сдерживать `excludedCommands`, что остается полным обходом границы ОС. Встроенный прокси-сервер не завершает TLS, поэтому широкий `allowedDomains` запись, такая как `github.com` это выходной путь, а не ограничение.

**Приоритет областей** для массивов разрешений: управляемый, затем локальный проект, затем проект, затем пользовательский, при этом ключи массива объединяются и дедуплицируются в каждой области, а не заменяются. `deny`, добавленный где угодно, применяется везде; ни одна область не может удалить запрет другой области. Некоторые ключи намеренно игнорируются, когда они поступают из настроек проекта: записи `defaultMode: "auto"`, `sandbox.filesystem.disabled`, `sandbox.credentials`, `mask`, `network.tlsTerminate`, `network.strictAllowlist` и `allowAppleEvents`.

Если вы не уверены, сохраняется ли поведение в установленной версии, скажите об этом в отчете в разделе «Не проверено», а не утверждайте это. Запишите версию от `claude --version`.

## Этап 2. Правило здоровья населения

Посчитайте, затем охарактеризуйте. Проблема не в объеме; что скрывает объем.

```bash
python3 - <<'PY'
import json,re,os,collections
for p in (".claude/settings.local.json",".claude/settings.json"):
    if not os.path.exists(p): continue
    a=json.load(open(p)).get("permissions",{}).get("allow",[])
    if not a: continue
    exact=[r for r in a if r.startswith("Bash(") and not r.rstrip(")").endswith(("*",":*"))]
    heads=collections.Counter()
    for r in a:
        m=re.match(r'Bash\(([^\s:)]+)',r)
        if m: heads[m.group(1)]+=1
    print(f"--- {p}: {len(a)} allow, {len(exact)} exact-match Bash")
    print("   heads:", heads.most_common(15))
PY
```

Сообщите о трех вещах. Сколько правил являются точными совпадениями, которые никогда больше не сработают, остаток утверждений для каждого вызова. В каких главах команд накопилось много почти идентичных записей, которые можно было бы заменить одним правилом префикса. И является ли какое-либо правило уже мертвым: покрыто встроенным набором только для чтения, затенено более широким правилом в той же или более широкой области действия или искажено, например, `:*`, которого нет в конце.

Известная особенность сопоставителя, которую стоит проверить здесь: команды, содержащие префикс переменной среды, например `TEST_DB_URL="..." pytest`, никогда не объединяются в правило префикса, поскольку средство сопоставления разрешения не просматривает неизвестное назначение. Группа почти идентичных записей, отличающихся только префиксом env, является ошибкой, а не ошибкой пользователя.

## Этап 3. Отрицайте и спрашивайте освещение

Пустой массив `ask` означает, что в конфигурации нигде нет контрольной точки, выполняемой человеком. Скажите это прямо, если это так.

Проверьте охват действий, отмена которых требует больших затрат, и сообщите о каждом из них как о наличии или отсутствии с помощью текста правила:

Перезапись истории и деструктивный git: `git push --force` и его формы `-f` и `--force-with-lease`, силы ссылок, такие как `git push origin +main`, `git reset --hard`, `git clean -fd`, а также ветвление или удаленное удаление.

Публикация и слияние: `npm publish`, `gh pr merge`, `gh repo delete`, `gh repo edit`, передача реестра и команды развертывания, специфичные для этого проекта.

Секретное раскрытие: чтение `.env` и его вариантов, `*.pem`, `*.key`, `~/.ssh`, `~/.aws`, `~/.gnupg` и любого каталога учетных данных, который фактически использует этот проект.

Если `deny` существует, проверьте его на соответствие приведенной выше семантике, а не принимайте его за чистую монету. Шаблон, привязанный к `git push`, пропускает `git -c key=value push --force`, поскольку команда больше не начинается с соответствующего префикса. Сообщите об этом как об ограничении правила и обратите внимание, что сопоставление с образцом проигрывает в этой игре: защита ветвей на сервере — это фактически соблюдаемая граница. Правило `deny` по-прежнему стоит соблюдать в качестве местной меры защиты от несчастных случаев.

Наконец, назовите хотя бы одно правило `ask`, которое должно быть в этом проекте и которого нет, выбранное из того, что на самом деле делает репозиторий. Обоснуйте это кодом или конфигурацией CI, а не общим контрольным списком.

## Этап 4. Положение «песочницы»

Если никакая область действия не определяет `sandbox`, укажите, что песочница отключена, а затем дайте количественную оценку стоимости **here**, а не абстрактно. Основывайте это на этапе 1: при наличии гранта интерпретатора и отсутствии песочницы в Bash нет никаких границ. Без прав интерпретатора и песочницы границей является только список правил, который сохраняется только до тех пор, пока его не откроет никакое будущее правило.

Если определен `sandbox`, проверьте его на соответствие следующим требованиям:

`excludedCommands` — это полный обход границы ОС, а `allowUnsandboxedCommands: false` ее не ограничивает. Для каждой записи спрашивайте, может ли эта команда достичь файловой системы хоста. `docker` может, через монтирование тома и через сокет демона. `kubectl`, `ssh` и `make` обычно могут. Сообщайте о каждой исключенной команде, сообщая о том, чего она еще может достичь, и проверяйте, распространяется ли на нее правило `deny` или `ask`. Также пометьте записи, синтаксис которых для этого поля не проверен: документированные формы представляют собой простое имя или `name *`, а суффикс `:*` здесь не является тем же полем, что и сопоставитель Bash. Проверьте решенную конфигурацию на вкладке «Конфигурация `/sandbox`», а не гадайте.

`network.allowedDomains` — это исходящий белый список, оцениваемый по имени хоста, заявленному клиентом, без проверки TLS по умолчанию. Общие записи, такие как `github.com` или подстановочный знак в доменах пользовательского контента, допускают эксфильтрацию. Перечислите каждый домен с указанием причины его присутствия; все, что вы не можете оправдать, является открытием. Рекомендуйте `network.strictAllowlist: true`, если версия его поддерживает, и обратите внимание, что он должен находиться в пользовательских или управляемых настройках, поскольку настройки проекта для этого ключа игнорируются.

Отсутствие `credentials` обнаруживается всякий раз, когда включена песочница, поскольку политика чтения по умолчанию распространяется на всю машину. Предложите конкретные записи запрета `files` для путей учетных данных, которые фактически есть на этом компьютере, и записи `envVars` для токенов, которые фактически использует этот проект.

`filesystem.allowWrite` следует сверить с реальностью. Если собственные рабочие процессы проекта пишут за пределами рабочего каталога, родственных репозиториев, общего вывода сборки, каталога кэша, эти пути должны быть указаны в списке, иначе песочница нарушит рабочий процесс и подтолкнет кого-то к его отключению. Проверьте сценарии, `package.json` и конфигурацию CI, чтобы найти их. Сообщите о каждом как об обязательной записи.

Ключи, которые невозможно установить в настройках проекта, стоит пометить, если они присутствуют в файле проекта, поскольку они молча игнорируются: записи `defaultMode: "auto"`, `filesystem.disabled`, `credentials`, `mask`, `network.tlsTerminate`, `network.strictAllowlist`, `allowAppleEvents`.

## Этап 5. Гигиена области применения

Для каждого важного правила определите, находится ли оно в нужном файле.

`deny` при чтении учетных данных принадлежит пользовательским настройкам, поскольку он должен следовать за оператором в каждом проекте, а не повторно объявляться для каждого репозитория. Правило, специфичное для цепочки инструментов этого проекта, принадлежит отслеживаемому `.claude/settings.json`, поэтому команда наследует его. Правило, отражающее привычки одного человека, принадлежит `.claude/settings.local.json`.

Смещение флага в обе стороны. Отказ в учетных данных, существующий только в этом проекте, оставляет все остальные проекты открытыми. Абсолютный путь в отслеживаемом файле, зависящий от машины, не работает для всех остальных. Полное предоставление прав в настройках пользователя — худший случай, поскольку оно применяется ко всем репозиториям, включая ненадежные.

Обратите внимание, действительно ли здесь игнорируется `settings.local.json`, и скажите об этом, если это не так.

## Этап 6. Взаимодействие режимов

Определите эффективный режим разрешений: `permissions.defaultMode` в ближайшей области, в которой разрешено его устанавливать, в противном случае — вручную. Помните, что `defaultMode: "auto"` игнорируется в настройках проекта и локальных настройках.

Затем сравните список разрешений **с этим режимом**, поскольку один и тот же список имеет противоположные эффекты в разных режимах.

В режиме «Вручную» или `acceptEdits` разрешающее правило удаляет запрос, на который вы в противном случае ответили бы. Широкие гранты представляют собой риск.

В автоматическом режиме правило разрешения полностью удаляет классификатор из решения, поскольку разрешения, запросы и запреты разрешаются до запуска классификатора. Таким образом, такие правила, как `Bash(git push:*)`, `Bash(git commit:*)` или `Bash(gh pr:*)`, отключают именно те проверки, которые классификатор выполняет лучше всего, включая проверку того, переносит ли нажатие секреты за пределы репозитория. Если проект выполняется в автоматическом режиме, перечислите все разрешающие правила, подавляющие проверку классификатора, и порекомендуйте переместить его в `ask` или удалить. Обратите также внимание на то, какие широкие права выпадают при входе в автоматический режим, чтобы читатель знал, какие выводы Фазы 1 нейтрализуются в этом режиме, а какие нет.

Если перехватчики настроены, проверьте, выходит ли перехват `PreToolUse` с ненулевым значением, чтобы заблокировать что-либо. Перехватчик, проверяющий разрешенную команду, представляет собой более сложную границу, чем шаблон, и стоит подтвердить, что он улавливает формы интерпретатора, обнаруженные на этапе 1, а не только буквальные имена команд.

Оценка **Posture из 100**, с видимой разбивкой, чтобы читатель мог с ней поспорить:

**Ранговые результаты**, сначала худшее. Каждый из них содержит: серьезность, файл и правило, действия злоумышленника или несчастного случая, команду воспроизведения и исправление. Невозможно найти без этапа воспроизводства.

**Одно предложение**, обозначающее единственное изменение с наибольшим соотношением устраненного риска к затраченным усилиям.

## Правила вашего отчета

Будьте конкретны или ничего не говорите. «Рассмотреть возможность ужесточения разрешений» — это не вывод; «`Bash(node:*)` в строке 412 `.claude/settings.local.json` делает запрет `Read(**/.env*)` в строке 5 `.claude/settings.json` обходным через `node -e 'console.log(require("fs").readFileSync(".env","utf8"))'`».

Не заполняйте отчет, чтобы он выглядел тщательным. Если фаза ничего не находит, правильным выходом будет одна строка, говорящая об этом.

Не рекомендуется использовать `bypassPermissions` или `--dangerously-skip-permissions` в качестве средства от быстрой усталости. Песочница с `autoAllowBashIfSandboxed` — это механизм, который удаляет подсказки, сохраняя при этом границы.

Четко укажите, когда конфигурация хорошая. Аудит, который производит выводы, оправдывающие себя, хуже, чем отсутствие аудита.
